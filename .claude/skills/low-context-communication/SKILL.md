# ハイコンテキストな書き方をしない

## この規約が要る理由

書き手（あなた）は、直前にドキュメントを読んだ状態でいる。読み手はそうではない。

この非対称が、書き手には見えない。「`subagentStatusLine` で行を書き換えられる」は、5分前に仕様を読んだ人間には完全な文に見える。読み手にとっては**それが設定なのか、コマンドなのか、関数なのかすら分からない**単語である。読み手は文を読むために別途ドキュメントを開くことになり、それは会話としては破綻している。

**読み手が文を理解するために外部の資料を開かなければならないなら、その文は書けていない。**

---

## 規則

### 固有名は、必ず「何であるか」と一緒に出す

コマンド、ツール、設定項目、環境変数、ファイルパス、APIの名前、ライブラリ名 —— これらを裸で置かない。**種別と機能をその場で添える。**

書き方の型: **`名前`（それが何か）＋ 何をするか**

| 悪い | 良い |
| --- | --- |
| SendMessage すると再開できる | 親エージェントから子エージェントへ後追いでメッセージを送る仕組み（`SendMessage` というツール）があり、これで止まっていたエージェントを再開できる |
| `subagentStatusLine` で行を書き換えられる | 設定ファイルに `subagentStatusLine` という項目がある。各サブエージェントの表示行を、自分で書いたスクリプトの出力に差し替えられる |
| `--bg` で起動する | `claude --bg "指示文"` というコマンドで、対話画面を占有しない別セッションとして起動できる |
| hooks に登録する | Claude Code には hook（フック）という、特定のタイミングで必ずコマンドを実行させる仕組みがある。ここに登録する |

### ドキュメントの章番号・ファイル番号だけで指さない

「08 の段4」「§6.2 の通り」「`13` の B」——これらは、その文書を開かないと意味を成さない。

**何が書いてあるかを、その場で1行にして出す。** 番号は補助として括弧に入れる。

| 悪い | 良い |
| --- | --- |
| 08 の段4 で対処する | 判断できないものは PO確認待ちキューへ登録する、というエスカレーション規約の4段目で対処する（`docs/decisions/08-escalation-criteria.md`） |
| §6.2 の通り | 要件定義書がオーケストレーターの責務として挙げている9項目（ゴール管理・タスク分解・登録・割り当て・進捗管理・停滞管理・健全性評価・エスカレーション管理・リソース管理）の通り |
| 00 §2.1 の懸念 | オーケストレーターのコンテキストが報告を受けるたびに膨張し、組織全体を見る余力を失う——という調査で確認済みの問題（`docs/decisions/00-research-notes.md`） |

### 略語・専門語は初出で開く

`PO`、`TDD`、`MCP`、`worktree`、`front matter` のような語は、**その会話での初出時に一度だけ説明する。** 二度目以降は短縮してよい。

- 悪い: 「PO確認待ちへ登録する」（PO が何か説明していない場合）
- 良い: 「PO（プロジェクトオーナー＝人間のユーザー）の確認待ちキューへ登録する」

**一度説明した語を毎回説明し直す必要はない。** 冗長さは別の失敗である。目安は「この会話でまだ説明していないなら開く、説明済みならそのまま使う」。

### 表や箇条書きで幅が足りないときは、直前か直後の本文で補う

表のセルは短くせざるを得ない。そこで説明を落とすのではなく、**表の前に1〜2文の導入を置くか、表の後に補足を書く。** 表だけを置いて済ませない。

## 判定に迷ったときの検査

書き終えた文を読み返して、この問いに答える。

> **この文の中に、読み手がドキュメントを開かないと意味が取れない単語があるか。**

あるなら、そこが直す場所である。

もう一つの検査:

> **半年後の自分が、前提知識ゼロでこれを読んで分かるか。**

この2つで、ほぼすべて拾える。

## やりすぎない

この規約は「全部を説明しろ」ではない。**読み手が知らない可能性が高いものを開く**という規約である。

説明しなくてよいもの:

- 読み手が明らかに知っている語（そのプロジェクトで日常的に使っている語、読み手自身が持ち出した語）
- この会話で既に説明した語
- 一般的な語（`git commit`、「テスト」、「レビュー」）

**判断がつかないときは開く側に倒す。** 冗長さのコストは、読み手が調べに行くコストより小さい。

---

## 適用範囲

チャットの返答だけではない。**ユーザーが読む可能性のあるすべての文章**に適用する。

- チャットの返答
- コミットメッセージ
- 設計ドキュメント・決定記録
- プルリクエストの本文
- コードコメント
- エラーメッセージ・ログ出力

特に決定記録は、**書いた本人以外が数ヶ月後に読む**ことを前提に書かれる文書である。この規約が最も効く場所でもある。
