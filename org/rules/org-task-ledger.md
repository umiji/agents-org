# タスク台帳の書き方

進捗の唯一の真実。索引（CSV）と詳細（タスク別Markdown）に分かれている。

**分けてある理由**: 1つのタスクを触るセッションが、完了済み全タスクの証拠まで読み込まずに済むようにするため。また、タスクごとにファイルが分かれていれば、並列で走る作業が同時に書いても衝突しない。

---

## 誰が何を書くか

| 対象 | 書く主体 |
| --- | --- |
| `docs/task-list-{project-name}.csv` | **オーケストレーターだけ** |
| `docs/tasks/T-XXX.md` の 決定ログ / 作業ログ / 証拠 / 進捗 | **担当エージェント**（自分のタスクのファイルだけ） |
| `docs/tasks/T-XXX.md` の 状態 / 担当 / 依存 / 優先度 / 申し送り | オーケストレーター |
| `docs/token-usage-{project-name}.csv`（トークン消費の記録） | **`.claude/scripts/org-tokens.py` だけ。誰も手で書かない** |
| `docs/decisions-index.md`（決定ログ索引） | **`.claude/scripts/org-decisions.py` だけ。誰も手で書かない** |

トークン消費の記録をタスク台帳と別ファイルにしてあるのは、書く主体が違うためである。タスク台帳は人（オーケストレーター）が書き、こちらはスクリプトが機械的に上書きする。混ぜると、集計が走るたびにタスク台帳の差分が汚れ、誰が何を書き換えたのかが追えなくなる。**このファイルを手で編集すると、次の集計で上書きされて消える。**

CSV は単一ファイルなので、複数が同時に書けば必ず壊れる。**書き手を1つに絞ることで構造的に防ぐ。**

---

## CSV索引

```csv
ID,作成日,更新日,タスク名,状態,優先度,担当,依存タスク,ドキュメント
```

| 列 | 規約 |
| --- | --- |
| ID | `T-###`（3桁連番）。**再利用しない。** 中止したタスクも行を残す |
| 作成日 / 更新日 | `YYYY-MM-DD`。不明なら `不明` と明記。**空欄にしない** |
| タスク名 | 10〜40文字程度 |
| 状態 | 下記10種のいずれか |
| 優先度 | `高` / `中` / `低` |
| 担当 | エージェント名。未割当なら `未割当` と明記 |
| 依存タスク | 下記の依存表現。無ければ `無し` と明記 |
| ドキュメント | リポジトリルート相対のパス |

**値にカンマ・改行を含めない。** 索引は短い値しか持たない。長い記述は詳細ファイルの領分。

**空欄を作らない。** `無し` / `不明` を明示する。空欄や `-` は「未確認」と読めてしまい、後から判別できない。

## 状態

| 状態 | 意味 |
| --- | --- |
| `未着手` | 登録済み。着手可能かは依存タスク次第 |
| `設計中` | `org-design` が作業中 |
| `テスト作成中` | 受け入れテストを先行作成中（TDD適用タスク） |
| `実装中` | `org-implementation` が作業中 |
| `テスト中` | 受け入れテスト実行・検証中 |
| `レビュー中` | レビュー実施中、または修正の往復中 |
| `PO確認待ち` | PO の判断待ち。ブロッカーに `Q-XXX` を書く |
| `完了` | 完了条件を全て満たし、証拠が記録されている |
| `保留` | PO確認以外の理由で進められない |
| `中止` | 実施しないと決めた。行は残す |

**終端は `完了` / `中止` の2つ。**

「ブロック中（依存待ち）」という状態は無い。依存タスク列から導出できるため。**導出できるものを状態にすると、依存先が完了したときの戻し忘れが停滞の誤検知になる。**

## 依存関係

| 形式 | 意味 |
| --- | --- |
| `T-001（ブロッカー）` | T-001 が `完了` になるまで開始できない |
| `T-001（推奨: 理由）` | 必須ではないが、この順が合理的 |
| `無し` | 依存が無いことを**確認済み**である |

複数は空白区切り。**ブロッカーの理由は詳細ファイルへ必ず書く。理由が書かれていない依存は、依存として認めない。** 説明できない依存は並列に走れる単位を潰す。

英語表記（`T-001 (blocker)` / `T-001 (recommended: reason)`）も読める。別方式の台帳から移ってきた場合のため。**どちらとも読めない注記は警告になり、安全側でブロッカーとして扱う**——推奨と誤読すると、着手できないはずのタスクが動き出すため。

## タスク別ファイル

**雛形が `.claude/templates/T-XXX.md` にある。手で組み立てず、コピーして使う。** 以下はその構成である。

```markdown
# T-XXX: タスク名

## メタデータ
- 作成日: YYYY-MM-DD
- 更新日: YYYY-MM-DD
- 状態: 未着手
- 優先度: 中
- 担当: 未割当
- 進捗: 一行で現状
- 依存: 依存タスクの全文（ブロッカーなら理由を必ず書く）
- TDD適用可否: 適用 / 適用外（適用外なら理由）
- 手戻り回数: 0

## 目的             なぜこの変更が要るか。飛ばすと何が壊れるか
## 変更範囲         どのファイル・領域を触るか
## 禁止事項         触ってはいけないもの
## 完了条件         二値で判定できる形。コマンドと出力で確認できること
## 判断してよい範囲 どこまで自律的に決めてよいか
## テスト方法       単体／結合／回帰。実環境確認の要否と実施者
## 停止条件         このタスク固有のもの。無ければ「共通の停止条件のみ」
## 参照すべき成果物 設計成果物、既存コード、過去の決定（docs/decisions-index.md で引ける）
## 連絡してよい相手 直接やりとりしてよい相手の宛先。無ければ「無し（すべてオーケストレーター経由）」
## 申し送り         上流タスクの結果から判明した、このタスクの担当が知らないと判断を誤る事実
## 成果物           完了時に何ができたか（ファイル・コミット）
## ブロッカー       今止めているもの。PO確認待ちなら Q-XXX

## 決定ログ
## 作業ログ
## 証拠
```

このファイルは**そのまま作業指示である**。作業指示を別途書き下ろさない。セクションが空であることが、指示の抜けを可視化する。

**`## 完了条件` / `## 判断してよい範囲` / `## 変更範囲` / `## 禁止事項` の4つは、担当が付いた時点で機械的に検査される。** 未記入のまま割り当てると警告が出る。`## 証拠` は、状態が `完了` のときに検査される。**雛形の案内文（`<!-- ... -->`）が残っているだけの節は、未記入として扱う。**

### `## 連絡してよい相手` は、書かなければ「無し」である

担当エージェントは、**誰が居るかを自分で一覧する手段を持たない。** つまり宛先を教えられなければ、直接やりとりは成立しない。この欄が空なら、その担当は**すべてオーケストレーター経由で連絡する**。それが既定である。

書くときは、**相手の宛先をそのまま書く。** 役割名（`org-implementation` など）だけを書いてはならない。**同じ名前が1セッション内で2回使われた時点で、その名前宛ての送信は拒否される**（黙って別のエージェントへ届くのではなく、送信が止まる）。オーケストレーターは役割名をタスクごとに使い回すため、**役割名だけの宛先は2回目の割り当てで必ず壊れる。** 宛先の作り方は `CLAUDE.md` の「エージェント間の直接通信」にある。

**この欄は機械的な検査の対象ではない。** 直接通信の経路が要らないタスクのほうが多く、必須にすると意味の無い記入を強いるためである。

### `## 申し送り` は、登録した後で埋まる唯一の指示欄である

他の指示欄（目的・完了条件・判断してよい範囲）は、タスクを登録した時点で書く。**申し送りだけは違う。** 上流のタスクが実際に何を作ったかは、それが終わるまで分からないためである。

書くのは**オーケストレーターだけ**。上流タスクの完了報告を受け取るのが彼だけだからである。書く中身は、例えば次のようなもの。

- 上流が作った仕組みの、指示書からは読み取れない挙動（「テストは仮想環境を有効にしないと落ちる」）
- 上流が決めた約束事（終了コードの意味、識別子の体系）
- 上流の完了報告に「未検証」と書かれた条件

**空なら `無し` と書く。** 空欄のままにすると、転記を忘れたのか、本当に無いのかが区別できない。

**メタデータは必ず `- キー: 値` の1行1項目で書く。** 整合性検査のスクリプトがこの形を読む。項目を1行にまとめたり、キーを省いたりすると読めなくなる。

## 3つの記録

| セクション | 答えるもの | 寿命 |
| --- | --- | --- |
| `## 決定ログ` | **なぜそうしたか** | 恒久。過去の項目を書き換えず、上書きする新項目を追記する |
| `## 作業ログ` | **何が、どの順で起きたか** | 一時的。完了時に数行へ畳む |
| `## 証拠` | **完了条件を満たしたと何故言えるか** | 恒久。コマンドと実出力のみ |

### 決定ログを書く条件（この4つ）

1. 人間（PO）の判断を仰いで得た
2. 別の選択肢が実際にあった技術選定
3. 登録後にスコープ・完了条件・禁止事項が変わった
4. **理由を知らない担当が、将来これを元に戻してしまいそうなもの**

通常の進捗は決定ではない。それは作業ログ。

```markdown
### YYYY-MM-DD 一行でわかる決定の要約
- 対象: 認証 / ログインAPI
- 決定: 実際に決めたこと
- 却下案: 採らなかった案 → なぜ負けたか
- 付帯条件: 承認に付いた条件（無ければ省略）
- 上書き対象: T-003 2026-05-10（この決定が失効させる過去の決定。無ければ省略）
- 出典: コミットSHA / 設計成果物のパス /「セッション内の判断、成果物なし」
```

**`却下案` が価値を担う行であり、最も省略されやすい。**「X を選んだ」は数週間で「なぜ X なのか」に劣化するが、「Y が使えないので X」は劣化しない。真剣に検討した対案が無ければ `却下案: なし` と書く。行ごと落とさない。

#### 4つ目の条件について

**上の3つはどれも「決めた瞬間に、決めたと自覚できるもの」である。** 4つ目はそうではないものを拾う——**意図的に共通化していない箇所、削れない待ち時間、あえて素朴に書いた実装**のような、後から見ると不自然で、**理由を知らなければ「整理」されて消えるもの**である。

**この組織は、その失敗が起きる構造そのものを持っている。** 担当エージェントは会話履歴を継承せず、担当同士は自由に話せない。人間のチームなら口頭の記憶で補われる部分が、構造的に存在しない。

**判定が主観的になることは承知の上で採る。迷ったら書く側に倒してよい。** 書きすぎの害（索引が伸びる）より、書かなかった害（消される）のほうが大きい。

#### `対象` と `上書き対象`

**`対象`（必須）** — その決定が支配する領域や部品を1〜3語で書く（「認証」「投稿一覧」）。**索引を束ねる単位であり、語をまだ知らない側が辿り着くための入口である。** 用語集（`docs/glossary.md`）に載っている語があればそれを使う。複数にまたがるときは ` / ` で区切る。

**`上書き対象`（該当するときだけ）** — この決定が失効させる過去の決定を、**タスクIDと日付**で指す（`T-003 2026-05-10`）。日付まで書くのは、**1つのタスクが決定を複数持ちうる**ためである。複数を失効させるなら ` / ` で区切る。

**過去の決定ログは書き換えない。** 新しい側に `上書き対象` を書けば、**索引を作るスクリプトが古い側の行の状態を「置き換え済み → T-021」に変える。** 失効は索引の上でだけ表す。

**見出しの行（`### YYYY-MM-DD 一行でわかる決定の要約`）は書式を厳守する。** 索引を作るスクリプトがこの行を主題として読む。要約は**短い名詞句か、決定を言い切る一文**にする（「調査した」「検討した」は決定ではない）。

### 決定ログ索引 `docs/decisions-index.md`

**決定ログの目的は「再燃防止」である**——同じ論点が別のタスクで、しばしば違う結論で、また争われるのを防ぐこと。**であれば引けることが機能の本体であり、書くこと自体には価値がない。**

決定はタスク別ファイルの中に埋まっており、タスクは**決定の主題ではなく、作業が起きた順**に並んでいる。そこで索引を作る。

| | |
| --- | --- |
| 作り方 | 全タスク別ファイルの `## 決定ログ` を走査して生成する。**完了・中止のタスクも含む** |
| 列 | `対象` / `日付` / `要約` / `決定`（要旨） / `タスク` / `状態` |
| 並び | `対象` ごとに束ね、その中は日付の新しい順 |
| 書き手 | **`.claude/scripts/org-decisions.py` だけ。手で書かない。書き換えても次の生成で消える** |

```sh
python3 .claude/scripts/org-decisions.py           # 索引を作り直す
python3 .claude/scripts/org-decisions.py --check   # 書き込まず、古くなっていないかだけ見る
```

**セッション開始時に自動で作り直される**（設定に入れてある）。書式が崩れている決定ログは警告として出るので、直す。

### 2つの約束事

- **`特記なし`** — このタスクに決定が本当に無かった。セクション自体は常に存在するので、**無いことが「未記入」を意味する**状態を保つ
- **`（記録なし）`** — 決定はあったが理由が当時記録されず、もう復元できない。**推測で理由を再構成して埋めてはならない。** 捏造された理由は、後から事実として読まれるため、認めた空白より悪い

## やってはいけないこと

- スコープ外のリファクタリング・警告修正
- **テストや期待値を書き換えて、落ちているテストを通すこと**
- 不明な仕様を推測で埋めること（聞く）
- 一度発行したタスクIDの再利用（中止したタスクのものでも）
