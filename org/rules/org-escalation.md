# エスカレーションと停止条件

**分からないことを無理に決めない。** ただし、決めてよいことまで上げない。

---

## 4段階

| 段 | やること | 次へ上がる条件 |
| --- | --- | --- |
| **1. 自分で解決** | 作業指示、参照すべき成果物、既存コード、**過去の決定**（決定ログ索引 `docs/decisions-index.md`）を確認する | これらを確認しても**答えが一意に定まらない**。または、定まるが自分の「判断してよい範囲」の外にある |
| **2. 許可された相手へ相談** | 直接通信の経路（4つ。`CLAUDE.md` の「エージェント間の直接通信」に一覧がある）を持つ場合のみ。**送り先は作業指示の `## 連絡してよい相手` に書かれた宛先をそのまま使う** | 相手が答えられない、または相手も判断できないと返した |
| **3. オーケストレーターへ上げる** | 自分のロールのエスカレーション条件に沿って報告する | オーケストレーターが PO 判断を要すると判断した |
| **4. PO確認待ちキューへ** | オーケストレーターが `docs/po-queue.md` へ登録する | — |

### 段2は、宛先が書かれているときだけ使える

`## 連絡してよい相手` が「無し」なら、**その経路は使えない。** 段2を飛ばして段3（オーケストレーターへ上げる）へ行く。**相手を自分で探そうとしないこと** —— 誰が居るかを一覧する手段は与えられていない。

宛先が書かれている場合は、**その文字列をそのまま**送り先に使う。役割名（`org-implementation` など）に読み替えてはならない。**役割名では届かない。**

オーケストレーターへ返すときの送り先は `main` と書く。

### 段1の打ち切りは「情報源を尽くしたか」で決める

「しばらく考えても分からなければ」では機能しない。上の4つの情報源を確認して定まらなければ、**それ以上は推測である**。

曖昧な指示を受けたエージェントは、エラーを上げずに誤った前提のまま作業を完了させる。失敗が沈黙するため、手戻りは下流で初めて発覚する。**着手前に差し戻す方が常に安い。**

## 全ロール共通の停止条件

自分のロールの条件に加えて、**以下に該当したら作業を止めてオーケストレーターへ上げる**。

| # | 条件 |
| --- | --- |
| S-1 | 仕様・指示・設計のどれかが**互いに矛盾している** |
| S-2 | **既存データを削除する／破壊的である**、または DBマイグレーションが既存データへ及ぼす影響を伴う |
| S-3 | 作業開始時点で、**作業ツリーに未確認の差分がある**（着手前に `git status` を確認する） |
| S-4 | 作業がタスクの `変更範囲` / `禁止事項` を**超える** |
| S-5 | 完了条件そのものが**実現不能**と判明した |
| S-6 | 作業指示に**必須項目が欠けている**（完了条件が無い、判断してよい範囲が無い、参照すべき成果物が実在しない） |

タスク固有の停止条件は、タスクの `## 停止条件` にある。

### S-3 の但し書き — 並列実行中は、他人の差分が見える

担当エージェントは**同じ作業ツリー（同じチェックアウト）を共有する**。他のタスクが同時に走っていれば、`git status` に**自分と無関係な差分が見えるのが正常**である。

止まるのは、**自分のタスクの `変更範囲` の中に、身に覚えのない差分があるとき**だけ。範囲の外にある差分は、**触らず、報告だけする**。他の担当エージェントが今まさに書いている途中のものを巻き戻すと、その作業が消える。

## 上げないもの

「判断してよい範囲」がタスクに書かれている以上、その範囲内のことは上げない。

| 上げない | 決める主体 |
| --- | --- |
| 実装手段の選択（命名、ファイル分割、関数の構造、ライブラリ内の書き方） | 実装 |
| 技術的優劣で決着がつく複数案 | 各ロールが自分で決める |
| 既に決定ログで確定済みの事項の再検討 | 誰も蒸し返さない。**索引の `状態` が「置き換え済み」でないかだけは確かめる** |
| タスクの分割方法、担当の割り当て、優先順位 | オーケストレーター |
| レビュー指摘への対応方針 | オーケストレーター |
| レビュー指摘そのものへの反論 | 実装が理由と根拠を付して直接返す |

**範囲が書かれていないタスクは S-6 で差し戻す。** 境界が示されていない状態で自制を求めても機能しない。

## エスカレーションの書き方（→ オーケストレーター）

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| タスクID | 必須 | |
| 判断できない事項 | 必須 | 何が決められないのか |
| なぜ自分で決められないか | 必須 | 権限外 / 情報不足 / 要件不明 / トレードオフ |
| 検討した選択肢 | 必須 | 自分で調べた範囲での案。無ければ「無し」と明示 |
| 影響範囲 | 必須 | このタスクだけか、他タスクにも波及するか |

## PO確認待ちキュー（オーケストレーターが書く）

`docs/po-queue.md`。1件を `Q-###`（3桁連番）で識別する。**雛形は `.claude/templates/po-queue.md`。**

### 書式 — 識別子と状態は、必ず同じ行に置く

1件は見出しで始める。

```markdown
### Q-001 [未回答] 一行でわかる質問の要約
- 登録日: YYYY-MM-DD
- 質問・判断事項: 何を決めてほしいか
- なぜ判断が必要か: 権限外 / 情報不足 / 要件不明 / トレードオフ
- 選択肢: A案 … / B案 …
- 各案の利害: A案は … / B案は …
- 推奨案: A案。理由 …
- 影響するタスク: T-XXX
- 待つ間も進められるタスク: T-YYY, T-ZZZ
- 回答: （回答後に記入）
```

**見出しの行に識別子（`Q-001`）と状態（`[未回答]`）を同じ行で置く。** 台帳の検査スクリプトが、この形で未回答の件数を数えるためである。状態を別の行へ書くと、**未回答は常に0件と数えられ**、ゴール健全性の指標（PO確認待ちが増加傾向にあるか）が機能しなくなる。

状態は `[未回答]` / `[回答済み]` / `[取り下げ]` の3つ。**状態はこの見出し行だけが持つ。** 本文にも状態を書くと、どちらが正か分からなくなる。

**`- 待つ間も進められるタスク:` を空にしない。** 書けないなら、組織全体が止まっているということである。それ自体が報告に値する事実であり、空欄で登録してはならない。

### 回答が来たら、4つやる

1. 見出しの状態を `[回答済み]` に書き換え、`- 回答:` を埋める
2. 影響していたタスクの `## 決定ログ` へ、決定・却下案・出典を転記する
3. タスクの状態を `PO確認待ち` から適切な工程へ戻す
4. **回答が個別の判断を超えて一般的な基準になっているなら、`CLAUDE.md` または `.claude/rules/` へ昇格させる**

4 を怠ると、同じ問いが何度も上がる。昇格の目安は「同じ種類の問いが2回以上上がった」または「回答が『このプロジェクトでは常に X する』という形をしている」。

`CLAUDE.md` は200行を超えると遵守率が落ちる。超えそうならトピック別に `.claude/rules/` へ分割し、手順に育ったものは Skill へ出す。
