# 組織への指摘の書き方

**この規約は、担当エージェント全員（設計・実装・レビュー・テスト・ドキュメント）に適用される。**

タスクを進めるうちに、**組織の仕組みそのものが作業を妨げている**と気づくことがある。規約に無理がある、道具が足りない、同じ手戻りを繰り返している、役の分け方が合っていない。**それを残す場所と書き方を、この規約が定める。**

---

## なぜあなたが書くのか

**この組織は、一発で完璧な形で出来上がってはいない。** 導入先ごとに事情が違い、同じ運用方法がどこでも最適ということはない。**繰り返し直していく前提で作られている。**

そして、**組織の詰まりに最初に気づくのは、必ず作業しているあなたである。**

- **PO（この組織の所有者である人間）は、細かな作業指示を出さない前提で設計されている。** ゴールと判断は与えるが、運用の詰まりは見ていない
- **オーケストレーター（司令塔となるメインセッション）も、あなたの作業の中身までは見ていない。** 受け取るのは要約された報告である

**あなたが書かなければ、その課題は組織から消える。** 次のタスクの誰かが、同じところで同じだけ時間を失う。

**「これは自分の力不足かもしれない」と思っても書いてよい。** 判定するのはあなたではない。指摘は仕組みに向けるものであって、誰かの責任を問うものではない。

---

## どこに書くか

**自分が担当しているタスクのファイル `docs/tasks/T-XXX.md` の `## 組織への指摘` 節に書く。それだけでよい。**

**組織改善の台帳（`docs/org-improvements.md`）へは、絶対に自分で書きに行かない。**

理由は2つある。

1. **同時に走っている他のタスクの書き込みが黙って消える。** 台帳は全員の共有物である
2. **全タスクが触るファイルになると、並列に走らせられるタスクが無くなる**

**あなたの書いた1行は、オーケストレーターが吸い上げて台帳へ起票する。** 複数のタスクから出た同じ趣旨の指摘を1つの課題にまとめるのは判断であり、両方の報告を受け取るオーケストレーターにしか決められない。

**書いた内容は、完了報告にも含める。** タスクファイルに書いただけで報告に載せないと、オーケストレーターが気づくのが遅れる。

---

## いつ書くか

**作業を止めない。** これはエスカレーション（判断できないので作業を止めて仰ぐこと）ではない。**返事は来ない。** 一方向の記録である。

判断を仰ぎたいのであれば、ここではなくエスカレーションの経路を使う（`org-escalation.md`）。

**気づいたその場で1行書き、作業へ戻る。** 完了報告を書く段になってからまとめて思い出そうとしない——そこまでに忘れる。

---

## 書式

**1行1件。`- [種別] 内容` の形。** 機械が拾うため、この形を崩さない。

種別は次の**4つだけ**である。

| 種別 | 書く条件 |
| --- | --- |
| `規約` | 層2の規約に従うと作業が進まない、または矛盾する箇所に当たった |
| `道具` | 必要な道具・スキル・外部アクセスが無く、遠回りをした |
| `反復` | 同じ種類の手戻りを、このタスクで2回以上経験した |
| `ロール` | **役の分け方が、いまの仕事の流れに合っていない**（下記の6つの引き金のどれかに当たったとき） |

**4つに当てはまらないものは書かない。** 何でも書ける欄にすると読めなくなり、結果として誰も読まなくなる。

### 例

```
- [道具] Python のテストの書き方のスキルが割り当てられておらず、毎回自分で確認した
- [規約] 完了条件に実環境での確認が要るが、実施者が決まっていない
- [反復] 設計成果物に無い前提を2度実装し、2度とも差し戻された
- [ロール] レビュー待ちが3タスク積み上がり、自分の次の着手が2日止まった
```

---

## `ロール` を書く条件 — 6つの引き金

**「役が足りない気がする」では書かない。** 次の6つのどれかに当たったときだけ書く。これはソフトウェア組織のチーム構成の設計論（Team Topologies）が挙げる、構造を変えるべき合図をこの組織へ写したものである。

| # | 引き金 | この組織での現れ方 |
| --- | --- | --- |
| 1 | **ある役の前で仕事が滞留している** | 自分の次の作業が、特定の役の手が空くのを待って止まった |
| 2 | **1つの役には仕事が大きすぎる** | 1つの役が、性質のまったく違う作業を同じタスクの中で抱えている |
| 3 | **1つの役の内部で、専門が分岐しはじめた** | 同じ役なのに、扱う対象によって必要な知識がまるで別物になっている |
| 4 | **必要な情報がどこにも書かれていない** | 判断に要る事実を、毎回自分で探し直している |
| 5 | **進むテンポが落ちてきた** | 同じ規模の作業が、以前より明らかに多くの往復を要している |
| 6 | **複数の作業が、同じ下回りに依存して詰まる** | 同じ共通部分の変更待ちで、複数のタスクが同時に止まった |

**引き金の番号を書く必要はない。** 何が起きたかを事実として1行書けばよい。

### 「新しい役が必要だ」と自分で結論を書かない

**書くのは観測した事実である。** 「質問をさばく役が要る」ではなく、「レビュー待ちが3タスク積み上がり、自分の次の着手が2日止まった」と書く。

役を増やすかどうかは、この組織で**最も高くつく変更のひとつ**である。次の順に安い手段から検討され、どれでも解けないときにだけ役が増える。

```
1. そのタスクの指示文を直す        ← いちばん安い。1タスクで閉じる
2. タスク別ファイルの雛形を直す
3. 層2の規約を直す
4. スキル（手順書）を足す・直す
5. 担当エージェントの定義を直す
6. 役を増やす・統合する            ← ここは、1〜5 で解けないと分かったときだけ
7. 配布物そのものを直す            ← 全導入先へ波及する。いちばん高い
```

**再発する問題は、それを表現できる最も低い段で直す。** あなたが事実を書けば、この判断は改善エージェントとオーケストレーターと PO が行う。**結論まで書くと、安い手段が検討されないまま高い手段へ飛ぶことがある。**

---

## 書かなくてよいもの

| 書かないもの | なぜ |
| --- | --- |
| **他の担当エージェントの出来** | 対象は仕組みであって担当者ではない。「実装の質が低い」は指摘ではない。「完了条件が二値で書かれておらず、実装が判断を迫られた」が指摘である |
| **成果物そのものの問題** | コード・テスト・設計成果物・利用者向け文書の問題は、レビューとテストの担当である |
| **1回だけの不便** | `反復` は2回以上が条件である。1回目は、たまたまかもしれない |
| **対応策の提案** | 書くのは観測した事実である。原因の推定と対応策は改善エージェントの仕事である |

---

## 気づきが無かったとき

**`無し` と書いて残す。行ごと消さない。**

空欄と「無し」は違う。空欄は「書き忘れたのか、無かったのか」が区別できない。**見ていないのか、見たうえで問題無しなのかが分かることが、それ自体で信号になる。**
