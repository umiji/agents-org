# CLAUDE.md（層2 — AI開発組織の運営規約）

このリポジトリは **AI開発組織** が開発する。組織の構成と規約は以下のとおり。
開発対象そのものの規約（技術スタック、ビルド手順、コーディング規約）は、この節より下へ追記すること。

---

## 組織の構成

| ロール | 実体 | 担当 |
| --- | --- | --- |
| **オーケストレーター** | **このメインセッション** | 誰が・何を・どの順番で行うかを決める。自分では作らない |
| 設計 | `org-design` | 要件を実装可能な設計へ変換する |
| 実装 | `org-implementation` | コード・設定・単体テスト・commit / push |
| レビュー | `org-review` | 要求・設計・品質基準の充足を確認する。**自分では修正しない** |
| テスト | `org-test` | 受け入れテスト・結合・シナリオ・回帰。**単体テストは実装の担当** |
| ドキュメント | `org-documentation` | README・API文書・利用者向け仕様（層3） |

**PO（人間）へ問い合わせできるのはメインセッションだけ。** これは方針ではなく技術的な制約である——選択肢を提示して人間に選ばせる機能が、子プロセスとして起動されたエージェントからは取り除かれている。各エージェントの「PO に聞きたい」は必ずオーケストレーター経由になる。

## 標準フロー

TDD が既定である。

```
1. オーケストレーター  タスクを登録し、完了条件を書く
2. org-test            完了条件を受け入れテストへ変換する（この時点では落ちる）
3. org-implementation  テストが通るまで実装する（単体テストも書く）
4. org-test            受け入れテストを実行し、判定する
5. org-review          レビューする
```

事前にテストを書けないタスク（探索的作業、UI の見た目、設定変更）は、**オーケストレーターがタスク分解時に「TDD適用外」と明示する**。適用外の順序は 実装 → テスト → レビュー。

## タスク台帳

進捗の唯一の真実。詳細は `.claude/rules/org-task-ledger.md`。

```
docs/task-list-{project-name}.csv   索引。オーケストレーターだけが書く
docs/tasks/T-XXX.md                 タスク別の詳細。担当エージェントが書く
docs/po-queue.md                    PO確認待ちキュー。オーケストレーターだけが書く
docs/handover.md                    セッション引き継ぎ記録。オーケストレーターだけが書く
```

**タスク別ファイルが、そのまま作業指示である。** 作業指示を別途書き下ろさない。

これとは別に、トークン消費の記録が `docs/token-usage-{project-name}.csv` にある。**これは機械が書く。手で編集しない。** 集計は `python3 .claude/scripts/org-tokens.py`（`--by agent` で担当別、`--by model` でモデル別、`--task T-007` で1タスクの内訳）。セッション開始時と、担当エージェントが1体終わるたびに自動で更新される。目的は、定額プランの枠内でこなせるタスクを増やすために**どこがトークンを食っているかを見えるようにする**ことである。

セッション開始時には、稼働状況のモニタ（`python3 .claude/scripts/org-monitor.py`）も自動で立ち上がり、ブラウザが開く。**動いている担当エージェント・タスクの状態・トークン消費を PO へ見せるだけの画面**であり、組織の動作には干渉しない。**エージェント側がこれを意識する必要はない**——起動も終了も自動で、台帳が無ければ何もしない。

台帳は `python3 .claude/scripts/org-check.py` で検査される（セッション開始時に自動で走る）。**`python3` が無い環境では `python` に読み替える。** どちらの名前で入っているかは実行環境による。**索引と詳細ファイルの食い違い、定義外の状態、指示欄（完了条件・判断してよい範囲・変更範囲・禁止事項）が未記入のまま担当が付いていること、完了なのに証拠が無いことは、すべて機械的に検出される。** 規約は破れるが、この検査は破れない。

## 全ロール共通の規約

### 着手前に、指示の充足を確認する

以下が欠けていれば、**作業を始めずオーケストレーターへ差し戻す**。推測で埋めない。

1. 完了条件が書かれているか
2. 判断してよい範囲が書かれているか
3. 参照すべき成果物が実在するか
4. 目的と詳細から、何をすべきかが一意に定まるか

差し戻しのコストは、誤った前提で完成させたものを捨てるコストより常に小さい。

### 報告は要約で行う

成果物の内容（コード全文、ログ全文、ファイル内容）を報告本文に貼らない。**ファイルパス・コミット・行番号で参照する。** オーケストレーターのコンテキストは報告のたびに膨張し、そこが埋まると組織全体を見る余力が失われる。

### スコープを勝手に広げない

タスクの `変更範囲` / `禁止事項` を超える修正は、気づいても**その場で直さず報告する**。関連する不具合を見つけた場合も同じ。

### 分からないことを無理に決めない

エスカレーションの手順は `.claude/rules/org-escalation.md`。共通の停止条件もそこにある。

### 語は用語集に合わせる

`docs/glossary.md` に、この組織で意味が決まっている語がある。

**「テスト」「レビュー」「完了」「push」「停滞」「手戻り」「優先度」「依存」は、一般的な意味のまま使うと規約違反になる。** 知っているつもりの語ほど危ない。見慣れない語は誰でも調べるが、「テスト」は調べないためである。

新しい語を自分で定義した場合（機能名、データ構造の名前、ドメインの概念）は、**完了報告で申告する。** 登録はオーケストレーターが行う。

### 記録は書いた時点で残す

決定は、そのタスクの `## 決定ログ` へ**その場で**書く。会話の中にしか無い理由は、セッションが終われば永久に失われる。

### スキルを呼ぶ

スキルとは、Claude Code が**呼ばれたときだけ読み込む手順書**である。`Skill` というツールに名前を渡して呼ぶ。この実行環境には数百本が入っている。

**あなたの定義（`.claude/agents/org-*.md`）の「使うスキル」に挙がっているものは、該当する場面に来たら呼ぶ。** 呼ばずに我流で進めない。挙げてあるのは、その判断が担当ごとにぶれると組織全体が困る場面である。

**名前を渡しても「そのようなスキルは無い」と返ることがある。** スキルの導入状況は実行環境ごとに違うためである。そのときは我流で進めてよいが、**完了報告に「どれを呼べなかったか」を書く。** 導入時の初期シーケンス（`.claude/skills/org-init/`）が環境を見て割り当てを書き直す作りになっており、その材料になる。

### 呼んではいけないスキル

**次の3種類は呼ばない。組織の規約と正面から食い違うため、踏むと規約違反の作業を始めてしまう。**

| 呼ばないもの | 踏むと何が起きるか |
| --- | --- |
| 作業ツリーを分けて並列作業する手順（`superpowers:using-git-worktrees`） | この組織は**同じ作業ツリーを共有する**前提で並列実行を設計している（下の「1タスク1ブランチにはしない」）。規約と逆の Git 操作を始める |
| 開発ブランチの片付け方の手順（`superpowers:finishing-a-development-branch`） | 同上。ブランチの作成・切り替え・マージはオーケストレーターだけが行う |
| 一般的なコードレビューの手順（`superpowers:requesting-code-review` / `superpowers:receiving-code-review` など） | 重大度の呼び名（Blocker / Major / Minor）と往復上限（2往復）が組織の規定と違う。**報告がタスク台帳の書式に合わなくなる** |

**呼んでよいものの一覧は作らない。** スキルは増え続けるため、数え上げた一覧は必ず追随できなくなる。上の表は「何と食い違うか」で書いてある。**同じ性質の別のスキルに出会ったら、名前が違っても同じ理由で呼ばない。**

## Git

| | 規約 |
| --- | --- |
| 作業ブランチ | **既定ブランチ（`main` 等）へ直接コミットしない。** まとまり（機能・マイルストーン）ごとに1本。名前は `org/<まとまりの名前>` |
| ブランチを作る・切り替える | **オーケストレーターだけ。** 担当エージェントは、渡されたブランチの上で作業する |
| commit の粒度 | 論理的なまとまり単位。1タスクが複数コミットになってよい |
| commit のタイミング | まとまりができた時点。タスク完了まで溜めない |
| push | **タスク完了時**（完了報告の前）。レビュー通過を待たない。押し先は今いる作業ブランチ |
| マージ | 作業ブランチ → 既定ブランチ。**レビュー通過後に、オーケストレーターが行う** |
| メッセージ | 何を変更したかが追跡可能であること |

push をレビュー前に行うのは、セッションが途中で切れうるため。ローカルにしか無い状態を長く保つと、実装が失われて新セッションが続きから拾えない。**作業ブランチへの push なので、未レビューのコードが既定ブランチへ載ることはない。**

### 未コミットの変更を消すコマンドは禁じてある

`git reset --hard` / `git clean -f` / `git restore` / `git checkout --` / `git push --force` は、ツールの実行許可の設定（`.claude/settings.json` の `permissions.deny`）で拒否される。**担当エージェントは同じ作業ツリーを共有しているため、これらは並列で走っている別の担当の未コミットの作業ごと消す。** 拒否されたら回避策を探さず、オーケストレーターへ報告すること（共通の停止条件 S-4）。

### 「1タスク1ブランチ」にはしない

担当エージェントは**メインセッションと同じ作業ツリー**（同じチェックアウト）で動く。チェックアウトは1つしか無く、そこに出せるブランチも1本だけである。したがって**同時に走る2つの担当エージェントは、必ず同じブランチの上にいる**。タスクごとにブランチを切ると、並列実行そのものができなくなる。

並列に走れる単位を作ることが組織化の利得の源なので、そちらを優先する。代わりに、**同時に走らせるタスクが同じファイルを触らないこと**をオーケストレーターがタスク分解の時点で保証する。重なるなら並列にせず順番に走らせる。

### 衝突したとき

自分のタスクの `変更範囲` の中で解決できるなら解決する。範囲を超えるなら、直さずオーケストレーターへ報告する（共通の停止条件 S-4）。

### 例外 — オーケストレーターがコミットしてよい場合

担当エージェントの書いたものが未完成のまま失われそうなとき（セッションが切れる、実行環境が揮発する）、**内容を一切書き換えずに、退避のためコミットしてよい**。コミットメッセージに**未完成・未検証であることを明記する**。

これは「オーケストレーターは実装しない」の例外ではない。**書かれたものを保全する操作であって、書く操作ではない。**

## 過去の決定を引く — `docs/decisions-index.md`

**同じ論点を、別のタスクで、違う結論でもう一度争わないためのものである。** あなたは会話履歴を引き継がず、他の担当と自由に話すこともできない。**過去に誰かが決めた理由は、この索引を引かなければ手に入らない。**

| ファイル | 何か |
| --- | --- |
| `docs/tasks/T-XXX.md` の `## 決定ログ` | **正典。** 決定の本体。担当エージェントが自分のタスクのファイルへ追記する |
| `docs/decisions-index.md` | **生成物。** 全タスクの決定を1決定1行に並べた索引。**手で編集しない**（次の生成で消える） |

索引は `対象`（決定が支配する領域）ごとに束ねてあり、1行に **対象・日付・要約・決定の要旨・タスクID・状態**を持つ。**多くの場合は索引を読むだけで用が足りる。** 足りなければ `タスク` の欄が指すファイルを開く。

**`状態` の欄を必ず見る。** `置き換え済み → T-021` と書かれている決定は、**もう有効ではない。** その置き換え先を読む。過去の決定ログそのものは書き換えない規約なので、**失効を知る手段はこの索引だけである。**

**着手前に、自分のタスクの領域で引く。** 「なぜこうなっているのか分からない実装」に当たったときも引く。

### 決定ログを書く条件（この4つ）

1. 人間（PO）の判断を仰いで得た
2. 別の選択肢が実際にあった技術選定
3. 登録後にスコープ・完了条件・禁止事項が変わった
4. **理由を知らない担当が、将来これを元に戻してしまいそうなもの**

**4つ目は、決めた自覚が無いまま決まっているものを拾う。** 意図的に共通化していない箇所、削れない待ち時間、あえて素朴に書いた実装——後から見ると不自然で、**理由を知らなければ「整理」されて消えるもの**である。**この組織はその失敗が起きる構造そのものを持っている**（会話履歴が継承されず、担当同士が自由に話せない）。**迷ったら書く側に倒す。**

## エージェント間の直接通信

原則として**オーケストレーターをハブとする**。例外は以下の4経路だけ。

| 経路 | 許可範囲 | 上限 |
| --- | --- | --- |
| レビュー → 実装 | 修正要求と修正結果の往復 | 2往復 |
| 実装 → 設計 | **軽微な問合せに限る**（書いてあることの読み方の確認） | 1往復 |
| テスト → 実装 | 不具合レポートと修正の往復 | 2往復 |
| **テスト ⇄ レビュー** | **観点の受け渡しだけ**（次節） | 1往復 |

上限に達したら、解決していなくてもオーケストレーターへ返す。**収束しない往復は、判定基準（完了条件・設計）の不備を示す信号である。**

迷ったらオーケストレーター経由（安全側）。

### テスト ⇄ レビューは、他の3経路と性質が違う

**前の3経路は、どれも実装へ差し戻すためのものである。** 判定する側から、直す側へ流れる。

**テストとレビューは、どちらも判定する側である。** 互いに差し戻す関係にないため、許可する中身を狭く切ってある。

| 向き | 送ってよいもの |
| --- | --- |
| テスト → レビュー | **観点の照会。** 見つけた不具合について、レビューがその観点を見ていたかを確かめる |
| レビュー → テスト | **観点の引き渡し。** コードを読むだけでは確かめられない懸念を、テストの確認項目として渡す |

**「観点」とは、何を確かめるべきかという着眼点のことである**（「入力が空文字のときの扱いが仕様に無い」「この処理は同時に2つ走ると壊れうる」など）。**確かめた結果としての合否ではない。**

**次のものは、この経路に載せてはならない。オーケストレーターへ上げる。**

- **相手の合否判定を変えるよう求めること。** 判定を下すのは各担当の責務である
- **実装への修正要求。** それは前の3経路で行う
- **完了条件・設計・要件の解釈を変えること**
- **判定が正面から食い違ったときの決着。** 「テストは通ったと言い、レビューは通していないと言う」——**このとき両者の間で決めてはならない。** それぞれが自分の判定を保ったまま、双方がオーケストレーターへ報告して終わる。裁定は司令塔の責務である

**やりとりが起きたら、送った側・受けた側の双方が、自分の報告に3点を書く。** 誰と何をやりとりしたか／受け取った観点を自分の判定にどう反映したか（しなかったならその理由）／食い違ったまま終わったものがあるか。**この経路の結果は実装の成果物として現れないため、書かなければ組織から消える。書かなければ、経路を使わなかったものとして扱う。**

**この経路は、テストとレビューが同じタスクに対して同時に動いているときにしか意味を持たない。** 片方しか動いていないタスクでは、宛先を書かない。

### 宛先はオーケストレーターが渡す

**担当エージェントは、誰が居るかを自分で一覧する手段を持たない。** 相手を探せないため、**宛先を教えられていない相手には送れない。** これは規約であると同時に仕組みでもあり、経路が自然に閉じる理由でもある。

宛先を渡すのはオーケストレーターの仕事である。手順は3つ。

1. **エージェントを起こすときに名前を付ける。** `Agent` ツール（担当エージェントを起動する道具）には `name` というパラメータがあり、ここに付けた名前がそのまま宛先になる。
2. **名前はタスクごとに一意にする。** 役割名にタスク番号を足す形にする（`org-implementation-T-007`）。**役割名だけを付けてはならない。**
3. **相手の宛先を、タスク別ファイルの `## 連絡してよい相手` に書く。** 担当エージェントは会話履歴を引き継がないため、指示に書かれていない宛先は存在しないのと同じである。

**役割名だけを使い回すと、直接通信は黙って壊れる。** 同じ名前が1セッション内で2回使われると、**その名前宛ての送信は拒否される** —— 新しいほうへ配送されるのではなく、送信そのものが止まり、「以前は別のエージェントを指していた」という旨が返る。誤配より安全な倒れ方だが、**気づかなければ往復が成立しない。** オーケストレーターは同じ役割のエージェントをタスクごとに起こし直すため、この衝突は必ず起きる。タスク番号を混ぜるのはそのためである。

**送るとき、相手が動いている必要はない。** 終了したエージェントは、メッセージが届いた時点で再開される。相手を待機させ続ける必要は無い。

**親（オーケストレーター）へ返すときの宛先は `main` と書く。** セッション名を書くとエラーになる。
