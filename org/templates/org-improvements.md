# 組織改善の台帳

**このファイルは、組織の仕組みそのものについての課題と、その対応を追う台帳である。**
開発する成果物の課題はここには書かない。それはタスク台帳（`docs/task-list-{project-name}.csv` と `docs/tasks/T-XXX.md`）の担当である。

---

## 書いてよいのは誰か

**担当エージェント（設計・実装・レビュー・テスト・ドキュメント）は、このファイルへ書かない。**
自分のタスクファイル `docs/tasks/T-XXX.md` の `## 組織への指摘` へ1行書く。それだけでよい。

理由は、このファイルが全員の共有物だからである。同時に走っている2体が同じファイルへ書けば、**片方の追記が黙って消える**。加えて、全タスクが触るファイルになると、並列に走らせられるタスクが無くなる。

| 誰が | 何を書くか |
| --- | --- |
| **オーケストレーター** | **唯一の書き手。** 担当エージェントから吸い上げた指摘を**1課題1レコードにまとめて起票**する。以後の状態の更新／改善エージェントの診断結果の転記／PO の回答／適用の記録／タスクの外で自分が気づいた課題の起票も行う |
| **改善エージェント** | **書かない。** 診断結果はオーケストレーターへ返す |
| **停滞検知・整合性検査のスクリプト**（`org-check.py`） | **書かない。** タスクファイルに書かれているのに、ここへ起票されていない指摘があれば警告するだけ |

**「まとめる」は判断である。** 3つの別々のタスクから同じ趣旨の指摘が出たとき、1レコードに束ねるか別々の課題として立てるかは、両者の報告を受け取るオーケストレーターにしか決められない。機械に集約させると必ず3レコードになり、優先度の基準（同じ課題が3件以上の別タスクから出ているか）が働かなくなる。

**タスクファイルの `## 組織への指摘` が原文（正典）、このファイルはまとめた作業台である。** タスク別ファイルが正典で CSV が索引、という関係と同じ形になっている。オーケストレーターが起票を怠っても原文は残り、改善エージェントが点検のたびに取りこぼしを拾う。

## 状態

| 状態 | 意味 | 次に動かすのは誰か |
| --- | --- | --- |
| `未処理` | 起票されたが、まだ誰も診ていない | 改善エージェント（次の組織点検で） |
| `診断済み` | 原因の推定と対応策が書かれ、優先度がついた | オーケストレーター |
| `承認待ち` | PO確認待ちキューへ載せた（重さが `中` か `重` のもの） | PO |
| `承認済み` | PO が承認した。まだ適用していない | オーケストレーター |
| `適用済み` | 層2へ反映した。効果はまだ見ていない | 改善エージェント（次の点検で照合） |
| `効果確認済み` | 期待した効果が出たと確認できた。**ここでいったん閉じる** | — |
| `撤回` | **適用した変更を戻した。** 効果が出なかったか、後から害が分かった。**戻した理由と、戻した日を必ず書く** | — |
| `却下` | 採らないと決めた。**理由を必ず書く** | — |
| `見送り` | 今は対処しないが消さない。再燃したら `未処理` へ戻す | — |

## 書式

**1課題1ブロック。** 見出しは `### OI-XXX: 一行でわかる課題名`。番号は起票順の通し番号で、**欠番を詰めない**。

**この番号は、適用した後も使う。** 層2の規約やスキルへ変更を反映するとき、変更した箇所の近くに `(OI-007)` と書き添える。**そうしないと、規約の側から「この一文はどの課題から入ったのか」を辿れなくなる。** 辿れないものは、効かないと分かったときにも戻せない。

### `効果確認済み` は終端ではない

**閉じた課題も、後から害が分かることがある。** 規約を1つ足したことで別のところが詰まった、という形で現れる。

そのときは**新しい課題として起票し直さない。** 元の課題の `経過` へ追記し、状態を `撤回` にする。**同じ課題が別の番号で2度立つと、「1度直したはずのことが再燃している」という最も重要な信号が見えなくなる。**

同じ課題が3回以上 `撤回` になったら、**対応策ではなく原因の推定が間違っている。** 原因からやり直す。

`未処理` の時点で埋まっているのは `状態` から `出所` までの5行だけでよい。残りは改善エージェントが診断したときに、オーケストレーターが埋める。
