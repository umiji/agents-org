# 初回運用の点検

**この組織は、このリポジトリで初めて動いている。** 設計どおりに動いているかを、最初のタスクが1件完了した時点で確かめる。

**自己申告を証拠にしない。** 「委譲しました」という報告ではなく、**ファイルに残った痕跡**で判定する。オーケストレーター自身が点検すると、自分の失敗を見落とすためである。

各項目について、**判定 / 根拠にしたファイルの実際の中身 / 動いていない場合の対処**を報告する。

---

## 点検1. セッション開始時の台帳検査が自動で走ったか

セッション開始時に必ずコマンドを実行させる設定（フック）が、この実行環境で発火したかどうか。

### 確かめ方

1. **このセッションの文脈の先頭に、台帳の検査結果が入っているか**を確認する。入っていれば、その全文をそのまま報告に貼る
2. 入っていなければ、手で実行して比べる:
   ```sh
   python3 .claude/scripts/org-check.py
   ```
   **「コマンドが見つからない」と言われたら `python` に読み替えて再実行する。** どちらの名前で Python が入っているかは実行環境による。

   手で実行すると結果が出るのに、セッション開始時には入っていなかった → **フックが発火していない**

### 判定

| 状態 | 意味 |
| --- | --- |
| 開始時の文脈に検査結果がある | **動いている** |
| 手で実行すると出るが、開始時には無い | **フックが発火していない**（下記の対処へ） |
| 手で実行してもエラーになる | スクリプトの配置か Python の実行環境の問題 |

### 動いていない場合の対処

設定ファイルへの追記が効いていないか、この実行環境がセッション開始時のフックに対応していない。

**運用で埋められる。** セッション再開の手順（`.claude/skills/org-session-resume/`）の3番目が同じ検査であり、そこで手動実行すればよい。ただし**フックと違って実行の強制力が無い**ため、「規約に書いてあるが実行されない回が出る」という弱さが残る。この事実を引き継ぎ記録へ書き残すこと。

## 点検2. 担当エージェントへ委譲されたか

オーケストレーターが自分で実装していないか。**これが最も起きやすい失敗である。**

### 確かめ方（3つを併用する。1つでは足りない）

| # | 見るもの | 何が分かるか |
| --- | --- | --- |
| 1 | **会話の画面**に、担当エージェントの実行が名前つきで表示されたか（`org-implementation` など） | **これが唯一の直接証拠。** 実際に起動されたかどうか |
| 2 | `python3 .claude/scripts/org-check.py` の警告に「状態が実装系なのに担当がオーケストレーター」が出ていないか | 台帳の上で委譲を怠っている痕跡 |
| 3 | `docs/tasks/T-XXX.md` の `## 作業ログ` に、担当エージェントが書いた記録があるか | 誰が手を動かしたかの記録 |

### 判定

| 状態 | 意味 |
| --- | --- |
| 1で担当エージェントの実行が見えた | **動いている** |
| 1で見えないが、台帳の担当欄は埋まっている | **オーケストレーターが自分でやった可能性が高い。** 担当欄だけ埋めて自分で書くと、2の警告では捕まらない |
| 2の警告が出ている | 委譲を怠っている。台帳に痕跡が残っている |

### 動いていない場合の対処

オーケストレーターの手順（`.claude/skills/org-orchestrate/`）の「委譲する」の節を読み直させる。それでも自分でやり続けるなら、**担当エージェントの説明文が曖昧で、委譲先が判断できていない**可能性がある。エージェント定義ファイルの説明文を具体化する。

## 点検3. タスク別ファイルが、そのまま作業指示として機能したか

作業指示を別途書き下ろす必要が出ていないか。

### 確かめ方

**まず検査を走らせる。** 指示欄の未記入は機械的に検出される。

```sh
python3 .claude/scripts/org-check.py
```

「指示が未記入のまま担当が付いている」という警告が出ていれば、そこが該当箇所である。警告が出ていなければ、次の4つは埋まっている。

`docs/tasks/T-XXX.md` を開いて目で見るのは、**埋まってはいるが指示として役に立っていない場合**を見つけるためである。特に次の4つ。

| セクション | 空だと何が起きるか |
| --- | --- |
| `## 完了条件` | レビューとテストが判定できない。両ロールが毎回推測する |
| `## 判断してよい範囲` | 担当エージェントが決めすぎるか、些末なことを全部上げてくる |
| `## 変更範囲` | スコープが広がっても誰も気づかない |
| `## 禁止事項` | 触ってはいけないものが触られる |

加えて、**担当エージェントを起動したときの指示文**が、タスク別ファイルを指しているか、それとも同じ内容を書き下ろしているかを見る。

### 判定

| 状態 | 意味 |
| --- | --- |
| 4つとも埋まっていて、指示文はファイルを指している | **動いている** |
| セクションが空、または「TBD」「未定」 | **テンプレートが守られていない。** 空欄が「指示の抜け」を可視化する仕組みが機能していない |
| 指示文にタスク別ファイルと同じ内容が書き下ろされている | 二重管理になっている。どちらが正か分からなくなる |

### 動いていない場合の対処

空欄のまま担当エージェントが着手していたなら、**着手前の確認（指示の充足チェック）が機能していない。** 層2の規約（`CLAUDE.md` の「着手前に、指示の充足を確認する」）を担当エージェントが読んでいるか確認する。

## 点検4. 完了条件がテストへ変換できたか

TDD（テスト駆動開発。先に失敗するテストを書き、それを通すように実装する進め方）を既定にした判断が、実際に機能したかどうか。

### 確かめ方

1. **テストファイルが実在するか。** リポジトリ内を探す
2. `docs/tasks/T-XXX.md` の `## 証拠` に、**実行したコマンドとその実際の出力**があるか
3. `## 作業ログ` に、**テストが最初は落ちて、実装後に通った**という経過があるか

### 判定

| 状態 | 意味 |
| --- | --- |
| テストが実在し、証拠にコマンドと出力がある | **動いている** |
| 証拠が空、または「手で確認した」だけ | **証拠の規約が守られていない。** 完了と言えない状態で完了になっている |
| テストエージェントが「完了条件をテストへ変換できない」と差し戻していた | **これは正常な動作である。** 判定不能な完了条件を、実装前に検出できたということ。**設計どおりに動いた証拠として扱う** |
| そもそもテストエージェントが起動していない | 点検2へ戻る |

3行目に注意。**差し戻しは失敗ではない。** TDD を既定にした最大の狙いが「テストへ変換できない完了条件を、実装が始まる前に見つけること」であるため。

## 点検5. ツールの実行許可が足りているか

**PO へ許可の確認が何回出たか。** この組織は「PO はゴールと判断を提供し、細かな作業指示は出さない」という前提で作られている。1タスクの間に何度も「このコマンドを実行してよいか」と聞かれているなら、その前提が崩れている。

### 確かめ方

1. **このタスクの間に、PO が許可を求められた回数と、その対象コマンド**を数える。会話の記録を遡る
2. `.claude/settings.json` の `permissions.allow` に、**開発対象そのもののビルド・テストのコマンドが入っているか**を確認する。配布物の推奨値には入っていない（技術スタックが分からないため、導入した側が足す決まりである）

### 判定

| 状態 | 意味 |
| --- | --- |
| 確認は0〜数回で、内容は取り込み（`git merge`）やブランチの切り替えだった | **動いている。** これらは意図して確認させている |
| テストやビルドのたびに確認が出ていた | **`allow` への追記が漏れている。** 最も起きやすい |
| 未コミットの変更を消すコマンドが拒否されて作業が止まった | **正常な動作である。** ただし止まった経緯を報告に残す |

### 動いていない場合の対処

そのリポジトリで実際に使ったビルド・テストのコマンドを `permissions.allow` へ足す。**足す前に、そのコマンドが何を書き換えるかを確かめる**（外部への通信やデータベースの作り直しを伴うものがある）。

配布物側の推奨値そのものが足りていなかったなら、**組織の定義を持つリポジトリ（`agents-org`）へ差し戻す。**

## 報告の形

```markdown
## 初回点検 YYYY-MM-DD

| # | 点検項目 | 判定 |
| --- | --- | --- |
| 1 | セッション開始時の台帳検査 | 動いている / 発火していない / エラー |
| 2 | 担当エージェントへの委譲 | 動いている / 疑わしい / 委譲されていない |
| 3 | タスク別ファイルが作業指示として機能 | 動いている / セクションが空 / 二重管理 |
| 4 | 完了条件のテストへの変換 | 動いている / 証拠が不足 / 差し戻された（正常） |
| 5 | ツールの実行許可 | 動いている / 追記が漏れている（確認が何度も出た） |

### 根拠
（各項目について、見たファイルと、その実際の中身を引用する）

### 動いていなかったもの
（何を、どう対処したか。対処できないものは、組織の定義側の問題として報告する）
```

**結果は引き継ぎ記録（`docs/handover.md`）へ書く。** 次のセッションが同じ点検を繰り返さずに済むようにするため。

**動いていなかった項目は、組織の定義を持つリポジトリ側（`agents-org`）へ差し戻す価値がある。** 仕様か配布物の不備であり、他のプロジェクトでも同じことが起きるためである。
