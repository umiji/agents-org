# セッション再開の手順

前のセッションは、トークン上限・コンテキスト上限で**予告なく切れている可能性がある**。引き継ぎ記録が最新とは限らない。

---

## 読む順序

| # | やること | なぜこの順か |
| --- | --- | --- |
| 1 | `CLAUDE.md`（自動で読み込まれる） | 組織の規約。層2 |
| 2 | **`docs/handover.md`** | 現在地・次の一手・環境。最初に読む |
| 3 | **台帳を検査する** — `python3 .claude/scripts/org-check.py` | **引き継ぎ記録は嘘をつきうる。信じる前に機械的な検査を通す** |
| 4 | `docs/task-list-{project-name}.csv` | 索引。全体像 |
| 5 | 進行中タスクの `docs/tasks/T-XXX.md` | **進行中のものだけ。完了済みは読まない** |
| 5-b | **`docs/decisions-index.md`（決定ログ索引）** | **完了済みタスクの決定も、ここでだけは読む。** 1決定1行なので費用が小さい |
| 6 | `docs/po-queue.md` の未回答項目 | PO へ再度確認すべきものがあるか |
| 7 | `git status` / `git log` | 未コミットの作業、直近のコミット |
| 8 | 指標を集計する — `python3 .claude/scripts/org-check.py --summary` — し、`handover.md` の前回値と比較する | 前進しているかを判定する。**集計はスクリプト、判定はあなた** |

**手順3・8のコマンドが「見つからない」と言われたら、`python3` を `python` に読み替える。** どちらの名前で Python が入っているかは実行環境による。

セッション開始時のフックが設定されていれば、手順3の結果は**既に文脈に入っている**。その場合は読むだけでよく、実行し直さなくてよい。

### 手順3を4より前に置く理由

前のセッションが引き継ぎ記録を更新できずに切れていれば、`handover.md` は古い。タスク台帳は各エージェントの作業で更新されているため、より新しい可能性がある。整合性検査が両者のずれを検出する。

**放置されたタスクを拾えるのは、この検査だけである。**

### 手順5の「完了済みは読まない」

台帳を索引と詳細に分けたのは、1つのタスクを触るために完了済み全タスクの証拠まで読み込む状態を避けるためである。**再開手順がそれを守らなければ、分けた意味が無い。**

### 手順5-b が例外である理由

**「完了済みは読まない」という規約こそが、過去の決定を引けなくしていた原因である。** 完了したタスクの決定ログは、この規約のせいで二度と読み返されない。**書く費用だけがかかって、効果が0になっていた。**

決定ログ索引はそのために作った生成物である。**全タスク（完了・中止を含む）の決定が1決定1行で並んでいる**ので、本文を読まずに済む。読む費用は決定の件数に比例するだけで、タスクの本文量には比例しない。

**索引が古いことがあるので、読む前に作り直す**（セッション開始時のフックが設定されていれば、既に作り直されている）。

```sh
python3 .claude/scripts/org-decisions.py --check   # 古くなっていないか見る
python3 .claude/scripts/org-decisions.py           # 作り直す
```

## 検査で見つかったものへの対処

| 検出 | 対処 |
| --- | --- |
| 停滞候補（更新日が2日以上前） | 停滞への対処へ（原因確認 → 再分割 → 再割り当て → PO） |
| PO確認待ちのリマインド候補 | PO へ通知する。組織への差し戻しではない |
| CSV と詳細ファイルの `更新日` / `状態` の食い違い | **詳細ファイル側を真とする**（担当が実際に作業した記録があるため）。CSV を直す |
| `ドキュメント` 列のパスが存在しない | 詳細ファイルを作るか、行を `中止` にする |
| 依存タスクのIDが CSV に存在しない | 誤記か、削除された行。どちらかを直す |
| 終端状態でないのに `担当` が `未割当` | 割り当てる。実質の停滞である |
| 状態が既定の10種でない | 直す。集計から漏れる |
| 実装系の状態なのに `担当` がオーケストレーター | **委譲を怠っている。** 担当エージェントへ渡す |
| 指示欄が未記入のまま担当が付いている | **着手前に埋める。** 完了条件が無いままレビューとテストへ流すと、両者が判定基準を推測することになる |
| 完了なのに `## 証拠` が空 | 完了と言える根拠が無い。担当へ差し戻すか、状態を戻す |
| PO確認待ちキューの書式違反 | 見出しを `### Q-001 [未回答] 要約` の形へ直す。**直すまで未回答件数が指標に出ない** |

## 再開したら最初に PO へ伝えること

長い報告は要らない。以下で足りる。

- 現在地（進行中のタスクと、その状態）
- 停滞・ずれの検出結果（無ければ「無し」）
- 未回答の PO確認待ち（あれば、その場で問う）
- 次の一手

---

## セッション中：引き継ぎ記録をいつ更新するか

**「セッション終了時にまとめて書く」は成立しない。** 上限は予告なく訪れ、書く余裕が残っていない状態で切れる。

**節目ごとに更新する。**

| いつ | 何を更新するか |
| --- | --- |
| タスクの状態が変わったとき | 現在地、次の一手 |
| PO の判断を得たとき | 直近の判断（そのタスクの決定ログへ転記するまでの間） |
| 健全性評価を行ったとき | 直近の健全性評価、次の一手 |
| ゴール達成条件が確定・変更されたとき | ゴール |
| セッション終了時（可能なら） | 全体 |

最終行は「可能なら」である。**それまでの更新で引き継ぎが成立していなければならない。**

### `docs/handover.md` の項目

| 項目 | 内容 |
| --- | --- |
| 更新日時 | いつ時点の状態か |
| ゴール | PO から受けたゴールと、**現時点で確定しているゴール達成条件** |
| 現在地 | 直近で何をしていたか。進行中のタスクID |
| 直近の判断 | まだタスクの決定ログへ書けていない決定。**無ければ「無し」と明記** |
| 次の一手 | 新セッションが最初にやること |
| PO確認待ち | 未回答の Q-ID 一覧 |
| 直近の健全性評価 | 8指標と判定。**次回が前回比を出すために参照する** |
| 環境・前提 | ビルド／テスト／リントのコマンド、未コミットの作業の有無 |

**1枚。常に上書きする。** 過去分は git 履歴に残る。追記して膨らませない。

### 決定は引き継ぎ記録に溜めない

`直近の判断` は**一時的な置き場**である。決定はタスクの `## 決定ログ` へ書くのが正であり、ここに残るのは「まだ書けていないもの」だけ。溜まっていること自体が、転記を怠っている信号になる。

**恒久的に確定したもの**（ビルドコマンド、常に守る規約）は、引き継ぎ記録ではなく `CLAUDE.md` へ昇格させる。引き継ぎ記録には流動的なものだけを残す。

**タスクの決定ログへ書いたら、決定ログ索引を作り直す**（`python3 .claude/scripts/org-decisions.py`）。索引は生成物なので、手で行を足さない。

## 引き継がないもの

| 引き継がない | なぜ |
| --- | --- |
| 会話の全文・要約 | 必要な情報は台帳と引き継ぎ記録に既にある |
| 完了済みタスクの詳細 | 索引に完了として載っていれば足りる。必要になったら開く |
| 各サブエージェントの内部状態 | サブエージェントは新規の隔離コンテキストで始まる。**引き継げるものが元々無い** |
| 未確定の推測・仮の方針 | 次のセッションで確定済みとして扱われる危険がある。確定していないなら書かない |

3行目が構造的に重要である。**状態は常にファイルにあり、エージェントには無い。** セッション引き継ぎが成立するのは、この非対称性のおかげである。
