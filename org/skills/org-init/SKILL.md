# 導入時の初期シーケンス

**これはオーケストレーター（メインセッション）が行う。** 担当エージェントへは委譲しない。エージェント定義そのものを書き換える作業であり、書き換えられる側が自分を書き換えると、何が変わったのかを確かめる立場が消えるためである。

**1回だけ走らせる。** 配布物をこのリポジトリへコピーし終えた直後、最初のゴールを受ける前が定位置である。

## なぜこの手順が要るのか

**担当エージェント（設計・実装・レビュー・テスト・ドキュメントの5つ）の定義には、使うスキルが最初から数本だけ書いてある。** スキルとは、Claude Code が呼ばれたときだけ読み込む手順書のことである。

初期状態で書いてあるのは、**言語やフレームワークに依存しないものだけ**である。書いた側は、この組織がどのリポジトリへ導入されるかを知らないためである。したがって次の2つが起こりうる。

- **書いてあるスキルが、この実行環境に入っていない。** 呼んでも「そのようなスキルは無い」と返る
- **このリポジトリの技術構成に必要なスキルが、書かれていない。** 例えば Python のリポジトリなのに Python のテストの書き方が割り当てられていない

**どちらも黙って起きる。** エラーは出ず、成果物も一応できる。だから導入時に1回、環境と突き合わせる。

---

## 段1. この実行環境から呼べるスキルを集める

**集めるのはスクリプトの仕事である。** 数え上げに判断は要らず、担当エージェントやオーケストレーターにやらせるとトークンを消費したうえに数え落とす。

```sh
python3 .claude/scripts/org-skills.py --names
```

**「コマンドが見つからない」と言われたら `python` に読み替えて再実行する。** どちらの名前で Python が入っているかは実行環境による。以降のコマンドもすべて同じである。

`--names` は名前だけを出す。**まずこれを見る。** 説明までまとめて読み込むと、この段だけで1万トークン規模を消費するためである。

候補を絞ったら、その分だけ説明を読む。

```sh
python3 .claude/scripts/org-skills.py --search テスト     # 名前か説明に語を含むものだけ
python3 .claude/scripts/org-skills.py --search python --full   # 説明を切り詰めずに出す
```

このスクリプトは**読むだけで何も書き換えない。** 出てくるのは3か所からの合算である——導入済みプラグインの中、利用者共通の置き場（`~/.claude/skills/`）、このリポジトリの中（`.claude/skills/`）。

### 1本も出てこなかったら

この実行環境にはスキルが入っていない。**段3の3番目（PO確認待ちキューへ載せる）へ進む。** 組織は自分の手順スキル（オーケストレーター・セッション再開・初回点検・この手順）だけで動けるので、ここで止めない。

---

## 段2. このリポジトリの技術構成を読む

**ここは判断なのであなたがやる。** 見るものは次の4つ。

| 見るもの | どこを見るか | 何が決まるか |
| --- | --- | --- |
| 言語 | 依存関係を宣言するファイル（`package.json` / `pyproject.toml` / `go.mod` / `Cargo.toml` / `pom.xml` など）、ソースの拡張子 | その言語の書き方・レビュー観点のスキルが要るか |
| フレームワーク | 同じファイルの依存の中身 | フレームワーク固有のスキルが要るか |
| テストの実行基盤 | テストを走らせるコマンドの定義、テストファイルの置き場 | テスト担当へ足すものが決まる |
| 自動実行の仕組み（CI） | `.github/workflows/` など | 完了の判定に何が含まれるか |

**まだ何も無い新規のリポジトリなら、この段は飛ばす。** 技術構成は設計エージェントがこれから決めるものであり、決まっていないものと突き合わせることはできない。**その場合はこの手順をもう一度走らせる時機を引き継ぎ記録（`docs/handover.md`）へ書く**——方式設計が終わった直後である。

---

## 段3. 突き合わせる

段2で「要る」と判断した種類ごとに、段1で集めた中から探す。**探す順番が決まっている。**

| 順 | 探し先 | どうやって | ネット接続 |
| --- | --- | --- | --- |
| 1 | この実行環境から呼べるスキル | `org-skills.py --search 語` | 不要 |
| 2 | **まだ導入していないプラグインの目録** | `org-skills.py --catalog --search 語` | 不要 |
| 3 | 1にも2にも無い | **PO確認待ちキュー（`docs/po-queue.md`）へ載せる** | — |

### 順2について

Claude Code には、プラグイン（スキル・エージェント定義・フックなどをまとめて配る単位）の配布元を登録する仕組みがある。登録すると、その配布元が持つプラグインの目録がローカルのファイルへ落ちてくる。`--catalog` はそれを読む。

**Claude Code には、スキルやプラグインを検索するコマンドが無い。** この目録がその代わりを果たす。

**目録に良さそうなものを見つけても、導入は自分でしない。** 導入するかどうかを PO確認待ちキューへ載せて、PO（プロジェクトオーナー＝人間の依頼主）の承認を待つ。プラグインはスキルだけでなく**フック**（特定のタイミングで必ずコマンドを実行させる仕組み）も持ち込むため、素性の分からない配布元を組織が自動で導入すると、**組織が把握していないコマンドの自動実行経路が増える。**

### 順3について

**PO確認待ちの間も、依存関係のないタスクは止めない。** 割り当てが1つ決まらないことは、組織全体を止める理由にならない。該当する担当エージェントは、そのスキル無しで動く。

---

## 段4. エージェント定義へ書き出す

書き換えるのは `.claude/agents/org-*.md` の5本である。**3種類の書き換えがある。**

### 4-a. 呼べないものを外す

初期状態で名指ししてあるスキルのうち、段1の一覧に**無かったもの**を消す。残しておくと、担当エージェントが呼んで失敗し、そのたびに「呼べなかった」という報告が上がってくる。

**消したものは引き継ぎ記録（`docs/handover.md`）へ書く。** 後から同じプラグインを導入したときに、戻す判断ができるようにするためである。

### 4-b. このリポジトリに要るものを足す

段3で見つけたものを、該当する担当エージェントの `## 使うスキル` の表へ足す。**表には3列ある。**

| 列 | 書くこと |
| --- | --- |
| 呼ぶスキル | 呼び出しに使う名前をそのまま。プラグインのものは `プラグイン名:スキル名` の形 |
| 何の手順か | **その名前を知らない人に通じる説明を1行で。** 名前を言い換えただけの説明を書かない |
| いつ呼ぶか | どの場面で呼ぶか。「必要なら」と書かない——それは判断を丸投げしている |

**名前は `org-skills.py` の出力からコピーする。** 記憶で書かない。1文字違うと呼べず、しかもその失敗は完了報告にしか現れない。

### 4-c. 使えるツールの欄を確かめる

各定義の冒頭にある `tools:` の行に **`Skill` が入っているか**を確認する。配布物には入れてあるが、導入先で既存の定義と混ざった場合に落ちることがある。

**これが無いと、スキルを1本も呼べないどころか、何が使えるのかの一覧すら担当エージェントへ提示されない。**

### 書き換えないもの

**呼んではいけないスキルの規定**（`CLAUDE.md` の「呼んではいけないスキル」）は触らない。組織の規約と食い違うものを挙げてあり、導入先の事情で変わるものではない。

---

## 段5. セッションを開き直す

**PO に開き直してもらう。** ここで一度止まる。

**エージェント定義は、セッションが始まった時点の内容が読み込まれる。** 書き換えても、いま動いているこのセッションには反映されない。

---

## 段6. 効いているかを確かめる

**省略できない。** ここを飛ばすと、**失敗が見えない形で残る。**

書き換えた直後のセッションで担当エージェントを起こすと、その担当エージェントは**スキルを1本も持たない古い定義のまま動く。** エラーは出ず、成果物も一応できあがる。**「スキルが効いていない」と気づく手段が無い。**

### 確かめ方

担当エージェントを1つ起こし、次を報告させる。**レビュー担当（`org-review`）で確かめるのがよい**——割り当てたスキルが最も重要な役割だからである。

1. 使えるツールに `Skill` が入っているか
2. 定義の `## 使うスキル` に挙がっている名前を実際に呼び、**本文が読み込まれたか**
3. 呼べなかったものがあれば、その名前と返ってきた内容

**「呼べます」という自己申告を証拠にしない。** 呼んだ結果、本文の見出しが読めたかどうかを報告させる。成功時はスキルの本文が会話へ挿入され、失敗時はエラーだけが返る。**この2つは明確に違う返り方をする。**

### 判定

| 状態 | 意味 |
| --- | --- |
| 全部呼べた | **効いている。** 初期シーケンスは完了 |
| 一部呼べなかった | その名前が間違っているか、この環境に無い。段4-a へ戻る |
| 1本も呼べず、一覧も提示されない | **`tools:` の行に `Skill` が入っていない。** 段4-c へ戻る |
| 使えるツールに `Skill` があるのに呼べない | セッションを開き直していない可能性がある。段5へ戻る |

---

## 終わったら

- **結果を引き継ぎ記録（`docs/handover.md`）へ書く。** 割り当てたスキル、外したもの、PO確認待ちへ載せたもの
- **この手順はもう走らせない。** 次に走らせるのは、技術構成が大きく変わったとき（新しい言語やフレームワークが入った）か、プラグインを導入・更新したときだけである
- 最初のタスクが1件完了したら、**初回運用の点検**（`.claude/skills/org-first-run-check/`）を行う。組織全体が設計どおりに動いているかを、こことは別の観点で見る
