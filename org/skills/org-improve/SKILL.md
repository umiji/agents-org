# 組織の観測と診断

**これは改善エージェントの手順である。** オーケストレーターや他の担当エージェントがこれを実行しない。

**あなたは何も書き換えない。** 読んで、診断して、オーケストレーターへ返す。台帳への転記も、規約の修正も、あなたの仕事ではない。

以下のコマンドで **「コマンドが見つからない」と言われたら `python3` を `python` に読み替えて再実行する。** どちらの名前で Python が入っているかは実行環境による。

---

## 段1. 前回の提案が効いたかを、先に照合する

**必ずここから始める。新しい信号を集める前である。**

理由は単純で、**効かなかった変更の上に別の変更を積むと、組織の規約が誰も意図していない堆積物になる**ためである。これは停滞管理が「同じ手を繰り返すのは停滞の解消ではなく停滞の継続である」と述べたのと同じ構造である。

組織改善の台帳（`docs/org-improvements.md`）から、状態が `適用済み` のものを全部拾う。各件の `期待する効果` 欄に、**どの指標がどう動けば成功か**が書いてある。それを実際に測る。

```sh
python3 .claude/scripts/org-check.py --summary    # ゴール健全性の8指標
python3 .claude/scripts/org-tokens.py --by task   # タスク別のトークン消費
```

判定は3値である。

| 判定 | 条件 | 返し方 |
| --- | --- | --- |
| **効いた** | 期待した指標が、期待した向きに動いた | 「`効果確認済み` にしてよい」と返す |
| **効かなかった** | 動かなかった、または逆に動いた | **変更を戻すか、原因の推定をやり直すか**を提案する。**上乗せで別の変更を積まない** |
| **まだ判定できない** | 母数が足りない（対象の工程をまだ通っていない等） | 次回へ持ち越す。**持ち越し2回目で、判定できない理由を報告する** |

**指標が動いていないのに「たぶん効いている」と書かない。** 数値で言えないなら「まだ判定できない」である。

## 段2. 信号を集める

**数え上げはスクリプトにやらせる。** 自分で台帳を全部読んで数えると、トークンを消費したうえに数え落とす。

```sh
python3 .claude/scripts/org-check.py             # 停滞と整合性の警告
python3 .claude/scripts/org-check.py --summary   # ゴール健全性の8指標
python3 .claude/scripts/org-tokens.py --by agent # 担当別のトークン消費
python3 .claude/scripts/org-tokens.py --by model # モデル別
python3 .claude/scripts/org-skills.py --names    # この環境から呼べるスキルの名前
```

集める信号は10種である。

| # | 信号 | どこで取るか |
| --- | --- | --- |
| 1 | 実時間基準の停滞（更新が2日以上止まっている） | 検査の警告 |
| 2 | サイクル基準の停滞（手戻り回数3以上） | 検査の警告 |
| 3 | ボトルネックとなっている工程（状態別の滞留日数の中央値） | 健全性の指標7 |
| 4 | エスカレーションの偏り（同じ論点が複数タスクから／特定のロールからばかり） | `docs/po-queue.md` を読む |
| 5 | PO確認待ちの滞留（未回答が2日以上） | 検査の警告 |
| 6 | トークン消費の偏り（特定の担当・モデル・タスクへの集中） | トークン集計 |
| 7 | **担当エージェントからの指摘**（4種別: `規約` `道具` `反復` `ロール`） | **まず組織改善の台帳（`docs/org-improvements.md`）の `未処理` を読む。** オーケストレーターがまとめて起票してある |
| 8 | **PO の反応**（差し戻し・却下・言い直し） | `docs/po-queue.md` の `反応` 欄 |
| 9 | 呼べるスキルと技術構成の食い違い | スキル収集の出力 ＋ 依存関係の宣言ファイル |
| 10 | **報告に書かれた作業量と、実際に費やされた量の食い違い** | トークン集計の `--task` ＋ タスクファイルの作業ログ |

### 信号7は、台帳だけを見て済ませない

**台帳への起票はオーケストレーターが手で行う。** つまり**起票され忘れた指摘がありうる。**

各タスクファイルの `## 組織への指摘` を横断して見て、**台帳に無いものが残っていないか**を毎回確かめる。

```sh
grep -A5 "## 組織への指摘" docs/tasks/*.md | grep "^\S*[-:]- \["
```

検査スクリプト（`org-check.py`）も同じ取りこぼしを警告する。**両方を使う。**

取りこぼしが見つかったら、それも観測結果として扱い、**「起票の取りこぼしが N 件あった」こと自体も報告する。** 手順が守られていない信号だからである。

### 指摘が0件であることを、問題が無いことと読まない

**数タスク回っても `## 組織への指摘` がどれも `無し` のままなら、書く仕組みが働いていない可能性のほうが高い。**

確かめ方は2つある。

- タスクファイルにその節が**そもそも存在するか**（雛形が古いまま配られていると、節ごと無い）
- 完了報告にその項目が含まれているか（節には書かれたが報告に載っていないなら、オーケストレーターが気づけない）

**「指摘0件」は、O-3 として必ず報告する。** 組織が健全なのか、経路が死んでいるのかは、この時点では区別できない——**区別できないこと自体を報告する。**

### 信号8を軽く見ない

**PO の反応が、最も価値の高い信号である。** 詳しい人からの少数の具体的な指摘は、大量の雑な評価に勝る。

**PO 由来の指摘1件は、担当エージェント由来の3件より重く扱う。** 件数の多さで順位をつけない。

### 信号10 — 報告だけで判断しない

**タスクファイルも完了報告も、担当エージェント自身が書いたものである。** そこから読めるのは「本人がそう認識した内容」であって、実際に何が起きたかではない。

**自分で書いた報告から評価するループは、その報告の楽観をそのまま受け継ぐ。** うまくいかなかったことが「対応済み」と書かれ、遠回りした事実が消える。**この組織の観測は、信号1〜9 のうち3種が書かれた文章であり、この弱点を構造として持っている。**

**完全に埋めることはできないが、食い違いは安く測れる。**

```sh
python3 .claude/scripts/org-tokens.py --task T-007    # 1タスクの内訳
```

見るのは**作業の規模と、費やされた量の釣り合い**である。

| 観測 | 疑うこと |
| --- | --- |
| 作業ログが短いのに、消費が同規模の他タスクより明らかに大きい | **報告に書かれていない遠回りがあった。** 情報を探し直した、同じことを繰り返した、指示が自己完結していなかった |
| 手戻り回数は0なのに、往復が多い | 差し戻しとして記録されない小さなやり直しが積み重なっている |
| 消費が極端に小さいのに完了している | 完了条件が緩すぎるか、確認が省かれている可能性がある |

**釣り合いの基準は、他のタスクとの比較である。** 絶対値の閾値は決まっていない——**比較できる母数が無いうちは、この信号を使わない。**

**食い違いを見つけても、それだけで断定しない。** そのタスクファイルの実物を読んで裏を取る。裏が取れなければ O-3 へ回す。

## 段3. 症状から原因へ当たりをつける

**症状をそのまま対応策にしない。** 「停滞している」への対応策は「停滞を解消する」ではない。

よくある症状と、まず疑うべき原因の対応表である。**これは当たりであって、確定ではない。** 必ずタスクファイルの実物を読んで裏を取る。

| 症状 | まず疑う原因 | 裏の取り方 |
| --- | --- | --- |
| 同じ論点が複数のタスクから上がってくる | 層2に判断基準が書かれていない。PO の回答の還元を怠っている | PO確認待ちキューで、過去に同種の回答が出ていないか探す |
| 特定のロールからばかりエスカレーションが上がる | そのロールへの作業指示が不足している | そのロールが担当したタスクファイルの `## 判断してよい範囲` が空か、狭すぎないか |
| 本来その場で決めてよいことが上がってくる | 「判断してよい範囲」が狭すぎるか、書かれていない | 同上 |
| PO確認待ちが増え続ける | ゴール達成条件が確定していない | 健全性評価の判定が「ゴールが揺らいでいる」に近づいていないか |
| 手戻り回数が特定のタスクで多い | 完了条件が二値で書かれていない。設計が確定する前に実装へ渡っている | そのタスクの `## 完了条件` がテストへ変換できる形か |
| 特定の工程で滞留日数が突出する | その工程の担当に、道具かスキルが足りていない | その工程を担当したタスクの `## 組織への指摘` の `道具` |
| トークン消費が特定の担当へ集中する | 作業指示が自己完結しておらず、毎回情報を集め直している | その担当のタスクファイルの指示欄が、それ単体で読めるか |
| 同じ誤りが複数のタスクで繰り返される | 規約として明文化されていない | 層2の規約に、その判断が書かれているか |
| 成果物はできるのに手順が守られない | 規約が読まれていない。**規約が長すぎる可能性がある** | `CLAUDE.md` の行数。200行を超えると遵守率が落ちる |
| ある役の手が空くのを待って、複数のタスクが止まる | その役の作業指示が重すぎるか、判断してよい範囲が狭すぎる。**役の分け方が原因なのは、これらを潰した後である** | 止まったタスクの `## 組織への指摘` の `ロール`。その役が担当したタスクの滞留日数の中央値 |

### 最後の行が最も見落とされる

**規約を足す方向にだけ倒さない。** 組織の指示は足せば足すほど守られなくなる。

**「規約を減らす」「別ファイルへ出す」「スキルへ移す」も対応策である。** 常に必要な事実は `CLAUDE.md`、トピック別の規約は `.claude/rules/`、多段階の手順は呼ばれたときだけ読まれるスキルへ——この振り分けが崩れていないかを、毎回1度は見る。

## 段3.5. 直す場所を選ぶ — 7段のはしご

**原因が分かったら、次は「どこを直すか」である。ここで段を間違えると、費用が跳ね上がる。**

手を入れられる場所は、安い順に7段ある。

| 段 | 直す場所 | 影響が及ぶ範囲 | 戻すときの費用 |
| --- | --- | --- | --- |
| 1 | そのタスクの指示文 | そのタスクだけ | ほぼ無し |
| 2 | タスク別ファイルの雛形 | 以後の全タスク | 小 |
| 3 | 層2の規約（`CLAUDE.md` / `.claude/rules/`） | 全担当エージェント、全タスク | 中 |
| 4 | スキル（呼ばれたときだけ読まれる手順書） | それを呼ぶ役だけ | 中 |
| 5 | 担当エージェントの定義 | その役の全タスク | 中 |
| 6 | **役を増やす・統合する** | 組織の構造そのもの | **大。決定記録と PO の判断が要る** |
| 7 | **配布物そのもの** | **全導入先** | **最大** |

**規則は1つ。再発する問題は、それを表現できる最も低い段で直す。**

**高い段のほうが「根本的」に見えるが、それは錯覚である。** 高い段は、影響範囲が広いぶん、効かなかったときに戻す費用も、副作用を切り分ける難しさも上がる。

### 段3と段4の使い分け — この組織では段4を既定にする

**層2の規約（段3）は毎セッション全文が読み込まれ、200行を超えると遵守率が落ちる。** つまり**規約は、足すたびに、既にそこにある規約の効き目を薄める。**

一方、スキル（段4）は**呼ばれたときだけ読み込まれる**ため、この上限を持たない。

**手順や判断基準を足すなら、まず段4を検討する。段3へ置くのは、全ロールが常に知っていなければならない事実だけである。**

**これは要約とは違う。** 既にある規約を短く書き直すのではなく、**移す**。書き直して縮めると、その領域固有の細部が落ちて全体が曖昧になり、繰り返すうちに一般論の塊へ潰れる。**縮めるのではなく、置き場所を変える。**

### 段6（役を増やす）へ飛ばないための確認

`ロール` 種別の指摘を受けたときは、**段1〜5 で解けないことを先に示す。** 順に確かめる。

| 確認 | 解けるなら段6は不要 |
| --- | --- |
| その役の `## 判断してよい範囲` が狭すぎないか | 段1または段2 |
| 判断基準が層2に書かれていないために、都度上がってきていないか | 段3 |
| その役に必要なスキルが割り当てられているか | 段4 |
| その役の責務の記述が、実際の仕事とずれていないか | 段5 |

**専門知識が足りないだけなら、役ではなくスキルを足す。役は責務の単位であって、知識の単位ではない。**

**すべて潰してなお解けないときだけ、「段6の変更を検討する価値がある」と提案する。** 提案であって決定ではない——役の増減は PO の判断と決定記録を要する。

## 段4. 優先度をつけ、上げる件数を絞る

**全件を上げてはいけない。** 全部上げると、この仕組み自体が「エスカレーションが多すぎる」という症状の原因になる。

| 優先度 | 基準 |
| --- | --- |
| **高** | 組織が止まっている／止まりかけている（停滞・ブロックの原因になっている）／同じ課題が**3件以上の別タスク**から出ている／**PO の反応に由来する** |
| **中** | 手戻りやトークンの無駄が、測れる形で出ている |
| **低** | 不便ではあるが、作業は進んでいる |

**1回の点検でエスカレートするのは最大3件。** 残りは台帳に `未処理` のまま残り、次の点検で再び優先度づけの対象になる。**消えるわけではない。**

## 段5. 対応策を書く

**8つの欄をすべて埋める。1つでも埋まらないなら、その提案はまだ出せる状態にない。**

| 欄 | 何を書くか |
| --- | --- |
| `信号` | どの信号から、何件観測したか |
| `原因の推定` | なぜそれが起きていると考えるか |
| `段` | **7段のはしごのどこで直すか（段3.5）。上の段を選ぶなら、下の段で解けない理由を1行** |
| `変更` | **どのファイルを、どう直すか。最小の編集で** |
| `適用範囲` | `このリポジトリのみ` / `配布物` |
| `重さ` | `軽` / `中` / `重` |
| `期待する効果` | **どの指標がどう動けば成功か** |
| `悪化しうるもの` | この変更で悪くなる可能性があるもの |

### 「最小の編集」の意味

**一度に大きく変えない。** 大きい変更は、効いたかどうかを切り分けられない。3箇所を同時に直して指標が動いても、どれが効いたのか分からず、次の判断に使えない。

**観測した具体的な事実を捉える、最も小さい編集**を書く。「規約を全面的に見直す」は対応策ではない。

**特に、既存の文書の全面的な書き直しを提案しない。** 蓄積した規約を一度に書き直させると、桁違いに縮み、具体的な事実を捉えていた記述が一般論に置き換わって、**一度も直していなかったときより悪くなることがある。** 直すのは、狙いを定めた1箇所である。

### 変更に、出自の刻印を付ける

**`変更` 欄には、書き足す一文の末尾に課題の番号を添える形で書く。**

```
.claude/rules/org-task-ledger.md の「完了条件」の説明へ次の1行を足す:
「実環境での確認が要る場合は、実施者を明記する (OI-007)」
```

**これが無いと、規約の側から「この一文はどの課題から入ったのか」を辿れない。** 辿れない規約は、効かないと分かったときにも戻せず、ただ積み上がる。

### `適用範囲` を必ず判定する

| 判定 | 条件 |
| --- | --- |
| `このリポジトリのみ` | 原因が、このリポジトリ固有の事情（技術構成・ゴール・チームの慣習）にある |
| `配布物` | **原因が組織の設計そのものにあり、同じ組織を導入した他のリポジトリでも同じことが起きる** |

**迷ったら `配布物` に倒す。** ここを取り違えると、他の導入先で同じ問題が再発し、**同じ問題を2箇所で別々に直すことになる。** これは実際に起きた失敗である。

### `期待する効果` が書けない提案は出さない

**これがこの組織における唯一の検証手段である。** 「良くなるはず」は効果ではない。使えるのは、次の測れる数値だけである。

- ゴール健全性の8指標（完了・未完了・停滞・ブロック中・PO確認待ち・手戻り件数・ボトルネック工程・残作業）
- 手戻り回数（タスク別）
- トークン消費（担当別・モデル別・タスク別）
- 組織への指摘の件数（種別ごと）

### `悪化しうるもの` を空にしない

**片側だけを見て最適化すると、片側だけが良くなる。** 「規約を足せば守られる」の裏には「規約が伸びれば守られなくなる」がある。**両側を書く。**

本当に何も悪化しないと考えるなら、その根拠を1行書く。「無し」とだけ書かない。

## 段5.5. 組織がこのリポジトリに馴染んできているかを見る

**ここまでの段は、1つひとつの改善が効いたかを見るものである。この段だけは、組織全体を見る。**

**この組織は、どの導入先でも同じ形で使われることを目指していない。** 導入先ごとに事情が違うため、**繰り返し直して、そのリポジトリに合った形へ寄っていくこと**が目指す状態である。**寄っているかどうかは、言葉ではなく量で見る。**

見るのは4つだけである。**点検のたびに、前回の値と並べる。**

| # | 量 | 馴染んできているなら | どこで取るか |
| --- | --- | --- | --- |
| 1 | PO確認待ちの新規件数（点検の間隔あたり） | **減る**。判断基準が層2へ降りてきているため | `docs/po-queue.md` |
| 2 | 手戻り回数の合計（同上） | **減る**。完了条件と設計の渡し方が噛み合ってきているため | 健全性の指標6 |
| 3 | 実時間基準・サイクル基準の停滞の発生回数 | **減る** | 検査の警告 |
| 4 | 同じ種別の指摘の再発件数 | **減る**。直したものが再発しなくなっているため | 台帳の `撤回` と、種別ごとの件数 |

**4つすべてが減っている必要はない。向きと、その理由が説明できることが要点である。**

- **どれかが増えているとき、それが悪いとは限らない。** 例えば PO確認待ちが増えるのは、それまで誰も気づかず勝手に決めていたものが表に出てきた結果かもしれない。**増えた理由を1行で言えるなら、それでよい**
- **「馴染んできた」と書くなら、必ずどの量がどう動いたかを添える。** 数値の裏付けが無いなら、書くのは「まだ判定できない」である
- **初回と2回目は、比較する前回が無いか浅い。** そのときは値を記録するだけでよい。**無理に傾向を語らない**

これは O-4 として返す。

## やってはいけないこと

| やらないこと | なぜ |
| --- | --- |
| **担当エージェントの出来を評定する** | 対象は仕組みであって担当者ではない。「実装エージェントの質が低い」は診断ではない。「完了条件が二値で書かれておらず、実装が判断を迫られている」が診断である |
| **母数が無いのに提案する** | 1件の観測から組織の欠陥を断定しない。**「まだ判定できない」と返すのが正しい振る舞い**である。母数の無い観測は当てにならない |
| **効かなかった変更の上に、別の変更を積む** | 戻すか、原因の推定をやり直す。積むと切り分けられなくなる |
| **自分で層2や台帳を書き換える** | あなたには編集系ツールが与えられていない。書けたとしても書かない |
| **成果物を見る** | コード・テスト・設計成果物・利用者向け文書はレビューエージェントとテストエージェントの担当である |
| **規約を足す方向にだけ倒す** | 減らす・移す・分けるも対応策である（段3の最後） |
| **PO へ直接問い合わせる** | 担当エージェントは PO へ問い合わせられない。オーケストレーター経由である |
| **既存の文書の全面的な書き直しを提案する** | 一度に縮めると具体が落ち、繰り返すうちに一般論の塊へ潰れる。直すのは狙いを定めた1箇所である |
| **報告だけを読んで評価する** | 報告はエージェント自身が書いたものであり、その楽観をそのまま受け継ぐ。信号10 で食い違いを見る |
| **「役が足りない」を、下の段を潰さずに提案する** | 段6 は最も高くつく変更である。段1〜5 で解けないことを先に示す（段3.5） |
| **`効果確認済み` の課題を、再発時に新しい番号で立て直す** | 同じ課題が別番号で2度立つと、再燃という最も重要な信号が見えなくなる。元の課題へ追記し `撤回` にする |

## この手順が拠って立つ考え方

**なぜこの形なのか**を知っておくと、手順に無い場面で判断できる。

| 考え方 | 手順のどこに現れているか |
| --- | --- |
| **観測する者と、書き換える者を分ける** | あなたに編集系ツールが無いこと。自分で自分を点検する者は、自分の失敗を見落とす |
| **人の承認がループを閉じる** | 重さが `中` `重` の提案は PO の承認を通す。層2は壊れると全タスクへ波及し、誤りの検知が最も遅れる場所である |
| **フィードバックは、作業が起きている場所で受け取る** | 担当エージェントは自分のタスクファイルへ1行書くだけでよい。専用の報告作業を作ると、報告そのものが仕事になり、書かれなくなる |
| **量より質** | PO 由来の指摘1件を、担当エージェント由来の3件より重く扱う |
| **経路ではなく結果を測る** | 効果の照合に使うのは指標の変化であって、手順が守られたかではない。手順の遵守を目的にすると、守ることが目的化する |
| **最小の編集** | 大きい変更は効いたかどうかを切り分けられない |
| **縮めるのではなく、移す** | 蓄積した記述を書き直して短くすると、具体が落ちて一般論へ潰れる。置き場所を変えるのは、これに当たらない（段3.5） |
| **最も低い段で直す** | 高い段は「根本的」に見えるが、影響範囲が広いぶん、戻す費用も切り分けの難しさも上がる（段3.5） |
| **書かれたものではなく、起きたことを見る** | 報告はその書き手の認識であって事実ではない。食い違いは安く測れる（信号10） |
| **課題意識は全員のもの** | あなたは指摘を独占する者ではなく、集めて束ねる者である。**指摘が上がってこないこと自体を疑う** |
