# 1. プロジェクト概要

本 MVP は、**PO（プロジェクトオーナー。人間のユーザー）**がアプリケーション開発における「最終的に実現したいゴール」を自然言語で入力すると、AI組織がそのゴールを達成するためのタスクを分解・管理し、適切な担当エージェントへ割り当て、実装・レビュー・テスト・ドキュメント作成等を進める仕組みを構築する。

PO は、細かな作業を逐一指示するのではなく、原則としてゴールと必要な判断のみを提供する。

**この組織の中で、PO だけが人間である。**

---

# 2. MVPの目的

## 2.1 最終目的

AIエージェントの組織が、PO から与えられた開発ゴールに対して、可能な限り少ない介入で開発作業を継続的に進められる状態を実現する。

## 2.2 MVPで検証する価値

- ゴールからタスクを自律的に分解できること
- タスクを適切な担当エージェントへ割り当てられること
- 各担当エージェントが担当作業を自律的に実行できること
- 判断不能な事項を適切にエスカレーションできること
- 停滞しているタスクを検知し、再計画・再割り当てできること
- ゴールに対して組織全体が前進しているかを継続的に評価できること
- Claude Code のセッションが終了しても、手動で新セッションへ引き継いで作業を継続できること

---

# 3. MVPスコープ

## 3.1 対象

1. アプリケーション開発
2. 開発に付随する仕様・設計・README等のドキュメント作成・更新
3. Git による変更管理
4. Git commit / push
5. 担当エージェント間のタスク引き継ぎ
6. PO へのエスカレーション
7. タスクの進捗・停滞管理

## 3.2 ゴール入力

PO は、基本的に自然言語で「何を実現したいか」を入力する。

例:

> 「ユーザーが食事内容を入力すると、1日の栄養素と目標との差分を表示するWebアプリを作りたい。」

PO があらかじめ詳細なタスク一覧を作成することは前提としない。

## 3.3 MVP対象外

- SNS投稿等の非開発業務
- 完全自動の Claude Code 新規セッション起動
- 24時間完全無人運転
- 複雑なWebダッシュボード
- 高度なKPI分析基盤
- 担当エージェント同士の自由なネットワーク型通信
- 複数AIプロバイダーを横断する実行基盤

ただし、将来追加できるよう拡張性は考慮する。

# 4. 設計原則

## 4.1 シンプルさ

MVP では独自システムを過剰に構築せず、Claude Code が標準で提供する仕組みを最大限利用する。

## 4.2 自律性

PO が細かな作業を逐一指示しなくても、オーケストレーターがタスクを管理し、組織を動かす。

## 4.3 継続性

1セッション内で作業が完了しない場合でも、作業状態を残し、新しいセッションから継続できる。MVP では新セッションの起動自体は手動とする（§15）。

## 4.4 拡張性

エージェント、スキル、MCP（外部ツールとの接続機構）、外部ツール等を後から追加しやすい構成とする。

新しい専門エージェントは、極端に言えば定義ファイルを追加するだけで組織へ追加できることを目指す。**この目標を成立させる条件は §17.1 で確定した。**

## 4.5 トークン効率

単純な繰り返し作業は可能な限りスクリプト等へ切り出し、AI の判断力は設計・問題解決等の価値の高い処理に集中させる。

**この原則が実際に適用された箇所**: 停滞検知と整合性検査、ゴール健全性の指標集計、利用者向け文書の結合。いずれも日付の比較・件数の集計・文書の連結であり、判断を含まない。

## 4.6 既存 Claude Code 拡張との共存

既存リポジトリに導入済みの Everything Claude Code、Superpowers 等の拡張を破壊・置換せず、共存できること（§19）。

# 5. AI組織の基本構造

## 5.1 構成

| ロール | 実体 | 役割 |
| --- | --- | --- |
| **オーケストレーター** | **メインセッション** | 誰が・何を・どの順番で行うかを判断し、組織を動かす |
| 設計エージェント | 担当エージェント | 要件を実装可能な設計へ変換する |
| 実装エージェント | 担当エージェント | コードを書き、単体テストを書き、Git へコミットする |
| レビューエージェント | 担当エージェント | 要求・設計・品質基準の充足を確認する |
| テストエージェント | 担当エージェント | 仕様の側から動作を検証する |
| ドキュメントエージェント | 担当エージェント | 利用者向け文書を最新に保つ |

**用語**: オーケストレーター以外の5つを総称して **担当エージェント** と呼ぶ。「サブエージェント」は Claude Code の実行機構を指す語であり、組織上の役割の意味では使わない（§26）。

## 5.2 オーケストレーターはメインセッションである

**これは選択ではなく、技術的な制約からの帰結である。**

1. Claude Code の子プロセスとして起動されたエージェントは、選択肢を提示して人間に選ばせる機能を使えない
2. PO へ問い合わせできるのはオーケストレーターだけである（§13）
3. ゆえに、オーケストレーターが子プロセス側に居ることはあり得ない

帰結として、オーケストレーターの定義はエージェント定義ファイルではなく、**組織の規約（層2の `CLAUDE.md`）とスキル**に置かれる（§17.1、§23）。

## 5.3 将来の拡張

SNS、マーケティング、データ分析、セキュリティ等の**専門エージェント**を追加可能とする（§17.1）。「専門エージェント」は**後から追加する特化ロール**を指す語であり、上記の基本5ロールには使わない。

# 6. オーケストレーター

## 6.1 ミッション

**PO から与えられたゴールを達成するために、AI組織全体を管理・調整する。**

オーケストレーター自身が成果物を作るのではなく、「誰が・何を・どの順番で行うか」を判断し、組織を動かすことに集中する。

## 6.2 主な責務

### ゴール管理

- PO の自然言語によるゴールを理解する
- ゴール達成条件を明確化する
- 必要に応じて PO へ質問する

### タスク分解

- ゴールを実行可能なサブタスクへ分解する
- タスク間の依存関係を整理する
- 優先順位を決定する
- 各タスクに必要なスキル・ロールを判断する
- **TDD（テスト駆動開発。先に失敗するテストを書き、それを通すように実装する進め方）の適用可否をタスクごとに判定する**（§20）

**並列実行できる単位を意図的に作る。** 複数エージェント構成が単一エージェントに勝つのは、タスクが独立した並列スレッドへ分解できるときに限られる。直列依存が連なる分解では、組織化のコストだけを払って利得が出ない。

分解時に確認すること:

- **依存関係は本当に必要か。順序を強制している理由を説明できるか**
- PO確認待ちが発生したとき、止まらずに進められるタスクが残るか（§13）
- 1タスクは、担当エージェントが1回の作業で完了できる大きさか

**計画は、自分のコンテキストが埋まる前に外部化する。** コンテキストが上限に達すると切り詰めが起き、計画そのものが失われる。「後でまとめて記録する」は取らない。分解した時点で書く。

### タスク登録

分解したタスクをタスク台帳へ登録する（形式は §25）。各タスクは以下を持つ。

**索引（CSV）に置くもの** — タスクID / タスク名 / 状態 / 優先度 / 担当 / 依存タスク / 作成日 / 更新日 / 詳細ファイルへのパス

**タスク別ファイルに置くもの** — 目的 / 変更範囲 / 禁止事項 / **完了条件** / **判断してよい範囲** / テスト方法 / 停止条件 / 参照すべき成果物 / 成果物 / ブロッカー / **TDD適用可否** / **手戻り回数** / 決定ログ / 作業ログ / 証拠

太字の5項目は v0.1 に無かったものである。追加の理由:

| 項目 | なぜ要るか |
| --- | --- |
| 完了条件 | レビューとテストが充足を判定する基準。無いと両ロールが毎回推測し、判定がぶれて手戻りが増える |
| 判断してよい範囲 | 境界が示されていないと、担当エージェントは決めすぎるか、些末な事を全部上げてくる |
| TDD適用可否 | 適用できるかは「そのタスクが何を達成するか」に依存し、分解の時点で最も見えている |
| 手戻り回数 | 健全性指標「手戻り件数」の算出元。作業ログから数えると書き方に依存して壊れる |
| 証拠 | 「完了」を、実行したコマンドとその出力で裏づける |

**タスク別ファイルは、そのまま作業指示になる。** 作業指示を毎回書き下ろす必要はない（§25.4）。

### タスク割り当て

各タスクを適切な担当エージェントへ割り当てる。**依存関係の無いタスクは同時に走らせる。1つの担当エージェントが同時に持つのは1タスクまで。**

### 進捗管理

- タスクの状態を把握する
- タスク間の依存関係を管理する
- 完了したタスクを次のタスクへつなげる
- **完了報告を受けたら、索引の状態と更新日を必ず更新する**（怠ると停滞検知が誤作動する）

### 停滞管理

停滞には2種類あり、**両方を見る**。

| | 実時間基準 | サイクル基準 |
| --- | --- | --- |
| 捉えるもの | セッションをまたいで**放置された**タスク | 1セッション内で**空回りしている**タスク |
| 判定 | 索引の更新日が **2日以上前**、かつ状態が `完了` でも `中止` でもない | レビューやテストの往復が**2往復に達した**、または手戻り回数が**3以上** |
| 検知 | スクリプトが機械的に判定する（§23） | オーケストレーターが往復の報告から判定する |

**両方が要る理由**: 担当エージェントは分単位で動くため、実時間基準では1セッション内で数十分空回りしているループを検知できない。逆にサイクル基準だけでは、セッション終了後に放置されたタスクを検知できない。

**停滞に数えないもの**: 状態が `PO確認待ち` のタスク（組織側の停滞ではない。ただし2日以上経過したら PO へのリマインド候補として別に数える）、状態が `保留` のタスク（意図して止めている）、ブロッカー依存の完了を待っている `未着手` のタスク（連鎖の根元だけを見ればよい）。

停滞を検知した場合の手順:

| 段 | やること | 適用する条件 |
| --- | --- | --- |
| 1 | **原因を確認する** — 担当へ状況を問い、タスク別ファイルの作業ログとブロッカーを読む | 常に最初 |
| 2 | **タスクを再分割する** | 完了条件が複数の独立した達成物を含んでいる。一部は完了しているのに全体が止まっている |
| 3 | **別の担当へ相談・再割り当てする** | 担当ロールの専門外の問題に当たっている。設計・要件の側に原因がある |
| 4 | **PO へエスカレーションする** | 1〜3 を試しても進まない |

**段を飛ばしてよい場合**: 原因が最初から明白で PO 判断が要るとき（段1の後、直接段4）。**同じタスクが2回目の停滞を起こしたとき**（段2・3 は既に効かなかったとみなし、段4へ）。

対処はタスク別ファイルの決定ログに残す。**何回停滞したかが追えることが要点である。**

### ゴール健全性評価

**単純なタスク消化数だけではなく、組織が最終ゴールへ近づいているかを評価する。**

指標は8つ。**集計はスクリプト、判定はオーケストレーター**が行う（§4.5）。

| # | 指標 | 算出方法 |
| --- | --- | --- |
| 1 | 完了タスク数 | 状態が `完了` の件数 |
| 2 | 未完了タスク数 | 状態が `完了` / `中止` 以外の件数 |
| 3 | 停滞タスク数 | 上記の停滞判定に該当する件数 |
| 4 | ブロック中タスク数 | ブロッカー依存が未完了の件数 + 状態が `保留` の件数 |
| 5 | PO確認待ち件数 | 状態が `PO確認待ち` のタスク数 **と** キューの未回答の質問数（両方を数える） |
| 6 | 手戻り件数 | 各タスク別ファイルの手戻り回数の総和 |
| 7 | ボトルネックとなっている工程 | 状態別の件数分布 + 各状態での滞留日数の中央値 |
| 8 | ゴール達成に必要な残作業 | 未完了タスクの**内容** + まだタスク化されていないと分かっている作業 |

**指標5を2つ数える理由**: 1つの質問が複数のタスクをブロックすることがある。質問が1件なのにタスクが8件止まっていれば、その1件を解けば組織が動き出す。

**指標8だけは機械では出せない。** タスク化されていない作業を含むため。ここを埋めるのがオーケストレーターの仕事であり、この評価の実質である。

**判定は3つ。数値の列挙で終わらせず、判定とその理由を添える。**

| 判定 | 目安 |
| --- | --- |
| **前進している** | 完了数が増え、かつ**残作業が減っている** |
| **停滞している** | 完了数が増えていない。停滞やブロックが積み上がっている。特定の工程に滞留が偏っている |
| **ゴールが揺らいでいる** | 完了数は増えているのに、**残作業が減っていない、または増えている**。手戻りが増え続けている。PO確認待ちが増加傾向 |

**3つ目がこの評価の存在理由である。**「タスクは消化されているのにゴールに近づいていない」という状態に名前を付けて、検知できるようにする。役割分割だけでは解けない課題があることが知られており、その兆候を早く掴むための指標である。

「ゴールが揺らいでいる」と判定したら、**タスク分解をやり直す。** それでも残作業が減る見通しが立たなければ、**ゴール達成条件そのものを PO へ確認する。** 組織の中で解こうとし続けることが、最も高くつく。

**実行タイミング**: セッション開始時 / セッション終了時 / 停滞検知時 / 機能のまとまりが完成した時 / PO から求められた時。

タスク完了のたびには行わない。1件ごとに全指標を再集計するとオーケストレーターのコンテキストを直接圧迫し、評価コストが作業量に比例して増えるため。

### エスカレーション管理

自分や組織で解決できない事項を PO へ上げる（§12）。**エスカレーションしても組織は止めない。** PO確認待ちへ登録した上で、その回答に依存しないタスクは進行させる（§13）。

### リソース管理

ゴール達成に必要なエージェント・スキル・MCP・外部アクセスが不足している場合、それを検知し、PO へ不足内容と必要性を説明して追加を提案する。

**担当を決められないタスクが発生したこと**が、最も分かりやすい検知経路である。

**ロールを増やす前に確認する**: 専門知識が要るだけならスキルを足す。ロールは責務の単位であって、知識の単位ではない（§17.3）。

### 層2の保守

開発対象リポジトリの `CLAUDE.md`、`.claude/rules/`、エージェント定義、**用語集**は、オーケストレーターが保守する。

これらは成果物ではなく**組織自身への指示**であり、§6.3 が担当外とする「通常のドキュメント作成」には当たらない（§11.2）。

保守が要るのは、例えば以下を発見したとき。

- 同じ誤りが複数のタスクで繰り返された（規約として明文化すべき）
- ビルド・テストのコマンドが確定した、または変わった
- 担当エージェントが毎回同じ確認を上げてくる（判断基準が書かれていない）
- **2人以上の担当エージェントが、同じ語について違う前提で動いた**（用語集へ登録する。§26）

**`CLAUDE.md` は200行を超えると遵守率が落ちる。** 超えそうならトピック別に `.claude/rules/` へ分割し、手順に育ったものはスキルへ出す。

## 6.3 やらないこと

オーケストレーターは原則として以下を担当しない。

- 本格的なコーディング
- 詳細なテスト実装
- 通常のドキュメント作成（層3の利用者向け文書）
- 通常のコードレビュー
- 単純な作業の代行

つまり、**「自分で作業する」のではなく「組織を動かす」ことを優先する。**

### この規約をどう担保するか

既知の失敗として、オーケストレーターが担当エージェントを呼ばず自分で作業を続けてしまうことがある。**規約だけでは破られる。**

v0.1 の時点では「オーケストレーターから編集系ツールを外す」ことで構造的に防ぐ案があったが、**採れない。** オーケストレーターはメインセッションであり（§5.2）、メインセッションにツール制限は適用できない。加えて、オーケストレーターは索引・PO確認待ちキュー・引き継ぎ記録・層2の規約を書く責務を負っており、編集系ツールを外すこと自体ができない。

代替として3つを置く。

| 手段 | 内容 |
| --- | --- |
| **構造** | 5つの担当エージェントが存在し、それぞれの説明文が明確であること。委譲先が曖昧だと委譲されない |
| **検知** | 整合性検査に **「状態が `設計中` / `テスト作成中` / `実装中` / `テスト中` / `レビュー中` なのに担当がオーケストレーターになっている」** を含める |
| 規約 | 着手前に「このタスクは自分がやるべきか」を確認する |

**規約は破られるが、台帳は嘘をつけない。** タスクには必ず担当が要るため、オーケストレーターが自分で実装すれば台帳に痕跡が残る。

# 7. 設計エージェント

## 7.1 ミッション

ゴールおよび要求を、実装可能な設計へ変換する。

**実装そのものは行わない。** 実装エージェントが判断に迷わず着手できる状態を作ることが完了地点である。

## 7.2 主な責務

要件の詳細化／技術的な実現方法の検討／アーキテクチャ設計／データ構造・API等の設計／実装方針の策定／実装エージェントからの設計相談への対応／設計上の不確実性の検知。

### 方式設計と詳細設計は別のタスクにする

| | 方式設計 | 詳細設計 |
| --- | --- | --- |
| 実施時期 | ゴール受領直後 | 各機能の実装直前 |
| 決めること | 全体構成、技術選定、主要なデータ構造、機能間の境界 | API仕様、処理フロー、画面遷移、個別のデータ項目 |
| 完了条件 | 実装タスクへ分割できる状態 | 実装エージェントが判断に迷わず着手できる状態 |

分けることで、初期の大きな設計タスクが単一の詰まりどころになるのを避ける。詳細設計は、先行実装で得た知見を反映できる。

### 品質基準を定める

方式設計の際、このプロジェクトの品質基準（レビューが参照する基準）を定める。定めた基準はオーケストレーターへ渡し、**層2へ書いてもらう**。タスクごとの完了条件へ複写しない（§25.5）。

## 7.3 出力（設計成果物）

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 対象範囲 | 必須 | この設計がカバーする範囲と、**カバーしない範囲** |
| 前提・制約 | 必須 | 依拠している前提。崩れたら設計が無効になる条件 |
| 方式 | 必須 | 構成、データ構造、API、処理フロー等 |
| **採用しなかった案と却下理由** | 必須 | 後から「なぜこうなっているか」を辿れるようにする |
| 実装時の注意点 | 任意 | 踏みやすい罠、順序の制約 |
| 未解決の不確実性 | 必須 | 残っていれば明示。無ければ「無し」と書く |
| **新しく定義した語** | 必須 | この設計で名前を付けた機能・データ構造・概念。無ければ「無し」と書く |

**「新しく定義した語」を必須にする理由**: 設計で付けた名前は、実装・レビュー・テストがそのまま使う。ところが担当エージェント同士は互いの会話が見えないため、意図した意味が伝わらなくても誰も気づけない。申告を経てオーケストレーターが用語集へ登録することで、初めて全員の共通の地面になる（§26）。

加えて、**実装タスクの分割提案**をオーケストレーターへ返す。分割案・依存関係・推奨順序・必要なスキル、そして**どの単位が並列に実行できるか**。設計エージェントは機能間の依存を最もよく把握している位置にいる。**登録はオーケストレーターが行う。**

## 7.4 エスカレーション

以下はオーケストレーターへ返す。

| # | 条件 | 判定の目安 |
| --- | --- | --- |
| E-1 | 要件そのものが不明確 | 作業指示を読んでも、満たすべき振る舞いが一意に定まらない |
| E-2 | 複数案があり PO 判断が要る | 技術的優劣で決着せず、PO の価値判断（コスト、期日、将来方針）に依存する |
| E-3 | 技術的制約でゴール達成方法が決まらない | 実現手段が存在しない、または既存構成と両立しない |
| E-4 | 重要なトレードオフの意思決定 | 性能／保守性／コスト／セキュリティのいずれかを明確に犠牲にする |
| E-5 | 前提の崩壊を検知した | 先行して確定した設計・決定が、今回の検討で成立しないと判明した |

**上げないもの**: 実装レベルの細部、技術的優劣で決着がつく複数案、既に確定済みの事項の再検討。

# 8. 実装エージェント

## 8.1 ミッション

設計・タスクに基づいて、実際のアプリケーションを実装する。

## 8.2 主な責務

コード実装／必要な設定変更／**自分が書いたコードの単体テスト**／ローカルでの検証／実装結果の報告／Git commit／Git push。

**「必要なテスト実装」は単体テストを指す。** 結合テスト、シナリオテスト、回帰テストはテストエージェントの担当である（§10.2）。分けるのは、実装者の思い込みを別ロールが仕様の側から検査することに価値があるためである。

### TDD適用タスクでは、受け入れテストが既に存在し、落ちている

これが実装の目標になる。**受け入れテストを通すために、テスト自体を書き換えてはならない。** テストが誤っていると判断した場合はテストエージェントへ差し戻す。テストを緩めて通すことは、完了条件を勝手に変更することに等しい。

### ローカル検証の範囲

タスクの完了条件を、実際に動かして確認する。

- 確認できた条件 → 何を実行してどう確認したかを報告に書く
- **自分では確認できない条件**（環境が要る、他機能との結合が要る）→ **「未検証」と明示して報告する。黙って完了にしない**

明示された未検証項目が、そのままテストエージェントの検証の起点になる。

### 完了報告に必ず含めるもの

完了条件の充足状況 / ローカル検証の結果 / コミット / **設計との差異** / **ドキュメント影響** / 派生して判明したこと。

**「設計との差異」が必須**なのは、ここが黙って埋まらないと、設計成果物と実態のずれが検知されないまま蓄積するためである。

**「ドキュメント影響」の判断者を実装エージェントにする理由**: 変更内容を最もよく知っており、判断がほぼ無コストで済む。ドキュメントエージェントに判断させると、変更を調べ直すために別のタスクとコンテキストが要る。無ければ「無し」、判断がつかなければ「要判断」と書く。

**報告は要約で行う。** コードを報告本文に貼らず、ファイルパス・コミット・変更行で参照する。実装エージェントの出力は組織内で最も長くなりやすく、そのままオーケストレーターのコンテキストを圧迫する。

## 8.3 判断の境界

### 自律的に決めてよいこと

命名、ファイル分割、関数の構造、ライブラリ内での書き方、設計で指定されていない実装レベルの細部、明らかな誤字・軽微なバグの修正。

### 勝手に決めないこと

| # | 条件 | 行き先 |
| --- | --- | --- |
| B-1 | 要件を変更する判断 | オーケストレーター |
| B-2 | 重要なアーキテクチャ変更 | オーケストレーター経由で設計エージェントへ |
| B-3 | セキュリティ・コスト等に重大な影響を与える変更 | オーケストレーター |
| B-4 | PO の意図が不明な仕様変更 | オーケストレーター |
| B-5 | 設計に書かれていない／設計と異なる実装が必要 | オーケストレーター |
| B-6 | 完了条件そのものが実現不能と判明した | オーケストレーター |

### スコープを勝手に広げない

作業指示の範囲を超える修正は、気づいても**その場で直さず報告する**。関連する不具合を見つけた場合も同じ。タスクの完了条件と成果物の対応が崩れると、レビューとテストの判定が成立しなくなる。

# 9. レビューエージェント

## 9.1 ミッション

実装された成果物が、要求・設計・品質基準を満たしているか確認する。

**自分では修正しない。修正は実装エージェントが行う。**

**これは構成で担保する。** レビューエージェントの定義には編集系のツールを与えない。5つの担当エージェントのうち、責務の外へ出られないことを構成で保証できるのはこのロールだけである。自分で直してしまうと、修正の意図が実装エージェントに伝わらず、同じ誤りが次のタスクで再発する。

## 9.2 主な責務

コードレビュー／設計との整合性確認／保守性確認／明らかなバグ・リスクの検出／セキュリティ上の問題の確認／改善点の提示／修正要求の作成。

## 9.3 指摘の重大度

| 重大度 | 定義 | 扱い |
| --- | --- | --- |
| **Blocker** | 完了条件を満たさない／明らかなバグ／セキュリティ上の問題 | 修正必須。残っている限り**通過させない** |
| **Major** | 設計との不整合／保守性の重大な問題 | 修正必須。ただし**別タスク化を協議できる**（判断はオーケストレーター） |
| **Minor** | 改善提案。動作・保守性に実害が無いもの | 任意。対応しなくても通過する |

Major に別タスク化の余地を残すのは、レビューで見つかる保守性の問題がしばしば元タスクの範囲を超えるためである。範囲を超える修正をその場で行わせると、実装側の「スコープを広げない」規約に反する。

修正要求は指摘ごとに、指摘ID / 重大度 / 対象箇所 / 何が問題か / なぜ問題か / **期待する状態**を持つ。**直し方の指定は任意**——実装手段の選択は実装エージェントの自律範囲であり、手段まで指定するとその境界を侵す。

## 9.4 反復の終了条件

| | 規定 |
| --- | --- |
| 通過条件 | **Blocker と Major が0件。** Minor は残っていてよい |
| 往復の数え方 | レビュー → 修正 → 再レビュー で1往復 |
| 上限 | **2往復** |
| 上限到達時 | 判定を保留し、残っている指摘・実装側の反論・双方の論拠をオーケストレーターへ渡す |

**2往復で解決しない場合、指摘の伝わり方か、設計・要件の側に構造的な問題がある可能性が高い。** 評価と修正のループは、評価者が出力の良し悪しを確実に判別できないときに循環する。往復が収束しないこと自体が、判定基準——すなわち完了条件や設計——の不備を示す信号である。上限到達時にオーケストレーターへ渡すのは、修正の続行ではなく**基準の見直し**を求めるためである。

この上限は停滞検知とは独立に働く。往復ループは2日より短い周期で回りうるため、実時間基準だけでは検知できない。

**実装エージェントは反論できる。** 重大度によらず、理由と根拠を示せばよい。「対応しない」だけの回答は認めない。レビューの指摘も誤りうるため、無条件に従う規定にはしない——誤った指摘に従うと、手戻りとコードの劣化を同時に生む。決着しなければ上限到達時にオーケストレーターが裁定し、それでも決まらなければ PO確認待ちへ。

## 9.5 エスカレーション

| # | 条件 | 判定の目安 |
| --- | --- | --- |
| E-1 | 判定基準が無い | 元タスクに完了条件が無い、または設計成果物が存在せず整合性を確認できない |
| E-2 | 実装エージェントと合意に至らない | 2往復の上限に達した |
| E-3 | **設計そのものに問題がある** | 実装は設計どおりだが、設計に欠陥がある |
| E-4 | **要件レベルの問題** | 実装も設計も正しいが、そもそもゴールを満たさない |
| E-5 | 重大なセキュリティ・コストの問題 | 実装の修正では収まらず、方針判断が要る |

**E-3 / E-4 が重要。** レビューエージェントは実装の下流にいるため、上流（設計・要件）の欠陥を最初に発見する位置にいる。実装へ差し戻しても直らないものは、上へ返す。

# 10. テストエージェント

## 10.1 ミッション

実装された機能が、期待どおり動作することを検証する。**実装者の思い込みを、別ロールが仕様の側から検査する**ことに価値がある。

## 10.2 主な責務

テストケース設計／テストコード作成／テスト実行／不具合の再現／不具合原因の切り分け／実装エージェントへのフィードバック。

**担当範囲は結合テスト、シナリオテスト、回帰テスト。単体テストは実装エージェントが書く。** 単体テストの不足に気づいた場合は、自分で書かず実装エージェントへフィードバックする。

## 10.3 受け入れテストは実装より先に書く

TDD が既定である（§20）。

**完了条件がテストへ変換できない場合、実装を待たずオーケストレーターへ差し戻す。** これが TDD を既定にする最大の利点である——テストへ変換できない完了条件は、そもそも判定不能な完了条件であり、従来なら実装が終わってから発覚して手戻りになっていた。

**受け入れテストは、書いた時点では落ちているのが正しい。** 実装前に通ってしまう場合、テストが完了条件を検証できていないか、既に実装済みであることを意味するため、オーケストレーターへ報告する。

## 10.4 完了条件は全て検証する

一つ合格しても残りを省略しない。検証ロールの既知の失敗に、**最初の確認に成功すると残りの失敗を見ないまま「合格」と判定して止まる**というものがある。テスト結果の必須項目に「完了条件ごとの検証結果」を置いているのは、この省略を構造的に防ぐためである。検証できなかった項目も、省略せず「検証できなかった」と記録する。

不具合レポートは、不具合ID / 重大度 / 再現手順 / 期待する動作とその根拠 / 実際の動作 / 切り分け結果を持つ。**修正方法は指定しない。**

重大度は §9.3 と同じ Blocker / Major / Minor を用いる。体系を分けると、オーケストレーターが2種類の尺度を突き合わせることになり、判断が複雑になる。**合格条件も同じく Blocker と Major が0件。** 反復上限も同じく2往復。

## 10.5 テストが落ちたときの行き先

| 状況 | 行き先 |
| --- | --- |
| 実装の不具合 | 実装エージェントへ（不具合レポート） |
| 実装は設計どおりだが期待動作にならない | オーケストレーターへ。**設計側の問題** |
| 期待動作が判定できない | オーケストレーターへ。完了条件・設計の不備 |
| 修正が2往復で収束しない | オーケストレーターへ |

**レビュー通過後にテストが落ちた場合、レビューへは戻さない。** テストが検出したのは動作の不具合であり、レビューの判定誤りとは限らない。実装エージェントが修正し、再テストする。ただし**同種の不具合が繰り返しレビューをすり抜ける場合**は、レビュー観点の不備としてオーケストレーターへ報告する。

## 10.6 エスカレーション

| # | 条件 |
| --- | --- |
| E-1 | 期待動作が判定できない（完了条件にも設計にも書かれていない） |
| E-2 | 重大な不具合（データ破損、セキュリティ、中核機能が動作しない） |
| E-3 | 不具合の原因が実装ではなく設計・要件にある |
| E-4 | 修正の反復が収束しない（2往復の上限） |
| E-5 | 検証環境が無く、検証自体が実施できない（リソース不足として §6.2 へ） |

# 11. ドキュメントエージェント

## 11.1 ミッション

開発成果物に必要なドキュメントを、最新状態に維持する。

## 11.2 担当範囲 — 文書の3つの層

「ドキュメント」が指すものは層によって全く違う。混同すると、誰が保守するのかが分からなくなる。

| 層 | 中身 | 読み手 | 保守する主体 |
| --- | --- | --- | --- |
| **層1** | AI組織を定義するリポジトリの要件定義と決定記録 | 組織を設計する人間（PO） | PO と、その作業を支援するセッション |
| **層2** | 開発対象リポジトリの `CLAUDE.md`、`.claude/rules/`、エージェント定義、**用語集** | **AI組織自身**（全エージェント） | **オーケストレーター**（§6.2） |
| **層3** | 開発対象アプリの成果物ドキュメント | AI組織 と 人間 の両方 | **ドキュメントエージェント** |

**本章が規定するのは層3である。** README・仕様・API文書・開発者向け文書はすべてここに属する。

**層2 をドキュメントエージェントが持たない理由**: 層2 は成果物の説明文書ではなく、**組織自身への指示**である。「このリポジトリでは pnpm を使う」は層2、「この API はこう呼ぶ」は層3。

設計エージェントとの境界:

| | ドキュメントエージェント | 設計エージェント |
| --- | --- | --- |
| 対象 | README、API文書、開発者向け文書、利用者向け仕様書 | 設計成果物 |
| 読み手 | 組織外（利用者・将来の開発者） | 組織内（実装・レビュー・テスト） |
| 書くこと | **現在どうなっているか、どう使うか** | **なぜその方式にしたか、却下した案** |

**設計成果物は参照するが、書き写さない。** 読み手が違う。

## 11.3 層3 は「エージェント用マスタ」と「人間用ビュー」の2階建て

```
docs/features/<機能名>.md      ← マスタ。機能単位
docs/guides/<目的・シーン>.md   ← マスタ。目的・シーン単位
docs/api/<対象>.md             ← マスタ
README.md                      ← 人間用ビュー。マスタから生成する
docs/handbook.md               ← 人間用ビュー。マスタを結合した通し読み用
```

| | エージェント用マスタ | 人間用ビュー |
| --- | --- | --- |
| 位置づけ | **正典。ここだけが真実** | マスタからの**生成物** |
| 粒度 | 機能・目的・シーン単位に**細かく分割** | 結合された通し読み用 |
| 更新 | ドキュメントエージェントが直接書く | **スクリプトで生成する。手で書かない** |

**細かく分割する理由**: エージェントは必要な断片だけを読めばよい。1ファイルに全機能が書かれていると毎回全体を読むことになる（§4.5）。加えて、機能ごとに分かれていれば複数のドキュメントタスクが衝突せず並列に走る。

**人間用ビューを生成物にする理由**: 分割すると人間は全体像を掴みにくくなる。マスタと人間用を二重に手で書くと必ず乖離するため、**生成の一方向に固定する。**

**生成をスクリプトで行う理由**: 文書の結合・目次生成は判断を伴わない機械的処理である（§4.5）。AI に結合させると、トークンを消費したうえに内容が書き換わる危険がある。

## 11.4 起動タイミング

| 対象 | タイミング |
| --- | --- |
| エージェント用マスタ | **機能のまとまりが完成した時点。** 実装エージェントの「ドキュメント影響」の申告を見て、オーケストレーターがタスクを起こす |
| 人間用ビュー | マスタ更新後にスクリプトで再生成。判断を伴わないので、都度でもセッション終了時でもよい |

## 11.5 エスカレーション

| # | 条件 | 判定の目安 |
| --- | --- | --- |
| E-1 | 実装の意図が読み取れない | コードからも設計からも、何のための機能か判断できない |
| E-2 | **実装とドキュメントのどちらが正しいか判断できない** | 既存文書と実装が矛盾し、どちらが意図された姿か決められない |
| E-3 | 公開範囲の判断が要る | 外部公開する情報の線引き（認証情報、内部構成、未公開機能） |
| E-4 | ドキュメントの構成そのものを変える必要がある | 個別更新では追いつかず、体系の再編が要る |

**E-2 が実務上もっとも起きる。** ドキュメントエージェントは実装の下流にいるため、**過去の意図と現在の実装のずれ**を最初に発見する位置にある。黙って実装側に合わせて書き換えると、意図されない仕様変更が記録として正当化されてしまう。

# 12. エスカレーション原則

エージェントは「分からないことを無理に決めない」。ただし、決めてよいことまで上げない。

## 12.1 4段階と、各段の打ち切り条件

| 段 | やること | 次へ上がる条件（＝この段の打ち切り） |
| --- | --- | --- |
| **1. 自分で解決** | 作業指示、参照すべき成果物、既存コード、確定済みの決定記録を確認する | これらを確認しても**答えが一意に定まらない**。または、定まるが自分の「判断してよい範囲」の外にある |
| **2. 許可された相手へ相談** | §14 の例外経路が存在する場合のみ | 相手が答えられない、または相手も判断できないと返した |
| **3. オーケストレーターへ上げる** | ロール別のエスカレーション条件に沿って報告する | オーケストレーターが PO 判断を要すると判断した |
| **4. PO確認待ちキューへ登録** | オーケストレーターが §13 の形式で登録する | — |

### 段1の打ち切りを「時間」ではなく「情報源」で定める理由

エージェントは実時間を体感できず、「15分考えても分からなければ」のような基準は機能しない。代わりに**参照すべき情報源を尽くしたか**で切る。上記4つを確認して定まらなければ、それ以上は推測になる。

**推測で埋めて着手しない。** 曖昧な指示を受けたエージェントは、エラーを上げずに誤った前提のまま作業を完了させる。失敗が沈黙するため、手戻りは下流で初めて発覚する。**差し戻しのコストは、誤った前提で完成させたものを捨てるコストより常に小さい。**

## 12.2 全ロール共通の停止条件

ロール別の条件に加え、**どのロールでも以下に該当したら作業を止めてオーケストレーターへ上げる**。ロール固有の条件は「自分の専門領域で判断できないこと」を拾うが、以下はそれとは別種——**専門領域の話ではなく、進めてよいかどうかの話**である。

| # | 条件 | なぜ止めるか |
| --- | --- | --- |
| S-1 | 仕様・指示・設計のどれかが**互いに矛盾している** | どちらに従っても、もう一方に違反する。選ぶこと自体が判断である |
| S-2 | **既存データを削除する／破壊的である**、または DB のマイグレーションが既存データへ及ぼす影響を伴う | 取り返しがつかない |
| S-3 | 作業開始時点で、**作業ツリーに未確認の差分がある** | 誰かの未完了の作業を巻き込む。着手前に `git status` を確認する |
| S-4 | 作業がタスクの変更範囲・禁止事項を**超える** | 範囲を超えるとレビュー・テストの判定が成立しなくなる |
| S-5 | 完了条件そのものが**実現不能**と判明した | 前提が崩れている。続けても完了しない |
| S-6 | 作業指示に**必須項目が欠けている**（完了条件が無い、判断してよい範囲が無い、参照すべき成果物が実在しない） | 着手前に差し戻す |

## 12.3 着手前の確認

作業指示を受けた担当エージェントは、着手前に以下を確認し、欠けていれば**作業を始めずオーケストレーターへ差し戻す**。

1. 完了条件が書かれているか
2. 判断してよい範囲が書かれているか
3. 参照すべき成果物が実在するか
4. 目的と詳細から、何をすべきかが一意に定まるか

## 12.4 上げないもの

| 上げない | 決める主体 |
| --- | --- |
| 実装手段の選択（命名、ファイル分割、関数の構造、ライブラリ内の書き方） | 実装エージェント |
| 技術的優劣で決着がつく複数案 | 各ロールが自分で決める |
| 既に確定済みの事項の再検討 | 誰も蒸し返さない |
| タスクの分割方法、担当の割り当て、優先順位の調整 | オーケストレーター |
| レビュー指摘への対応方針 | オーケストレーター |
| レビュー指摘そのものへの反論 | 実装エージェントが理由と根拠を付して直接返す |

**「判断してよい範囲」がタスクに書かれている以上、その範囲内のことは上げない。** 逆に、範囲が書かれていないタスクは S-6 で差し戻す。境界が明示されていない状態で自制を求めても機能しない。

## 12.5 エスカレーションが多すぎるとき

これは個々のエージェントの問題ではなく、**組織側の信号**である。

| 症状 | 疑うべき原因 |
| --- | --- |
| 同じ論点が複数のタスクから上がる | 層2に判断基準が書かれていない。回答の還元（§13.3）を怠っている |
| 特定のロールからばかり上がる | そのロールへの作業指示が不足している |
| 段1で解決すべきものが上がってくる | 「判断してよい範囲」が狭すぎるか、書かれていない |
| PO確認待ちが増え続ける | ゴール達成条件が確定していない。健全性評価の「ゴールが揺らいでいる」に近づいている |

# 13. PO確認待ちキュー

## 13.1 実体

開発対象リポジトリの `docs/po-queue.md`。1つの質問を `Q-001` のような番号で識別する。

タスク台帳を索引と詳細に分けた（§25）のに対し、こちらは**1ファイルの Markdown で足りる**。件数がタスクほど増えず（増えていたら、それ自体が組織の異常である）、書き手はオーケストレーターだけなので衝突せず、PO が人間として通しで読むものだからである。**索引と本体を分ける利得が出ない規模には、分ける仕組みを入れない**（§4.1）。

## 13.2 項目

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| Q-ID | 必須 | 連番。再利用しない |
| 登録日 | 必須 | `YYYY-MM-DD` |
| 状態 | 必須 | `未回答` / `回答済み` / `取り下げ` |
| 質問・判断事項 | 必須 | 何を決めてほしいか |
| なぜ判断が必要か | 必須 | 組織で決められない理由 |
| 選択肢 | 必須 | 各案。無ければ「選択肢を提示できない」と理由を書く |
| 各選択肢のメリット・デメリット | 必須 | |
| 推奨案 | 必須 | オーケストレーターとしての推奨と、その理由 |
| 回答がない場合に影響するタスク | 必須 | ブロックされるタスクID |
| **待つ間も進められるタスク** | 必須 | |
| 回答 | 回答後 | PO の結論と補足 |

**「待つ間も進められるタスク」を必須にする理由**: 「PO の回答を待っている間も、依存関係のないタスクは継続して実行する」を宣言で終わらせないため。**登録時に書けなければ、組織全体が止まっているということであり、それ自体が報告に値する事実である。**

タスク側は、タスク別ファイルのブロッカー欄に `Q-001` を書き、索引の状態を `PO確認待ち` にする。両方向に辿れるようにするのは、健全性指標を索引だけで数えられるようにするためと、回答が来たときに戻すべきタスクを探し直さずに済むようにするためである。

## 13.3 回答の還元 — 一度の回答を、以後の判断基準にする

PO の回答は、そのタスクを解いて終わりではない。**同じ問いが二度上がることを防ぐところまでが処理である。**

1. キューの質問を `回答済み` にし、回答を記録する
2. 影響していたタスクの決定ログへ、決定・却下案・出典を転記する
3. タスクの状態を `PO確認待ち` から適切な工程へ戻す
4. **回答が個別の判断を超えて一般的な基準になっている場合、層2へ昇格させる**

段4が主眼である。**昇格させる目安**: 同じ種類の問いが2回以上上がった、または回答が「このプロジェクトでは常に X する」という形をしている。

昇格先は、常に必要な**事実**なら `CLAUDE.md`、トピック別なら `.claude/rules/`、**手順**に育ったものはスキル。語の意味を確定させた回答なら**用語集**（§26）。

## 13.4 PO へ問い合わせできるのはオーケストレーターだけ

これは方針ではなく**技術的な制約**である。Claude Code の子プロセスとして起動されたエージェントは、選択肢を提示して人間に選ばせる機能を使えない。したがって PO と直接やりとりできるのはメインセッションだけであり、キューの一元管理は必然的な帰結である（§5.2）。

# 14. エージェント間コミュニケーション

## 14.1 原則

**担当エージェント同士の自由な通信は MVP では行わない。オーケストレーターをハブとする。**

## 14.2 例外 — 承認済みの3経路

| 経路 | 許可範囲 | 上限 |
| --- | --- | --- |
| **レビュー → 実装** | 修正要求と修正結果の往復 | 2往復 |
| **実装 → 設計** | **軽微な問合せに限る**（設計に書いてあることの読み方の確認） | 1往復 |
| **テスト → 実装** | 不具合レポートと修正の往復 | 2往復 |

**この3つ以外に直接通信は無い。** 3経路に共通する性質は、**実装への差し戻しであり、設計や要件を変えない**ことである。オーケストレーターを経由させる利得がなく、往復のコストだけが増える。

### 実装 → 設計 の判定基準

| | 直接（問合せ） | オーケストレーター経由（設計変更要求） |
| --- | --- | --- |
| 判定 | 設計成果物に**書いてあることの読み方**の確認 | 書かれていない、または書かれていることと違うことをする必要がある |
| 結果 | 設計成果物は更新されない | 設計成果物が更新される |
| 例 | 「このAPIの戻り値はこの解釈で合っているか」 | 「この構造ではこの要件を満たせない」 |

**迷ったらオーケストレーター経由**（安全側）。

## 14.3 実現手段

直接通信は、エージェント間でメッセージを送る機能で実現できる。ただし**環境によって使えないことを前提に置く。**

| 直接通信が | 反復ループの回し方 |
| --- | --- |
| 使える | 相手へ直接送る。オーケストレーターは結果だけ受け取る |
| 使えない | **オーケストレーターが作業指示を再発行し、往復を中継する** |

**どちらでも往復上限は2回。** 上限の意味は「収束しない評価ループを検知する」ことであり、通信手段には依存しない。

## 14.4 経路を増やすとき

§14.2 への追加は組織規約の変更であり、エージェント定義ファイルの追加だけでは済ませない。**ここに摩擦を残すのは意図的である**——追加が簡単だと、経路は必ず増える。

**新しい経路を足す条件**: 定型的である（その場限りの相談ではない）／設計・要件を変えない／反復上限がある／オーケストレーターを通す利得が無いことを説明できる。

# 15. セッション継続

## 15.1 MVP方針

Claude Code のトークン・コンテキスト上限等によって現在のセッションで作業を継続できなくなった場合、新しいセッションを **PO が手動で起動する。**

## 15.2 残すもの — タスク台帳 + 引き継ぎ記録

| | 中身 | 更新頻度 |
| --- | --- | --- |
| **タスク台帳**（§25） | 各タスクの状態・完了条件・決定ログ・作業ログ・証拠 | タスクが動くたび |
| **引き継ぎ記録** `docs/handover.md` | 「今どこにいるか」だけ。タスクに紐づかない文脈 | 節目ごと |

### 引き継ぎ記録を別に持つ理由

タスク台帳が常に最新なら専用文書は不要、という立場は採らない。**台帳に現れない情報が確実にあるため**である。

- **なぜ今この順序で進めているか。** 台帳は順序を持つが、その順序を選んだ理由は個々のタスクの決定ログには載らない
- **まだタスク化されていない、次にやろうとしていたこと**
- **直前に得た判断のうち、まだどのタスクにも書けていないもの**
- **環境の状態。** 未コミットの作業があるか、ビルド・テストのコマンドが何か

これらは会話の中にしか存在せず、**セッションが切れれば失われる。**

### 詳細なセッションログを採らない理由

作業経緯を時系列で全部残せば復元力は最も高いが、**新セッションが読む量が増え、そのまま初期コンテキストを圧迫する。** 引き継ぎの目的は記録の保存ではなく、次のセッションが**速く正しい状態に立つこと**である。経緯は既にタスク別ファイルの作業ログと Git 履歴にある。

## 15.3 引き継ぎ記録の項目

**1枚。常に上書きする。** 過去分は Git 履歴に残るため、追記して膨らませない。

| 項目 | 内容 |
| --- | --- |
| 更新日時 | いつ時点の状態か |
| ゴール | PO から受けたゴールと、**現時点で確定しているゴール達成条件** |
| 現在地 | 直近で何をしていたか。進行中のタスクID |
| 直近の判断 | まだタスクの決定ログへ書けていない決定。**無ければ「無し」と明記** |
| 次の一手 | 新セッションが最初にやること |
| PO確認待ち | 未回答の質問ID一覧 |
| 直近の健全性評価 | 8指標と判定。**次回が前回比を出すために参照する** |
| 環境・前提 | ビルド／テスト／リントのコマンド、未コミットの作業の有無 |

**「直近の判断」は一時的な置き場である。** 決定はタスクの決定ログへ書くのが正であり、ここに残るのは「まだ書けていないもの」だけ。溜まっていること自体が、転記を怠っている信号になる。恒久的に確定したもの（ビルドコマンド、常に守る規約）は層2へ昇格させる。

## 15.4 いつ書くか — 「セッション終了時」では書けない

**節目ごとに更新する。** 上限は予告なく訪れ、**書く余裕が残っていない状態で切れる**ためである。

| いつ | 何を更新するか |
| --- | --- |
| タスクの状態が変わったとき | 現在地、次の一手 |
| PO の判断を得たとき | 直近の判断 |
| 健全性評価を行ったとき | 直近の健全性評価、次の一手 |
| ゴール達成条件が確定・変更されたとき | ゴール |
| セッション終了時（可能なら） | 全体 |

最終行は「可能なら」である。**それまでの更新で引き継ぎが成立していなければならない。**

## 15.5 新セッションの再開手順

| # | やること | なぜこの順か |
| --- | --- | --- |
| 1 | `CLAUDE.md`（自動で読み込まれる） | 組織の規約 |
| 2 | **引き継ぎ記録** | 現在地・次の一手・環境 |
| 3 | **台帳を検査する**（停滞検知と整合性検査のスクリプト） | **引き継ぎ記録は嘘をつきうる。信じる前に機械的な検査を通す** |
| 4 | タスク索引（CSV） | 全体像 |
| 5 | 進行中タスクの詳細ファイル | **進行中のものだけ。完了済みは読まない** |
| 6 | PO確認待ちキューの未回答項目 | |
| 7 | `git status` / `git log` | 未コミットの作業、直近のコミット |
| 8 | 健全性評価を実行し、引き継ぎ記録の前回値と比較する | 前進しているかを判定する |

**手順3を4より前に置く理由**: 前セッションが引き継ぎ記録を更新できずに切れていれば、記録は古い。台帳は各担当エージェントの作業で更新されているため、より新しい可能性がある。整合性検査が両者のずれを検出する。**放置されたタスクを拾えるのは、この検査だけである。**

**手順5の「完了済みは読まない」**: 台帳を索引と詳細に分けたのは、1つのタスクを触るために完了済み全タスクの証拠まで読み込む状態を避けるためである。再開手順がそれを守らなければ意味がない。

この手順は多段階のチェックリストなので、毎セッション全文が読み込まれる `CLAUDE.md` ではなく**スキルに置く**（§23）。

## 15.6 引き継がないもの

| 引き継がない | なぜ |
| --- | --- |
| 会話の全文・要約 | 必要な情報は台帳と引き継ぎ記録に既にある |
| 完了済みタスクの詳細 | 索引に完了として載っていれば足りる |
| 各担当エージェントの内部状態 | 子プロセスとして起動されたエージェントは新規の隔離された記憶で始まる。**引き継げるものが元々無い** |
| 未確定の推測・仮の方針 | 次のセッションで確定済みとして扱われる危険がある |

3行目が構造的に重要である。**状態は常にファイルにあり、エージェントには無い。** セッション引き継ぎが成立するのは、この非対称性のおかげである。

## 15.7 MVPでは実装しないもの

- 自動的な Claude Code 新規起動
- バックグラウンドセッション管理
- 自動セッション監視
- 自動セッション引き継ぎ

# 16. Git要件

| | 規約 |
| --- | --- |
| commit の粒度 | **論理的なまとまり単位。** 1タスクが複数コミットになってよい |
| commit のタイミング | まとまりができた時点。**タスク完了まで溜めない** |
| push のタイミング | **タスク完了時**（完了報告の前）。**レビュー通過を待たない** |
| コミットメッセージ | 何を変更したかが追跡可能であること |

**push をレビュー前に行う理由**: §15 が「セッションが継続できなくなる」ことを前提に置いているため。ローカルにしか存在しない状態を長く保つと、セッション断で実装が失われ、新セッションが続きから拾えない。

MVP で実行可能とするのは status確認 / diff確認 / commit / push。

# 17. 拡張性

## 17.1 エージェント追加

**目標**: 新しい専門エージェントを、定義ファイルを1つ足すだけで組織へ追加できること。

### この目標を成立させる条件

「定義ファイルを1つ足すだけ」が成立するのは、**追加時に既存ファイルを編集しなくてよい**ときだけである。

| 追加時に必要になりそうなこと | 既存ファイルの編集が要るか | 解 |
| --- | --- | --- |
| オーケストレーターが「どのエージェントがいるか」を知る | **要らない** | Claude Code はエージェント定義を自動的に認識し、その説明文から用途を判断する。**組織側でエージェント一覧を持たない** |
| タスクの担当欄に新しい値が入る | 要らない | 担当は自由記述であり、値の集合を定義していない |
| 新エージェントが読む組織共通の規約 | 要らない | **`CLAUDE.md` の階層は子プロセスへ継承される。** エージェント定義ごとに規約を複写しない |
| 新エージェントの専門能力 | 要らない | スキルとして独立したファイルで足す（§17.3） |
| **直接通信経路を増やす** | **要る**（§14.4） | 意図的に摩擦を残す |

**1行目が要点である。**「どのエージェントがいるか」を組織が自前で管理しないことが、ファイル追加だけで済ませられる理由であり、§4.1「Claude Code 標準機能を最大限使う」の具体的な帰結である。一覧を独自に持った瞬間、追加のたびに2箇所を直すことになり、目標が崩れる。

### エージェント定義の必須構成

各ロールの定義は5要素で書く。既存6ロールと同じ形である。

| 要素 | 内容 |
| --- | --- |
| **ミッション** | このロールが達成すること。1〜2文 |
| **責務** | 担当すること。**および担当しないこと** |
| **入力** | 何を、誰から受け取るか。情報項目のレベルで |
| **出力** | 何を、誰へ返すか。情報項目のレベルで |
| **エスカレーション条件** | 何を上げるか、**何を上げないか**。判定の目安付き |

加えて定義ファイルに書くもの: **説明文**（オーケストレーターが割り当てを判断する唯一の材料）／直接通信の可否（既定は不可）／使用ツールの範囲／プリロードするスキル。

**説明文の書き方**: 曖昧な説明文は割り当ての誤りとして表面化する。**既存ロールとの境界が一文で言えないなら、そのロールは追加しない。** 境界は「対象 / 読み手 / 書くこと」の3点で既存ロールと対比する。

**ツールの制限で責務を担保する**: 「このロールが責務を踏み越えるとしたら、どのツールを使うか。それは外せるか」を必ず問う。レビューエージェントから編集系ツールを外すのがその実例である（§9.1）。規約は破られるが、構成は破られない。

### 追加の手順

| # | やること | 主体 |
| --- | --- | --- |
| 1 | 不足を検知する（担当を決められないタスクの発生） | オーケストレーター |
| 2 | PO へ提案する（不足しているもの / なぜ必要か / 滞る作業 / 追加案） | オーケストレーター |
| 3 | 承認する | PO |
| 4 | **決定記録を書く**（5要素を確定させる） | PO と支援セッション |
| 5 | エージェント定義ファイルを**1つ**追加する | |
| 6 | 必要ならスキルを追加する | |

**段4を飛ばさない。** 定義ファイルをいきなり書くと、入力・出力・エスカレーション条件が未確定のまま実装形式だけが決まる。

**手順5で既存ファイルを触る必要が生じたら、それは構造が綻んだ箇所である。** 黙って編集せず、何を編集したかと理由を記録へ残す。綻びが3回起きたら構造の側を見直す。

### ロールを増やさない方が良い場合

**追加が容易であることは、追加すべき理由にはならない。**

| 増やさず、既存で対応する | 理由 |
| --- | --- |
| 既存ロールとの境界が一文で言えない | 曖昧なエージェントを増やすと性能が落ちる |
| 一度きりの作業のため | ロールは繰り返し現れる責務に対して作る。単発ならタスクとスキルで足りる |
| 既存ロールの負荷が高いだけ | 責務の分割ではなく、タスク分解の粒度（§6.2）を疑う |
| **専門知識が要るだけで、責務は既存と同じ** | **スキルを足す。ロールは責務の単位であって、知識の単位ではない** |

最後の行が最もよく当たる。「セキュリティに詳しいエージェントが要る」の多くは、レビューエージェントにセキュリティレビューのスキルを足せば済む。

## 17.2 MCP・外部ツール

後から追加できる構成とし、**特定の MCP に組織全体を強く依存させない。** あるロールが特定の MCP を要求する場合、その依存はそのロールの定義に閉じる。

**MCP の不在は、エージェントの不在と同じ扱いで検知する**（§6.2 リソース管理）。テストエージェントの「検証環境が無く検証自体が実施できない」がこの経路に乗る具体例である。

## 17.3 スキル

エージェントの専門能力はスキルとして分離できる構造を優先する。**エージェント定義に長い手順を書かない。**

「常に必要な事実」は `CLAUDE.md`、「呼ばれたときに必要な手順」はスキル。**`CLAUDE.md` の一節が事実ではなく手順に育ったら、それはスキルにすべきである。**

# 18. 設定・定義ファイルに関する方針

MVP では、Claude Code だけで完結する範囲について、不要な独自の設定ファイルを作らない。`CLAUDE.md` とスキル等の標準的な仕組みを優先する。

独自の構造化ファイルが必要になるのは、以下の場合に**実際に到達したとき**だけである。「将来必要になりそうだから」は理由にならない。

- Claude Code 以外のエージェント実行基盤にも対応する
- 複数の実行環境を抽象化する必要が出る
- **機械的に読み書きする構造化データが必要になる**
- ワークフローが複雑化し、自然言語だけでは管理しにくくなる

## 18.1 タスク台帳が例外に該当する理由

**3番目の条件に実際に到達した。** 経緯を残す。

1. §6.2 の停滞管理とゴール健全性評価は、日付の比較と件数の集計を必須とする
2. §4.5 は、そうした単純な繰り返し処理をスクリプトへ切り出せと定める
3. スクリプトが読むには、機械可読な形式が要る

**加えて、タスク台帳はそもそも設定ファイルではない。** 本章が禁じているのは、標準機能で足りるものを独自の設定形式で置き換えることである。タスク台帳は組織の**状態記録**であり、`CLAUDE.md` やスキルが代替できる対象ではない。

**構造化の範囲は最小に抑える。** 索引は CSV（独自形式ではない）で、短い値だけを持つ。判断と文脈はすべて Markdown 側に置く（§25）。

# 19. 既存 Claude Code 拡張との共存

Everything Claude Code、Superpowers 等が導入済みの環境で共存できること。

| 規約 | 内容 |
| --- | --- |
| **名前空間** | 組織の定義はすべて `org-` を前置する（エージェント定義、スキル） |
| **既存を上書き・削除しない** | 既存のコマンド／スキル／フックを触らない |
| **フックは追記のみ** | 設定へフックを足す場合、既存エントリを**置換せず追記**する。設定ファイルごと上書きしない |
| **衝突したら組織側が譲る** | 名前が衝突した場合、既存拡張ではなく組織側の名前を変える |

`org-` の前置は、独自の仕組みではなく**命名の約束だけ**で分離を達成している。§4.1 に従い、これ以上の隔離機構は作らない。

# 20. MVPの基本ワークフロー

## 20.1 標準フロー（TDD適用タスク）

```
PO
 │ 自然言語でゴールを入力
 ▼
オーケストレーター
 ├─ ゴール理解 / ゴール達成条件の明確化
 ├─ タスク分解（並列に走れる単位を作る / TDD適用可否を判定）
 ├─ タスク台帳へ登録（完了条件を書く）
 └─ 担当エージェントへ割り当て
       │
       ├─ 1. 設計エージェント     方式設計 → 実装タスクの分割提案
       │
       ├─ 2. テストエージェント   完了条件を受け入れテストへ変換（この時点では落ちる）
       │
       ├─ 3. 実装エージェント     テストが通るまで実装（単体テストも書く）→ commit / push
       │
       ├─ 4. テストエージェント   受け入れテストを実行し判定
       │
       ├─ 5. レビューエージェント レビュー（Blocker と Major が0件で通過）
       │
       └─ 6. ドキュメントエージェント（機能のまとまり完成時）
       ↓
   進捗・停滞管理 / ゴール健全性評価
       │
       ├─ 解決可能 → 再計画・再割り当て
       │
       └─ 解決不能 → PO確認待ちキューへ
                      └─ 回答に依存しないタスクは継続
```

**v0.1 からの変更**: v0.1 は実装 → レビューと実装 → テストを**並列**に描いていた。**直列へ改める。**

## 20.2 TDD を既定にする理由

**完了条件の曖昧さを、実装が始まる前に検出できる。** テストへ変換できない完了条件は、そもそも判定不能な完了条件である。従来なら実装が終わってレビュー・テスト段階で初めて発覚し、手戻りになっていた。

副次的に、レビューとテストの順序問題も解消する。テストが落ちている実装をレビューしても、修正後に再レビューが必要になるだけで無駄が出る。テストが先に判定を出すため、**レビューは動作するコードに対してのみ行われる。** 並列実行より総コストが小さく、§4.5 と整合する。

## 20.3 TDD適用外

探索的なタスク、UI の見た目の調整、設定変更など、事前にテストを書けない作業はある。この場合、**オーケストレーターがタスク分解時に「TDD適用外」と明示する。** 適用外タスクの順序は **実装 → テスト → レビュー**（レビューを最後に置く理由は同じ）。

判断を実装・テスト側に委ねずオーケストレーターが持つのは、適用可否が「そのタスクが何を達成するか」に依存し、タスク分解の時点で最も見えているためである。

# 21. MVP完了条件

以下を満たした時点で MVP の主要機能が成立したと判断する。**判定方法**は本版で併記した。

| # | 条件 | 判定方法 |
| --- | --- | --- |
| 1 | PO が自然言語で開発ゴールを入力できる | 実運用で確認 |
| 2 | オーケストレーターがゴールをタスクへ分解できる | 台帳にタスクが登録される |
| 3 | タスクをタスク台帳へ登録できる | 索引の CSV とタスク別ファイルが作られ、整合性検査が通る |
| 4 | タスクを担当エージェントへ割り当てられる | 索引の担当列が埋まる。`未割当` のまま進行中の状態が無い |
| 5 | 設計→実装→レビュー→テストの基本フローを実行できる | 状態が §25.3 の順に遷移する |
| 6 | 必要なドキュメントを更新できる | 実装の完了報告の「ドキュメント影響」からタスクが起きる |
| 7 | Git commit / push まで実行できる | タスク別ファイルの証拠にコミットが記録される |
| 8 | 担当エージェントが判断不能な事項をエスカレーションできる | §12 の経路で上がる |
| 9 | PO確認待ちキューへ登録できる | 質問が登録され、対応タスクの状態が `PO確認待ち` になる |
| 10 | PO確認待ち中も独立したタスクを継続できる | 質問の「待つ間も進められるタスク」が実際に進む |
| 11 | 2日以上更新がないタスクを停滞として検知できる | **検知スクリプトが停滞候補として出力する** |
| 12 | 停滞タスクに対して再分割・再割り当て等を試行できる | 決定ログに対処が記録される |
| 13 | エージェント不足を検知して PO へ提案できる | 担当を決められないタスクから提案が上がる |
| 14 | 新しいセッションから作業を手動で再開できる | §15.5 の8手順が通る |
| 15 | 既存の Claude Code 拡張と共存できる | 導入時に既存のコマンド／スキル／フックが失われない |
| 16 | 新しいエージェントやスキルを追加しやすい | §17.1 の手順で、既存ファイルの編集なしに追加できる |

**現時点で未達なのは、実運用でしか確かめられない項目である**（§23）。

# 24. 重要な設計判断

- **オーケストレーターはメインセッションであり、司令塔に徹する。** 原則として実装しない。担保はツール制限ではなく整合性検査で行う
- PO は最終ゴールを自然言語で入力する
- ゴールはオーケストレーターがタスクへ分解する。**並列に走れる単位を意図的に作る**
- 分解したタスクは**タスク台帳（CSV索引 + タスク別Markdown）**へ登録する
- **タスク別ファイルがそのまま作業指示になる**
- **TDD を既定とし、受け入れテストを実装より先に書く**
- レビューとテストの反復は**2往復で打ち切り**、収束しなければ基準の見直しへ回す
- 停滞は**実時間基準とサイクル基準の両方**で管理する
- ゴールに対する組織全体の健全性を評価する。**「タスクは消化されているがゴールに近づいていない」を判定値として持つ**
- エージェント不足もオーケストレーターが検知する
- 判断不能な事項は**段階的に**エスカレーションする。各段に打ち切り条件がある
- PO確認待ちでも独立タスクは継続する
- 担当エージェント間の通信は原則制限し、**承認済みの3経路のみ**直接通信を許可する
- セッション引き継ぎは手動。**引き継ぎ記録は節目ごとに更新する**
- Git push まで対応する。**push はタスク完了時**
- Claude Code 標準機能を最大限利用する
- **独自の構造化ファイルは、条件に実際に到達するまで作らない**（タスク台帳は到達した）
- 既存 Claude Code 拡張と共存する
- エージェント・スキル・MCP 等を後から追加できることを重視する。**組織側でエージェント一覧を持たない**
- 単純な繰り返し処理はスクリプト化する
- **語の意味は用語集で固定する**

# 25. タスク台帳

本版で新設。v0.1 では保存形式を意図的に未定としていたが、§6.2 の停滞管理と健全性評価をスクリプト化するために確定させた（§18.1）。

## 25.1 構成

開発対象リポジトリに置く。

```
docs/task-list-{プロジェクト名}.csv   索引
docs/tasks/T-XXX.md                   タスク別の詳細。正典
docs/tasks/README.md                  台帳の読み方
docs/po-queue.md                      PO確認待ちキュー（§13）
docs/handover.md                      引き継ぎ記録（§15）
docs/glossary.md                      用語集（§26）
```

**索引と詳細に分ける理由**:

| 制約 | どう応えるか |
| --- | --- |
| 子プロセスとして起動されたエージェントは新規の隔離された記憶で始まる | タスク別ファイルなので、担当は自分のタスク1件分だけ読めばよい |
| 並列に走る作業が同時に台帳を書く | ファイルが分かれ、**同時更新が衝突しない** |
| オーケストレーターのコンテキストは報告のたびに膨張する | 索引だけで全体像が取れる |
| 停滞検知・健全性評価をスクリプト化する | CSV が機械可読。判断は Markdown、集計は CSV と役割が分かれる |

## 25.2 索引の列

```csv
ID,作成日,更新日,タスク名,状態,優先度,担当,依存タスク,ドキュメント
```

**索引に入れる基準は一つ**——「詳細を開かずに次の一手を決めるために使うか」。使わないものは詳細ファイルへ置く。

| 列 | 規約 |
| --- | --- |
| ID | `T-###`（3桁連番）。**再利用しない。** 中止したタスクも行を残し、番号は退役させる |
| 作成日 / 更新日 | `YYYY-MM-DD`。不明なら `不明` と明記。**空欄にしない** |
| タスク名 | 10〜40文字程度 |
| 状態 | §25.3 の10種 |
| 優先度 | `高` / `中` / `低` |
| 担当 | エージェント名。未割当なら `未割当` と明記 |
| 依存タスク | §25.4 の形式。無ければ `無し` と明記 |
| ドキュメント | リポジトリルート相対のパス |

**値にカンマ・改行を含めない。** 索引は短い値しか持たないため、これで引用符処理が不要になり、スクリプト側が壊れにくくなる。

**空欄を作らない。** 空欄や `-` は「未確認」と読めてしまい、後から判別できない。

## 25.3 状態（10種）

| 状態 | 意味 |
| --- | --- |
| `未着手` | 登録済み。着手可能かは依存タスク次第 |
| `設計中` | 設計エージェントが作業中 |
| `テスト作成中` | 受け入れテストを先行作成中（TDD適用タスク） |
| `実装中` | 実装エージェントが作業中 |
| `テスト中` | 受け入れテスト実行・検証中 |
| `レビュー中` | レビュー実施中、または修正の往復中 |
| `PO確認待ち` | PO の判断待ち。ブロッカー欄に質問IDを書く |
| `完了` | 完了条件を全て満たし、証拠が記録されている |
| `保留` | PO確認以外の理由で進められない |
| `中止` | 実施しないと決めた。行は残す |

**終端は `完了` / `中止` の2つ。**

**「ブロック中（依存待ち）」を状態に置かない理由**: 依存タスク列から機械的に導出できるため。状態として持つと、依存先が完了したときに人手で戻す必要が生じ、更新漏れが停滞の誤検知になる。**導出できるものは状態にしない。**

**`PO確認待ち` を `保留` から分離する理由**: 健全性指標が「ブロック中タスク数」と「PO確認待ち件数」を別に数えるため。索引だけで数え分けられる必要がある。

## 25.4 依存関係の表現

| 形式 | 意味 |
| --- | --- |
| `T-001（ブロッカー）` | T-001 が `完了` になるまでこのタスクを開始できない |
| `T-001（推奨: 理由）` | 必須ではないが、この順で進める方が合理的 |
| `無し` | 依存が無いことを**確認済み**である |

複数ある場合は空白区切り。ブロッカーの理由の全文は詳細ファイルへ書く。

**ブロッカー指定には理由を必ず書く。詳細ファイルに理由が書かれていない依存は、依存として認めない。** 説明できない依存は、たいてい「なんとなくこの順」であり、それが並列実行できる単位を潰す。**依存を書くコストを、意図的に少し高くしておく。**

## 25.5 タスク別ファイル

```markdown
# T-XXX: タスク名

## メタデータ
- 作成日: YYYY-MM-DD
- 更新日: YYYY-MM-DD
- 状態: 未着手
- 優先度: 中
- 担当: 未割当
- 進捗: 一行で現状
- 依存: 依存タスクの全文（ブロッカーなら理由を必ず書く）
- TDD適用可否: 適用 / 適用外（適用外なら理由）
- 手戻り回数: 0

## 目的             なぜこの変更が要るか。飛ばすと何が壊れるか
## 変更範囲         どのファイル・領域を触るか
## 禁止事項         触ってはいけないもの
## 完了条件         二値で判定できる形。コマンドと出力で確認できること
## 判断してよい範囲 どこまで自律的に決めてよいか
## テスト方法       単体／結合／回帰。実環境確認の要否と実施者
## 停止条件         このタスク固有のもの。無ければ「§12.2 の共通停止条件のみ」
## 参照すべき成果物 設計成果物、既存コード、確定済みの決定記録
## 成果物           完了時に何ができたか（ファイル・コミット）
## ブロッカー       今止めているもの。PO確認待ちなら質問ID

## 決定ログ
## 作業ログ
## 証拠
```

**メタデータは必ず `- キー: 値` の1行1項目で書く。** 整合性検査のスクリプトがこの形を読む。

### タスク別ファイルは、そのまま作業指示である

作業指示が必要とする項目——目的 / 詳細 / 完了条件 / 参照すべき成果物 / 判断してよい範囲 / 期待する成果物の形——は、上記の構成にすべて含まれている。**オーケストレーターは作業指示を毎回書き下ろす必要がなく、タスク別ファイルを参照させればよい。**

これは、指示が不完全なまま下流が進んでしまう失敗への構造的な対策になる。指示を都度書くと項目の抜けが起きるが、テンプレートが固定されていれば、抜けは「セクションが空である」という形で可視化される。

### 品質基準はどこにあるか

| | プロジェクト全体の品質基準 | タスク固有の基準 |
| --- | --- | --- |
| 置き場所 | 層2（`CLAUDE.md` / `.claude/rules/`） | タスク別ファイルの完了条件 |
| 定める主体 | 設計エージェントが方式設計時に定め、オーケストレーターが層2へ書く | オーケストレーター |

**タスクごとに全体の基準を複写しない。** 量が増えるうえに、基準を変えるとき全タスクを直すことになる。層2 に一度書けば全エージェントが参照する。

## 25.6 3つの記録

| セクション | 答えるもの | 寿命 |
| --- | --- | --- |
| `## 決定ログ` | **なぜそうしたか** | 恒久。過去の項目を書き換えず、上書きする新項目を追記する |
| `## 作業ログ` | 何が、どの順で起きたか | 一時的。完了時に数行へ畳む |
| `## 証拠` | 完了条件を満たしたと何故言えるか。コマンドと実出力のみ | 恒久 |

**決定ログを書く条件は3つに限る**——(1) PO の判断を仰いで得た、(2) 別の選択肢が実際にあった技術選定、(3) 登録後にスコープ・完了条件・禁止事項が変わった。通常の進捗は決定ではなく作業ログである。

```markdown
### YYYY-MM-DD 一行でわかる決定の要約
- 決定: 実際に決めたこと
- 却下案: 採らなかった案 → なぜ負けたか
- 付帯条件: 承認に付いた条件（無ければ省略）
- 出典: コミットSHA / 設計成果物のパス /「セッション内の判断、成果物なし」
```

**`却下案` が価値を担う行であり、最も省略されやすい。**「X を選んだ」は数週間で「なぜ X なのか」に劣化するが、「Y が使えないので X」は劣化しない。真剣に検討した対案が無ければ `却下案: なし` と書く。行ごと落とさない。

2つの決まり文句:

- **`特記なし`** — このタスクに決定が本当に無かった。項目自体は常に置くので、無いことが「まだ書いていない」を意味する状態を保つ
- **`（記録なし）`** — 決定はあったが理由が当時記録されず、もう復元できない。**推測で理由を再構成して埋めてはならない。** 作られた理由は後から事実として読まれるため、認めた空白より悪い

**決定ログは事務ではない。** §14 が担当エージェント同士の自由な通信を禁じている以上、**会話の中にしか存在しない理由は、そのセッションが終われば組織から永久に失われる。** 同じ論点が別のタスクで、しばしば違う結論で、また争われることになる。

## 25.7 誰が書くか

| 対象 | 書く主体 |
| --- | --- |
| 索引（CSV） | **オーケストレーターのみ** |
| タスク別ファイルの 決定ログ / 作業ログ / 証拠 / 進捗 | **担当エージェント**（自分のタスクのファイルのみ） |
| タスク別ファイルのメタデータの 状態 / 担当 / 依存 / 優先度 | オーケストレーター |

並列実行を前提にする以上、**単一ファイルである索引への同時書き込みは必ず衝突する。** 書き手を1人に絞ることで構造的に防ぐ。

**索引と詳細のずれ**は必ず起きる。放置すると停滞検知が誤作動する（詳細は動いているのに索引が古く、停滞と判定される）。対策は2つ——完了報告の受領と索引の更新を1つの動作にすること、そして**整合性検査をスクリプトに含めること**。規約だけでは破られるため、検査をフックで必ず走らせる。

## 25.8 一度に1タスクか

**組織全体としては採らない。** §13 と §6.2 が並列実行を前提としているため。

**ただし1つの担当エージェントは同時に1タスク。** 同時に走ってよいのは依存関係の無いタスク間のみ。1つのエージェントが複数タスクを抱えると、記憶が独立している利点が消え、報告が混線する。

## 25.9 ブートストラップ

開発対象リポジトリで最初のタスクを登録する前に、オーケストレーターが索引の CSV（見出し行のみ）、`docs/tasks/` ディレクトリ、台帳の読み方（`docs/tasks/README.md`）、PO確認待ちキュー、引き継ぎ記録、用語集を作る。

これらは層2 であり、オーケストレーターの保守対象である（§6.2）。

# 26. 用語

本版で新設。

## 26.1 用語集を層2に置く

開発対象リポジトリの `docs/glossary.md`。**オーケストレーターが保守する**（組織自身への指示であり、ドキュメントエージェントの担当外。§11.2）。

## 26.2 何を載せるか

判断の基準は1つ。

> **その語を一般的な意味のまま使ったら、この組織では間違った行動になるか。**
> **なる → 載せる。ならない → 載せない。**

一般的な技術用語は載せない。**読み手が既に正しく理解しており、載せても何も買えないうえに、毎回読む量だけが増える。**

載せるのは3種類。

| 分類 | 何か | 例 |
| --- | --- | --- |
| **1. 一般的な意味と違う語** | 誰でも知っている語だが、この組織が意味を狭めた／変えたもの | 「テスト」「レビュー」「完了」「push」 |
| **2. 範囲を明示しないと曖昧になる語** | 指す対象が2つ以上あり、文脈だけでは決まらないもの | 「ユーザー」「ドキュメント」 |
| **3. このプロジェクトの語** | この組織・このプロジェクトの外では通じないもの | 「担当エージェント」「タスク台帳」 |

**分類1が最も危険で、最も見落とされる。** 見慣れない語が出てくれば人もAIも調べるが、「テスト」では調べない。知っているつもりでいるからである。**一般語であることが、狭められている事実を隠す。**

具体例: 「必要なテストを書いてください」を一般的な意味で受け取った実装エージェントは、結合テストまで書く。一般常識としては正しいが、§8.2 の分担に反する。**規約違反だが、本人には違反した自覚がない。**

## 26.3 登録の引き金

| 引き金 | 何を登録するか |
| --- | --- |
| 設計エージェントが設計成果物で**新しい語を定義した**（完了報告で申告される。§7.3） | その語の定義と、どの設計成果物で決まったか |
| **2人以上の担当エージェントが、同じ語について違う前提で動いた** | どちらの意味に統一するか。**綴りが衝突しているなら片方を改名する** |
| PO の回答が、ある語の意味を確定させた | 確定した意味と、質問IDへの参照 |

2番目が最も重要である。**担当エージェントは互いの会話が見えないため、語の食い違いに自分たちで気づけない。** 両者の報告を受け取るオーケストレーターだけが、それを検知できる位置にいる。

**「文脈で使い分ける」という解決は採らない。** 書き手には文脈が見えていて、読み手には見えていないためである。

## 26.4 語の定義を変えるとき

用語集を直したうえで、**その語を使っている設計成果物とタスクも直す。** 定義だけ変えて放置すると、古い文書が別の意味で読まれる。
