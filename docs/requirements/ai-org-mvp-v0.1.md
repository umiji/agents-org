# AI開発組織 MVP 詳細要件定義書

**Version:** 0.1  
**Status:** Draft  
**目的:** Claude Code上で自律的にアプリケーション開発を進めるAI組織MVPを構築するための詳細要件

---

## 1. プロジェクト概要

本MVPは、ユーザーがアプリケーション開発における「最終的に実現したいゴール」を自然言語で入力すると、AI組織がそのゴールを達成するためのタスクを分解・管理し、適切なエージェントへ割り当て、実装・レビュー・テスト・ドキュメント作成等を進める仕組みを構築する。

人間であるプロジェクトオーナー（以下、PO）は、細かな作業を逐一指示するのではなく、原則としてゴールと必要な判断のみを提供する。

---

## 2. MVPの目的

### 2.1 最終目的

AIエージェントの組織が、ユーザーから与えられた開発ゴールに対して、可能な限り少ないユーザー介入で開発作業を継続的に進められる状態を実現する。

### 2.2 MVPで検証する価値

- ゴールからタスクを自律的に分解できること
- タスクを適切なエージェントへ割り当てられること
- 各エージェントが担当作業を自律的に実行できること
- 判断不能な事項を適切にエスカレーションできること
- 停滞しているタスクを検知し、再計画・再割り当てできること
- ゴールに対して組織全体が前進しているかを継続的に評価できること
- Claude Codeのセッションが終了しても、手動で新セッションへ引き継いで作業を継続できること

---

## 3. MVPスコープ

### 3.1 対象

MVPでは以下を対象とする。

1. アプリケーション開発
2. 開発に付随する仕様・設計・README等のドキュメント作成・更新
3. Gitによる変更管理
4. Git commit / push
5. エージェント間のタスク引き継ぎ
6. ユーザーへのエスカレーション
7. タスクの進捗・停滞管理

### 3.2 ゴール入力

ユーザーは、基本的に自然言語で「何を実現したいか」を入力する。

例：

> 「ユーザーが食事内容を入力すると、1日の栄養素と目標との差分を表示するWebアプリを作りたい。」

ユーザーがあらかじめ詳細なタスク一覧を作成することは前提としない。

### 3.3 MVP対象外

以下はMVPでは必須としない。

- SNS投稿等の非開発業務
- 完全自動のClaude Code新規セッション起動
- 24時間完全無人運転
- 複雑なWebダッシュボード
- 高度なKPI分析基盤
- エージェント同士の自由なネットワーク型通信
- 複数AIプロバイダーを横断するエージェント実行基盤

ただし、将来追加できるよう拡張性は考慮する。

---

## 4. 設計原則

### 4.1 シンプルさ

MVPでは独自システムを過剰に構築せず、Claude Codeが標準で提供する仕組みを最大限利用する。

### 4.2 自律性

ユーザーが細かな作業を逐一指示しなくても、オーケストレーターがタスクを管理し、組織を動かす。

### 4.3 継続性

1セッション内で作業が完了しない場合でも、作業状態を残し、新しいClaude Codeセッションから継続できる。

MVPでは新セッションの起動自体は手動とする。

### 4.4 拡張性

エージェント、スキル、MCP、外部ツール等を後から追加しやすい構成とする。

新しい専門エージェントは、極端に言えば定義ファイルを追加するだけで組織へ追加できることを目指す。

### 4.5 トークン効率

単純な繰り返し作業は可能な限りスクリプト等へ切り出し、LLMのトークンは判断・設計・問題解決等の価値の高い処理に集中させる。

### 4.6 既存Claude Code拡張との共存

既存リポジトリに導入済みのEverything Claude Code、Superpowers等の拡張を破壊・置換せず、共存できること。

---

# 5. AI組織の基本構造

MVPでは以下のロールを基本構成とする。

1. オーケストレーター
2. 設計エージェント
3. 実装エージェント
4. レビューエージェント
5. テストエージェント
6. ドキュメントエージェント

将来的に、SNS、マーケティング、データ分析、セキュリティ等の専門エージェントを追加可能とする。

---

# 6. オーケストレーター

## 6.1 ミッション

**ユーザーから与えられたゴールを達成するために、AI組織全体を管理・調整する。**

オーケストレーター自身が成果物を作るのではなく、「誰が・何を・どの順番で行うか」を判断し、組織を動かすことに集中する。

## 6.2 主な責務

### ゴール管理

- ユーザーの自然言語によるゴールを理解する
- ゴール達成条件を明確化する
- 必要に応じてユーザーへ質問する

### タスク分解

- ゴールを実行可能なサブタスクへ分解する
- タスク間の依存関係を整理する
- 優先順位を決定する
- 各タスクに必要なスキル・ロールを判断する

### タスク登録

分解したタスクをタスクリストへ登録する。

各タスクには最低限、以下の情報を持たせる。

- タスクID
- タスク名
- 目的
- 詳細
- 優先度
- 担当エージェント
- 前提タスク
- ステータス
- 作成日時
- 最終更新日時
- 成果物
- ブロッカー
- 備考

### タスク割り当て

各タスクを適切なエージェントへ割り当てる。

### 進捗管理

- タスクの状態を把握する
- タスク間の依存関係を管理する
- 完了したタスクを次のタスクへつなげる

### 停滞管理

一定期間タスクの進捗更新がない場合、停滞として扱う。

MVPでは「2日以上進捗更新がない」を停滞検知の初期基準とする。

停滞を検知した場合：

1. 原因を確認する
2. タスクの再分割を検討する
3. 別エージェントへの相談・再割り当てを検討する
4. 解決できない場合はPOへエスカレーションする

### ゴール健全性評価

オーケストレーターは、単純なタスク消化数だけではなく、組織が最終ゴールへ近づいているかを評価する。

初期的に確認する指標：

- 完了タスク数
- 未完了タスク数
- 停滞タスク数
- ブロック中タスク数
- PO確認待ち件数
- 手戻り件数
- ボトルネックとなっている工程
- ゴール達成に必要な残作業

MVPでは専用のKPIエージェントを設けず、オーケストレーターの責務とする。

### エスカレーション管理

自分や組織で解決できない事項を適切なレベルへエスカレーションする。

### リソース管理

ゴール達成に必要なエージェント・スキル・ツールが不足している場合、それを検知する。

例：

- 必要な専門知識を持つエージェントが存在しない
- 必要なMCPが存在しない
- 必要な外部サービスへのアクセスがない

この場合、POへ不足リソースと必要性を説明し、追加を提案する。

## 6.3 やらないこと

オーケストレーターは原則として以下を担当しない。

- 本格的なコーディング
- 詳細なテスト実装
- 通常のドキュメント作成
- 通常のコードレビュー
- 単純な作業の代行

つまり、**「自分で作業する」のではなく「組織を動かす」ことを優先する。**

---

# 7. 設計エージェント

## ミッション

ゴールおよび要求を実装可能な設計へ変換する。

## 主な責務

- 要件の詳細化
- 技術的な実現方法の検討
- アーキテクチャ設計
- データ構造・API等の設計
- 実装方針の策定
- 実装エージェントからの設計相談への対応
- 設計上の不確実性の検知

## エスカレーション

以下の場合はオーケストレーターへ返す。

- 要件そのものが不明確
- 複数案からPO判断が必要
- 技術的制約によりゴール達成方法が決められない
- 重要なトレードオフについて意思決定が必要

---

# 8. 実装エージェント

## ミッション

設計・タスクに基づいて実際のアプリケーションを実装する。

## 主な責務

- コード実装
- 必要な設定変更
- 必要なテスト実装
- ローカルでの検証
- 実装結果の報告
- Git commit
- 必要に応じたGit push

## 判断

実装上の軽微な判断は自律的に行う。

ただし、以下は勝手に決定しない。

- 要件を変更する判断
- 重要なアーキテクチャ変更
- セキュリティ・コスト等に重大な影響を与える変更
- POの意図が不明な仕様変更

---

# 9. レビューエージェント

## ミッション

実装された成果物が要求・設計・品質基準を満たしているか確認する。

## 主な責務

- コードレビュー
- 設計との整合性確認
- 保守性確認
- 明らかなバグ・リスクの検出
- セキュリティ上の問題の確認
- 改善点の提示
- 修正要求の作成

レビューで問題がある場合は、実装エージェントへ修正を依頼する。

---

# 10. テストエージェント

## ミッション

実装された機能が期待どおり動作することを検証する。

## 主な責務

- テストケース設計
- テストコード作成
- テスト実行
- 不具合の再現
- 不具合原因の切り分け
- 実装エージェントへのフィードバック

重大な不具合や仕様不明点はオーケストレーターへ報告する。

---

# 11. ドキュメントエージェント

## ミッション

開発成果物に必要なドキュメントを最新状態に維持する。

## 主な責務

- README更新
- 仕様ドキュメント更新
- API等の技術ドキュメント更新
- 開発者向けドキュメント更新
- 実装変更とドキュメントの整合性確認

---

# 12. エスカレーション原則

エージェントは「分からないことを無理に決めない」。

エスカレーションは以下の優先順位で行う。

1. 自分の担当範囲で解決
2. 必要に応じて許可された他エージェントへ相談
3. オーケストレーターへエスカレーション
4. オーケストレーターでも判断不能ならPO確認待ちへ登録

---

# 13. PO確認待ちキュー

ユーザーの判断が必要な事項は、確認待ちキューへ登録する。

ただし、POの回答を待っている間も、依存関係のないタスクは継続して実行する。

確認待ち項目には最低限以下を記録する。

- 質問・判断事項
- なぜ判断が必要なのか
- 選択肢
- 各選択肢のメリット・デメリット
- 推奨案
- 回答がない場合に影響するタスク

---

# 14. エージェント間コミュニケーション

## 原則

サブエージェント同士の自由な通信はMVPでは行わない。

基本的にはオーケストレーターをハブとする。

## 例外

オーケストレーターが許可した定型的なワークフローについては、サブエージェント間の直接通信を許可する。

代表例：

**実装 → レビュー → 実装**

レビュー結果に基づいて実装エージェントが修正するような反復ループは、直接連携を許可できる。

この仕組みは、将来的なエージェント間協調へ拡張できる余地を残す。

---

# 15. セッション継続

## MVP方針

Claude Codeのトークン・コンテキスト上限等によって現在のセッションで作業を継続できなくなった場合、新しいClaude Codeセッションを**ユーザーが手動で起動する**。

新セッションでは、既存のタスク状態・成果物・進捗情報を読み取り、作業を再開する。

## MVPでは実装しないもの

- 自動的なClaude Code CLI新規起動
- バックグラウンドセッション管理
- 自動セッション監視
- 自動セッション引き継ぎ

これらは将来の自動化フェーズで検討する。

---

# 16. Git要件

AI組織はGitを利用して変更を管理する。

MVPでは以下を実行可能とする。

- status確認
- diff確認
- commit
- push

重要な変更については、何を変更したかが追跡可能な状態を維持する。

---

# 17. 拡張性

## 17.1 エージェント追加

新しい専門エージェントを追加しやすい構成とする。

例：

- SNSエージェント
- セキュリティエージェント
- データ分析エージェント
- UI/UXエージェント
- マーケティングエージェント

理想としては、エージェント定義を追加するだけで組織に新しい役割を追加できる構造を目指す。

## 17.2 MCP・外部ツール

MCPや外部ツールを後から追加できる構成とする。

特定のMCPに組織全体を強く依存させない。

## 17.3 スキル

エージェントの専門能力はスキルとして分離できる構造を優先する。

Claude Code標準のSkills等を活用し、可能な限り独自の仕組みを増やさない。

---

# 18. 設定・定義ファイルに関する方針

MVPでは、Claude Codeだけで完結する範囲について、不要な独自JSON/YAML設定ファイルを作らない。

Claude Codeの標準的な仕組み（CLAUDE.md、Skills等）を優先する。

独自設定ファイルが必要になるのは、例えば以下の場合とする。

- Claude Code以外のエージェント実行基盤にも対応する
- 複数の実行環境を抽象化する必要が出る
- 機械的に読み書きする構造化設定が必要になる
- ワークフローが複雑化し、自然言語だけでは管理しにくくなる

つまり、**「独自設定ファイルを作ること」自体をMVPの目的にしない。**

---

# 19. 既存Claude Code拡張との共存

現在のリポジトリに存在する既存のClaude Code関連拡張と共存できること。

対象例：

- Everything Claude Code
- Superpowers

既存のcommands / skills / hooks等を不必要に上書き・削除しない。

組織独自の定義は可能な限り独立した領域に配置し、既存拡張との責務を分離する。

# 20. MVPの基本ワークフロー

```text
PO
 │
 │ 自然言語でゴールを入力
 ▼
オーケストレーター
 │
 ├─ ゴール理解
 ├─ タスク分解
 ├─ タスクリスト登録
 ├─ 優先順位付け
 └─ エージェント割り当て
       │
       ├── 設計エージェント
       │
       ├── 実装エージェント
       │      │
       │      └── レビューエージェント
       │               │
       │               └── 実装へ修正依頼
       │
       ├── テストエージェント
       │
       └── ドキュメントエージェント

       ↓
   進捗・停滞管理
       │
       ├─ 解決可能 → 再計画・再割り当て
       │
       └─ 解決不能
              ↓
       オーケストレーター
              ↓
       PO確認待ちキュー
              │
              └─ 他のタスクは継続
```

- [ ] エージェントが判断不能な事項をエスカレーションできる

# 23. 次回セッション再開時の手順

このドキュメントを読み込んだ状態から再開する。

### 最初にやること

**各エージェントの「ミッション → 責務 → 入力 → 出力 → エスカレーション条件」を順番に確定する。**

推奨順序：

1. オーケストレーター
2. 設計エージェント
3. 実装エージェント
4. レビューエージェント
5. テストエージェント
6. ドキュメントエージェント

その後、

7. タスク管理仕様
8. エスカレーション・クライテリア
9. 停滞管理
10. ゴール健全性評価
11. セッション引き継ぎ
12. エージェント追加方式

を詰める。

### 次回の最初の問い

> 「前回のAI開発組織MVPの詳細要件定義書を読みました。まずオーケストレーターのミッション・責務・入力・出力・エスカレーション条件を確定しましょう。」

# 24. 現時点での重要な設計判断

- オーケストレーターは司令塔に徹し、原則として実装しない
- ユーザーは最終ゴールを自然言語で入力する
- ゴールはオーケストレーターがタスクへ分解する
- 分解したタスクはタスクリストへ登録する
- タスクの停滞を管理する
- ゴールに対する組織全体の健全性を評価する
- エージェント不足もオーケストレーターが検知する
- 判断不能な事項は段階的にエスカレーションする
- PO確認待ちでも独立タスクは継続する
- サブエージェント間通信は原則制限し、承認されたワークフローでは直接通信を許可する
- MVPのセッション引き継ぎは手動
- Git pushまで対応する
- Claude Code標準機能を最大限利用する
- 独自設定ファイルは必要になるまで作らない
- 既存Claude Code拡張と共存する
- エージェント・Skills・MCP等を後から追加できることを重視する
- 単純な繰り返し処理はスクリプト化し、LLMトークンを節約する

---
