# 要件定義書 v0.1 からの変更（次版へ反映すること）

**Status:** 確定済みの差分の集積
**用途:** `docs/decisions/01`〜`12` の確定作業で、要件定義書 v0.1 の記述に変更・追加・具体化が生じたものを一覧する。次版（v0.2）を切るときは、この一覧を本文へ取り込む。

各項目は「どの節が、どう変わるか」と、根拠となる決定記録への参照を持つ。**詳細は決定記録が正典であり、ここは索引である。**

## 役割定義の確定に伴う変更（2026-08-19）

| # | 対象 | 変更内容 | 記録 |
| --- | --- | --- | --- |
| 1 | §6.2 タスク項目 | `完了条件` を**追加**。レビュー／テストエージェントが充足を判定する基準として必要 | `01` 確定事項 A |
| 2 | §6.2 タスク項目 | `TDD適用可否` を**追加**。#7 に伴う | `01` の O-0 |
| 3 | §14 直接通信の例外 | **「実装 → 設計 → 実装」を追加**。ただし**軽微な問合せに限る**。設計変更を伴うものはオーケストレーター経由 | `02` 確定事項 C |
| 4 | §8 / §10 | テスト責務の重複を解消。§8「必要なテスト実装」＝**単体テストに限定**、§10「テストコード作成」から単体テストを除く | `03` 確定事項 A |
| 5 | §8 | 「必要に応じた Git push」を具体化。commit は論理単位、push は**タスク完了時**（レビュー通過を待たない） | `03` 確定事項 B |
| 6 | §14 直接通信の例外 | **「テスト → 実装」を追加**。テストの不具合レポートはレビューの修正要求と同性質（実装への差し戻しであり設計・要件を変えない） | `05` 確定事項 B |
| 7 | §20 ワークフロー | **TDD 既定へ変更**。完了条件 → **受け入れテスト（実装前）** → 実装 → テスト実行 → レビュー。§20 の図は実装→レビューと実装→テストを並列に描いているが、**直列へ改める**。事前にテストを書けないタスクはオーケストレーターが「TDD適用外」と明示する | `05` 確定事項 D |
| 8 | §22-6 | 「レビュー→実装の反復回数・終了条件」を**確定**。指摘は Blocker / Major / Minor の3段階。Blocker と Major が0件で通過、**2往復**で解決しなければオーケストレーターへエスカレーション。実装側は理由と根拠を付して反論でき、決着しなければオーケストレーターが裁定する | `04` 確定事項 A・B・C |
| 9 | §6.3 の解釈 | 層2（開発対象リポジトリの `CLAUDE.md` / `.claude/rules/` / エージェント定義）の保守は**オーケストレーターの責務**。組織自身への指示であって成果物ではないため、§6.3「通常のドキュメント作成は担当しない」とは矛盾しない | `06` 確定事項 D |

## タスク管理仕様以降の確定に伴う変更（2026-08-20）

| # | 対象 | 変更内容 | 記録 |
| --- | --- | --- | --- |
| 10 | §18 | タスクリストの保存形式として **CSV索引 + タスク別Markdown** を採用。§18 の例外「機械的な読み書きが必要な構造化設定」に**実際に到達した**ための決定であり、§6.2 の停滞管理・健全性評価がスクリプトによる集計を要求することが根拠。判断と文脈は Markdown 側に置き、CSV は索引に徹する | `07` |
| 11 | §22-1 / §22-2 | 「各ロールの入力形式・出力形式」を**確定**。情報項目のレベルで `01`〜`06` に定義済み。加えて、**タスク別ファイルがそのまま作業指示を兼ねる**（01 の O-2 の必須項目を全て含むため） | `01`〜`06`、`07` |
| 12 | §22-3 | 「タスクステータスの具体的な種類」を**確定**。10種: `未着手` / `設計中` / `テスト作成中` / `実装中` / `テスト中` / `レビュー中` / `PO確認待ち` / `完了` / `保留` / `中止`。終端は `完了` / `中止` の2つ | `07` |
| 13 | §22-4 | 「タスク間依存関係の表現」を**確定**。`T-001（ブロッカー）` / `T-001（推奨: 理由）` の2形式。無い場合は `無し` と明記。**ブロッカーには理由の記載を必須とし、書けない依存は依存として認めない**（並列実行できる単位を潰さないため） | `07` |
| 14 | §22-5 | 「エスカレーション条件の詳細なクライテリア」を**確定**。§12 の4段階に各段の打ち切り条件を定義。加えて**全ロール共通の停止条件 S-1〜S-6** を新設 | `08` |
| 15 | §13 | PO確認待ちキューの実体を `docs/po-queue.md`（開発対象リポジトリ）と**確定**。項目に `Q-ID` / `登録日` / `状態` / `回答` を追加。**PO の回答が一般的な基準になった場合、層2（`CLAUDE.md` / `.claude/rules/`）へ昇格させる**ことを規約化 | `08` |
| 16 | §22-8 | 「停滞判定の詳細」を**確定**。**実時間基準（CSV の `更新日` が2日以上前かつ非終端）** と **サイクル基準（往復上限2回到達、または `手戻り回数` 3以上）** の併用。`PO確認待ち` / `保留` / 依存待ちの `未着手` は停滞に数えない。検知は**スクリプト + SessionStart hook** で行う | `09` |
| 17 | §6.2 停滞管理 | 検知後の4段階に、各段の適用条件と次へ進む条件を定義。**同じタスクが2回目の停滞を起こしたら段2・3を飛ばして PO エスカレーションへ** | `09` |
| 18 | §22-9 | 「ゴール健全性評価の具体的な指標」を**確定**。8指標の算出方法を CSV とタスク別ファイルから定義。判定は3値（前進している / 停滞している / **ゴールが揺らいでいる**）。実行タイミングは**節目 + PO要求時** | `10` |
| 19 | §6.2 タスク項目 | タスク別ファイルのメタデータに `手戻り回数` を**追加**。§6.2 の健全性指標「手戻り件数」の算出元 | `10` |
| 20 | §22-11 | 「セッション引き継ぎ時に必ず保存すべき情報」を**確定**。**タスクリスト + 引き継ぎ記録 `docs/handover.md`**（1枚・常に上書き）。8項目を必須化。**節目ごとに更新する**（セッション終了時にまとめて書く運用は成立しない） | `11` |
| 21 | §15 | 新セッションの再開手順を**確定**（8ステップ）。**停滞検知スクリプトの実行をタスクリスト読み込みより前に置く**（引き継ぎ記録が古い可能性があるため）。手順は Skill として置く | `11` |
| 22 | §22-10 | 「エージェント追加時の定義方法」を**確定**。必須構成は 01〜06 と同じ5要素。**組織側でエージェント一覧を持たない**ことがファイル追加だけで済む条件。追加手順6段。**直接通信経路の追加だけは §14 の変更を要する**（意図的な摩擦） | `12` |
| 23 | §19 | 既存拡張との共存規約を具体化。組織の定義は **`org-` プレフィックス**。hook は**追記のみ**（既存エントリを置換しない）。名前が衝突したら**組織側が譲る** | `12` |
| 24 | §22-12 | 「Claude Code の具体的な標準機能へのマッピング」を**確定**。CLAUDE.md の対応表に加え、**組織の状態（タスク・PO確認待ち・引き継ぎ）は開発対象リポジトリの `docs/` 配下**、**必ず実行させる検査は hook + スクリプト** | `07`〜`11` |
