# 09. 停滞管理

**Status:** Confirmed（PO確認 2026-08-20）
**根拠:** 要件定義書 v0.1 §6.2 / §21 / §22-8 / §23-9
**前提:** 07 でタスクリストの形式が確定した。停滞判定は CSV の `更新日` と `状態` から機械的に行える。

## この文書が確定したこと

- **停滞の判定は2基準の併用。** 実時間基準（索引の更新日が2日以上前かつ非終端）と、サイクル基準（往復が2回に達した、または手戻り回数が3以上）。実時間だけでは1セッション内の空回りを、サイクルだけでは放置されたタスクを捉えられない
- **PO確認待ち・保留・依存待ちの未着手は停滞に数えない。** PO確認待ちは別枠でリマインド候補として数える
- **検知はスクリプト＋セッション開始フック。** 契約（入力・出力・終了コード・整合性の検査項目）を定め、後に実装した
- **検知後の4段階に適用条件を与えた。** 同じタスクが2回目の停滞を起こしたら、段2・3を飛ばして PO へ上げる

---

## PO の提案への回答

> 「タスクリストの更新日が2日経過していたらフォローアップ」

**これを採用する。** §6.2 / §21 の「2日以上進捗更新がない」を、07 で確定した CSV の `更新日` 列に対する判定として具体化したものであり、要件定義書と一致する。加えて **07 で形式が決まったことで、この判定は初めてスクリプト化できるようになった**（§4.5、CLAUDE.md の機能マッピング）。

ただし、これ**だけ**では取りこぼす種類の停滞がある。以下に述べる通り、実時間基準と併せて**サイクル基準**を置く。

---

## 二つの停滞

エージェントは分単位で動くため、「2日」という物差しが届かない領域がある。

| | 実時間基準（S-A） | サイクル基準（S-B） |
| --- | --- | --- |
| 捉えるもの | セッションをまたいで**放置された**タスク | 1セッション内で**空回りしている**タスク |
| 典型例 | PO 確認待ちのまま忘れられた。担当が割り当てられないまま残った。前セッションの終了時に進行中だったものが引き継がれなかった | レビュー→修正→再レビューが収束しない。テスト→修正→再テストで同じ不具合が消えない。同じ設計論点を何度も検討している |
| 判定 | CSV の `更新日` が **2日以上前**、かつ状態が終端でない | 同一タスクで往復が上限（**2往復**）に達した、または `手戻り回数` が **3以上** |
| 検知の主体 | スクリプト（機械的） | オーケストレーター（往復の報告を受けて） |

**両方が要る。** 実時間基準だけでは、数十分で10回空回りしているループを検知できない。サイクル基準だけでは、セッションが終わった後に放置されたタスクを検知できず、§21 のチェック項目「2日以上更新がないタスクを停滞として検知できる」を満たさない。

サイクル基準の閾値を2往復に置くのは、04 確定事項 B（レビュー）および 05 確定事項 B（テスト）で確定済みの反復上限と揃えるためである。**新しい物差しを増やさない。** 04 が述べた通り、往復が収束しないこと自体が判定基準——完了条件や設計——の不備を示す信号であり、これは停滞の一形態にほかならない。

## 停滞に数えないもの

| 状態 | 扱い | 理由 |
| --- | --- | --- |
| `完了` / `中止` | 対象外 | 終端状態。動かないのが正しい |
| `PO確認待ち` | **停滞に数えない。別枠で数える** | 組織側の停滞ではない。オーケストレーターが手を打っても動かない |
| `保留` | 停滞に数えない。ただし**保留理由の妥当性を節目ごとに再確認する** | 意図して止めている。ただし「保留にしたまま忘れる」が起きうる |
| `未着手` かつ ブロッカー依存が未完了 | 停滞に数えない | 依存先が進めば動く。依存先の方を見る |

`PO確認待ち` を分離するのは §6.2 が「停滞タスク数」と「PO確認待ち件数」を別の指標として並べているためである。混ぜると、PO の応答待ちが組織の停滞として計上され、10 の判定が歪む。

**ただし PO確認待ちも放置はしない。** `更新日` が2日以上前の `PO確認待ち` は「**PO へのリマインド候補**」として別に出す。これは組織への差し戻しではなく、PO への通知である。

`未着手` かつ依存待ちのタスクを対象外にする一方で、**依存先を辿った先が誰も動いていない**場合は、その依存先が停滞として検出される。連鎖の根元だけを見ればよいので、待っている側を数える必要はない。

## 検知スクリプトの契約

§4.5 は「単純な繰り返し処理はスクリプトへ切り出す。LLMのトークンは判断・設計・問題解決に使う」と定めている。停滞判定は日付の比較と状態の突合せであり、判断を含まない。**LLM に数えさせない。**

### 入力

| 引数 | 内容 |
| --- | --- |
| CSV のパス | `docs/task-list-{project-name}.csv` |
| 基準日数 | 既定 2。変更可能にしておく |
| 基準日 | 既定 実行日 |

### 出力（1）停滞候補

各行に: タスクID / タスク名 / 状態 / 担当 / 最終更新日 / 経過日数 / 検知区分（S-A）

### 出力（2）PO確認待ちのリマインド候補

各行に: タスクID / ブロッカーの Q-ID / 経過日数

### 出力（3）整合性の警告

07 で述べたずれを検出する。**停滞の誤検知は、ほとんどが台帳のずれから来る。**

| 検査 | 何を防ぐか |
| --- | --- |
| CSV の `更新日` と詳細ファイルの `更新日` が食い違う | 詳細だけ更新され CSV が古く、動いているタスクを停滞と誤判定する |
| CSV の `状態` と詳細ファイルの `状態` が食い違う | どちらが真か分からなくなる |
| `ドキュメント` 列のパスが存在しない | 詳細ファイルが作られていない、または移動された |
| 依存タスクに書かれたIDが CSV に存在しない | 依存が辿れず、ブロック中タスク数が誤る |
| 終端状態でないのに `担当` が `未割当` | 誰も動かさないまま残っている（実質の停滞） |
| 状態が `設計中` / `テスト作成中` / `実装中` / `テスト中` / `レビュー中` なのに `担当` がオーケストレーター | **委譲を怠っている**（`13` A の手段2）。オーケストレーターはメインセッションでありツール制限をかけられないため、この検査が §6.3「実装しない」の担保になる |
| `依存タスク` / `作成日` / `更新日` が空欄 | 07 の「空欄にしない」規約違反。判定不能な行になる |
| 状態が 07 の10種のいずれでもない | 集計から漏れる |

### 終了コード

| コード | 意味 |
| --- | --- |
| 0 | 停滞候補・整合性警告ともに無し |
| 1 | 停滞候補または警告あり（出力を読むこと） |
| 2 | CSV が読めない、書式が壊れている |

**このスクリプトは判定するが、対処はしない。** 何をするかはオーケストレーターが決める（後述）。スクリプトが自動でタスクを再割り当てすると、判断がログに残らず、なぜそうなったか追えなくなる。

### 実行タイミング

| いつ | 手段 |
| --- | --- |
| **セッション開始時** | **hook（SessionStart）** |
| 節目（10 の健全性評価と同時） | オーケストレーターが実行 |
| PO から求められたとき | オーケストレーターが実行 |

セッション開始時を hook にするのは、**CLAUDE.md が強制力を持たない**ためである（00 §1.2）。「セッション開始時に停滞を確認せよ」と CLAUDE.md に書いても、実行されない回が出る。必ず実行させたいものは hook にする——これは CLAUDE.md の機能マッピングで既に定めた方針であり、停滞検知はその最初の適用例になる。

セッション開始時に置くことには、もう一つの意味がある。**前セッションが引き継ぎを書かずに切れた場合、放置されたタスクを最初に拾えるのはこの検査だけである**（11 参照）。

## 検知後の手順

§6.2 は4段階を定めている。各段の適用条件を判定可能にする。

| 段 | やること | 適用する条件 | 次へ進む条件 |
| --- | --- | --- | --- |
| **1. 原因を確認する** | 担当エージェントへ状況を問う。何が止めているのか。詳細ファイルの `作業ログ` / `ブロッカー` を読む | 常に最初に行う | 原因が判明し、それが 2〜4 のいずれかに該当する |
| **2. タスクを再分割する** | 完了条件を満たす途中の状態を、独立して完了できる単位へ割る | タスクが大きすぎる。完了条件が複数の独立した達成物を含んでいる。一部は完了しているのに全体が未完了のまま止まっている | 分割後のタスクが着手可能になった |
| **3. 別エージェントへ相談・再割り当てする** | 担当を変える、または上流ロールへ差し戻す | 担当ロールの専門外の問題に当たっている。設計・要件の側に原因がある（04 の E-3/E-4、05 の E-3 と同じ構造） | 新しい担当が着手できた |
| **4. PO へエスカレーションする** | 08 の形式で `docs/po-queue.md` へ登録 | 1〜3 を試しても進まない。または原因が 01 の E-1〜E-6 に該当する | — |

### 段を飛ばしてよい場合

- 原因が最初から明白で 01 の E-1〜E-6 に該当する → **段1の後、直接 段4**
- **同じタスクが2回目の停滞を起こした** → 段2・3 は既に効かなかったとみなし、**段4へ**

2番目が重要である。同じ手を繰り返すのは停滞の解消ではなく停滞の継続である。**再分割と再割り当てを何度も試すループ自体が、S-B（サイクル基準）で検知されるべき対象になる。**

### 記録

停滞への対処は、タスク別ファイルの `## 決定ログ` に残す（07 の記録条件 3「登録後にスコープ・完了条件が変わった」に該当する場合が多い）。

```markdown
### 2026-08-20 T-014 の停滞に対し、担当を設計へ差し戻した
- 決定: 実装から設計へ差し戻し、API の戻り値仕様を先に確定させる
- 却下案: 実装側で仮決めして進める → 仮決めが要件変更に当たる（03 の B-1）ため不可
- 出典: セッション内の判断、成果物なし
```

**何回停滞したかが追えることが要点である。** 2回目の停滞で段4へ飛ぶ判定は、この記録が無いと下せない。

## 停滞の予防は、タスク分解の側にある

停滞は検知して対処するより、起こさない方が安い。01 の O-0 と 07 が既にその手を打っている。

| 予防手段 | 確定した場所 |
| --- | --- |
| 1タスクは担当が1回の作業で完了できる大きさにする | 01 の O-0 |
| 説明できない依存を書かない（並列に走れる単位を残す） | 01 の O-0、07 |
| 完了条件を必須にし、テストへ変換できるか実装前に確かめる | 01 確定事項 A、05 確定事項 D |
| 判断してよい範囲を明示する | 01 確定事項 B |
| PO確認待ちの登録時に「待つ間も進められるタスク」を必須で書く | 01 の O-3、08 |

最後の一つは停滞管理そのものである。§13 が「POの回答を待っている間も、依存関係のないタスクは継続して実行する」と定めているのは、**PO確認待ちが組織全体の停止に化けることを防ぐため**であり、それを登録時点で確認する仕組みが「待つ間も進められるタスク」の必須化である。

## 実装（2026-08-20 実装済み）

`org/scripts/org-check.py`。開発対象リポジトリの `.claude/scripts/` へ配置する。

| 決めたこと | 内容 | 理由 |
| --- | --- | --- |
| 実装言語 | **Python 3.8 以降、標準ライブラリのみ** | このスクリプトは**任意の開発対象リポジトリへ配られる**。追加インストールを要求すると、導入先の言語や構成に依存してしまう。日付の計算と CSV の読み取りは標準ライブラリで足りる |
| 配置 | `.claude/scripts/org-check.py` | 組織のファイルを1つの名前空間へまとめ、開発対象リポジトリ自身の `scripts/` と衝突させない |
| 実行 | セッション開始時のフック（`org/settings.snippet.json`）＋ 節目で手動 | |

### 集計モードを同じスクリプトへ入れた

`10` が「09 の検知スクリプトと同一のものにしてよい」と述べていたとおり、統合した。どちらも同じ CSV を読み、同じ状態と日付を数えるため、分けると解析の実装が二重になる。

| モード | 出すもの |
| --- | --- |
| （既定） | 停滞候補・リマインド候補・整合性の警告 |
| `--summary` | ゴール健全性の8指標（`10`） |
| `--statusline` | 1行にまとめたもの（画面下部のステータス行向け） |

### フック用のモードが要った理由

Claude Code のセッション開始フックは、**終了コードが 0 のときだけ標準出力をセッションの文脈へ入れる。** 契約どおり「検出あり = 1」を返すと、**検出があるときほど結果が Claude に届かない**という逆転が起きる。

そのため `--hook` を足した。検出があっても 0 で終わる。直接実行したときの終了コードは契約どおり（0 / 1 / 2）のまま。

### 整合性検査に追加した項目

`09` の初版になかったものを、実装時に追加した。いずれも機械的に判定でき、誤検知しない。

- 優先度が `高` / `中` / `低` のどれでもない
- ID が `T-###` の形になっていない
- 更新日が `YYYY-MM-DD` になっていない
- 詳細ファイルに「## メタデータ」節が無い、または `- キー: 値` の形になっていない

最後の項目のために、**タスク別ファイルのメタデータ書式を確定させた**（`07`）。初版の書式は項目名を並べただけで、行の形が決まっておらず、機械が読めなかった。

## 未確定のまま残すもの

- PO確認待ちのリマインド間隔（08 から引き継ぐ）。既定は停滞と同じ2日とするが、PO の応答速度に依存するため運用で調整する
- `手戻り回数` 3以上を S-B の閾値としたが、これは 04/05 の2往復から導いた暫定値である（2往復＝差し戻し2回、3回目は収束していない）。運用で見直す
- **サイクル基準（S-B）のうち、機械的に取れるのは `手戻り回数` だけ**である。「レビューの往復が上限に達した」はタスク別ファイルの作業ログからしか読めず、判定はオーケストレーターが行う
