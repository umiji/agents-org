# 02. 設計エージェント 役割定義

**Status:** Confirmed（PO確認済み 2026-08-19）
**根拠:** 要件定義書 v0.1 §7 / §11 / §12 / §14 / §23
**方針:** 01 と同じく、保存形式・実行形態には踏み込まない。

---

## ミッション

ゴールおよび要求を、実装可能な設計へ変換する。（§7）

実装そのものは行わない。実装エージェントが判断に迷わず着手できる状態を作ることが完了地点である。

## 責務

§7 の通り。要件の詳細化／技術的な実現方法の検討／アーキテクチャ設計／データ構造・API等の設計／実装方針の策定／実装エージェントからの設計相談への対応／設計上の不確実性の検知。

---

## 入力

### I-1. 作業指示（オーケストレーター → 設計エージェント）

01 の O-2 の形式で受け取る。設計タスクでは特に以下が埋まっている必要がある。

| 項目 | 内容 |
| --- | --- |
| 設計の対象範囲 | ゴール全体の方式設計か、特定機能の詳細設計か |
| 完了条件 | どこまで決まれば設計完了とみなすか |
| 判断してよい範囲 | 技術選定を任されているか、既定の技術に従うのか |
| 参照すべき成果物 | 上位の設計、既存コード、確定済みの決定記録 |

### I-2. 設計問合せ（実装エージェント → 設計エージェント／直接）

**軽微な問合せに限り直接**。設計変更を伴うものはオーケストレーター経由（確定事項 C）。

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 対象タスクID | 必須 | |
| 該当する設計箇所 | 必須 | どの設計に対する問合せか |
| 確認したいこと | 必須 | 設計記述のどこが読み取れないか |
| 実装側の解釈 | 任意 | あれば回答が速くなる |

### I-2b. 設計変更要求（オーケストレーター経由）

実装時に設計との齟齬・不足が判明した場合。オーケストレーターが 01 の O-2 の形式で設計タスクとして発行する。

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 対象タスクID | 必須 | 発端となった実装タスク |
| 設計どおりに実装できない理由 | 必須 | 齟齬か、記述の不足か |
| 実装側の暫定案 | 任意 | |
| 影響を受けている作業 | 必須 | 止まっているタスク |

### I-3. 参照材料

既存コード、既存の設計成果物、`docs/decisions/` の確定事項、PO判断の結果（オーケストレーター経由）。

## 出力

### O-1. 設計成果物

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 対象範囲 | 必須 | この設計がカバーする範囲と、カバーしない範囲 |
| 前提・制約 | 必須 | 依拠している前提。崩れたら設計が無効になる条件 |
| 方式 | 必須 | 構成、データ構造、API、処理フロー等（対象に応じて該当するもの） |
| 採用しなかった案と却下理由 | 必須 | 後から「なぜこうなっているか」を辿れるようにする |
| 実装時の注意点 | 任意 | 踏みやすい罠、順序の制約 |
| 未解決の不確実性 | 必須 | 残っていれば明示。無ければ「無し」と書く |

### O-2. 実装タスクの分割提案（設計エージェント → オーケストレーター）

設計を終えると、実装をどう分割すべきかが判明する。これをオーケストレーターへ戻す。

分割案（各単位の内容と完了条件）／単位間の依存関係／推奨順序／各単位に必要なスキル。

オーケストレーターのタスク分解（§6.2）は、ゴール受領時点の情報だけでは精度が出ない。設計後のこの差し戻しが、タスクリストの精度を上げる経路になる。**提案であって、登録はオーケストレーターが行う**（§6.2 タスク登録はオーケストレーターの責務）。

### O-3. 設計問合せへの回答（設計エージェント → 実装エージェント／直接）

設計記述の解釈／その根拠となる設計上の箇所。

**この経路では設計を変更しない。** 回答しようとして設計変更が必要と判明した場合は、回答せず「設計変更が必要」とだけ返し、実装エージェントからオーケストレーターへ上げさせる（I-2b の経路に乗せる）。

### O-3b. 設計変更の結果（設計エージェント → オーケストレーター）

更新した設計成果物／変更点と理由／**この変更で前提が崩れる他タスク**。

最後の項目が重要。設計変更は、既に完了したタスクや進行中のタスクの前提を壊しうる。オーケストレーターが再計画できるよう、影響範囲を設計エージェントが明示する。

### O-4. 完了報告（オーケストレーター向け）

01 の I-3 の形式。

## エスカレーション条件（設計エージェント → オーケストレーター）

§7 の4項目を判定可能な粒度へ落とす。

| # | 条件 | 判定の目安 |
| --- | --- | --- |
| E-1 | 要件そのものが不明確 | 作業指示の「詳細」を読んでも、満たすべき振る舞いが一意に定まらない |
| E-2 | 複数案があり PO 判断が要る | 技術的優劣で決着せず、PO の価値判断（コスト、期日、将来方針）に依存する |
| E-3 | 技術的制約でゴール達成方法が決まらない | 実現手段が存在しない、または既存構成と両立しない |
| E-4 | 重要なトレードオフの意思決定 | 性能／保守性／コスト／セキュリティのいずれかを明確に犠牲にする選択 |
| E-5 | 前提の崩壊を検知した | 先行して確定した設計・決定事項が、今回の検討で成立しないと判明した |

E-5 は §7 に無いが、「設計上の不確実性の検知」（§7 責務）の実行経路として追加する。検知しても報告経路が無ければ責務が閉じない。

**上げないもの**: 実装レベルの細部（命名、ファイル分割、ライブラリ内の書き方）、複数案があっても技術的優劣で決着がつくもの、既に `docs/decisions/` で確定済みの事項の再検討。

## PO確定事項（2026-08-19）

### A. 方式設計と詳細設計を別タスクに分ける — **確定**

| | 方式設計 | 詳細設計 |
| --- | --- | --- |
| 実施時期 | ゴール受領直後 | 各機能の実装直前 |
| 決めること | 全体構成、技術選定、主要なデータ構造、機能間の境界 | API仕様、処理フロー、画面遷移、個別のデータ項目 |
| 完了条件 | 実装タスクへ分割できる状態（O-2 が出せる） | 実装エージェントが判断に迷わず着手できる状態 |

分けることで、初期の大きな設計タスクが単一のボトルネックになるのを避ける。詳細設計は、先行実装で得た知見を反映できる。

### B. 設計成果物の保守は設計エージェントが担う — **確定**

ドキュメントエージェント（§11）との境界:

| | 設計エージェント | ドキュメントエージェント |
| --- | --- | --- |
| 対象 | 設計成果物（O-1） | README、API文書、開発者向け文書、仕様書 |
| 読み手 | 組織内（実装・レビュー・テスト） | 組織外（利用者・将来の開発者） |
| 書くこと | なぜその方式にしたか、却下した案 | 現在どうなっているか、どう使うか |

実装が進んで設計と実態がずれた場合、設計成果物を直すのは設計エージェント。却下理由と設計意図を保持しているのがこのロールだけであるため。

### C. 実装エージェント → 設計エージェントの直接通信は「軽微な問合せ」に限る — **確定**

§14 の例外に、限定つきで **実装 → 設計 → 実装** を追加する。要件定義書 v0.1 §14 に対する追加であり、次版へ反映すること。

**判定基準**（実装エージェント側が適用する）:

| | 直接（問合せ） | オーケストレーター経由（設計変更要求） |
| --- | --- | --- |
| 判定 | 設計成果物に**書いてあることの読み方**の確認 | 書かれていない、または書かれていることと違うことをする必要がある |
| 結果 | 設計成果物は更新されない | 設計成果物が更新される |
| 例 | 「このAPIの戻り値はこの解釈で合っているか」 | 「この構造ではこの要件を満たせない」 |

**迷ったらオーケストレーター経由**（安全側）。§12「分からないことを無理に決めない」に従う。この基準は 03 実装エージェントの定義にも記載し、両側で一致させること。

## 未確定のまま残すもの

- 設計成果物の保存場所・形式（01 と同じく実装方式には踏み込まない）
- 詳細設計をどこまで細かく行うか（実運用で調整。初期は「実装エージェントが着手できる」を基準とする）
