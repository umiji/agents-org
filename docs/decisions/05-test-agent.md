# 05. テストエージェント 役割定義

**Status:** Draft（論点をリサーチ後にまとめて確認）
**根拠:** 要件定義書 v0.1 §10 / §12 / §14 / §22-7 / §23
**前提:** 03 確定事項 A により、単体テストは実装エージェントの担当。本ロールはそれ以外を担う。

---

## ミッション

実装された機能が、期待どおり動作することを検証する。（§10）

実装者の思い込みを、別ロールが**仕様の側から**検査することに価値がある。実装を直すのは実装エージェント。

## 責務

§10 の通り。テストケース設計／テストコード作成／テスト実行／不具合の再現／不具合原因の切り分け／実装エージェントへのフィードバック。

**担当範囲**（03 確定事項 A）: 結合テスト、シナリオテスト、回帰テスト。単体テストは実装エージェントが書く。単体テストの不足に気づいた場合は、自分で書かず実装エージェントへフィードバックする。

## エスカレーション条件（テストエージェント → オーケストレーター）

§10 は「重大な不具合や仕様不明点はオーケストレーターへ報告する」とのみ述べる。判定可能な粒度へ落とす。

| # | 条件 | 判定の目安 |
| --- | --- | --- |
| E-1 | 期待動作が判定できない | 完了条件にも設計にも書かれておらず、何が正しいか決められない（§10「仕様不明点」） |
| E-2 | 重大な不具合 | データ破損、セキュリティ、ゴールの中核機能が動作しない（§10「重大な不具合」） |
| E-3 | 不具合の原因が実装ではなく設計・要件にある | 実装は設計どおりだが期待動作にならない |
| E-4 | 修正の反復が収束しない | 論点 B の上限に達した |
| E-5 | 検証環境が無く、検証自体が実施できない | 必要なリソースの不足（01 の O-5 リソース管理へ） |

## 論点（リサーチ後にまとめて確認）

### A. テスト失敗時のフロー（§22-7）

不合格の場合、どこへ戻すか。実装エージェントへ直接か、オーケストレーター経由か。レビューを通過した後にテストが落ちた場合、レビューへも戻すのか。

### B. 不具合フィードバックの経路と反復上限

§14 が明示的に許可する直接通信は「実装 → レビュー → 実装」のみ。テスト → 実装 は例外リストに無い（02 で「実装 → 設計」を追加したのと同じ構造の問題）。

反復上限も、04 の確定事項 B（2往復）と揃えるか、テストは性質が違うと見るかを決める必要がある。

### C. 不具合の重大度分類

04 で指摘に Blocker / Major / Minor を導入した。不具合にも同じ体系を使うか、テスト固有の分類を設けるか。

### D. レビューとテストの実行順序

§20 のワークフロー図では、実装 → レビュー、実装 → テストが並列に描かれている。直列（レビュー通過後にテスト）か並列かで、手戻りの量と速度が変わる。
