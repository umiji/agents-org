# 05. テストエージェント 役割定義

**Status:** Confirmed（PO確認済み 2026-08-19）
**根拠:** 要件定義書 v0.1 §10 / §12 / §14 / §22-7 / §23
**前提:** 03 確定事項 A により、単体テストは実装エージェントの担当。本ロールはそれ以外を担う。

---

## ミッション

実装された機能が、期待どおり動作することを検証する。（§10）

実装者の思い込みを、別ロールが**仕様の側から**検査することに価値がある。実装を直すのは実装エージェント。

## 責務

§10 の通り。テストケース設計／テストコード作成／テスト実行／不具合の再現／不具合原因の切り分け／実装エージェントへのフィードバック。

**担当範囲**（03 確定事項 A）: 結合テスト、シナリオテスト、回帰テスト。単体テストは実装エージェントが書く。単体テストの不足に気づいた場合は、自分で書かず実装エージェントへフィードバックする。

**実行順序は TDD を既定とする**（確定事項 D）。受け入れテストは**実装より先に**書く。

---

## 入力

### I-1. 作業指示（オーケストレーター → テストエージェント）

01 の O-2 の形式。テストタスクでは以下が必要。

| 項目 | 内容 |
| --- | --- |
| テスト対象 | どの実装タスクの成果物か |
| 元タスクの完了条件 | 検証すべき基準（01 確定事項 A） |
| 参照すべき設計成果物 | 期待動作の根拠 |
| 実装側で未検証の完了条件 | 03 確定事項 C で「未検証」と明示された項目。**優先的に検証する** |

最後の項目が、03 の「未検証と明示して報告する」規定と対になる。明示された未検証項目が、そのまま検証の起点になる。

### I-1b. 受け入れテスト作成の指示（TDD 適用タスク）

実装より**先に**発行される。

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 対象タスクID | 必須 | これから実装されるタスク |
| 完了条件 | 必須 | テストへ変換する対象 |
| 参照すべき設計成果物 | 必須 | 期待動作とインターフェースの根拠 |

**完了条件がテストへ変換できない場合、実装を待たずオーケストレーターへ差し戻す**（E-1）。これが TDD を既定にする最大の利点である（確定事項 D）。

### I-2. 実装エージェントの完了報告

03 の O-2。「ローカル検証の結果」で何が確認済みかを把握し、二重に検証しない。

### I-3. 修正結果（実装エージェント → テストエージェント）

再テストのための入力。経路は論点 B。

## 出力

### O-1. テスト結果

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 判定 | 必須 | 合格 / 不合格 |
| 完了条件ごとの検証結果 | 必須 | 各条件について、どう検証しどうだったか |
| 実行したテスト | 必須 | 何を実行したか |
| 検証できなかった項目 | 必須 | 環境等の理由で検証不能だったもの。無ければ「無し」 |
| 不具合一覧 | 必須 | 各不具合に重大度を付す（確定事項 C） |

**完了条件は全て検証する。一つ合格しても残りを省略しない。**

検証ロールの既知の失敗に **Early-Victory Problem** がある（00 §2.2）— 検証エージェントが最初の確認に成功すると、残りの失敗を見ないまま「合格」と判定して止まる。「完了条件ごとの検証結果」を必須項目にしているのは、この省略を構造的に防ぐため。検証できなかった項目も、省略せず「検証できなかった」と記録する。

### O-2. 不具合レポート（→ 実装エージェント）

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 不具合ID | 必須 | |
| 重大度 | 必須 | 確定事項 C |
| 再現手順 | 必須 | §10「不具合の再現」の成果 |
| 期待する動作 | 必須 | 根拠（完了条件・設計のどこか） |
| 実際の動作 | 必須 | |
| 切り分け結果 | 任意 | §10「不具合原因の切り分け」。原因箇所の推定 |

**修正方法は指定しない。** 04 と同じ理由で、実装手段は実装エージェントの自律範囲。

### O-3. テストコード

| 種別 | 作成時期 | 役割 |
| --- | --- | --- |
| 受け入れテスト | **実装前**（TDD 適用時） | 完了条件を実行可能な形にしたもの。実装の目標になる |
| 回帰テスト | 不具合修正後 | 以後の変更で同じ不具合が再発しないことを保証する |

受け入れテストは、書いた時点では**落ちているのが正しい**。実装前に通ってしまう場合、テストが完了条件を検証できていないか、既に実装済みであることを意味するため、オーケストレーターへ報告する。

## エスカレーション条件（テストエージェント → オーケストレーター）

§10 は「重大な不具合や仕様不明点はオーケストレーターへ報告する」とのみ述べる。判定可能な粒度へ落とす。

| # | 条件 | 判定の目安 |
| --- | --- | --- |
| E-1 | 期待動作が判定できない | 完了条件にも設計にも書かれておらず、何が正しいか決められない（§10「仕様不明点」） |
| E-2 | 重大な不具合 | データ破損、セキュリティ、ゴールの中核機能が動作しない（§10「重大な不具合」） |
| E-3 | 不具合の原因が実装ではなく設計・要件にある | 実装は設計どおりだが期待動作にならない |
| E-4 | 修正の反復が収束しない | 論点 B の上限に達した |
| E-5 | 検証環境が無く、検証自体が実施できない | 必要なリソースの不足（01 の O-5 リソース管理へ） |

## 確定事項（既存決定と調査からの導出）

以下 A〜C は、01〜04 で確定済みの内容と整合させることで一意に決まるため、PO へ改めて問わずに確定させる。異論があれば差し戻すこと。

### A. テスト失敗時のフロー（§22-7）

| 状況 | 行き先 |
| --- | --- |
| 実装の不具合 | 実装エージェントへ（O-2 不具合レポート） |
| 実装は設計どおりだが期待動作にならない | オーケストレーターへ（E-3）。設計側の問題 |
| 期待動作が判定できない | オーケストレーターへ（E-1）。完了条件・設計の不備 |
| 修正が収束しない | オーケストレーターへ（E-4）。確定事項 B の上限 |

**レビュー通過後にテストが落ちた場合、レビューへは戻さない。** テストが検出したのは動作の不具合であり、レビューの判定誤りとは限らない。実装エージェントが修正し、再テストする。ただし同種の不具合が繰り返しレビューをすり抜ける場合は、レビュー観点の不備としてオーケストレーターへ報告する。

### B. 不具合フィードバックの経路と反復上限

**テスト → 実装 の直接通信を許可する。** §14 の例外に追加する（02 で「実装 → 設計」を追加したのと同じ構造）。要件定義書 v0.1 §14 への追加であり、次版へ反映すること。

理由: テストの不具合レポートは、レビューの修正要求（§14 が既に許可）と同じ性質——実装への差し戻しであり、設計や要件を変えない。オーケストレーターを経由させる利得がなく、往復のコストだけが増える。

**反復上限は 2往復**（04 確定事項 B と揃える）。2往復して同じ不具合が解消しない場合、原因が実装ではなく設計・要件にある可能性が高い（E-3 / E-4）。

ただしレビューと異なり、テストの判定は客観的である（テストが通るか落ちるか）。04 が対処した「評価者が良し悪しを判別できず循環する」問題（00 §2.3）は起きにくい。上限は、収束しない修正を検知するための安全弁として置く。

### C. 不具合の重大度

04 と同じ **Blocker / Major / Minor** を用いる。体系を分けると、オーケストレーターが2種類の尺度を突き合わせて優先順位を決めることになり、判断が複雑になる。

| 重大度 | テストでの意味 |
| --- | --- |
| **Blocker** | 完了条件を満たさない／データ破損／セキュリティ／中核機能が動作しない |
| **Major** | 副次的な機能の不具合、境界条件での誤動作 |
| **Minor** | 実害の小さい挙動の差異 |

合格条件は 04 と同じく **Blocker と Major が0件**。

### D. TDD を既定とし、実行順序を「テスト先行 → 実装 → テスト実行 → レビュー」とする — **確定**

#### 標準フロー（TDD 適用タスク）

```
1. オーケストレーター    タスクに完了条件を書く
2. テストエージェント    完了条件を受け入れテストへ変換する（この時点では落ちる）
3. 実装エージェント      テストが通るまで実装する（単体テストも書く）
4. テストエージェント    受け入れテストを実行し、判定する
5. レビューエージェント  レビューする
```

#### TDD を既定にする理由

**完了条件の曖昧さを、実装が始まる前に検出できる。** テストへ変換できない完了条件は、そもそも判定不能な完了条件である。従来なら実装が終わってレビュー・テスト段階で初めて発覚し、手戻りになっていた。01 の確定事項 A で `完了条件` をタスク項目へ追加した価値が、ここで最大化される。

副次的に、レビューとテストの順序問題（当初の論点 D）も解消する。テストが落ちている実装をレビューしても、修正後に再レビューが必要になるだけで無駄が出る。テストが先に判定を出すため、**レビューは動作するコードに対してのみ行われる**。並列実行より総コストが小さく、§4.5 と整合する。

§20 のワークフロー図は実装 → レビューと実装 → テストを並列に描いているが、上記フローへ改める。要件定義書 v0.1 §20 に対する変更であり、次版へ反映すること。

#### TDD 適用外

探索的なタスク、UI の見た目の調整、設定変更など、事前にテストを書けない作業はある。この場合、**オーケストレーターがタスク分解時に「TDD 適用外」と明示する**。適用外タスクの順序は 実装 → テスト → レビュー とする（レビューを最後に置く理由は同じ）。

判断を実装・テスト側に委ねず、オーケストレーターがタスク単位で決めるのは、適用可否の判断が「そのタスクが何を達成するか」に依存し、タスク分解時点で最も見えているためである。
