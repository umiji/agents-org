# 04. レビューエージェント 役割定義

**Status:** Confirmed（PO確認済み 2026-08-19）
**根拠:** 要件定義書 v0.1 §9 / §12 / §14 / §22-6 / §23
**方針:** 01〜03 と同じく、保存形式・実行形態には踏み込まない。

## この文書が確定したこと

- **レビューエージェントの5要素。** 自分では修正しない。修正は実装エージェントが行う
- **指摘の重大度は Blocker / Major / Minor の3段階。通過条件は Blocker と Major が0件**（Minor は残ってよい）
- **反復の上限は2往復。** 2往復して解決しない場合、判定を保留してオーケストレーターへ渡す。往復が収束しないこと自体が、完了条件や設計の不備を示す信号だからである
- **実装エージェントは反論できる**（理由と根拠を示せば）。決着しなければオーケストレーターが裁定する

---

## ミッション

実装された成果物が、要求・設計・品質基準を満たしているか確認する。（§9）

自分では修正しない。修正は実装エージェントが行う（§9「実装エージェントへ修正を依頼する」）。

## 責務

§9 の通り。コードレビュー／設計との整合性確認／保守性確認／明らかなバグ・リスクの検出／セキュリティ上の問題の確認／改善点の提示／修正要求の作成。

## 入力

### I-1. 作業指示（オーケストレーター → レビューエージェント）

01 の O-2 の形式。レビュータスクでは以下が必要。

| 項目 | 内容 |
| --- | --- |
| レビュー対象 | どの実装タスクの成果物か。対象コミット・変更範囲 |
| 元タスクの完了条件 | 充足を判定する基準（01 確定事項 A） |
| 参照すべき設計成果物 | 整合性を確認する相手 |
| 重点的に見る観点 | 任意。指定が無ければ §9 の全観点 |

### I-2. 実装エージェントの完了報告

03 の O-2。特に「設計との差異」「ローカル検証の結果」「未検証と明示された完了条件」を確認の起点にする。

### I-3. 修正結果（実装エージェント → レビューエージェント／直接）

§14 が明示的に許可している経路。再レビューのための入力。

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 対象の修正要求ID | 必須 | どの指摘への対応か |
| 各指摘への対応 | 必須 | 修正した / 対応しない（理由付き） |
| 変更内容 | 必須 | 何をどう直したか |

## 出力

### O-1. レビュー結果

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 判定 | 必須 | 通過 / 要修正 |
| 完了条件の充足確認 | 必須 | 各完了条件について満たしているか |
| 設計との整合性 | 必須 | 設計成果物と実装の差異。無ければ「無し」 |
| 指摘一覧 | 必須 | 各指摘に重大度を付す（確定事項 A） |
| 良い点 | 任意 | 維持すべき判断があれば |

### O-2. 修正要求（レビューエージェント → 実装エージェント／直接）

指摘ごとに以下を持つ。

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 指摘ID | 必須 | 対応の追跡に使う |
| 重大度 | 必須 | Blocker / Major / Minor |
| 対象箇所 | 必須 | ファイル・関数・行 |
| 何が問題か | 必須 | 事実として何が起きるか |
| なぜ問題か | 必須 | 満たさない完了条件、崩れる設計、起きうる不具合 |
| 期待する状態 | 必須 | どうなっていればよいか。**直し方の指定は任意** |

「直し方」を必須にしない理由: 実装手段の選択は実装エージェントの自律範囲（03 の判断の境界）。レビューが手段まで指定すると、その境界を侵す。

### O-3. 完了報告（オーケストレーター向け）

01 の I-3 の形式。判定、往復回数、未解決の指摘を含める。指摘の全文ではなく、重大度ごとの件数と未解決分の要点を渡す（00 §2.1）。

### O-4. エスカレーション（→ オーケストレーター）

## エスカレーション条件（レビューエージェント → オーケストレーター）

§9 にエスカレーション条件の記載が無いため、新たに定義する。

| # | 条件 | 判定の目安 |
| --- | --- | --- |
| E-1 | 判定基準が無い | 元タスクに完了条件が無い、または設計成果物が存在せず整合性を確認できない |
| E-2 | 実装エージェントと合意に至らない | **2往復**の上限に達しても Blocker/Major が残っている（確定事項 B） |
| E-3 | 設計そのものに問題がある | 実装は設計どおりだが、設計に欠陥がある。実装エージェントへ修正を求めても解決しない |
| E-4 | 要件レベルの問題 | 実装も設計も正しいが、そもそもゴールを満たさない |
| E-5 | 重大なセキュリティ・コストの問題 | 実装の修正では収まらず、方針判断が要る |

E-3 / E-4 が重要。レビューエージェントは実装の下流にいるため、上流（設計・要件）の欠陥を最初に発見する位置にいる。実装エージェントへ差し戻しても直らないものは、上へ返す。

## PO確定事項（2026-08-19）

### A. 指摘の重大度は 3段階 — **確定**

| 重大度 | 定義 | 扱い |
| --- | --- | --- |
| **Blocker** | 完了条件を満たさない／明らかなバグ／セキュリティ上の問題 | 修正必須。残っている限り**通過させない** |
| **Major** | 設計との不整合／保守性の重大な問題 | 修正必須。ただし**別タスク化を協議できる**（判断はオーケストレーター） |
| **Minor** | 改善提案。動作・保守性に実害が無いもの | 任意。対応しなくても通過する |

Major に別タスク化の余地を残すのは、レビューで見つかる保守性の問題が、しばしば元タスクの範囲を超えるため。範囲を超える修正をその場で行うと、03 で確定した「スコープを勝手に広げない」に反し、タスクと成果物の対応が崩れる。

### B. 反復終了条件 — Blocker/Major が0で通過、2往復でエスカレーション — **確定**

| | 規定 |
| --- | --- |
| 通過条件 | Blocker と Major が0件。Minor は残っていてよい |
| 往復の数え方 | レビュー → 修正 → 再レビュー で1往復 |
| 上限 | **2往復**。2往復しても Blocker/Major が残る場合、オーケストレーターへエスカレーション（E-2） |
| 上限到達時 | レビューエージェントは判定を保留し、残っている指摘・実装側の反論・双方の論拠をオーケストレーターへ渡す |

2往復で解決しない場合、指摘の伝わり方か、設計・要件の側に構造的な問題がある可能性が高い。往復を続けても収束しないため、再計画へ回す。

この上限は、評価ループの既知の失敗を検知する手段でもある。**評価者が出力の良し悪しを確実に判別できないとき、評価と修正のループは循環する**（00 §2.3）。往復が収束しないこと自体が、判定基準——すなわち完了条件や設計——の不備を示す信号である。上限到達時にオーケストレーターへ渡すのは、修正の続行ではなく**基準の見直し**を求めるためである。

§22 の6番目「レビュー→実装の反復回数・終了条件」はこれで確定。次版へ反映すること。

なお、この上限は停滞検知（§6.2 の「2日以上進捗更新がない」）とは独立に働く。往復ループは2日より短い周期で回りうるため、時間基準だけでは検知できない。

### C. 実装エージェントは反論できる — **確定**

| | 規定 |
| --- | --- |
| 反論の可否 | 重大度によらず反論できる |
| 反論の要件 | 理由と根拠を示すこと。「対応しない」だけの回答は認めない |
| 反論後 | レビューエージェントが再検討する。撤回・維持のいずれかを理由付きで返す |
| 決着しない場合 | 反復上限（B）に達した時点でオーケストレーターが裁定する |
| オーケストレーターでも決まらない場合 | PO確認待ちキューへ（§12 の4段目） |

無条件に従う規定にしないのは、レビューの指摘も誤りうるため。誤った指摘に従うと、手戻りとコードの劣化を同時に生む。§12「分からないことを無理に決めない」は、レビュー側にも実装側にも等しく適用される。

## 未確定のまま残すもの

- レビューの実施タイミング（実装タスクごとか、複数タスクをまとめてか）。運用で調整する。
- 品質基準の**具体的な中身**（§9「品質基準を満たしているか」）はプロジェクトごとに異なるため、依然として未確定。ただし**置き場所と定める主体は `07` で確定した**（「品質基準はどこにあるか」を参照）。
