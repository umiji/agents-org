# 04. レビューエージェント 役割定義

**Status:** Draft（PO確認待ち）
**根拠:** 要件定義書 v0.1 §9 / §12 / §14 / §22-6 / §23
**方針:** 01〜03 と同じく、保存形式・実行形態には踏み込まない。

---

## ミッション

実装された成果物が、要求・設計・品質基準を満たしているか確認する。（§9）

自分では修正しない。修正は実装エージェントが行う（§9「実装エージェントへ修正を依頼する」）。

## 責務

§9 の通り。コードレビュー／設計との整合性確認／保守性確認／明らかなバグ・リスクの検出／セキュリティ上の問題の確認／改善点の提示／修正要求の作成。

---

## 入力

### I-1. 作業指示（オーケストレーター → レビューエージェント）

01 の O-2 の形式。レビュータスクでは以下が必要。

| 項目 | 内容 |
| --- | --- |
| レビュー対象 | どの実装タスクの成果物か。対象コミット・変更範囲 |
| 元タスクの完了条件 | 充足を判定する基準（01 確定事項 A） |
| 参照すべき設計成果物 | 整合性を確認する相手 |
| 重点的に見る観点 | 任意。指定が無ければ §9 の全観点 |

### I-2. 実装エージェントの完了報告

03 の O-2。特に「設計との差異」「ローカル検証の結果」「未検証と明示された完了条件」を確認の起点にする。

### I-3. 修正結果（実装エージェント → レビューエージェント／直接）

§14 が明示的に許可している経路。再レビューのための入力。

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 対象の修正要求ID | 必須 | どの指摘への対応か |
| 各指摘への対応 | 必須 | 修正した / 対応しない（理由付き） |
| 変更内容 | 必須 | 何をどう直したか |

---

## 出力

### O-1. レビュー結果

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 判定 | 必須 | 通過 / 要修正 |
| 完了条件の充足確認 | 必須 | 各完了条件について満たしているか |
| 設計との整合性 | 必須 | 設計成果物と実装の差異。無ければ「無し」 |
| 指摘一覧 | 必須 | 各指摘に重大度を付す（確定事項 A） |
| 良い点 | 任意 | 維持すべき判断があれば |

### O-2. 修正要求（レビューエージェント → 実装エージェント／直接）

指摘ごとに以下を持つ。

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 指摘ID | 必須 | 対応の追跡に使う |
| 重大度 | 必須 | Blocker / Major / Minor |
| 対象箇所 | 必須 | ファイル・関数・行 |
| 何が問題か | 必須 | 事実として何が起きるか |
| なぜ問題か | 必須 | 満たさない完了条件、崩れる設計、起きうる不具合 |
| 期待する状態 | 必須 | どうなっていればよいか。**直し方の指定は任意** |

「直し方」を必須にしない理由: 実装手段の選択は実装エージェントの自律範囲（03 の判断の境界）。レビューが手段まで指定すると、その境界を侵す。

### O-3. 完了報告（オーケストレーター向け）

01 の I-3 の形式。判定、往復回数、未解決の指摘を含める。

### O-4. エスカレーション（→ オーケストレーター）

## エスカレーション条件（レビューエージェント → オーケストレーター）

§9 にエスカレーション条件の記載が無いため、新たに定義する。

| # | 条件 | 判定の目安 |
| --- | --- | --- |
| E-1 | 判定基準が無い | 元タスクに完了条件が無い、または設計成果物が存在せず整合性を確認できない |
| E-2 | 実装エージェントと合意に至らない | 確定事項 B の反復上限に達した |
| E-3 | 設計そのものに問題がある | 実装は設計どおりだが、設計に欠陥がある。実装エージェントへ修正を求めても解決しない |
| E-4 | 要件レベルの問題 | 実装も設計も正しいが、そもそもゴールを満たさない |
| E-5 | 重大なセキュリティ・コストの問題 | 実装の修正では収まらず、方針判断が要る |

E-3 / E-4 が重要。レビューエージェントは実装の下流にいるため、上流（設計・要件）の欠陥を最初に発見する位置にいる。実装エージェントへ差し戻しても直らないものは、上へ返す。

---

## PO判断が必要な点

### A. 指摘の重大度分類を設けるか

全ての指摘を同格に扱うと、些細な改善提案でも往復が発生し、レビュー→実装のループが止まりにくくなる。一方で分類を設けると、レビューエージェントが重大度を判定する必要が生じる。

ドラフトでは 3段階（Blocker / Major / Minor）を前提に書いた。

### B. レビュー → 実装の反復終了条件（§22-6）

無限ループを防ぐ規定が必要。何回往復してよいか、上限に達したらどうするか。

### C. 実装エージェントは指摘に反論できるか

レビューの指摘が誤っている場合がある。無条件に従う規定にすると、誤った指摘で品質が下がる。反論を認める場合、合意に至らないときの裁定者を決める必要がある。
