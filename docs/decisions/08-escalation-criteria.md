# 08. エスカレーション・クライテリア

**Status:** Confirmed（既存決定からの導出 2026-08-20）
**根拠:** 要件定義書 v0.1 §12 / §13 / §22-5 / §23-8
**前提:** ロール別のエスカレーション条件（E-*）は 01〜06 で確定済み。本ファイルは**横断的な規約**——いつ上げるか、どう上げるか、上げた後どうなるか——を定める。

---

## 本ファイルが埋める空白

01〜06 は「何を上げるか」を条件表（E-1〜E-6）で確定した。残っているのは以下である。

1. §12 の4段階を、各段で**何をどれだけ試したら次へ上がるか**が判定できる形にする
2. 全ロール共通の**停止条件**（ロール固有の条件では拾えないもの）
3. PO確認待ちキューの**実体と運用**
4. PO の回答をどう組織へ還元するか

---

## §12 の4段階を判定可能にする

§12 は優先順位だけを定めている。各段の**打ち切り条件**が無いと、上げなさすぎ（推測で決めて誤った前提のまま完成させる）と上げすぎ（些末な確認を全部投げる）の両方が起きる。

| 段 | やること | 次へ上がる条件（＝この段の打ち切り） |
| --- | --- | --- |
| **1. 自分で解決** | 作業指示、参照すべき成果物、既存コード、`docs/decisions/` の確定事項を確認する | これらを確認しても**答えが一意に定まらない**。または、定まるが自分の「判断してよい範囲」の外にある |
| **2. 許可された他エージェントへ相談** | §14 の例外経路が存在する場合のみ。**1往復まで** | 相手が答えられない、または相手も判断できないと返した |
| **3. オーケストレーターへ上げる** | ロール別の E-* に沿って報告する | オーケストレーターが 01 の E-1〜E-6 に該当すると判断した |
| **4. PO確認待ちキューへ登録** | オーケストレーターが §13 の形式で登録する | — |

### 段1の打ち切り基準を「時間」ではなく「情報源」で定める理由

エージェントは実時間を体感できず、「15分考えても分からなければ」のような基準は機能しない。代わりに**参照すべき情報源を尽くしたか**で切る。上表の4つ（作業指示・参照成果物・既存コード・確定済み決定記録）を確認して定まらなければ、それ以上は推測になる。

**推測で埋めて着手しない。** 差し戻しのコストは、誤った前提で完成させたものを捨てるコストより常に小さい（01）。00 §2.2 の **Incomplete Context Transfer** は、曖昧な指示を受けたエージェントがエラーを上げずに進むことで起きる。段1の打ち切りを明確にすることが、その対策の実行部分である。

### 段2が使える経路（§14 の例外、確定済みのすべて）

| 経路 | 許可範囲 | 確定した場所 |
| --- | --- | --- |
| レビュー → 実装 | 修正要求と修正結果の往復。**2往復まで** | §14 本文、04 確定事項 B |
| 実装 → 設計 | **軽微な問合せに限る。** 設計変更を伴うものはオーケストレーター経由 | 02 確定事項 C |
| テスト → 実装 | 不具合レポートと修正の往復。**2往復まで** | 05 確定事項 B |

**この3つ以外に直接通信は無い。** 経路を増やすには §14 の例外として組織規約へ追記する必要がある（12 参照）。ここに摩擦を残すのは意図的である——サブエージェント間の自由な通信は MVP で行わない（§14）。

段2で**迷ったらオーケストレーター経由**（安全側）。02 確定事項 C が実装→設計について定めた原則を、全経路へ適用する。

## 全ロール共通の停止条件

ロール別の E-* に加え、**どのロールでも、以下に該当したら作業を止めてオーケストレーターへ上げる**。ロール固有の条件は「自分の専門領域で判断できないこと」を拾うが、以下はそれとは別種——**専門領域の話ではなく、進めてよいかどうかの話**である。

| # | 条件 | なぜ止めるか |
| --- | --- | --- |
| S-1 | 仕様・指示・設計のどれかが**互いに矛盾している** | どちらに従っても、もう一方に違反する。選ぶこと自体が判断である |
| S-2 | **既存データを削除する／破壊的である**、または DB マイグレーションが既存データへ及ぼす影響を伴う | 取り返しがつかない。01 の E-6（セキュリティ・コスト・外部影響）と同じ理由 |
| S-3 | 作業開始時点で、**作業ツリーに未確認の差分がある** | 誰かの未完了の作業を巻き込む。着手前に `git status` を確認する |
| S-4 | 作業がタスクの `変更範囲` / `禁止事項` を**超える** | 03「スコープを勝手に広げない」の実行条件。範囲を超えるとレビュー・テストの判定が成立しなくなる |
| S-5 | 完了条件そのものが**実現不能**と判明した | 前提が崩れている。作業を続けても完了しない（03 の B-6） |
| S-6 | 作業指示に**必須項目が欠けている**（完了条件が無い、判断してよい範囲が無い、参照すべき成果物が実在しない） | 01「受け取った側は、着手前に指示の充足を確認する」。着手前に差し戻す |

S-1〜S-4 は task-cycle の停止条件を本組織向けに言い換えたもの（07 の D-9）。S-5 / S-6 は 01・03 で確定済みの内容を共通条件として引き上げた。

**タスク固有の停止条件**がある場合は、タスク別ファイルの `## 停止条件` に書く。無ければ「08 の共通停止条件のみ」と明記する（07）。

## PO確認待ちキュー

### 実体

開発対象リポジトリの `docs/po-queue.md`。1つの質問を `Q-###` で識別する。

タスクリストを CSV+Markdown に分けた（07）のに対し、こちらは**1ファイルの Markdown で足りる**。理由: 件数がタスクほど増えず（増えていたら、それ自体が組織の異常である）、書き手はオーケストレーターだけなので衝突せず、PO が人間として通しで読むものだからである。**索引と本体を分ける利得が出ない規模には、分ける仕組みを入れない**（§4.1）。

### 項目（§13 の6項目 + 01 の追加）

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| Q-ID | 必須 | `Q-###`。連番。再利用しない |
| 登録日 | 必須 | `YYYY-MM-DD` |
| 状態 | 必須 | `未回答` / `回答済み` / `取り下げ` |
| 質問・判断事項 | 必須 | 何を決めてほしいか |
| なぜ判断が必要か | 必須 | 組織で決められない理由（01 の E-1〜E-6 のどれに当たるか） |
| 選択肢 | 必須 | 各案。無ければ「選択肢を提示できない」と理由を書く |
| 各選択肢のメリット・デメリット | 必須 | |
| 推奨案 | 必須 | オーケストレーターとしての推奨と、その理由 |
| 回答がない場合に影響するタスク | 必須 | ブロックされるタスクID |
| **待つ間も進められるタスク** | 必須 | 01 の O-3 で追加。§13 を実際に守るため |
| 回答 | 回答後 | PO の結論と補足 |

`待つ間も進められるタスク` を必須にするのは、§13「POの回答を待っている間も、依存関係のないタスクは継続して実行する」を宣言で終わらせないため。**登録時に書けなければ、組織全体が止まっているということであり、それ自体が報告に値する事実である。**

### タスクとの結び付け

| 方向 | 手段 |
| --- | --- |
| タスク → 質問 | タスク別ファイルの `## ブロッカー` に `Q-XXX` を書く。CSV の状態を `PO確認待ち` にする |
| 質問 → タスク | `回答がない場合に影響するタスク` にタスクIDを書く |

両方向に辿れるようにするのは、10 の指標（PO確認待ち件数、ブロック中タスク数）を索引だけで数えられるようにするためと、回答が来たときに戻すべきタスクを探し直さずに済むようにするためである。

### PO への問い合わせはオーケストレーターだけが行える

方針ではなく**技術的制約**である。サブエージェントは `AskUserQuestion` を使えない（00 §1.1）。したがって PO と直接やりとりできるのはメインセッションだけであり、キューの一元管理は必然である（01）。

各エージェントが「PO に聞きたい」と考えた場合、必ず段3（オーケストレーター）を経由する。

## 回答の還元 — 一度の回答を、以後の判断基準にする

PO の回答は、そのタスクを解いて終わりではない。**同じ問いが二度上がることを防ぐところまでが処理である。**

| 回答を受けたら | 行き先 |
| --- | --- |
| 1. `docs/po-queue.md` の Q を `回答済み` にし、回答を記録する | po-queue |
| 2. 影響していたタスクの `## 決定ログ` へ、決定・却下案・出典を転記する | タスク別ファイル |
| 3. タスクの状態を `PO確認待ち` から適切な工程へ戻す | CSV |
| 4. **回答が個別の判断を超えて一般的な基準になっている場合、層2へ昇格させる** | 開発対象リポジトリの `CLAUDE.md` / `.claude/rules/` |

段4がこの節の主眼である。01 の I-2 が「補足・理由」を「以後の類似判断の基準になる」と位置づけ、06 確定事項 D がオーケストレーターに層2の保守を課している。両者はここで繋がる。

**昇格させる判断の目安**: 同じ種類の問いが2回以上上がった、または回答が「このプロジェクトでは常に X する」という形をしている。

昇格先の選び方は 00 §1.2 に従う——常に必要な**事実**は `CLAUDE.md`、トピック別・パス限定は `.claude/rules/`、**手順**に育ったものは Skills。CLAUDE.md は200行を超えると遵守率が落ちるため、超えそうなら分割する。

## 上げすぎを防ぐ — 上げないものの一覧

各ロールの「上げないもの」は 01・02 で個別に定めた。横断的にまとめる。

| 上げない | 決める主体 |
| --- | --- |
| 実装手段の選択（命名、ファイル分割、関数の構造、ライブラリ内の書き方） | 実装エージェント（03） |
| 技術的優劣で決着がつく複数案 | 各ロールが自分で決める（02） |
| 既に `docs/decisions/` で確定済みの事項の再検討 | 誰も蒸し返さない（02） |
| タスクの分割方法、担当エージェントの割り当て、優先順位の調整 | オーケストレーター（01） |
| レビュー指摘への対応方針 | オーケストレーター（01） |
| レビュー指摘そのものへの反論 | 実装エージェントが理由と根拠を付して直接返す（04 確定事項 C） |

**「判断してよい範囲」がタスクに書かれている以上、その範囲内のことは上げない。** 逆に、範囲が書かれていないタスクは S-6 で差し戻す。境界が明示されていない状態でエージェントに自制を求めても機能しない。

## エスカレーションが多すぎるとき

これは個々のエージェントの問題ではなく、**組織側の信号**である。オーケストレーターは以下を疑う。

| 症状 | 疑うべき原因 |
| --- | --- |
| 同じ論点が複数のタスクから上がる | 層2（CLAUDE.md / rules）に判断基準が書かれていない。上記「回答の還元」の段4を怠っている |
| 特定のロールからばかり上がる | そのロールへの作業指示が不足している（完了条件・判断範囲・参照成果物） |
| 段1で解決すべきものが上がってくる | 「判断してよい範囲」が狭すぎるか、書かれていない |
| PO確認待ちが増え続ける | ゴール達成条件が確定していない。01 の E-1 に該当する可能性が高い |

最後の行が最も重い。**PO確認待ちの件数は §6.2 の健全性指標であり、10 で判定に使う。** 増加傾向そのものが、ゴールの分解が誤っているという信号になりうる。

## 未確定のまま残すもの

- PO確認待ちの滞留に対するリマインド間隔。09 で停滞管理と併せて扱うが、PO の応答速度に依存するため運用で調整する
- `docs/po-queue.md` が長くなった場合の分割方針。件数が増えていること自体が異常なので、分割の仕組みを先に作らない
