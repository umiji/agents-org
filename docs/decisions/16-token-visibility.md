# 16. トークン消費の可視化

**Status:** Confirmed（PO 指示により確定 2026-08-25）
**根拠:** 要件定義書 v0.2 §4.5（単純な繰り返し処理はスクリプトへ）/ §18（独自設定ファイルを作らない）、`00` §2.1（オーケストレーターのコンテキスト膨張）、`07`（タスク管理仕様）、`13`（実行形態と配置）
**position:** §23 の12項目には無い。PO が新たに出した要求として確定させた。

## この文書が確定したこと

- **可視化するのはトークン消費量であって、金額ではない。** PO は Claude Code の定額プランを使っており、金額は請求と対応しない。**枠内でこなせるタスクを増やす**ことが目的である
- **新しい記録の仕組みは作らない。** Claude Code が既に書き出している会話記録を読む
- **タスクへの紐付けは、指示文に書かれたタスクIDから拾う。** 担当エージェント分は正確、オーケストレーター分は近似
- **記録はタスク台帳とは別のファイルに置く**（`docs/token-usage-{project-name}.csv`）
- **記録の更新はフックで自動的に行う。** 規約に書くだけでは実行されない回が出る
- **削減策は、この文書では決めない。** 数タスク分の実測が溜まるまで、何が効くかは分からない

---

## A. なぜ金額ではなく量なのか — PO確定

PO の要求は次のとおり（2026-08-25）。

> 現状 Claude Code のサブスクリプションプランを使っているが、その1週間・1日の利用制限枠の中でできる限り実行できるタスクを増やしたい。

定額プランでは、消費したトークンに対して金額が請求されるわけではない。**制約は金額ではなく枠**である。したがって金額へ換算しても、判断に必要な情報は増えない。

### 採らなかった案

| 案 | 却下理由 |
| --- | --- |
| 公開されている単価で金額へ換算して出す | 請求額と対応しないため、数字が独り歩きする。「$50 使った」と出ても、それが枠のどれだけを食ったのかは分からない |
| 消費枠に対する残量（何%使ったか）を出す | 枠の換算式が公開されていない。**推測で埋めない**という本リポジトリの原則に反する |

### 未確定のまま残す

**金額への換算は今後の課題として残す。** 従量課金へ移る、あるいは他人へコストを説明する必要が出たときに要る。そのときは次の3点を確定させること。

1. モデル別の単価表をどこに置くか（**独自の設定ファイルを作らないという制約に触れる論点である**。単価は改定されるため、スクリプトへ直接書くと古くなる）
2. キャッシュ書込の保持時間（5分 / 1時間）ごとの倍率。会話記録には内訳が残っているので、分けて数えれば出せる
3. 定額プランと従量課金のどちらの前提で出すか

## B. データの出どころ — 新しい記録の仕組みを作らない

Claude Code は会話記録を、1行1イベントの JSONL 形式で次の場所へ書き出している。

```
~/.claude/projects/<作業ディレクトリを符号化した名前>/
    <セッションID>.jsonl              メインセッション（オーケストレーター）
    <セッションID>/subagents/
        agent-XXXX.jsonl              担当エージェント1体分の会話
        agent-XXXX.meta.json          その担当エージェントの種別（agentType）
```

モデルの返答1回ごとに、使ったトークン数が4種類（新規入力・出力・キャッシュ書込・キャッシュ読出）に分かれ、モデル名と一緒に記録されている。**担当エージェント別・モデル別の集計は、こちらで何も仕込まなくてもこの構造だけで取れる。**

これは要件定義書 §4.5（単純な繰り返し処理はスクリプトへ切り出し、LLM のトークンは判断・設計・問題解決に使う）にそのまま当てはまる。集計にトークンを使っては本末転倒である。

### 置き場の特定に、ディレクトリ名の規則を使わない

`<作業ディレクトリを符号化した名前>` の符号化規則は推測しない。**同じパスでも大文字小文字が違うだけで別のディレクトリになっている実例が、この環境に実在する**（`C--Users-...` と `c--Users-...`）。規則から組み立てると取りこぼす。

代わりに、記録の中に入っている `cwd`（そのセッションの作業ディレクトリ）を読んで突き合わせる。これは記録そのものが持つ事実なので、Claude Code 側の符号化規則が変わっても壊れない。

## C. タスクへの紐付け — 指示文から拾う（PO確定）

「このトークンは T-007 のもの」という情報は会話記録に無い。3案を PO へ提示し、**A案（指示文から自動で拾う）**が選ばれた。

| 案 | やり方 | 利害 |
| --- | --- | --- |
| **A（採用）** | 指示文に書かれたタスクIDを正規表現で拾う | 記録の手間がゼロ。既にある制約を利用するので破綻しにくい |
| B | タスク別ファイルへ、担当エージェントの識別子を手で書き残す | 正確だが、書き忘れると穴が空く。層2の `CLAUDE.md` は実行を強制できない |
| C | フックで、担当エージェントの終了時に記録する | 書き忘れが起きない。ただし記録の追記処理を自前で持つことになる |

A が成り立つ根拠は、**担当エージェントへの指示が自己完結でなければならない**という制約（`00` §1.2 — 子プロセスとして起動されるエージェントは会話履歴を継承しない）である。「さきほどの方針で」が通じない以上、指示文にはタスクIDが書かれる。**制約を守っていれば紐付けも成立するという構造**になっており、別途の努力を要求しない。

### 精度の非対称を明示する

| 対象 | やり方 | 精度 |
| --- | --- | --- |
| 担当エージェント | 記録の**先頭の指示文だけ**を見て、最初のタスクIDを採る | **正確** |
| オーケストレーター | 時系列に読み、タスクIDが現れたら以降の返答をそのタスクへ帰属させる。次のIDで切り替える | **近似** |

先頭の指示文だけを見るのは意図的である。以降の会話には、読み込んだファイルの中身（他のタスクの記録など）が入っており、そこまで見ると取り違える。

オーケストレーター側が近似になるのは避けられない。1つのセッションが複数タスクを横断し、切れ目が記録に残らないためである。**「どのタスクが重かったか」の比較には十分効くが、1トークン単位の正確な帰属ではない。** 最初のタスクIDが現れる前の分は `タスク外` に入れる——組織の運営そのものにどれだけ使っているかも、これで見える。

## D. 記録の置き場 — タスク台帳とは別ファイル（PO確定）

PO の要求は次のとおり。

> ORG は他プロジェクトに入った場合タスクリストを作成するはずだが、そのリストとは別でタスクIDとコスト、内訳などをまとめておく表があったほうが管理が楽かな。

`docs/token-usage-{project-name}.csv` に置く。索引の CSV（`docs/task-list-{project-name}.csv`）と同じ名前の付け方にそろえる。

**別ファイルにする理由は、書く主体が違うことである。** タスク台帳は「何をやるか」の記録で、**オーケストレーターだけが書く**と `07` で決まっている。トークン台帳は「いくら食ったか」の記録で、スクリプトが機械的に上書きする。混ぜると、集計が走るたびにタスク台帳の差分が汚れ、誰が何を書き換えたのかが追えなくなる。

列は12個。

```
タスクID, 担当, モデル, 入力, 出力, キャッシュ書込, キャッシュ読出, 合計, 返答回数, セッションID, 記録元, 最終更新
```

1行の粒度は **(セッション, 記録元, タスクID, モデル)** である。この粒度にしたのは、モデル別（Haiku / Sonnet / Opus のどれを使ったか）を見たいという PO の要求に応えるためと、更新を冪等にするためである。

### 独自の設定ファイルを作らないという制約に触れないか

触れない。これは**設定**ではなく**組織の状態の記録**である。要件定義書 §22-12 のマッピング表で、組織の状態（タスク・PO確認待ち・引き継ぎ）は開発対象リポジトリの `docs/` 配下に置くと決めてある。トークン消費はその一種であり、既存の置き方に従っている。

## E. 更新のタイミング — フックで自動化（PO確定 = 案 (c)）

PO が選んだのは「フックで自動記録まで入れる」である。走る場面は2つ。

| Claude Code の呼び出し口 | 何のため |
| --- | --- |
| `SubagentStop`（担当エージェントが1体終わったとき） | その担当が使った分を、終わった時点で記録する |
| `SessionStart`（セッションが始まったとき） | 取りこぼしの回収。**過去のセッション分まで読み直す** |

2箇所に入れるのは取りこぼしを防ぐためである。担当エージェントの終了時に記録するのが本筋だが、セッションが異常終了した場合や、担当エージェントを使わなかった場合の分が落ちる。

**規約に書くだけでは足りない理由**は `00` の調査結果のとおり——層2の `CLAUDE.md` は読まれる文脈であって実行される設定ではない。「タスク完了時にトークンを記録せよ」と書いても、実行されない回が出る。

### 冪等であることが、この設計の前提である

フックは繰り返し呼ばれる。単純な追記にすると、担当エージェントが5体終わればメインセッション分が5回足し込まれる。

したがって**足し込みではなく置き換え**にした。同じ (セッション, 記録元) の行は毎回捨てて入れ直す。会話が伸びれば数字は増え、タスクの紐付けも後から変わりうる（タスクIDが遅れて登場した場合、それ以前の分の帰属が変わる）ため、置き換えのほうが正確でもある。

**会話記録が既に消えているセッションの行は、そのまま保存する。** 再計算できないものを黙って消すと、過去の消費が台帳から消える。

## F. 削減策は、この文書では決めない

PO の意図は最終的に「削減手法をスキルへ反映していく」ことにある。しかし**今スキルに書ける削減策は推測でしかない。**

この組織は実運用のタスクを1件も持っていない。何が支配的かは、数タスク分の実測が溜まってから決める。`06`（ドキュメントエージェント）で人間用ビューの生成スクリプトを後回しにしたのと同じ判断である——**検証できないものを先に作らない。**

### ただし、最初に疑う場所は既に見えている

過去の別プロジェクトのセッション1件を実測したところ、**消費の95%がキャッシュ読出**だった（1億2217万トークンのうち1億1637万）。出力は0.4%に過ぎない。

キャッシュ読出とは、モデルが返答するたびに、それまでの会話全体をもう一度読み込んでいる分である。**会話が伸びるほど1回あたりの消費が増える。** つまり削るべきは「モデルに書かせる量」ではなく「毎回読ませている量」である。

この組織の設計には既に対策が入っている——報告は要約とし、成果物はパス・コミットで参照させる（`00` §2.1 への対処）。**トークン計測は、その規約が実際に効いているかを数字で検証する道具になる。** 効いていなければ、1タスクあたりのキャッシュ読出量が右肩上がりになる。

オーケストレーターがタスク完了時に見るのは2点だけと決めた（`org/skills/org-orchestrate/`）。キャッシュ読出の割合と、他タスクと比べた大きさ。**分析にトークンを使っては本末転倒**であり、対策の判断は PO の領分である。

## 未確定のまま残すもの

| 論点 | 内容 |
| --- | --- |
| 金額への換算 | A の末尾のとおり。単価表の置き場が、独自設定ファイルを作らないという制約に触れる |
| 消費枠に対する残量 | 定額プランの枠の換算式が公開されていない。出せるようになったら指標として足す |
| ゴール健全性評価への組み込み | `10` の8指標へ「1タスクあたりのトークン消費」を9つ目として足すか。**数タスク分の実測が溜まってから判断する** |
| 停滞との関係 | 停滞しているタスクはトークンも食っているはずである。両者を突き合わせると早期の異常検知になりうるが、これも実測が先 |
