# 12. エージェント追加方式

**Status:** Confirmed（既存決定からの導出 2026-08-20）
**根拠:** 要件定義書 v0.1 §4.4 / §17 / §19 / §22-10 / §23-12
**目標:** §4.4 —「新しい専門エージェントは、極端に言えば定義ファイルを追加するだけで組織へ追加できる」

## この文書が確定したこと

- **「定義ファイルを1つ足すだけ」を成立させる条件**を特定した。鍵は**組織側でエージェント一覧を持たない**こと。一覧を自前で管理した瞬間、追加のたびに2箇所を直すことになる
- **エージェント定義の必須構成は5要素**（ミッション／責務／入力／出力／エスカレーション条件）。既存6ロールと同じ形
- **追加の手順は6段。** 定義ファイルを書く前に決定記録で5要素を確定させる段を飛ばさない
- **直接通信の経路を増やすときだけは摩擦を残す。** ファイル追加では済ませず、組織規約の変更として扱う
- **ロールを増やさない方が良い場合**も定めた。専門知識が要るだけならスキルを足す——ロールは責務の単位であって、知識の単位ではない

---

## 目標を成立させる条件

「定義ファイルを1つ足すだけ」が成立するのは、**追加時に既存ファイルを編集しなくてよい**ときだけである。何が編集を強制しうるかを潰す。

| 追加時に必要になりそうなこと | 既存ファイルの編集が要るか | 解 |
| --- | --- | --- |
| オーケストレーターが「どのエージェントがいるか」を知る | **要らない** | Claude Code はサブエージェント定義を自動的に認識し、`description` から用途を判断する（00 §1.1）。**組織側でエージェント一覧を持たない** |
| タスクの `担当` 欄に新しい値が入る | 要らない | CSV の `担当` は自由記述（07）。値の集合を定義していない |
| 新エージェントが読む組織共通の規約 | 要らない | **CLAUDE.md 階層はサブエージェントへ継承される**（00 §1.1）。エージェント定義ごとに規約を複写しない |
| 新エージェントの専門能力 | 要らない | Skills として独立したファイルで足す（§17.3） |
| 新エージェントとの**直接通信経路**を増やす | **要る**（§14 の例外リスト） | 後述。ここだけ意図的に摩擦を残す |

上表の1行目が要点である。**「どのエージェントがいるか」を組織が自前で管理しないことが、ファイル追加だけで済ませられる理由**であり、これは §4.1「Claude Code 標準機能を最大限使う」の具体的な帰結である。一覧を独自に持った瞬間、追加のたびに2箇所を直すことになり、§4.4 の目標が崩れる。

---

## エージェント定義の必須構成

01〜06 が確定した5要素を、そのままテンプレートにする。**新しいエージェントも同じ5要素で定義する。**

| 要素 | 内容 | 参照 |
| --- | --- | --- |
| **ミッション** | このロールが達成すること。1〜2文 | 01〜06 の冒頭 |
| **責務** | 担当すること。**および担当しないこと** | §6.3 が「やらないこと」を明示したのと同じ形 |
| **入力** | 何を、誰から受け取るか。情報項目のレベルで | 01〜06 の I-* |
| **出力** | 何を、誰へ返すか。情報項目のレベルで | 01〜06 の O-* |
| **エスカレーション条件** | 何を上げるか、**何を上げないか**。判定の目安付き | 01〜06 の E-* |

加えて、定義ファイルに書くもの:

| 項目 | 内容 |
| --- | --- |
| `description` | **オーケストレーターが割り当てを判断する唯一の材料。** 何を任せられるロールかを、他のロールと区別できる形で書く |
| 直接通信の可否 | 既定は**不可**（§14）。例外を持つなら、相手と許可範囲を明記 |
| 使用ツールの範囲 | 責務の外へ出られない構成にする（後述） |
| プリロードするスキル | 専門能力を分離した先（§17.3） |

### `description` の書き方

オーケストレーターは `description` を見て割り当てる。**曖昧な description は、割り当ての誤りとして表面化する。**

00 §2.1 は「3〜5個の明確に定義されたエージェントが、十数個の曖昧なエージェントより高性能」と記録している。ロールを増やすこと自体は利得ではない。**既存ロールとの境界が一文で言えないなら、そのロールは追加しない。**

境界の書き方は 02 確定事項 B（設計 vs ドキュメント）と 06（層2 vs 層3）が手本になる——「対象 / 読み手 / 書くこと」の3点で既存ロールと対比する。

### ツールの制限で責務を担保する

00 §1.1 の通り、`tools` / `disallowedTools` でサブエージェントのツールを制限できる。01 は既にこれを用いる方針を示している——**オーケストレーターから編集系ツール（Write / Edit 等）を外せば、実装は構造的に不可能になる**。00 §2.2 の **Failure to Delegate**（オーケストレーターが委譲せず自分で作業を続ける）への対策である。

新しいエージェントを足すときも同じ問いを立てる: **「このロールが責務を踏み越えるとしたら、どのツールを使うか。それは外せるか。」**

規約は破られるが、構成は破られない。

## 追加の手順

| # | やること | 主体 | 根拠 |
| --- | --- | --- | --- |
| 1 | 不足を検知する | オーケストレーター | §6.2 リソース管理 |
| 2 | PO へ提案する（不足しているもの / なぜ必要か / それが無いことで滞る作業 / 追加案） | オーケストレーター | 01 の O-5 |
| 3 | PO が承認する | PO | §12 の4段目 |
| 4 | **決定記録を書く**（`docs/decisions/` に 01〜06 と同じ形式で、5要素を確定させる） | PO と支援セッション | §23 の順序と同じ |
| 5 | エージェント定義ファイルを**1つ**追加する | | §4.4 |
| 6 | 必要なら Skill を追加する | | §17.3 |

**段4を飛ばさない。** 定義ファイルをいきなり書くと、入力・出力・エスカレーション条件が未確定のまま実装形式だけが決まる。本リポジトリが 01〜06 で踏んだ順序——ミッション → 責務 → 入力 → 出力 → エスカレーション条件——は、そのまま新ロールにも適用される（§23）。

段1と2は、既存ロールの誰も担当できないタスクが発生したときに起きる。**タスクの `担当` を決められないこと**が、リソース不足の最も分かりやすい検知経路である。

### 既存ファイルの編集が必要になったら、それを記録する

手順5で既存ファイルを触る必要が生じたら、それは §4.4 の構造が綻んだ箇所である。**黙って編集せず、何を編集したかと理由を決定記録へ残す。** 綻びが3回起きたら、構造の側を見直す。

## 直接通信の追加だけは摩擦を残す

§14 の例外リストへの追加は、組織規約の変更である。**定義ファイルの追加だけでは済ませない。**

現在の例外は3つ（08 に一覧）——レビュー→実装、実装→設計（軽微な問合せに限る）、テスト→実装。いずれも「実装への差し戻しであり、設計や要件を変えない」という共通の性質を持つ（05 確定事項 B）。

**新しい経路を足す条件:**

| 条件 | 内容 |
| --- | --- |
| 定型的である | §14 の「オーケストレーターが許可した定型的なワークフロー」に当たる。その場限りの相談ではない |
| 設計・要件を変えない | **書いてあることの読み方の確認だけが直接**。書かれていないことをする必要が出たらオーケストレーター経由（02 確定事項 C と同じ判定） |
| 反復上限がある | 04 / 05 が定めた **2往復**。収束しない往復を検知できること |
| オーケストレーターを通す利得が無いことを説明できる | 通す方が安全なのが既定。例外の側が理由を負う |

追加は §14 への変更として要件定義書へ反映し、層2（`CLAUDE.md` / `.claude/rules/`）へも書く。**ここに手間を残すのは意図的である**——サブエージェント間の自由な通信は MVP で行わない（§14）。追加が簡単だと、経路は必ず増える。

## 既存拡張との共存（§19）

Everything Claude Code / Superpowers 等が導入済みの環境で共存する前提（§4.6 / §19）。

| 規約 | 内容 |
| --- | --- |
| **名前空間** | 組織の定義は `org-` を前置する（`org-orchestrator`、`org-implementation` 等）。スキルも同様 |
| **既存を上書き・削除しない** | 既存の commands / skills / hooks を触らない |
| **hook は追記のみ** | 設定へ hook を足す場合、既存エントリを**置換せず追記**する。09 の停滞検知（SessionStart）が最初の例になる |
| **衝突したら組織側が譲る** | 名前が衝突した場合、既存拡張ではなく組織側の名前を変える |

`org-` プレフィックスは、独自の仕組みではなく**命名の約束だけ**で分離を達成している。§4.1 に従い、これ以上の隔離機構（独自のローダ、名前空間ファイル等）は作らない。

## スキル・MCP・外部ツールの追加（§17.2 / §17.3）

| 対象 | 方針 |
| --- | --- |
| **Skills** | 専門能力はスキルへ分離する。エージェント定義に長い手順を書かない。00 §1.2 —「CLAUDE.md の一節が事実ではなく手順に育ったら、それは skill にすべき」 |
| **MCP** | 後から追加できる構成にする。**特定の MCP に組織全体を強く依存させない**（§17.2）。あるロールが特定の MCP を要求する場合、その依存はそのロールの定義に閉じる |
| **外部ツール** | 不足の検知と提案は 01 の O-5（リソース管理）の経路に乗せる。エージェント追加と同じ手順1〜3 |

**MCP の不在は、エージェントの不在と同じ扱いで検知する。** §6.2 のリソース管理は「必要なMCPが存在しない」「必要な外部サービスへのアクセスがない」を明示的に挙げている。05 の E-5（検証環境が無く検証自体が実施できない）は、この経路へ乗る具体例である。

---

## ロールを増やさない方が良い場合

追加方式を定めた上で、逆向きの規約も置く。**追加が容易であることは、追加すべき理由にはならない。**

| 増やさず、既存で対応する | 理由 |
| --- | --- |
| 既存ロールとの境界が一文で言えない | 00 §2.1 — 曖昧なエージェントを増やすと性能が落ちる |
| 一度きりの作業のため | ロールは繰り返し現れる責務に対して作る。単発ならタスクとスキルで足りる |
| 既存ロールの負荷が高いだけ | 責務の分割ではなく、タスク分解の粒度（01 の O-0）を疑う |
| 専門知識が要るだけで、責務は既存と同じ | **Skill を足す**（§17.3）。ロールを増やさない |

最後の行が最もよく当たる。「セキュリティに詳しいエージェントが要る」の多くは、レビューエージェントにセキュリティレビューのスキルを足せば済む。**ロールは責務の単位であって、知識の単位ではない。**

## 未確定のまま残すもの

- エージェント定義ファイルの配置ディレクトリ。`.claude/agents/` が標準だが、既存拡張との衝突は導入先の環境を見てから確認する（`org-` プレフィックスで回避できる想定）
- ツール制限の具体（どのロールから何を外すか）。エージェント定義を書く段階で、ロールごとに決める
