# 18. 稼働状況のモニタ（簡易UI）

**Status:** Confirmed（PO 指示により確定 2026-08-25）
**根拠:** 要件定義書 v0.2 §3.3（MVP対象外は「**複雑な**Webダッシュボード」）/ §4.5（単純な繰り返し処理はスクリプトへ）/ §18（独自設定ファイルを作らない）、`00` §1.5（`CLAUDE.md` は強制力を持たない。必ず実行させたい処理は hook にする）、`16`（トークン消費の可視化。会話記録の読み方はここで確立済み）
**position:** §23 の12項目には無い。PO が新たに出した要求として確定させた。

## この文書が確定したこと

- **セッション開始時に、稼働状況を見せる画面を自動で立ち上げる。** 出すのは「動いている担当エージェント」「タスクの状態」「トークン消費」の3つだけ
- **立ち上げるのは hook であって、オーケストレーターではない**（PO が選択）
- **タスク台帳が無いセッションでは何もしない。** 組織を動かしていない普通の作業でブラウザを開かない
- **新しい記録の仕組みは作らない。** Claude Code が既に書き出している会話記録を読む（`16` と同じ出どころ）
- **読むだけで、組織の動作には干渉しない**
- **将来ダッシュボード化する可能性を PO が明言している。** そのため、状態を組み立てる部分と画面を分けてある

---

## A. なぜ作るのか

組織が動いている最中、PO から見えるのはメインセッションの画面だけである。担当エージェントは隔離されたコンテキストで並列に動くため、**いま何体が、どのタスクで、どれだけ動いているか**は、オーケストレーターの発言を追う以外に知る方法が無い。

`16` でトークン消費は見えるようになったが、あれは**事後の集計**である。タスク台帳への記録は hook のタイミングでしか更新されず、「今まさに動いているもの」は映らない。

### MVP対象外との関係

要件定義書 §3.3 がMVP対象外に挙げているのは「**複雑な**Webダッシュボード」である。今回のものは表示3項目・1画面・操作なしであり、これに当たらないと判断した。**PO もこの認識を確認している**（2026-08-25）。

ただし PO は「**将来的にダッシュボード化していく可能性はある**」とも述べている。そのときは §3.3 の対象外項目そのものに触れるため、**改めて MVP の範囲を切り直す判断が要る。** 今回の実装は、その判断が下りたときに作り直しにならないよう、後述の形にしてある。

---

## B. 誰が立ち上げるか — PO確定

3案を提示し、**A案（セッション開始時の hook）**が選ばれた。

| 案 | やり方 | 利害 |
| --- | --- | --- |
| **A（採用）** | セッション開始時に必ず実行される hook から起動する | 確実に起動する。ただし組織以外のセッションでも開いてしまう問題があり、**タスク台帳の有無で判定して抑止する** |
| B | オーケストレーターの手順書（`skills/org-orchestrate/`）に「起動せよ」と書く | 組織が動くときだけ開くのは自然。ただし**手順書に強制力が無く**、起動しない回が出る。モニタ起動の判断にトークンも使う |
| C | PO が手で起動する | 開くタイミングを完全に制御できる。ただし毎回の手間があり、「セッションが立ち上がったら自動で」という当初の要求から外れる |

PO の当初の想定は B（オーケストレーターが立ち上げる）だったが、**`CLAUDE.md` や手順書は読まれる文脈であって実行される設定ではない**という確認済みの制約（`docs/decisions/00-research-notes.md` §1.5）と衝突するため、A を推奨して採用された。

### 「組織以外のセッションで開いてしまう」への対処

hook は、そのリポジトリのセッションが始まれば必ず走る。組織を動かしていない普通の作業でブラウザが開くのは邪魔である。

**タスク台帳（`docs/task-list-{project-name}.csv`）が在るときだけ立ち上げる。** 台帳は、オーケストレーターが最初のタスクを登録する直前に雛形から作られる（`07`）。つまり**台帳の存在は「この組織が動いている」ことと同じ意味**であり、新しい判定材料を持ち込まずに済む。

### hook を待たせない

hook は、呼んだコマンドが終わるまでセッションの開始を止める。モニタは待ち受け続けるものなので、そのまま起動すると開始が止まる。**自分を切り離した別プロセスとして起動し、hook 側は即座に戻る。**

## C. データの出どころ — `16` と同じ

新しい記録の仕組みは作らない。会話記録（`~/.claude/projects/` の下の、1行1イベントの JSONL 形式のファイル）を読む。置き場の特定も `16` と同じで、ディレクトリ名の符号化規則には頼らず、記録の中に入っている作業ディレクトリの値を突き合わせる。

| 表示 | 出どころ |
| --- | --- |
| 担当・作業内容 | `agent-XXXX.meta.json` の `agentType` と `description` |
| 稼働中か終了済みか | 同ファイルの `toolUseId`（起動を識別する番号）が、メインセッションの会話記録に「実行結果」の行として現れたか |
| タスクID | 担当エージェントへの指示文から `T-数字` を拾う（`16` の C で確立した方法をそのまま使う） |
| トークン | 会話記録の `usage` 欄 |
| タスクの状態 | タスク台帳の索引 CSV（`org-check.py` の読み取りをそのまま使う） |

### 稼働中の判定に、この方法を選んだ理由

「動いているか」を直接示す欄は記録に無い。2案あった。

| 案 | 利害 |
| --- | --- |
| **採用: 会話記録から判定する** | 新しい記録を作らない。判定の根拠が Claude Code 自身の記録なので、こちらの書き漏らしで狂わない |
| 却下: hook で起動・終了を状態ファイルへ書く | 判定は単純になるが、**状態ファイルという新しい持ち物が増える**（§18 に触れる）。また、セッションが異常終了すると「動いている」と書かれたまま残る |

**実データで確認した事実**: 終了した担当エージェントの `toolUseId` は、メインセッションの記録に実行結果として1件現れる。稼働中のものは現れない。この差で判定できる。

### トークンはタスク台帳（CSV）から読まない

`16` で作ったトークン消費の台帳は、hook のタイミング（セッション開始時と担当エージェントの終了時）でしか更新されない。**リアルタイム表示には遅れる**ので、モニタは会話記録を直接読む。

同じ数字を2つの経路で出すことになるが、**役割が違う**。台帳は積み上げの記録（消えても作り直せる、手で編集しない）、モニタは今の値の表示（何も残さない）。

## D. 読み込みの重さへの対処

会話記録は数メガバイトになる。画面は2秒ごとに状態を取りに来るので、毎回全部読み直すと成立しない。

- **前回どこまで読んだかを覚えて、増えた分だけ読み足す**
- **書き込みの途中の行（改行がまだ来ていない行）は読まず、次回に回す。** 会話記録はセッションが動いている最中に読まれるため、これは異常ではなく正常な出来事である
- **対象セッションの探索（会話記録の総なめ）は30秒に1回に留める**

---

## E. 将来ダッシュボード化するときのために

PO が可能性を明言しているため、そのときに作り直しにならない形にした。

- **状態を組み立てる部分（`Watcher`）と、画面（HTML）を分けてある**
- **画面が読んでいるのは `/api/state` が返す JSON だけ**である。状態の組み立てには一切触れずに、画面側だけを差し替えられる
- 逆に、**表示項目を増やすときは `Watcher` を直す**。画面側で会話記録を読みに行く作りにはしない

**ただし、ダッシュボード化そのものは、この文書では決めない。** MVP の範囲（§3.3）に触れるため、PO の判断が要る。

## F. まだ決めていないこと

1. **複数の開発対象リポジトリを1画面で見るか。** 現状は1リポジトリ＝1モニタである。並行して複数のプロジェクトを走らせる運用になったときに要る
2. **停滞（実時間基準・サイクル基準）の警告を画面へ出すか。** 判定は `org-check.py` が既に持っているが、モニタは今それを呼んでいない。「見ているだけで気づける」ようにするなら足す価値がある
3. **PO確認待ちキューを画面へ出すか。** PO が最も反応すべき情報だが、今は出していない（表示3項目という PO の指定に従った）
