# 13. 実行形態と配置

**Status:** Confirmed（既存決定からの導出 2026-08-20）
**根拠:** 要件定義書 v0.1 §4.1 / §4.4 / §14 / §19、`00` §1.1、`01`〜`12`
**position:** 01 が「意図的に決めていない」とした実行形態を、エージェント定義ファイルを書くために確定させる。異論があれば差し戻すこと。

## この文書が確定したこと

- **オーケストレーターはメインセッションであり、子プロセスとして起動されるエージェントではない。** 人間へ問い合わせられるのがメインセッションだけである以上、これは選択ではなく帰結である
- **その帰結として、「実装しない」の担保をツール制限から整合性検査へ移した。** メインセッションにツール制限は適用できないため、「工程が進行中なのに担当がオーケストレーター」を検査項目に加えた
- **組織の実行時ファイルは `org/` にまとめ、開発対象リポジトリへ配置する。** 層2の規約はそのリポジトリのルートに置かれるため、層1の規約と同居できない
- **レビューエージェントから編集系ツールを外した。** 5ロールのうち、責務の外へ出られないことを構成で保証できるのはこのロールだけである

## A. オーケストレーターはメインセッションである — 導出により確定

**これは選択ではなく、既存の確定事項からの帰結である。**

1. サブエージェントは `AskUserQuestion` を使えない（`00` §1.1）
2. PO へ問い合わせできるのはオーケストレーターだけである（`01`、`08`）
3. ゆえに **オーケストレーターはサブエージェントであり得ない**

`01` は実行形態を未決としたが、`08` で PO確認待ちキューの一元管理を確定させた時点で、選択肢は消えていた。

### 帰結

| | 内容 |
| --- | --- |
| オーケストレーターの定義の置き場所 | `.claude/agents/` では**ない**。層2の `CLAUDE.md`（常に必要な事実）と Skill（手順）へ置く |
| 他の5ロール | サブエージェント（`.claude/agents/org-*.md`） |
| 委譲の手段 | メインセッションから Agent ツールで起動する |
| ネストの深さ | 2層。既定の上限3層に収まる（`00` §1.1） |

### §6.3「実装しない」の担保をどうするか

`01` は「オーケストレーターの定義から編集系ツールを外せば、実装は構造的に不可能になる」と述べていた。**メインセッションにはこの手が使えない。** ツール制限はサブエージェント定義の機能であり、メインセッションには適用できない。加えて、オーケストレーターは CSV索引・`po-queue.md`・`handover.md`・層2の規約を書く責務を負っており（`07`・`08`・`11`・`06` 確定事項 D）、編集系ツールを外すこと自体ができない。

代替の担保を3つ置く。**構造で1つ、検知で1つ、規約で1つ。**

| # | 手段 | 内容 |
| --- | --- | --- |
| 1 | **構造** | 5つのサブエージェントが存在し、`description` が明確であること。委譲先が曖昧だと `00` §2.2 の **Failure to Delegate** が起きる |
| 2 | **検知** | 整合性検査に **「状態が `設計中` / `テスト作成中` / `実装中` / `テスト中` / `レビュー中` なのに `担当` がオーケストレーター」** を加える（`09` の出力3へ追加）。委譲を怠ると台帳に痕跡が残る |
| 3 | 規約 | オーケストレーター運用スキルの着手前チェックに「このタスクは自分がやるべきか」を置く |

2 が要点である。**規約は破られるが、台帳は嘘をつけない。** タスクには必ず `担当` が要り（`07`）、オーケストレーターが自分で実装すれば `担当` がそうなるか、または空欄のまま状態だけが進む。どちらも検査で捕まる。

## B. 配置 — 開発対象リポジトリへ配る「束」として持つ

組織の実行時ファイル（エージェント定義・スキル・層2の規約）は、**開発対象リポジトリ**で動く（`06` の層2、CLAUDE.md のディレクトリ規約）。本リポジトリはその**定義を持つ**場所である。

本リポジトリのルート `.claude/` へ直接置かない。理由は2つ。

1. 層2の `CLAUDE.md` は開発対象リポジトリのルートに置かれるものであり、**本リポジトリのルート `CLAUDE.md`（層1）と同じ場所には置けない**
2. 本リポジトリでのセッションに、開発対象リポジトリ向けの規約とサブエージェントが読み込まれてしまう

したがって、配布物としてまとめる。

```
org/
  README.md                          導入手順
  CLAUDE.md                          → 開発対象リポジトリのルートへ（層2）
  rules/org-task-ledger.md           → .claude/rules/
  rules/org-escalation.md            → .claude/rules/
  agents/org-*.md                    → .claude/agents/（5ロール）
  skills/org-orchestrate/SKILL.md    → .claude/skills/
  skills/org-session-resume/SKILL.md → .claude/skills/
```

**`org-` プレフィックスは `12` の確定どおり。** 既存拡張（Everything Claude Code / Superpowers 等）と名前が衝突したら組織側が譲る（§19、`12`）。

## C. サブエージェントのツール制限

`00` §1.1 の `tools` / `disallowedTools` を使い、**責務の外へ出られない構成にする**（`12`）。

| ロール | 編集系 | 根拠 |
| --- | --- | --- |
| org-design | あり | 設計成果物を書く（`02` の O-1） |
| org-implementation | あり | コード・設定・単体テスト（`03` の O-1）。Git commit / push も行う（`03` 確定事項 B） |
| org-review | **なし** | 「自分では修正しない。修正は実装エージェントが行う」（`04`）。**これは構造で担保できる唯一のロールである** |
| org-test | あり | 受け入れテスト・回帰テストを書く（`05` の O-3） |
| org-documentation | あり | 層3のドキュメント（`06` の O-1） |

**全ロール共通で外すもの**: `Agent`（サブエージェントを更に起動させない。オーケストレーターをハブとする §14 の原則）、`AskUserQuestion`（そもそも使えない。`00` §1.1）。

`org-review` から編集系を外せることには、副次的な価値がある。**レビューが自分で直してしまうと、修正の意図が実装エージェントに伝わらず、同じ誤りが次のタスクで再発する。** 04 が「直し方の指定は任意」とした設計と同じ向きである。

### 設計・ドキュメントが実装コードを書かない担保

`org-design` と `org-documentation` は編集系を持つため、コードを書けてしまう。ツールでは防げない（パス単位の制限は無い）。**規約と検知で担保する**——A の手段2と同じ経路で、`担当` と成果物の対応が崩れれば整合性検査に出る。

## D. 直接通信の実装

`§14` の例外3経路（レビュー→実装、実装→設計、テスト→実装。`08` に一覧）は、`00` §1.1 の通り `SendMessage` で技術的に実現できる。

ただし**環境によって使えないことを前提に置く**。

| 直接通信が | 反復ループの回し方 |
| --- | --- |
| 使える | `SendMessage` で相手へ直接。オーケストレーターは結果だけ受け取る |
| 使えない | **オーケストレーターが作業指示を再発行する**（往復を中継する） |

**どちらでも往復上限は2回**（`04` 確定事項 B / `05` 確定事項 B）。上限の意味は「収束しない評価ループを検知する」ことであり（`00` §2.3）、通信手段には依存しない。

ツールでは通信相手を制限できないため、**許可された相手と範囲は各エージェント定義の本文に書く**。

## E. hook

`09` が定めた停滞検知・整合性検査を `SessionStart` hook で必ず実行させる。**CLAUDE.md は強制力を持たない**ため（`00` §1.2）、確実に走らせたいものは hook にする。

既存の hook 設定を**置換せず追記する**（`12`、§19）。
