# 24. 配布方式を、手動コピーからプラグイン機構へ移す

**Status:** **方式は Confirmed（PO 判断 2026-08-28）。実装方式は未確定**（プラグインの構成を実物で調べていない）
**根拠:** `docs/decisions/14-open-questions.md` 論点1（3案と各案の利害、および「2つ目の導入先が現れたときが引き金」という条件を書いた文書。**本記録でこの論点は決着する**）、要件定義書 v0.2 §4.4（拡張はファイル追加で済むように）/ §18（独自の設定ファイルを作らない）/ §19（既存拡張を壊さない）
**位置づけ:** §23 の12項目には無い。論点1 に書いた引き金の条件が実際に満たされたことによる決着。
**実装:** 未着手。**先に調査が要る**（後述 D）

## この文書が確定したこと

- **配布方式は、Claude Code のプラグイン機構を使う**（`14-open-questions.md` 論点1 の案B）。手動コピー（案A）は移行が済むまでの暫定手段として残す
- **`docs/decisions/14-open-questions.md` の論点1 は、これで決着した。** 未決の論点ではなくなる
- **移行の実装より先に、プラグインの構成を実物で調べる。** 何をどこへ置くと、担当エージェントの定義・スキル・規約・スクリプト・フックがそれぞれ認識されるのかが分かっていない
- **決定ログ索引の実装（`docs/decisions/21-decision-log-index.md`）より、この移行を先に片付ける。** 索引スクリプトの置き場が移行で変わるため

## A. なぜ今決めたか — 引き金の条件が満たされた

`docs/decisions/14-open-questions.md` の論点1 は、判断そのものを先送りする代わりに、**いつ決めるかの条件を書き残していた**。

> **MVP の間は A（手動コピー）のまま。実際に2つ目の開発対象リポジトリへ導入するときが B の引き金。**
> 1つのリポジトリでしか動かしていない間は、更新の追随という B の最大の利点が効かない。2つ目が現れた瞬間に、「配布元を直したとき、導入済みの2つをどう追随させるか」が実際の問題になる。

**この条件は満たされた。**

- **導入先が2つになった** —— トライアル運用中の別リポジトリ（SNS Agent）と、それ以前の導入先
- **更新の追随ができない問題が、実際に起きている。** 本リポジトリ側で直した内容が、導入済みのリポジトリへ届いていない。2026-08-25 の修正6件、トークン消費の集計の一式、稼働状況のモニタが未反映のまま残っている（このリポジトリの `CLAUDE.md` の「次にやること」に、届いていないものの一覧がある）
- **追随すべきファイルは増え続けている。** 配布物のスクリプトは5本になり、スキルは4本、担当エージェントの定義は5本ある。**手でコピーし直す方式は、ファイルが増えるほど取りこぼす**

**さらに、この方式のまま進むと問題が深刻化する。** 決定ログ索引の実装（決定記録21）は配布物のスクリプトを6本目として足すため、追随すべき対象がまた増える。

## B. 何が選ばれ、何が選ばれなかったか

`14-open-questions.md` 論点1 が挙げた3案のうち、**案B（プラグイン機構）を採る。**

| 案 | 内容 | 判断 |
| --- | --- | --- |
| A. 手動コピー（現状） | `org/README.md` の手順どおりファイルをコピーする | **採らない**（移行完了までの暫定としてのみ残す）。更新の追随ができないという欠点が、実際に問題として現れた |
| **B. プラグイン機構** | Claude Code が持つプラグイン（スキル・担当エージェントの定義・フックなどをまとめて配る単位）の仕組みに載せ、有効化するだけで入る形にする | **採る** |
| C. インストールスクリプト | コピー作業を自動化するだけ | **採らない。** 導入の手間は減るが、**更新の追随という本題は解決しない**。A の欠点をそのまま抱える |

### 案B を採る理由

1. **更新の追随ができる。** 配布元を直せば、導入済みのリポジトリが取り込める。これが今まさに起きている問題への直接の答えである
2. **要件定義書 §4.4（拡張はファイル追加で済むように）と §19（既存拡張を壊さない）を、より強く満たす。** プラグインは、既存の拡張（Everything Claude Code や Superpowers など、この実行環境に既に入っているもの）と並んで置かれる単位であり、**互いに上書きし合わない置き場が仕組みとして用意されている**
3. **本リポジトリは既にプラグインを「読む側」として扱っている。** 導入時の初期シーケンス（`org/skills/org-init/`）が使うスクリプト `org/scripts/org-skills.py` は、導入済みプラグインの実体の置き場を辿って中のスキルを数え上げている。**プラグインの置かれ方についての知識が、部分的には既にこのリポジトリにある**

### §18（独自の設定ファイルを作らない）に抵触しないこと

要件定義書 §18 は、独自形式の JSON / YAML 設定ファイルを作ることを禁じている。**プラグインの構成ファイルは Claude Code の標準形式であって独自形式ではない**ため、§18 には抵触しない。これは `14-open-questions.md` 論点1 の「注意」に既に書かれていた確認であり、本記録で覆さない。

## C. 何がまだ決まっていないか

**決まったのは「プラグイン機構を使う」という方式だけである。** 次のことは決まっていない。**推測で埋めてはならない。**

| 未確定のもの | 中身 |
| --- | --- |
| **プラグインの構成** | 何をどのディレクトリ・どのファイル名で置くと、担当エージェントの定義・スキル・規約（`.claude/rules/`）・スクリプト・フック（決まった場面で必ずコマンドを実行させる仕組み）が、それぞれ認識されるのか |
| **規約とスクリプトが載るかどうか** | プラグインが運べるのはスキル・担当エージェントの定義・フックだと分かっているが、**`.claude/rules/` に置く規約と、`.claude/scripts/` に置く Python スクリプト6本が同じ形で運べるかは未確認**。運べないものがあれば、その分は別の手段が要る |
| **`org/CLAUDE.md` の扱い** | 層2の運営規約は、開発対象リポジトリのルート `CLAUDE.md` へ**追記**する形で入っている（既存の `CLAUDE.md` を置き換えないため）。**追記という形をプラグインが取れるかは未確認** |
| **配布元の登録方法** | プラグインの配布元をどう用意し、導入する側がどう登録するか |
| **本リポジトリ内での置き場** | 現在 `org/` にある配布物を、プラグインの構成へどう並べ替えるか。`org/` という名前と場所を保つのか |
| **導入済み2箇所の移行手順** | 既にコピー方式で入っている2つのリポジトリを、どう切り替えるか。**切り替え中に組織が止まらないこと**が条件 |
| **移行後の導入手順** | `org/README.md` の「導入」の節と、本リポジトリの導入手順書を書き換える |

## D. 次にやること — 実装より先に調査

**決定記録21（決定ログを引けるようにする方式）と同じ進め方をとる。** つまり、**実装に入る前に実物へ当たり、調べた結果を `docs/experiments/` へ記録票として残す**（記録票には判断を書かない。判断は決定記録へ書く）。

| 順 | やること | 出力先 |
| --- | --- | --- |
| 1 | **プラグインの構成を実物で調べる。** この実行環境に導入済みのプラグイン（`~/.claude/plugins/` の下に実体がある）を開き、何がどう置かれているかを見る。C の表の未確定7項目に答える | `docs/experiments/03-plugin-distribution.md`（新規） |
| 2 | 調べた結果をもとに、**構成・移行手順・導入手順を確定させる** | 本記録への追記、または新しい決定記録 |
| 3 | **本リポジトリの配布物を、プラグインの構成へ並べ替える** | `org/` 配下 |
| 4 | **導入済み2箇所を移行する** | 各開発対象リポジトリ |

### 調査で必ず確かめること

**「動いた」だけでは足りない。** 次の3点は、確かめずに済ませると後で壊れる。

- **既存拡張と共存できるか。** 導入先には Everything Claude Code などが既に入っている。**組織のプラグインを入れたことで、既存の commands / skills / hooks が消えたり上書きされたりしないこと**（要件定義書 §19）
- **フックが追記になるか。** 組織は、セッション開始時と担当エージェント終了時に走らせるフックを4件持っている。**既存のフックを置換せず追記する**必要がある（`org/README.md` の「設定ファイルへの追記」の節が、手動コピーのときの同じ注意を書いている）
- **導入先ごとに違う設定を、上書きしてしまわないか。** ツールの実行許可（`permissions`）は、**開発対象のビルド・テストのコマンドを導入した側が足す**建て付けになっている（`docs/decisions/17-tool-permissions.md`）。更新のたびにそれが消えると、導入先が壊れる

## E. 順序の制約 — これを先にやる

**決定ログ索引の実装（`docs/decisions/21-decision-log-index.md` の「作るもの」9件）より、この移行を先に片付ける。**

理由は、索引スクリプト `org-decisions.py` が**配布物の6本目**として追加されるためである。移行前に作れば、置き場をプラグインの構成へ移し替える作業がもう一度発生し、**その間に索引スクリプトの配布先が2方式に分かれる**。

**ただし、決定記録21 の内容そのものは移行の影響を受けない。** 索引の作り方・決定ログへ足す2つの欄・失効の表し方は、どこにスクリプトを置くかとは独立している。**先送りするのは実装の着手だけであって、設計をやり直す必要は無い。**

## F. 暫定期間中の扱い

**移行が済むまでは、手動コピー（案A）で運用を続ける。** 移行を待って更新を止めない。

- 本リポジトリの導入手順書（`docs/introduce-to-a-project.md`）は、**手動コピーの手順として書いてある**。移行後に書き換える
- **未反映のものを溜めない。** 現在届いていない分（2026-08-25 の修正6件、トークン消費の集計の一式、稼働状況のモニタ）は、移行を待たずに手でコピーし直す。**移行が済むまで放置すると、移行時に「どこまで届いているか」が分からなくなり、突き合わせの手間がそのまま増える**
