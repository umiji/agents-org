# 20. 役割ごとのスキル割り当てと、導入時の初期シーケンス

**Status:** Confirmed（PO 承認 2026-08-28）
**根拠:** 要件定義書 §4.1 / §4.5 / §4.6 / §17.2 / §17.3 / §18 / §19、`docs/experiments/03-agent-skill-access.md`
**実装:** 下の「作るもの」の1〜4が完了（2026-08-28）。5と6は未着手

## この文書が確定したこと

- **担当エージェントに専門知識のスキルを新規に書く必要は、当面ない。** 環境に導入済みのスキルを呼べるようにするほうが先である
- **そのために、担当エージェント5つの「使えるツール」へ `Skill` を足す。** これが無いと、スキルを1本も呼べないどころか、何が使えるのかの一覧すら提示されない
- **役割ごとに、呼ぶスキルをエージェント定義の本文へ名指しする。** 別の設定ファイルは作らない
- **組織の規約と衝突するスキルは、名指しで禁止する。** 264本の除外一覧は作らない
- **導入時に1回だけ走る初期シーケンス**（スキル `org-init`）を新設し、環境とリポジトリを突き合わせて割り当てを書き出す
- **書き出した内容は次のセッションから効く。** この手順を明示しないと、黙って失敗する

---

## 背景 — 「スキルが0本」は問題の言い換えを間違えていた

`docs/handover.md` は不足として「専門知識のスキルが0本」を挙げていた。実測の結果、この記述は問題を取り違えていた。

**このマシンには264本のスキルが既に存在する**（ECC 249本・Superpowers 14本・その他1本。いずれも利用者スコープの導入なので、どの開発対象リポジトリからも見える）。**にもかかわらず、担当エージェントからは1本も見えていない**——使えるツールを列挙する形の定義に `Skill` が含まれていないため、呼び出す手段も、一覧を知る手段も無い（実験03の検証1・2）。

**書き足すべきものが無いのではなく、呼び出し口が塞がっていた。**

---

## 確定事項A — 使えるツールへ `Skill` を足す

担当エージェント5つ（設計・実装・レビュー・テスト・ドキュメント）の定義の `tools` へ、`Skill` を追加する。

**全部か無しかの選択である。** スキルを1本ずつ許可・禁止できるかは確かめていない（実行許可の設定は `Bash(git status:*)` のように「ツール名（対象の絞り込み）」の形をとるので、`Skill(...)` の形が効く可能性はあるが、現行の設定に例が無い）。

**確かめない。** 理由は、絞る動機として挙がったトークン節約の効きが小さいためである。実測では、一覧の常時コストは概算1,600〜13,800トークンでセッションに1回・システムプロンプト側（同じ内容が繰り返し送られるため料金の割引が効く領域）に載る。対して、誤って呼ばれたスキル1本は中央値で約1,700、長いもので約7,600トークンを都度消費する。**削って浮く分より、誤って呼ばれる分のほうが大きい。**

**絞る本当の理由はトークンではなく、規約との衝突である**（確定事項C）。

---

## 確定事項B — 役割ごとの割り当ては、エージェント定義の本文へ書く

**別の設定ファイルを作らない。** 要件定義書 §18 は、独自の JSON / YAML 設定ファイルを作ってよい条件を限定しており、この用途はそこに到達していない。エージェント定義ごとに使うスキルを書けば足りる。

初期状態の割り当て（言語・フレームワークに依存しないものだけ。導入先のスタックに応じて初期シーケンスが足す）:

| 担当エージェント | 名指しするスキル | 何のために |
| --- | --- | --- |
| **レビュー** | `ecc:security-review`（セキュリティ観点のレビュー手順）／`ecc:coding-standards`（コーディング規約）／`ecc:error-handling`（エラー処理の型） | **最優先。** レビューの判定表は最も重い重大度 Blocker の定義に「セキュリティ上の問題」を含めているのに、何がそれに当たるかの基準が配布物のどこにも無い |
| **テスト** | `superpowers:systematic-debugging`（不具合の切り分け手順）／`ecc:e2e-testing`（利用者の操作をなぞる形のテスト） | 責務に「不具合原因の切り分け」があるのに手順が無かった |
| **実装** | `superpowers:test-driven-development`（テストを先に書く進め方）／`superpowers:verification-before-completion`（完了と言う前に実際に動かして確かめる） | 後者は完了報告の「ローカル検証の結果」を必須項目にしている狙いと同じ |
| **設計** | `ecc:api-design`（APIの設計指針）／`ecc:architecture-decision-records`（設計判断を記録に残す形式） | 設計成果物の形が定義に書かれていないため、型を借りる |
| **ドキュメント** | **足さない** | 人間用ビューの生成手順は既に組織側にある（`docs/decisions/06-documentation-agent.md`）。重複させない |

**レビューの3本が最優先である。** 他は無くても回るが、これが無いとレビューの判定が担当エージェントごとに変わる。判定基準が揺れると、レビューの往復が収束しない——レビューエージェントの定義自身が「評価者が良し悪しを確実に判別できないとループする」と書いている。

## 確定事項C — 衝突するスキルは名指しで禁止する

264本の中には、組織の規約と正面から食い違うものがある。**除外一覧を作らず、衝突する分だけを禁止として書く。**

| 禁止するもの | 踏むと何が起きるか |
| --- | --- |
| `superpowers:using-git-worktrees`（作業ツリーを分けて並列作業する手順） | 組織は「1タスク1ブランチにはしない」と決めている（`org/CLAUDE.md`）。**担当エージェントが規約と逆の Git 操作を始める** |
| `superpowers:finishing-a-development-branch`（ブランチの片付け方） | 同上 |
| 一般的なコードレビューの手順（`superpowers:requesting-code-review` / `superpowers:receiving-code-review`） | 重大度の呼び名（Blocker / Major / Minor）と往復上限（2往復）が組織の規定と違う。**報告がタスク台帳の書式に合わなくなる** |

**2026-08-28 の訂正（実装時に判明）:** この表は当初 `ecc:code-review` を挙げていたが、**それはスキルではなくコマンド**（人間が `/` を付けて打つ入口）であり、担当エージェントが呼ぶ対象ではなかった。担当エージェントが呼びうる同種のスキルは上の2本である。**禁止する理由は変わっていない。**

**除外一覧にしない理由:** 264本のうち使わせない分を全部並べると、スキルが増えるたびに追随が要る。更新の追随はこの組織の既知の弱点である（`docs/decisions/14-open-questions.md` の論点1）。**許すほうを名指しし、危険な数本だけを禁止する**ほうが短く、増えても壊れない。

## 確定事項D — 導入時の初期シーケンス（スキル `org-init`）

開発対象リポジトリへ組織を導入したとき、**1回だけ**走らせる手順。オーケストレーター用のスキルとして作る。

| 段 | やること | 誰が |
| --- | --- | --- |
| 1 | **環境を調べる。** 導入済みプラグインとそこに含まれるスキルの名前・説明・見込みトークン量を集める。リポジトリ内の `.claude/skills/` も見る | **スクリプト**（`org/scripts/org-skills.py` を新設。判断を含まないため。§4.5） |
| 2 | **リポジトリを調べる。** 言語・フレームワーク・テスト基盤・CI を読み取り、必要なスキルの種類を決める | オーケストレーター（判断） |
| 3 | **突き合わせる**（探索順は後述） | オーケストレーター |
| 4 | **エージェント定義へ書き出す。** 役割ごとの割り当て、`Skill` の追加、禁止するスキルの明示 | オーケストレーター |
| 5 | **セッションを開き直す** | PO |
| 6 | **効いているかを確かめる。** 担当エージェントを1つ起こし、割り当てたスキルを呼べたかを報告させる | 既存の「初回運用の点検」（`org/skills/org-first-run-check/`）へ点検項目として追加 |

### 段5と6を省略できない理由

**エージェント定義はセッション開始時に読み込まれる**（実験03の検証3）。書き出した直後のセッションでは反映されない。

まずいのは、**失敗が見えない形で起きる**ことである。書き出した直後に担当エージェントへ割り当てると、担当エージェントは**スキルを1本も持たない古い定義のまま動く。** エラーは出ず、成果物も一応できる。「スキルが効いていない」と気づく手段が無い。

### 段3の探索順

| 順 | 探し先 | ネット接続 | 誰が |
| --- | --- | --- | --- |
| 1 | 導入済みのプラグイン（`claude plugin list`）と、リポジトリ内の `.claude/skills/` | 不要 | スクリプトが集める |
| 2 | 登録済み配布元の目録。**公式マーケットプレイス `claude-plugins-official` は登録済みで、289件が名前と説明つきでローカルのファイルに入っている** | 不要 | スクリプトが集め、オーケストレーターが選ぶ |
| 3 | 1と2に無い → **PO確認待ちキューへ登録**する。依存関係のないタスクは止めない（§13） | — | オーケストレーター |

**導入（`claude plugin install`）の実行は PO の承認後に限る。** プラグインはスキルだけでなくエージェント定義やフック（特定のタイミングで必ずコマンドを実行させる仕組み）も持ち込める。素性の分からない配布元を組織が自動で導入すると、**組織が把握していないコマンドの自動実行経路が増える。**

**外部サイト（`https://buildwithclaude.com/` 等）は手順に組み込まない。** 取得を試したところ HTTP 403（アクセス拒否）が返り、ブラウザ以外からの取得は弾かれる。**PO が手で見る場所**としてのみ記す。

### 検索コマンドは存在しない

`claude plugin` にスキルやプラグインを検索する副コマンドは無い。配布元は名前か URL で明示的に登録する。**探索順2がその代わりを果たす。**

## Web版・モバイル版での扱い

PO は Web版・モバイル版の Claude Code でもこの組織を使いたいと述べている。ローカルとは環境が異なり、同じアカウントでも導入されているスキルが違いうる。

**`claude plugin` コマンドがそこで使えるかは確かめていない。** 使えない場合の退避路は、**必要なスキルを開発対象リポジトリの `.claude/skills/` へ置き、リポジトリごと運ぶ**ことである。この組織が自分の3本（オーケストレーターの手順・セッション再開・初回点検）で既に採っている方法そのものであり、新しい仕組みを要しない。段3の3番目の落とし先をこれにできる。

**次のセッションで、Web版で `claude plugin list` が通るかを実測してから決める。**

### 禁止を層2の規約側へ置いた理由（実装時の判断）

確定事項Cの禁止3種類は、**5つの定義すべてに共通する**。エージェント定義ごとに同じ表を複写すると、**追随できずに片方だけ古くなる。** 層2の規約（`CLAUDE.md`）はすべての担当エージェントへ継承されるので、共通の事実はそこへ置く——これは元からの制約である（`docs/decisions/00-research-notes.md` の、CLAUDE.md 階層がサブエージェントへ継承されるという実測）。

**役割ごとの割り当て（確定事項B）は、確定した通りエージェント定義の本文にある。** 別の設定ファイルは作っていない。
