# 11. セッション引き継ぎ

**Status:** Confirmed（PO確認 2026-08-20）
**根拠:** 要件定義書 v0.1 §4.3 / §15 / §22-11 / §23-11
**前提:** MVP では新セッションの起動は**手動**（§15）。自動起動・自動監視・自動引き継ぎは作らない。

---

## 何を残すか — タスクリスト + 引き継ぎ記録（PO確定 2026-08-20）

| | 中身 | 更新頻度 |
| --- | --- | --- |
| **タスクリスト**（07） | 各タスクの状態・完了条件・決定ログ・作業ログ・証拠 | タスクが動くたび |
| **引き継ぎ記録** `docs/handover.md` | 「今どこにいるか」だけ。タスクに紐づかない文脈 | 節目ごと |

### 引き継ぎ記録を別に持つ理由

タスクリストが常に最新なら専用文書は不要、という立場もある。採らない。**タスクリストに現れない情報が確実にあるため**である。

- **なぜ今この順序で進めているか。** タスクリストは順序を持つが、その順序を選んだ理由は個々のタスクの決定ログには載らない
- **まだタスク化されていない、次にやろうとしていたこと。** 10 の指標8がまさにこれを扱う
- **直前に得た判断のうち、まだどのタスクにも書けていないもの**
- **環境の状態。** 未コミットの作業があるか、ビルド・テストコマンドが何か

これらは会話の中にしか存在せず、**セッションが切れれば失われる**。00 §1.3 の通り、プロジェクトルートの CLAUDE.md はコンパクション後に再注入されるが、**会話中だけで与えた指示は失われる**。00 §2.2 の **Context Loss During Handoffs**——引き継ぎ時に文脈が失われ、重複作業や沈黙した失敗が起きる——は、この空白から生じる。

### 詳細なセッションログを採らない理由

作業経緯を時系列で全部残せば復元力は最も高いが、**新セッションが読む量が増え、そのまま初期コンテキストを圧迫する**。引き継ぎの目的は記録の保存ではなく、次のセッションが**速く正しい状態に立つこと**である。経緯は既にタスク別ファイルの作業ログと git 履歴にある。引き継ぎ記録が二重に持つ必要はない。

## `docs/handover.md` の内容

開発対象リポジトリに置く。**1枚。常に上書きする。** 過去分は git 履歴に残るため、追記して膨らませない。

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 更新日時 | 必須 | いつ時点の状態か |
| ゴール | 必須 | PO から受けたゴールと、**現時点で確定しているゴール達成条件** |
| 現在地 | 必須 | 直近で何をしていたか。進行中のタスクID |
| 直近の判断 | 必須 | まだタスクの決定ログへ書けていない決定。**無ければ「無し」と明記** |
| 次の一手 | 必須 | 新セッションが最初にやること。10 の評価の「次の一手」をそのまま置ける |
| PO確認待ち | 必須 | 未回答の Q-ID 一覧（`docs/po-queue.md` への参照） |
| 直近の健全性評価 | 必須 | 10 の出力。**前回比を出すために次回が参照する** |
| 環境・前提 | 必須 | ビルド／テスト／リントのコマンド、未コミットの作業の有無、実行に要る前提 |

**「直近の判断」を必須にし、無ければ「無し」と書かせる**のは、07 の `特記なし` と同じ理屈である。項目が空であることが「未記入」と区別できなければ、無いのか書き忘れたのか分からなくなる。

**「環境・前提」を持つ**のは、新セッションが最初につまずくのがここだからである。本リポジトリの CLAUDE.md が「最初の実行可能物が入った時点でコマンドの節を追記すること」と定めているのと同じ理由——確定したコマンドは、毎回発見し直すものではない。恒久的に確定したものは層2（`CLAUDE.md`）へ昇格させ、引き継ぎ記録には流動的なものだけを残す。

## いつ書くか — 「セッション終了時」では書けない

**節目ごとに更新する。** セッション終了時にまとめて書く運用は成立しない。トークン・コンテキストの上限は予告なく訪れ、**書く余裕が残っていない状態で切れる**ためである。

00 §2.4 が記録している通り、Anthropic の研究システムではリードエージェントが**コンテキストが埋まる前に**計画をメモリへ保存している。200,000トークンを超えると切り詰めが起き、計画そのものが失われるためである。01 が「計画を早期に外部化する」と定めたのと同じ制約が、引き継ぎ記録にも等しく効く。

更新する節目:

| いつ | 何を更新するか |
| --- | --- |
| タスクの状態が変わったとき | 現在地、次の一手 |
| PO の判断を得たとき | 直近の判断（そのタスクの決定ログへ転記するまでの間） |
| 健全性評価を行ったとき（10） | 直近の健全性評価、次の一手 |
| ゴール達成条件が確定・変更されたとき | ゴール |
| セッション終了時（可能なら） | 全体 |

最終行は「可能なら」である。**それまでの更新で引き継ぎが成立していなければならない。** セッション終了時の更新は仕上げであって、頼りにするものではない。

### 決定は引き継ぎ記録に溜めない

`直近の判断` は**一時的な置き場**である。決定はタスクの `## 決定ログ` へ書くのが正であり（07）、引き継ぎ記録に残るのは「まだ書けていないもの」だけ。溜まっていること自体が、決定ログへの転記を怠っている信号になる。

## 新セッションの再開手順

§15 は「新セッションでは、既存のタスク状態・成果物・進捗情報を読み取り、作業を再開する」とだけ述べる。手順を確定する。

1. `CLAUDE.md`（自動で読み込まれる。層2の組織規約）
2. `docs/handover.md` — **最初に読む。** 現在地・次の一手・環境
3. **停滞検知スクリプトを実行**（09） — 前セッションが引き継ぎを書かずに切れた場合、放置されたタスクを拾えるのはこれだけである
4. `docs/task-list-{project-name}.csv` — 索引。全体像
5. 進行中タスクの詳細ファイル `docs/tasks/T-XXX.md` — **進行中のものだけ。完了済みは読まない**
6. `docs/po-queue.md` の未回答項目
7. `git status` / `git log` — 未コミットの作業、直近のコミット
8. ゴール健全性評価（10）を実行し、`handover.md` の前回値と比較する

### 手順3を4より前に置く理由

**引き継ぎ記録は嘘をつきうる。** 前セッションが更新できずに切れていれば、`handover.md` は古い。タスクリストは各エージェントの作業で更新されているため、より新しい可能性がある。3の整合性検査（09 の出力3）が両者のずれを検出する。

**引き継ぎ記録を信じる前に、機械的な検査を通す。**

### 手順5の「完了済みは読まない」

07 で CSV索引 + タスク別ファイルに分けた目的がここに出る。1つのタスクを触るために完了済み全タスクの証拠まで読み込む状態（PO の実例で 42KB）を避けるための構造であり、**再開手順がそれを守らなければ意味がない。**

### この手順は Skill にする

00 §1.2 の使い分けに従う——**手順は Skills（呼ばれた時のみロード）**、常に必要な事実は CLAUDE.md。再開手順は多段階のチェックリストであり、毎セッション全文をロードする CLAUDE.md に置くものではない。CLAUDE.md には「セッション再開時はこのスキルを使う」という一行だけを置く。

配置と命名は 12 の規約に従う（既存拡張との共存のため、組織のスキルは独立した名前空間へ置く）。

## 何を引き継がないか

| 引き継がないもの | なぜ |
| --- | --- |
| 会話の全文・要約 | 量が多く、必要な情報はタスクリストと引き継ぎ記録に既にある |
| 完了済みタスクの詳細 | 索引に完了として載っていれば足りる。必要になったら開く |
| 各サブエージェントの内部状態 | サブエージェントは新規の隔離コンテキストで始まる（00 §1.1）。引き継げるものが元々無い |
| 未確定の推測・仮の方針 | 確定していないものを引き継ぐと、次のセッションで確定済みとして扱われる危険がある。確定していないなら書かない（本リポジトリ CLAUDE.md の原則と同じ） |

3行目が構造的に重要である。**サブエージェントの側に引き継ぐべき状態を持たせない設計になっている。** 各エージェントの作業結果はタスク別ファイルと git に落ちており、次のセッションの新しいサブエージェントは、そこから自己完結した作業指示を受け取って始める（01 の O-2）。セッション引き継ぎが成立するのは、この非対称性——**状態は常にファイルにあり、エージェントには無い**——のおかげである。

## MVP で作らないもの（§15 の再確認）

- 自動的な Claude Code CLI 新規起動
- バックグラウンドセッション管理
- 自動セッション監視
- 自動セッション引き継ぎ

**新セッションの起動は PO が手動で行う。** 本ファイルが定めるのは、起動された新セッションが正しく再開できるための情報と手順だけである。
