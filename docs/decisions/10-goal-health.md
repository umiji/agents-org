# 10. ゴール健全性評価

**Status:** Confirmed（PO確認 2026-08-20）
**根拠:** 要件定義書 v0.1 §6.2 / §22-9 / §23-10
**前提:** 01 の確定事項 C（実行タイミングの保留）を、ここで解く。07 で形式が確定したため、指標は CSV から機械的に算出できる。

---

## この評価が答える問い

§6.2 は明確に述べている——**「単純なタスク消化数だけではなく、組織が最終ゴールへ近づいているかを評価する」**。

区別が要点である。タスクは順調に消化されているのに、ゴールへは近づいていない、ということが起こりうる。00 §2.6 が記録している限界——役割特化型システムが複雑な課題で10回試行しても中核機能を欠いたという報告——は、まさにこの状態である。**消化量を見ているだけでは検知できない。**

---

## 実行タイミング — 節目 + PO要求時（PO確定 2026-08-20）

| いつ | なぜ |
| --- | --- |
| **セッション開始時** | 前セッションからの継続点を掴む。09 の停滞検知と同時に走る |
| **セッション終了時** | 結果がそのまま引き継ぎ記録になる（11） |
| **停滞検知時** | 停滞が単発か、全体の失速かを切り分ける |
| **機能のまとまりが完成した時点** | 06 確定事項 C（ドキュメントタスクの起動タイミング）と揃える。まとまりの完成が組織の自然な節目である |
| **PO から求められたとき** | 常に応じる |

### 採らなかった案

| 案 | 却下理由 |
| --- | --- |
| タスク完了のたび | 1件ごとに全指標を再集計することになり、オーケストレーターのコンテキストを直接圧迫する（00 §2.1）。評価コストが作業量に比例して増え、§4.5 に反する |
| 一定件数ごと（5件完了ごと等） | 件数はゴールへの前進量と相関しない。小さいタスク5件と大きいタスク5件が同じ扱いになる。まさに本評価が避けようとしている「消化数で測る」ことそのもの |

**評価コストが作業量に比例しないこと**が、節目方式を採る理由である。節目の数はセッション数と機能のまとまりの数で決まり、タスクの粒度に左右されない。

## 指標の算出（§22-9 の確定）

§6.2 の8指標を、07 の CSV とタスク別ファイルから算出できる形に落とす。**集計はスクリプト、判定はオーケストレーター**（§4.5）。

| # | 指標 | 算出方法 | 出所 |
| --- | --- | --- | --- |
| 1 | 完了タスク数 | 状態 = `完了` の行数 | CSV |
| 2 | 未完了タスク数 | 状態が `完了` / `中止` 以外の行数 | CSV |
| 3 | 停滞タスク数 | 09 の S-A（更新日が2日以上前かつ非終端）+ S-B（往復上限到達）。`PO確認待ち` / `保留` / 依存待ちの `未着手` は除く | CSV + 09 |
| 4 | ブロック中タスク数 | ブロッカー依存が未完了の行数 + 状態 = `保留` の行数 | CSV（依存タスク列から導出） |
| 5 | PO確認待ち件数 | 状態 = `PO確認待ち` のタスク数 **と** `docs/po-queue.md` の `未回答` の Q 数 | CSV + po-queue |
| 6 | 手戻り件数 | 各タスク別ファイルの `手戻り回数` の総和 | タスク別ファイルのメタデータ |
| 7 | ボトルネックとなっている工程 | 状態別のタスク数分布 + 各状態での滞留日数（更新日からの経過）の中央値 | CSV |
| 8 | ゴール達成に必要な残作業 | 未完了タスクの**内容**（数ではない） + まだタスク化されていないと分かっている作業 | CSV + 判断 |

### 指標5を2つ数える理由

1つの質問（Q）が複数のタスクをブロックすることがあり、逆に1つのタスクが複数の質問を待つこともある。**タスク側の件数は「組織がどれだけ止まっているか」、質問側の件数は「PO にどれだけ判断を求めているか」を表す**。両者が乖離しているときに分かることがある——質問が1件なのにタスクが8件止まっていれば、その1件を解けば組織が動き出す。

### 指標6の算出元

`手戻り回数` は、タスク別ファイルのメタデータに置く（07 の D-5）。**オーケストレーターが差し戻しを行った時点で加算する。** 作業ログから機械的に数えようとすると書き方に依存して壊れるため、明示的なカウンタを持つ。

「差し戻し」に数えるもの: レビューの修正要求（04 の O-2）、テストの不具合レポート（05 の O-2）、オーケストレーターによる担当の戻し（09 の段3）。**数えないもの**: 実装エージェントが自分で気づいて直したもの、Minor 指摘への対応。

### 指標8だけが判断を含む

1〜7 はスクリプトが出す。**8 だけは出せない。** 未完了タスクの一覧は機械的に取れるが、「ゴール達成に必要な残作業」は、タスク化されていない作業を含むためである。

ここを埋めるのがオーケストレーターの仕事であり、この評価の実質である。

---

## 判定 — 数値の列挙で終わらせない

01 の O-4 が定めた通り、**「ゴールに近づいているか」の判定と、そう判断した理由**を添える。判定は3値。

| 判定 | 目安 |
| --- | --- |
| **前進している** | 完了タスク数が増え、かつ指標8の残作業が**減っている**。停滞・ブロック中が全体の一定割合を超えていない |
| **停滞している** | 完了タスク数が増えていない。または停滞タスク・ブロック中タスクが積み上がっている。特定の工程に滞留が偏っている |
| **ゴールが揺らいでいる** | 完了タスク数は増えているのに、**指標8の残作業が減っていない、または増えている**。手戻り件数が増え続けている。PO確認待ちが増加傾向にある |

### 3つ目の判定が、この評価の存在理由である

**「タスクは消化されているがゴールに近づいていない」**——これを名前を付けて検知できるようにしておく。§6.2 が「単純なタスク消化数だけではなく」と書いたのは、この状態を指している。

疑うべきこと:

| 症状 | 原因の候補 |
| --- | --- |
| 残作業が減らない | ゴールの分解が誤っている。タスクを消化するたびに新しいタスクが同量発生している |
| 手戻り件数が増え続ける | 完了条件が判定基準として機能していない（04 確定事項 B が述べた「評価者が良し悪しを判別できない」状態） |
| PO確認待ちが増加傾向 | ゴール達成条件が確定していない（01 の E-1）。08 の「エスカレーションが多すぎるとき」と同じ信号 |
| 特定工程への滞留（指標7） | その工程のロールに対する作業指示が不足している。またはそのロールの担当範囲が広すぎる |

### 判定が「停滞している」「ゴールが揺らいでいる」だったときの行動

| 判定 | オーケストレーターがやること |
| --- | --- |
| 停滞している | 09 の検知後手順を、停滞している個々のタスクへ適用する。滞留が特定工程に偏っているなら、その工程への作業指示の品質を疑う |
| ゴールが揺らいでいる | **タスク分解をやり直す。** それでも残作業が減る見通しが立たなければ、**ゴール達成条件そのものを PO へ確認する**（01 の E-1、08 の形式で登録） |

2行目は、個々のタスクを直しても解けない。00 §2.6 の限界——深い推論と抽象化を要する課題は役割分割だけでは解決しない——に当たっている可能性があり、そのときに必要なのはゴールの見直しである。**組織の中で解こうとし続けることが、最も高くつく。**

## 出力の形

01 の O-4 の通り。8指標 + 判定 + 理由。**レポートは短く保つ。**

```markdown
## ゴール健全性 YYYY-MM-DD

判定: 前進している / 停滞している / ゴールが揺らいでいる
理由: （2〜3文。数値のどれを根拠にしたか）

| 指標 | 値 | 前回比 |
| 完了 / 未完了 / 停滞 / ブロック中 / PO確認待ち / 手戻り | ... | ... |

ボトルネック: （工程名と、そう判断した根拠）
残作業: （タスク化済みの未完了 + まだタスク化されていない作業）
次の一手: （判定に対して何をするか）
```

**前回比を持つのは指標1〜6である。** 前進しているかどうかは1時点の値では判定できない。前回の評価結果は `docs/handover.md` に残っている（11）ため、そこから取る。

「次の一手」を出力に含めるのは、評価がそのまま引き継ぎ記録として使われるためである（11）。**評価して終わりにしない。**

## 未確定のまま残すもの

- 「停滞タスクが全体の一定割合」の具体値。タスク総数に依存するため、運用で見極める。初期は割合を固定せず、傾向（増えているか）で判断する
- 集計スクリプトの実装。09 の検知スクリプトと同一のものにしてよい（どちらも CSV を読み、状態と日付を数える）。実装時に統合を検討する
