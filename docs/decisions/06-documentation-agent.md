# 06. ドキュメントエージェント 役割定義

**Status:** Confirmed（PO確認済み 2026-08-19）
**根拠:** 要件定義書 v0.1 §11 / §12 / §23
**前提:** 02 確定事項 B により、設計成果物は設計エージェントの持ち物。本ロールは**組織外向け**のドキュメントを担う。

---

## 前提：本組織が扱う文書の3つの層

「ドキュメント」という語が指すものが層によって異なるため、先に区別する。

| 層 | 内容 | 読み手 | 保守する主体 |
| --- | --- | --- | --- |
| **層1** | 本リポジトリ（`agents-org`）の要件定義・決定記録 | 組織を設計する人間（PO） | PO と、その作業を支援するセッション |
| **層2** | 開発対象リポジトリの `CLAUDE.md` / `.claude/rules/` / エージェント定義 | **AI組織自身**（全エージェント） | **オーケストレーター**（確定事項 D） |
| **層3** | 開発対象アプリの成果物ドキュメント | AI組織 と 人間 の両方 | **ドキュメントエージェント** |

**本ファイルが規定するのは層3である。** §11 が挙げる README・仕様・API文書・開発者向け文書はすべてここに属する。

層2 をドキュメントエージェントが持たない理由は確定事項 D に記す。

---

## ミッション

開発成果物に必要なドキュメントを、最新状態に維持する。（§11）

## 責務

§11 の通り。README更新／仕様ドキュメント更新／API等の技術ドキュメント更新／開発者向けドキュメント更新／実装変更とドキュメントの整合性確認。

**担当範囲**（02 確定事項 B）:

| | ドキュメントエージェント | 設計エージェント |
| --- | --- | --- |
| 対象 | README、API文書、開発者向け文書、利用者向け仕様書 | 設計成果物 |
| 読み手 | 組織外（利用者・将来の開発者） | 組織内（実装・レビュー・テスト） |
| 書くこと | 現在どうなっているか、どう使うか | なぜその方式にしたか、却下した案 |

## エスカレーション条件（ドキュメントエージェント → オーケストレーター）

§11 にエスカレーション条件の記載が無いため、新たに定義する。

| # | 条件 | 判定の目安 |
| --- | --- | --- |
| E-1 | 実装の意図が読み取れない | コードからも設計からも、何のための機能か判断できない |
| E-2 | 実装とドキュメントのどちらが正しいか判断できない | 既存文書と実装が矛盾し、どちらが意図された姿か決められない |
| E-3 | 公開範囲の判断が要る | 外部公開する情報の線引き（認証情報、内部構成、未公開機能） |
| E-4 | ドキュメントの構成そのものを変える必要がある | 個別更新では追いつかず、体系の再編が要る |

E-2 が実務上もっとも起きる。ドキュメントエージェントは実装の下流にいるため、**過去の意図と現在の実装のずれ**を最初に発見する位置にある。これを黙って実装側に合わせて書き換えると、意図されない仕様変更が記録として正当化されてしまう。

## 確定事項

### A. 層3 は「エージェント用マスタ」と「人間用ビュー」の2階建てとする — **確定**

```
docs/                      ← マスタ。正典。エージェントが読み書きする
  features/<機能名>.md         機能単位
  guides/<目的・シーン>.md      目的・シーン単位
  api/<対象>.md
README.md                  ← 人間用ビュー。マスタから生成する
docs/handbook.md           ← 人間用ビュー。マスタを結合した通し読み用
```

| | エージェント用マスタ | 人間用ビュー |
| --- | --- | --- |
| 位置づけ | **正典。ここだけが真実** | マスタからの**生成物** |
| 粒度 | 機能単位・目的単位・シーン単位に**細かく分割** | 結合された通し読み用 |
| 最適化の対象 | トークン効率（必要な断片だけ読める） | 人間の可読性 |
| 更新 | ドキュメントエージェントが直接書く | **スクリプトで生成する。手で書かない** |

**分割する理由**: エージェントは必要な断片だけを読めばよく、1ファイルに全機能が書かれていると毎回全体を読むことになる（§4.5 のトークン効率）。加えて、機能ごとに分かれていれば**複数のドキュメントタスクが衝突せず並列に走る**。

**人間用ビューを生成物にする理由**: 分割すると人間は全体像を掴みにくくなる。マスタと人間用を二重に手で書くと必ず乖離するため、**生成の一方向に固定する**。マスタが唯一の真実であり、人間用ビューは常に捨てて作り直せる。

**生成はスクリプトで行う**。文書の結合・目次生成は判断を伴わない機械的処理であり、§4.5「単純な繰り返し処理はスクリプトへ切り出す」に該当する。LLM に結合させると、トークンを消費したうえに書き換わる危険がある。

生成スクリプトの実装は最初のドキュメントタスクが発生した時点で作る。**人間用ビューは生成物なので、実装方式の判断（生成先、結合順、目次の作り方）はここでは固定しない。**

### B. ドキュメント更新の要否は実装エージェントが申告する — **確定**

実装エージェントの完了報告（03 の O-2）に、**ドキュメント影響**を項目として追加する。

| 項目 | 内容 |
| --- | --- |
| ドキュメント影響 | この変更で更新が要る文書。無ければ「無し」。判断がつかなければ「要判断」 |

オーケストレーターはこの申告を見てドキュメントタスクを起こす。

判断者を実装エージェントにする理由: 変更内容を最もよく知っており、判断が**ほぼ無コスト**で済む。ドキュメントエージェントに判断させると、変更を調べ直すために別途タスクとコンテキストが要る。オーケストレーターに判断させると、要約された報告からの推測になり精度が落ちる。

「要判断」を許すのは、§12「分からないことを無理に決めない」に従うため。

### C. 起動タイミング — マスタは機能のまとまりごと、人間用ビューは生成のみ — **確定**

| 対象 | タイミング |
| --- | --- |
| エージェント用マスタ | **機能のまとまりが完成した時点**。関連する実装タスク群が一通り終わったら、オーケストレーターがドキュメントタスクを起こす |
| 人間用ビュー | マスタ更新後に**スクリプトで再生成**。判断を伴わないので、都度でも、セッション終了時でもよい |

A で分割したことにより、この頻度が現実的になる。1ファイルに集約していると更新のたびに全体を読み書きすることになり、頻度を上げられない。分割されていれば該当ファイルだけを触ればよく、コストが粒度に比例する。

### D. 層2（開発対象リポジトリの規約）はオーケストレーターが保守する — **確定**

`CLAUDE.md`、`.claude/rules/`、エージェント定義など、**AI組織自身の動き方を規定する文書**は、ドキュメントエージェントではなくオーケストレーターが保守する。

理由: これらは成果物ではなく**組織の設定**である。読み手はエージェントであり、内容は組織の運営方針そのもの。オーケストレーターは §6.2 でリソース管理・進捗管理を担っており、組織の動き方に責任を持つ立場にある。

§6.3「通常のドキュメント作成は担当しない」との関係: **層2 は「通常のドキュメント」ではない**。成果物の説明文書ではなく、組織自身への指示である。したがって §6.3 とは矛盾しない。ただし境界を明確にしておく。

| | オーケストレーターが書く | ドキュメントエージェントが書く |
| --- | --- | --- |
| 対象 | 層2（組織への指示） | 層3（成果物の説明） |
| 例 | 「このリポジトリでは pnpm を使う」 | 「この API はこう呼ぶ」 |

なお、CLAUDE.md は **200行を超えると遵守率が落ちる**（00 §1.2）。オーケストレーターは層2を保守する際、この制約を守る。超えそうな場合はトピック別に `.claude/rules/` へ分割する。
