# 19. Claude Code の Agent Teams を採るかどうか

**Status:** Confirmed（実測から導出して確定 2026-08-26。異論があれば差し戻せる）
**根拠:** `docs/experiments/01-agent-teams.md`（検証0〜4・対照実験・追試。すべて実測）、要件定義書 v0.2 §4（Claude Code 標準機能を最大限使う）/ §14（サブエージェント間の自由な通信はしない）/ §18（独自設定ファイルを作らない）、`docs/decisions/00-research-notes.md` 制約1、`docs/decisions/12-agent-addition.md`（直接通信の経路を増やすときは意図的に摩擦を残す）
**position:** §23 の12項目には無い。Claude Code 本体に新しく現れた機能への対応として確定させた。

## この文書が確定したこと

- **MVP では Agent Teams を採らない。** 既定（無効）のまま運用する
- **配布物に有効化の設定を混ぜない。** `org/settings.snippet.json` に関連する環境変数を書かない
- **要件定義書 §14.2 が認めた3経路の直接通信は、Agent Teams を使わずに実装する。** 実装は済んでいる（コミット `252e29d`）
- **自前で持っているもの（タスク台帳・PO確認待ちキュー・停滞検知・稼働状況のモニタ）は、どれも置き換えない**
- **再評価する条件を3つ決めた**（末尾 D）

---

## A. Agent Teams とは何か、なぜ判断が要ったか

**Agent Teams** は Claude Code 本体が持つ実験的な機能で、複数の Claude Code セッションを1つの「チーム」として動かす。既定では無効で、環境変数 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` を立てた対話セッションでだけ有効になる。有効にすると、そのセッションを長とするチームが自動で1つ作られ、起こしたエージェントが名簿（`~/.claude/teams/<チーム名>/config.json`）へ登録され、メンバーごとの受信箱ができる。

判断が要ったのは、**この組織が自前で作った4つのものと正面から重なる**ためである。

| 自前で持っているもの | Agent Teams 側の対応物 |
| --- | --- |
| 担当エージェント間の直接通信を禁じ、オーケストレーターをハブとする規約（§14） | チームメンバーが名簿を通じて呼び合う仕組み |
| 自作タスク台帳（CSV索引 + タスク別 Markdown） | チームで共有するタスクリスト |
| PO確認待ちキュー（`docs/po-queue.md`） | チームメイトから人間への問い合わせ |
| 停滞検知スクリプト（`org-check.py`） | チームの稼働状況の把握 |

設計制約1（要件定義書 §4）は「**Claude Code 標準機能を最大限使う。CLAUDE.md と Skills で足りることに独自の仕組みを作らない**」と定めている。標準側に同等物があるなら、自前実装を続ける理由を説明できなければならない。**そこで、推測ではなく実測で確かめた。**

---

## B. 実測の結果 — 重なりは4つとも解消しなかった

詳細と証拠は `docs/experiments/01-agent-teams.md` にある。ここには結論だけを置く。

### B-1. 直接通信は、Agent Teams の上乗せ分ではない

**エージェント間の直接通信は、Agent Teams を無効にしたままでも使える。** 対照実験で確認した——子エージェントはメッセージを送る道具（`SendMessage`）を持ち、親（メインセッション）へも、別の子エージェントへも本文が届いた。

さらに追試で、**起動時に名前を付ければ（`Agent` ツールの `name`）、素の名前だけを宛先にして送れる**ことも確かめた。これも Agent Teams が無効な状態での結果である。

**つまり §14.2 の3経路は、この機能を採らずに実装できる。** 実際に実装した（宛先を渡す手順を配布物へ入れた。コミット `252e29d`）。

### B-2. タスク台帳は置き換えられない。機能が存在しないため

**「入る項目が少ない」のではない。共有タスクリストへ書き込む道具（`TodoWrite`）が、このビルドのチームのセッションに存在しない。** 常時読み込まれる道具の一覧にも、必要時に読み込む一覧にも無く、名指しで検索しても該当が無い。チーム用のタスク置き場（`~/.claude/tasks/`）は最後までファイル0件だった。

自作台帳が持つ13項目との突き合わせは、**全10項目が「該当なし」**で終わった。

### B-3. PO確認待ちキューの設計根拠は、そのまま有効

**チームメイトから PO へ直接問いを出す手段は無い。** 人間へ選択肢を出して問う道具（`AskUserQuestion`）は、道具の制限をかけていない汎用エージェントにも与えられていない。一方、チームの長（メインセッション）はこれを持っている。

**これは Agent Teams の有無と無関係である。** 調査メモ（`00`）の制約1「サブエージェントは `AskUserQuestion` を使えない。PO確認待ちキューをオーケストレーターが一元管理するのは技術的必然」は、どちらの状態でも成立する。

### B-4. 停滞検知と稼働状況のモニタは、作り替え不要

チームメイトは `Agent` ツールで起こす限り**従来のサブエージェントと同じファイルを書く**（`backendType` が `in-process` のため）。稼働状況のモニタ（`org-monitor.py`）の出力に、そのまま1体として現れた。**モニタの改修は要らなかった。**

停滞検知（`org-check.py`）はタスク台帳を読むものであり、B-2 の通り台帳は置き換わらないので影響を受けない。

## C. 採らない理由

上乗せ分は、実測の結果**次の3つだけ**に絞られた。

| 上乗せ分 | 中身 |
| --- | --- |
| 名簿 | 誰が居るかが `config.json` に記録される |
| 受信箱 | メンバーごとの受信箱ファイルができる |
| 伝言の体裁 | 指示が送り主を明示した形で届く |

この3つに対して、採る側のコストと不利益は次の通り。

### C-1. 経路が緩むこと自体が、この組織にとっては不利

要件定義書 §14 は「担当エージェント同士の自由な通信はしない」と定め、`12` は「**直接通信の経路を増やすときだけは意図的に摩擦を残す**」としている。

**Agent Teams を無効にした状態では、この制限が規約だけでなく仕組みとしても成立している。** 担当エージェントは誰が居るかを一覧する手段を持たないため、**オーケストレーターが作業指示で教えた宛先にしか送れない。** 教えなければ、その経路は存在しない。

名簿があると、この「探せないから送れない」という物理的な壁が下がる。**上乗せ分の筆頭である名簿は、この組織にとっては利点ではなく、規約を仕組みで裏打ちしていたものを外す変更である。**

### C-2. 対話セッション専用である

有効にできるのは対話セッションだけで、**非対話モード（`claude -p`）では有効にならない**（検証0）。自動実行・バッチ実行の道が塞がるため、将来の運用の幅を狭める。

### C-3. 実験的機能である

既定で無効であり、起動オプション（`--agent-teams`）はこのビルドでは受け付けられず、チームを作る道具（`TeamCreate`）も存在しない。**仕様が固まっていない。** 配布物がこれに依存すると、本体の更新で組織が動かなくなりうる。配布先は開発対象リポジトリであり、追随の負担は既に論点になっている（`14` の論点1）。

### C-4. 有効化には環境変数が要る

**これは §18（独自設定ファイルを作らない）に触れるものではない**——Claude Code 標準の設定であって、独自形式のファイルではない。ただし配布物へ混ぜると、**組織を入れた全リポジトリで実験的機能が有効になる。** 採らない以上、混ぜない。

## D. 再評価する条件

**「採らない」は現時点の判断であって、永続の否定ではない。** 次のいずれかが起きたら、この文書を差し戻して評価し直す。

1. **別プロセスの独立セッションをチームに加える必要が出たとき。** 今回検証したのは `Agent` ツールで起こす形（同一プロセス）だけである。独立セッションを組み込む形は未検証で、**その場合は稼働状況のモニタに映らない見込み**であり、名簿（`config.json`）を読む改修が要る。並列実行の規模を上げる段になったら、ここが判断の分かれ目になる
2. **共有タスクリストへ書き込む道具が本体に実装されたとき。** B-2 の「置き換えられない」理由は機能の不在であり、設計上の優劣ではない。実装されたら突き合わせをやり直す
3. **Agent Teams が実験的機能でなくなったとき。** C-3 の理由が消える

**再評価するときに、まず確かめるべき未検証事項:**

- 設定ファイル経由での有効化（`.claude/settings.local.json` の環境変数欄）が単独で効くか。効くなら、配布物へ混ぜずにリポジトリ単位で実験を切り分けられる
- Agent Teams を有効にした状態で、**名前の使い回しがどう扱われるか**。無効な状態では送信が拒否されるが、名簿に登録される形では挙動が変わりうる
- エージェント定義に実行モデル（`model`）を明示した場合の引き継ぎ、スキルとMCPサーバの指定の扱い
- 公式ドキュメント由来の制限6件のうち、本実験で確かめていない5件

---

## E. この判断で得られたもの

**採らない結論だが、検証は無駄ではなかった。** 3つの成果が残った。

1. **§14.2 の3経路が、規約としては在るのに実際には成立していなかったことが判明した。** 宛先を渡す手順がどこにも無く、担当エージェントは相手を探せない。往復はすべてオーケストレーターを経由する形に落ちていたはずである。**この欠落を埋めた**（コミット `252e29d`）
2. **`org/agents/` の定義が、道具の絞り込みも層2の規約も引き継いだまま機能することを確認した**（検証1）。レビュー担当が編集系の道具を持たない設定は守られ、さらに自分で迂回することも拒んだ
3. **`00` の制約1（`AskUserQuestion` は担当エージェントに与えられない）が、機能の有無に関わらず成立することを確かめた**
