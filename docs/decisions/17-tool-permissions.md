# 17. ツールの実行許可

**Status:** Confirmed（既存の確定事項から導出。異論があれば差し戻せる 2026-08-25）
**位置づけ:** 要件定義書 §23 の12項目には無い。配布物（`org/`）に実行許可の設定例が一切無く、**「PO は細かな作業指示を出さない」という設計前提（§1）が実運用で崩れていた**ため確定させた
**関連:** `13`（実行形態と配置）/ `15`（ブランチ運用と並列実行）/ `16`（トークン消費の可視化）

## この文書が確定したこと

- **配布物は `permissions` の推奨値を持つ。** 置き場は `org/settings.snippet.json`（hook と同じファイル）
- **事前に許可するのは、組織そのものが常時使うものだけ** — 変更を伴わない Git の閲覧、規約が担当エージェントに命じている `git add` / `git commit` / `git push`、配布物のスクリプト2本
- **開発対象そのもののビルド・テストのコマンドは、配布物に書かない。** 導入した側が足す
- **未コミットの変更を消す Git の操作は禁じる**（`deny`）。担当エージェントが作業ツリーを共有しているため
- **秘密情報のファイルの読み取りを禁じる**
- **「ブランチの作成と切り替えはオーケストレーターだけ」は、この設定では強制できない。** 規約のままとする

---

## なぜ決める必要があったか

Claude Code は、シェルコマンドの実行やファイルの読み書きのたびに人間へ許可を確認するのが既定である。担当エージェント5つは**いずれもシェルコマンドを実行する道具（`Bash`）を持っている**（`agents/*.md` の `tools:` 欄）。

配布物には許可の設定例が無かった。その結果、トライアル運用では **`git status` ひとつ動かすのにも PO へ確認が降りた**。

要件定義書 §1 は「PO はゴールと判断を提供し、細かな作業指示は出さない」と定めている。**許可の確認が降り続けるなら、PO は結局すべての手を見ていることになり、この前提は成立していない。** 組織化の利得そのものが消える。

---

## 何を許可し、何を許可しなかったか

判断の基準は2つ。**(1) その操作が何かを書き換えるか。(2) その操作がどれくらいの頻度で起きるか。**

読むだけで、かつ頻繁に起きるものを許可する。書き換えるか、稀にしか起きないものは確認させる。

| 分類 | 対象 | 判断 |
| --- | --- | --- |
| 読むだけ・高頻度 | `git status` / `git diff` / `git log` / `git show` / `git blame` / `git ls-files` / `git rev-parse` / `git branch --list` | **許可** |
| 書き換えるが、規約が命じている・高頻度 | `git add` / `git commit` / `git push` | **許可**。層2の規約（`org/CLAUDE.md` の Git の節）が担当エージェントに実行させると定めている。押し先は作業ブランチなので、未レビューのコードが既定ブランチへ載ることはない（`15`） |
| ほぼ読むだけ・高頻度 | `org-check.py` / `org-tokens.py`（`python3` と `python` の両方の呼び出し名） | **許可**。書き換えるのはトークン消費の記録だけで、それは機械が上書きすると決めてある（`16`） |
| 影響が広い・低頻度 | `git merge` / `git switch` / `git checkout <ブランチ名>` / `git branch <新しい名前>` / `git rebase` | **許可しない**。まとまりごとに1回しか起きないので、確認が出ても PO の負担にならない。ブランチの切り替えは**同じ作業ツリーで動いている担当エージェント全員に影響が及ぶ**（`15`） |
| 技術スタックに依存 | 開発対象のビルド・テスト・実行 | **配布物には書かない**（後述） |

### 禁止したもの

**並列で走る担当エージェントは、同じ作業ツリー（同じチェックアウト）を共有している**（`15` の「決定を規定する事実」）。したがって片方が未コミットの変更を消す操作は、**もう片方の成果を巻き添えにする**。

`git reset --hard` / `git clean -f` / `git restore` / `git checkout --` / `git push --force` / `git push -f` を禁じる。

加えて `.env` / `.env.*` / `*.pem` / `id_rsa` / `id_ed25519` / `credentials.json` の読み取りを禁じる。読めば会話記録に残り、報告や成果物へ混ざりうるため。

## 開発対象のコマンドを配布物に書かない理由

配布物は**どのリポジトリへも入る**（`13`）。そこで何を実行するかは分からない。

推測で `npm test` を書けば、Python のリポジトリでは無意味な行が残る。網羅しようとすれば、使われない許可が積み上がる——**許可は「使われないなら無害」ではない。** 何を許してあるのかを人が読み切れなくなった時点で、設定は安全装置として機能しなくなる。

代わりに、**導入した側が足す**と決め、README に例と注意書きを置いた。注意書きの中身は「足す前に、そのコマンドが何を書き換えるかを確かめること」——テストの実行に見えて、実際にはデータベースを作り直す、外部へ通信する、といったものがあるため。

**この追記の漏れは最も起きやすい。** そのため初回運用の点検手順（`org/skills/org-first-run-check/`）に点検項目を1つ足し、「テストやビルドのたびに確認が出ていたら追記漏れ」と判定させるようにした。

## この設定でできないこと

### 担当エージェントごとに許可を変えられない

実行許可の設定は**セッション全体に効き、担当エージェントもそれを受け継ぐ**。どの担当が呼んだかで許可を変える仕組みは無い。

したがって `15` が定めた「**ブランチを作る・切り替えるのはオーケストレーターだけ**」は、**この設定で強制することができない**。層2の規約（`org/CLAUDE.md`）に書いてあるだけであり、破れる。

区別できるのは**道具の単位**だけである。エージェント定義ファイルの `tools:` 欄に何を書くかで、その担当が持つ道具そのものを絞れる。レビューエージェント（`org/agents/org-review.md`）が編集系の道具を持たないのはこの方式である。ただしこれは「シェルコマンドのうちこれだけ」という粒度では指定できない。

### 禁止は前方一致であり、すり抜ける

`deny` に書いた `git push --force` は、コマンドの**先頭からの一致**で照合される。引数の順番を変えた書き方（`git push origin main --force` のように `--force` を後ろへ置いたもの）は一致せず、禁止に当たらない。

**事故を減らす柵であって、壁ではない。** 悪意ある回避を防ぐものではなく、うっかり実行することを減らすものである。

### Windows で Git Bash が無い実行環境では、コマンドの書き方が違う

その環境ではシェルコマンドが PowerShell の書き方になる。`rm -rf` ではなく `Remove-Item -Recurse -Force` が走るため、上記の禁止項目は当たらない。README に注意書きを置き、その環境で運用するなら PowerShell の書き方でも同じ禁止項目を足すよう促している。
