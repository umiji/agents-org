# 論点1. 配布方式 — 手動コピーか、プラグイン機構か

**状態:** **決着済み（PO 判断 2026-08-28）。案B（プラグイン機構）を採る。** 確定内容・未確定として残っている点・次にやる調査は `docs/decisions/24-distribution-plugin.md` にある。**この節の以下の記述は、決着に至った検討の記録である**

## 何を決める必要があるか

組織の実行時ファイル（`org/` の中身）を、開発対象リポジトリへどう届けるか。

## 選択肢

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| **A. 手動コピー**（現状） | `org/README.md` の手順どおりファイルをコピーする | 仕組みがゼロ。何が置かれるか完全に見える | 導入のたびに手作業。**更新の追随ができない**（配布元が直っても、導入済みのリポジトリは古いまま） |
| **B. プラグイン機構** | Claude Code のプラグインとしてまとめ、有効化するだけで入る | 「定義ファイルを足すだけ」（要件定義書 §4.4）と「既存拡張と共存」（§19）の両方をより強く満たす。更新の追随ができる | プラグインの構成を学ぶ必要がある。組織の中身がプラグインの枠組みに縛られる |
| C. インストールスクリプト | コピーを自動化するだけ | Aの手間だけ減る | 更新の追随は解決しない |

## 推奨

**MVP の間は A のまま。実際に2つ目の開発対象リポジトリへ導入するときが B の引き金。**

1つのリポジトリでしか動かしていない間は、更新の追随という B の最大の利点が効かない。2つ目が現れた瞬間に、「配布元を直したとき、導入済みの2つをどう追随させるか」が実際の問題になる。

## 注意

要件定義書 §18 は「独自の設定ファイルを作らない」と定めているが、**プラグインの構成ファイルは Claude Code の標準形式であって独自形式ではない**ため、§18 には抵触しない。

# 論点2. 担当エージェントを独立セッションで動かすか

**状態:** **Pending（PO が判断を保留。2026-08-28）。** MVP は現行構成（担当エージェントをオーケストレーターの子プロセスとして起動する形）のまま進める。**判断を求めたが、PO は今は決めないと述べた**——移行の引き金（オーケストレーターのコンテキストが実際に律速になること）がまだ観測されていないため

## 何を決める必要があるか

現在、5つの担当エージェントはオーケストレーターの子プロセスとして起動される。これを**それぞれ独立したセッション**にすると、各担当エージェントが PO へ直接質問できるようになる。

## 調査済みの事実（2026-08-20 に一次資料で確認）

再調査しなくてよいように記録する。

| 事実 | 内容 |
| --- | --- |
| 起動方法 | `claude --bg --agent <名前> "指示"` で、エージェント定義を独立したセッションとして背後で起動できる |
| 監視画面 | `claude agents` で一覧・監視・新規起動ができる。状態は Working / **Needs input** / Idle / Completed / Failed / Stopped の6種で色分けされる |
| 質問の受け取り方 | 質問したセッションは `Needs input` になり、**他のセッションはブロックされない**。`Space` で内容を覗き、**選択肢は番号付きで表示され数字キーで選べる** |
| 作業ツリー | **セッションごとに Git の worktree（同じリポジトリの別チェックアウト）へ自動的に分離される** |
| 機械可読な状態 | `claude agents --json` で取得できる |
| コスト | **並列セッション数に比例して利用枠を消費する（10並列なら約10倍）** |
| 生存期間 | 未接続のまま約1時間で停止する |

## 利点

- **オーケストレーターのコンテキスト上限が律速でなくなる。** ロールごとに独立した予算を持つ
- 中継による情報の欠落が無くなる（オーケストレーターが要約して伝えると細部が落ちる）
- 1つのセッションが落ちても組織全体は止まらない

## 新しく発生する問題

| 問題 | 内容 |
| --- | --- |
| **台帳の書き込み衝突** | 「索引を書けるのはオーケストレーターだけ」は、彼が唯一の直列アクターだから成立していた。独立セッションでは崩れる。**さらに worktree 分離が台帳の共有と正面から衝突する**（各セッションが自分のチェックアウトに書くため、台帳が分裂する） |
| **PO への質問が N 方向になる** | 制約が消えてもキューは要る。人間は同時に1つしか答えられない。**単一キューは技術的制約への対処であると同時に、流量の抑制としても働いていた** |
| **回答が層2へ昇格しなくなる** | 各セッションが直接聞くと、回答が N 箇所に散り、一般的な基準として層2へ昇格されない。同じ問いが何度も PO に飛ぶ |
| コスト | 上記のとおり並列数に比例 |
| 停滞検知の対象が増える | タスクの停滞に加え、**セッションの死活**も見る必要が出る |

## 台帳の分裂への対処案

- 台帳を worktree の**外**（メインのチェックアウト、または別ディレクトリ）に置く
- 索引を**追記専用の記録**にし、一覧はスクリプトで生成する（索引が「書くもの」から「生成されるもの」になる）
- 各セッションが**自分のファイルだけ書く**規律を維持し、索引を導出物にする ← 現行の思想の自然な延長

## 推奨

**全面移行より、質問の性質で経路を分ける方が筋が良い。**

| 問いの種類 | 経路 | 理由 |
| --- | --- | --- |
| **タスク内の明確化**（「この API の戻り値はどちらの解釈か」） | 担当セッションが直接 PO へ | 中継すると要約で細部が落ちる。影響範囲がそのタスクに閉じている |
| **要件・ゴールに関わるもの** | オーケストレーターのキューへ | 複数タスクに波及し、**一度記録して再利用すべき**もの。層2への昇格経路が要る |

これなら「回答が層2へ昇格しない」問題を避けつつ、中継による情報損失だけを取り除ける。

**移行の引き金**: オーケストレーターのコンテキストが実際に律速になったとき。それまでは、解決済みの問題（キューイング）を、未解決の2つ（並行制御と人間側の競合）に交換することになる。

# 論点3. 進捗の可視化をどこまで作るか

**状態:** **Pending（PO が判断を保留。2026-08-28）。** 停滞検知スクリプト（`org/scripts/org-check.py`）に1行出力の機能だけ入れてあり、配布物へは同梱していない。**判断を求めたが、PO は今は決めないと述べた**

## 調査済みの事実（2026-08-20 に一次資料で確認）

| 手段 | 何ができるか |
| --- | --- |
| **エージェントパネル** | 子プロセスとして走っているエージェントが、入力欄の下に1行ずつ並ぶ。既定の表示は「名前・説明・トークン数」 |
| **`subagentStatusLine` の設定** | その1行を**自分のスクリプトの出力に差し替えられる**。渡ってくる項目は id / 名前 / 状態 / 説明 / **開始時刻** / トークン数 / コンテキスト上限 / 作業ディレクトリ |
| **`statusLine` の設定** | 画面下部に任意のシェルスクリプトの出力を出せる。コンテキスト使用率・コスト・利用枠の残りも取れる |
| **`claude agents`** | 独立セッション構成のときの監視画面（論点2を参照） |

## 分かったこと — 組み込みで見えるのは「セッションの状態」であって「進捗」ではない

| 見たいもの | どこから取れるか |
| --- | --- |
| 今どの担当エージェントが動いているか | 組み込みで取れる |
| 何のタスクをやっているか | 組み込みは説明文しか持たない。**起動時にタスクIDを含める規約が要る** |
| 工程・停滞・残作業・手戻り | **タスク台帳以外に無い** |

## 現状

停滞検知スクリプトに `--statusline` を入れてあり、次のような1行が出る。

```
[org] 完了 1/11 · 実装中4 テスト中1 レビュー中1 · 停滞2 · PO待ち1 · 手戻り4
```

## 残っている判断

- `statusLine` の設定として配布物へ同梱するか（現状は同梱していない）
- `subagentStatusLine` 用のスクリプトを作るか。作るなら、**エージェント起動時の説明文にタスクIDを入れる規約**が要る

## 注意 — 進捗率（％）は出さない

タスク単位では完了か未完了かの二値しかなく、「12/31 完了 = 39%」は嘘をつく。残りの19件が消化した12件と同じ重さである保証がないためである。ゴール健全性評価が「タスク消化数ではなくゴールへの前進」を見て、**「ゴールが揺らいでいる」という第3の判定値**を持つのはこのためである。

# 論点4. 質問をさばく中間エージェントを置くか

**状態:** 未決。MVP では置かないと判断した（`docs/decisions/22-org-self-improvement.md` にも「中間エージェントは置かずに進める」として記録がある）

## 何を決める必要があるか

担当エージェントからの問い合わせを、オーケストレーターの手前で受けて処理する専用のロールを置くか。

## 技術的な可否

**置ける。** エージェント間でメッセージを送る機能があるため、担当エージェント同士の通信は可能である。

**ただし決定的な限界がある。** 中間エージェントも子プロセスとして起動される以上、**人間へ質問できない。**

| エスカレーションの段 | 中間エージェントが担えるか |
| --- | --- |
| 1. 自分で解決 | 担える。決定記録・設計成果物・規約を検索して答える |
| 2. 他エージェントへ相談 | 担える |
| 3. オーケストレーターへ | 中継はできるが、判断はできない |
| 4. PO確認待ちへ | **担えない。人間に届かない。必ずメインセッションへ戻る** |

## 価値はどこにあるか

**PO への経路を短くすることではなく、オーケストレーターのコンテキストを守ること。** 問い合わせの全文が司令塔のコンテキストに入らずに済む。

境界は一文で言える——**「既に決定済みの事項を検索して答える。新しい判断はしない」**。要件定義書 §17.1 の「境界が一文で言えないなら追加しない」は満たす。

## 推奨

**MVP では置かない。** 理由は3つ。

1. 6ロール規模では問い合わせ量がそれほど出ない
2. 一段増えると往復とトークンが増える（中間エージェント自身がコンテキストを持つ）
3. **「答えられるものを答える」は、本来各エージェントがエスカレーション段1でやること。** 中間エージェントが必要に見えるということは、段1が機能していない信号かもしれない

**先に試すべきこと**: 同じ問いが繰り返し上がるなら、まず **PO の回答を層2へ昇格させる**（要件定義書 §13.3）。それを尽くしてもなお溢れるときが、中間エージェントの引き金である。

# 動かせない制約（参考）

論点2・4 の検討で確認した、設計で回避できない事実。

- **ツールの実行許可だけは、必ず人間に来る。** どのエージェントからのメッセージも、保留中の許可要求への承認にはならない
- **子プロセスとして起動されたエージェントは、途中で止まって問い合わせることができない。** いったん結果を返して終わり、親からメッセージを受けて再開する。**ただし再開時に自分の記憶は完全に保持される**（止まっていた間に親側で起きたことは入らない）
