# 07. タスク管理仕様

**Status:** Confirmed（PO提案を採用 2026-08-20）
**根拠:** 要件定義書 v0.1 §6.2 / §13 / §18 / §22-1〜4 / §23-7
**前提:** 01〜06 で各ロールの入力・出力・エスカレーション条件が確定済み。本ファイルはそれらが流れる**器**を定める。

---

## 決定の出発点：PO の task-cycle 方式を採用する

PO が別プロジェクトで運用している `task-cycle` スキル（**CSV索引 + タスク別Markdown**）を、本組織のタスク管理の基礎として採用する。

01 では「タスクリストの保存形式は意図的に決めない」としていた。これを解く。理由は、§6.2 の停滞管理とゴール健全性評価が**機械的な集計**を要求し、§4.5 がそれをスクリプトへ切り出せと定めているため。形式が未決のままでは 09・10 が書けない。

### なぜこの方式が本組織に適合するか

task-cycle は単一セッションの単独作業を想定して作られているが、その構造は本組織の制約と正面から噛み合う。

| 本組織の制約 | task-cycle の構造がどう応えるか |
| --- | --- |
| サブエージェントは**新規の隔離コンテキスト**で始まる（00 §1.1） | タスク別ファイルなので、担当は自分のタスク1件分だけ読めばよい |
| 並列実行できる単位を意図的に作る（01 O-0、00 §2.5） | タスクごとにファイルが分かれ、**同時更新が衝突しない** |
| オーケストレーターのコンテキストは報告のたびに膨張する（00 §2.1） | CSV索引だけで全体像が取れる。詳細は必要なときだけ開く |
| 停滞検知・健全性評価をスクリプト化する（§4.5） | CSV が機械可読。判断はMarkdown、集計はCSV、と役割が分かれている |
| 計画を早期に外部化する（00 §2.4、01） | 登録時点で両ファイルが書かれる。「後でまとめて記録する」が起きない |

PO 側の実績も根拠になる: 単一Markdown表で運用した結果 42KB に達し、1タスクを触るセッションが完了済み全タスクの証拠まで読み込む状態になった。**同じ失敗が本組織では6ロール分の並列で起きる。**

### §18「独自設定ファイルを作らない」との関係

抵触しない。理由は3つ。

1. **タスクリストは設定ファイルではない。** §18 が禁じているのは、Claude Code 標準機能で足りるものを独自の設定形式で置き換えることである。タスクリストは組織の**状態記録**であり、CLAUDE.md や Skills が代替できる対象ではない。
2. それでも構造化形式を選ぶ理由は、§18 が挙げる例外「機械的な読み書きが必要な構造化設定」に実際に到達したためである。§6.2 の停滞管理・健全性評価は集計を必須とし、§4.5 はそれをスクリプト化せよと定める。**「将来必要になりそうだから」ではなく、既に確定した責務が要求している。**
3. CSV は独自形式ではない。加えて、**判断と文脈はすべて Markdown 側に置き、CSV は索引に徹する**。構造化の範囲を最小に抑える。

## 保存形式

開発対象リポジトリの中に置く（本リポジトリ `agents-org` ではない。層2・層3の区別は 06 参照）。

```
docs/task-list-{project-name}.csv   索引。{project-name} = リポジトリのルートディレクトリ名
docs/tasks/T-XXX.md                 タスク別の詳細記録。正典
docs/tasks/README.md                台帳の読み方（ブートストラップ時に作る）
docs/po-queue.md                    PO確認待ちキュー（08 で規定）
docs/handover.md                    セッション引き継ぎ記録（11 で規定）
```

### CSV索引の列

```csv
ID,作成日,更新日,タスク名,状態,優先度,担当,依存タスク,ドキュメント
```

task-cycle の7列に **優先度** と **担当** を加えた。この2列は §6.2 の必須項目であり、かつオーケストレーターが**詳細ファイルを開かずに次の一手を決める**ために要る。索引に入れる基準はこれ一つ——「詳細を開かずに判断へ使うか」。使わないものは詳細ファイルへ置く。

| 列 | 規約 |
| --- | --- |
| ID | `T-###`（3桁連番）。**再利用しない。** 中止したタスクも行を残し、番号は退役させる |
| 作成日 / 更新日 | `YYYY-MM-DD`。不明なら `不明` と明記。**空欄にしない** |
| タスク名 | 10〜40文字程度。何をするタスクか一読で分かること |
| 状態 | 後述の10状態のいずれか |
| 優先度 | 高 / 中 / 低 |
| 担当 | エージェント名。未割当なら `未割当` と明記 |
| 依存タスク | 後述の依存表現。無ければ `無し` と明記。**空欄や `-` にしない**（「未確認」と読めてしまう） |
| ドキュメント | リポジトリルート相対のパス（例 `docs/tasks/T-001.md`） |

**値にカンマ・改行を含めない。** 索引は短い値しか持たないため、これで引用符処理が不要になり、スクリプト側が壊れにくくなる。長い記述が要るものは詳細ファイルの領分である。

### タスク別ファイルの構成

```markdown
# T-XXX: タスク名

## メタデータ
- 作成日: YYYY-MM-DD
- 更新日: YYYY-MM-DD
- 状態: 未着手
- 優先度: 中
- 担当: 未割当
- 進捗: 一行で現状
- 依存: 依存タスクの全文（ブロッカーなら理由を必ず書く）
- TDD適用可否: 適用 / 適用外（適用外なら理由）
- 手戻り回数: 0

## 目的            ← なぜこの変更が要るか。飛ばすと何が壊れるか
## 変更範囲        ← どのファイル・領域を触るか
## 禁止事項        ← 触ってはいけないもの
## 完了条件        ← 二値で判定できる形。コマンドと出力で確認できること
## 判断してよい範囲 ← どこまで自律的に決めてよいか（01 の O-2 必須項目）
## テスト方法      ← 単体／結合／回帰。実環境確認の要否と実施者
## 停止条件        ← このタスク固有のもの。無ければ「08 の共通停止条件のみ」
## 参照すべき成果物 ← 設計成果物、既存コード、確定済み決定記録
## 成果物          ← 完了時に何ができたか（ファイル・コミット）
## ブロッカー      ← 今止めているもの。PO確認待ちなら Q-XXX

## 決定ログ        ← なぜそうしたか。決定／却下案と理由／出典。必須（無ければ「特記なし」）
## 作業ログ        ← いつ何をしたか。追記式。完了時に数行へ畳んでよい
## 証拠            ← 完了条件を満たした根拠。コマンドと実出力のみ
```

#### §6.2 のタスク項目との対応

| §6.2 の項目（+ 01 で追加した2項目） | 置き場所 |
| --- | --- |
| タスクID / タスク名 / 優先度 / 担当エージェント / 前提タスク / ステータス / 作成日時 / 最終更新日時 | CSV索引（詳細ファイルのメタデータにも写す） |
| 目的 / 詳細 / **完了条件** / **TDD適用可否** / 成果物 / ブロッカー / 備考 | タスク別ファイル |

§6.2 の「詳細」は、task-cycle の `変更範囲` / `禁止事項` / `テスト方法` へ分解される。「備考」は `決定ログ` / `作業ログ` が受け持つ。**分解した方が良い**理由は、単一の「詳細」欄では書かれる内容が書き手ごとにばらつき、レビュー・テストが判定の根拠を探せなくなるため。

#### タスク別ファイルは、そのまま作業指示になる

これが本方式を採る最大の実務上の利得である。

01 の O-2（作業指示）が要求する項目——目的 / 詳細 / 完了条件 / 参照すべき成果物 / **判断してよい範囲** / 期待する成果物の形——は、上記の構成にすべて含まれている。よって**オーケストレーターは作業指示を毎回書き下ろす必要がなく、タスク別ファイルを参照させればよい**。

これは 00 §2.2 の **Incomplete Context Transfer** への構造的な対策になる。指示を都度書くと項目の抜けが起きるが、テンプレートが固定されていれば、抜けは「セクションが空である」という形で可視化される。01 が定めた「受け取った側は着手前に指示の充足を確認する」も、確認対象がファイル上の定位置にあるため機械的に行える。

#### 3つの記録を分ける（task-cycle §2.1 を継承）

| セクション | 答えるもの | 寿命 |
| --- | --- | --- |
| `## 決定ログ` | **なぜそうしたか** | 恒久。過去の項目を書き換えず、上書きする新項目を追記する |
| `## 作業ログ` | **何が、どの順で起きたか** | 一時的。完了時に数行へ畳む |
| `## 証拠` | **完了条件を満たしたと何故言えるか** | 恒久。コマンドと実出力のみ |

決定ログを書く条件は3つに限る——(1) 人間の判断を仰いで得た、(2) 別の選択肢が実際にあった技術選定、(3) 登録後にスコープ・完了条件・禁止事項が変わった。通常の進捗は決定ではなく作業ログである。

項目の形式:

```markdown
### YYYY-MM-DD 一行でわかる決定の要約
- 決定: 実際に決めたこと
- 却下案: 採らなかった案 → なぜ負けたか
- 付帯条件: 承認に付いた条件（無ければ省略）
- 出典: コミットSHA / 設計成果物のパス / 「セッション内の判断、成果物なし」
```

`却下案` が価値を担う行であり、最も省略されやすい。「X を選んだ」は数週間で「なぜ X なのか」に劣化するが、「Y が使えないので X」は劣化しない。真剣に検討した対案が無ければ `却下案: なし` と書く。行ごと落とさない。

2つの約束事:

- `特記なし` — このタスクに決定が本当に無かった。セクション自体は常に存在するので、**無いことが「未記入」を意味する**状態を保つ。
- `（記録なし）` — 決定はあったが理由が当時記録されず、もう復元できない。**推測で理由を再構成して埋めてはならない。** 捏造された理由は、後から事実として読まれるため、認めた空白より悪い。

決定ログは事務ではない。担当エージェント同士の自由な通信を原則として禁じている以上、**会話の中にしか存在しない理由は、そのセッションが終われば組織から永久に失われる**。同じ論点が別のタスクで、しばしば違う結論で、また争われることになる。

## タスクの状態（§22-3 の確定）

task-cycle の8状態を、本組織のフロー（05 確定事項 D の TDD 既定）へ合わせる。

| 状態 | 意味 | 次に動く主体 |
| --- | --- | --- |
| `未着手` | 登録済み。着手可能かは依存タスク次第 | オーケストレーター |
| `設計中` | 設計エージェントが作業中 | 設計 |
| `テスト作成中` | 受け入れテストを先行作成中（TDD適用タスク） | テスト |
| `実装中` | 実装エージェントが作業中 | 実装 |
| `テスト中` | 受け入れテスト実行・検証中 | テスト |
| `レビュー中` | レビュー実施中、または修正の往復中 | レビュー / 実装 |
| `PO確認待ち` | PO の判断待ちで進めない。ブロッカーに `Q-XXX` を書く | PO |
| `完了` | 完了条件を全て満たし、証拠が記録されている | — |
| `保留` | PO確認以外の理由で進められない（リソース不足、外部要因） | オーケストレーター |
| `中止` | 実施しないと決めた。行は残す | — |

**終端状態は `完了` / `中止` の2つ。** 09 の停滞判定と 10 の集計は、この定義を使う。

「ブロック中（依存待ち）」を状態に置かない理由: 依存タスク列から機械的に導出できるため。状態として持つと、依存先が完了したときに人手で戻す必要が生じ、更新漏れが停滞の誤検知になる。**導出できるものは状態にしない。**

`PO確認待ち` を `保留` から分離する理由: §6.2 の健全性指標が「ブロック中タスク数」と「PO確認待ち件数」を別に数えるよう定めているため。索引だけで両者を数え分けられる必要がある。

## 依存関係の表現（§22-4 の確定）

task-cycle の2形式を採用する。

| 形式 | 意味 |
| --- | --- |
| `T-001（ブロッカー）` | T-001 が `完了` になるまでこのタスクを開始できない |
| `T-001（推奨: 理由）` | 必須ではないが、この順で進める方が合理的 |
| `無し` | 依存が無いことを**確認済み**である |

複数ある場合は空白区切り。理由の全文は詳細ファイルの `## メタデータ` に書き、CSV には短縮形だけを置く。

### ブロッカー指定には理由を必ず書く

01 の O-0 が「依存関係は本当に必要か。順序を強制している理由を説明できるか」を問うている。これを運用で守らせる規約が要る。

**詳細ファイルにブロッカーの理由が書かれていない依存は、依存として認めない。** 説明できない依存は、たいてい「なんとなくこの順」であり、それが並列実行できる単位を潰す。00 §2.5 の通り、独立した並列スレッドへ分解できないゴールではマルチエージェント構成の利得が出ない。**依存を書くコストを、意図的に少し高くしておく。**

`推奨` の方には理由をその場に書く（`T-001（推奨: 同じモジュールを触るため衝突を避ける）`）。こちらは開始を妨げないため、短い理由で足りる。

## 更新の責任者 — CSV を書くのはオーケストレーターだけ

並列実行を前提にする以上、**単一ファイルである CSV への同時書き込みは必ず衝突する**。構造で防ぐ。

| 対象 | 書く主体 |
| --- | --- |
| `docs/task-list-{project-name}.csv` | **オーケストレーターのみ** |
| `docs/tasks/T-XXX.md` の 決定ログ / 作業ログ / 証拠 / 進捗 | **担当エージェント**（自分のタスクのファイルのみ） |
| `docs/tasks/T-XXX.md` の メタデータの 状態 / 担当 / 依存 / 優先度 | オーケストレーター |

各エージェントは自分が担当するタスクのファイル1つしか書かないため、並列で走っても衝突しない。オーケストレーターは唯一の CSV 書き手であり、直列に動くため衝突しない。

**新しいタスクの登録はオーケストレーターが行う**（§6.2「タスク登録」）。設計エージェントの分割提案（02 の O-2）やテスト・レビューからの派生作業も、提案として上がり、登録はオーケストレーターが行う。

### 索引と詳細のずれを検知する

CSV の `更新日` と詳細ファイルの `更新日` は二重管理であり、必ずずれる。ずれたまま放置すると 09 の停滞検知が誤作動する（詳細ファイルは動いているのに CSV が古く、停滞と判定される）。

対策は2つ。

1. **完了報告を受けたら CSV を更新する**をオーケストレーターの規約とする。報告の受領と索引の更新を1つの動作にする。
2. **整合性検査をスクリプトに含める**（09）。CSV と詳細ファイルの `更新日` / `状態` の食い違い、`ドキュメント` 列のパスが存在しない、依存先のIDが存在しない、終端状態でないのに `担当` が `未割当`——これらは機械的に検出できる。

規約だけでは破られる（CLAUDE.md は強制力を持たない。00 §1.2）。検査をスクリプトに置き、hook で必ず走らせる。

## task-cycle スキルからの差分

task-cycle §6 は「プロジェクト固有の調整は差分だけ書け」と定めている。それに従い、変更点のみを列挙する。**ここに書かれていない部分は task-cycle のまま。**

| # | task-cycle の規定 | 本組織での扱い | 理由 |
| --- | --- | --- | --- |
| D-1 | **一度に1タスク**。現在のタスクが終端状態に達するまで次を始めない | **組織全体としては採らない。** ただし**1エージェントは同時に1タスク**とする。同時に走ってよいのは、依存関係の無いタスク間のみ | 本組織は並列前提（§13「PO確認待ち中も独立タスクは継続」、00 §2.5）。ただし1エージェントが複数タスクを抱えると、隔離コンテキストの利点が消え、報告が混線する |
| D-2 | 不足項目は**ユーザーに聞く** | オーケストレーターへ差し戻す。オーケストレーターでも決まらなければ PO確認待ちキューへ（§12） | サブエージェントは `AskUserQuestion` を使えない（00 §1.1）。PO と直接やりとりできるのはメインセッションのみ |
| D-3 | CSV は7列 | **優先度 / 担当 を追加**して9列 | §6.2 の必須項目。オーケストレーターが詳細を開かずに割り当てと順序を決めるために要る |
| D-4 | 状態は8種 | **10種へ変更**（設計中 / テスト作成中 / テスト中 / レビュー中 / PO確認待ち を追加、ローカル検証済み / 実環境検証待ち / 調査中 を廃止） | 状態が「今どの工程にあるか」を表す必要がある。検証の粒度は 03 確定事項 C の「未検証と明示」で詳細ファイル側が担う |
| D-5 | メタデータは 作成日/更新日/状態/進捗/依存 | **TDD適用可否 / 手戻り回数 / 優先度 / 担当 を追加** | TDD適用可否は 01 O-0 で確定。手戻り回数は §6.2 の健全性指標「手戻り件数」の算出元 |
| D-6 | セクションは 目的/変更範囲/禁止事項/完了条件/テスト方法/停止条件 + 3ログ | **判断してよい範囲 / 参照すべき成果物 / 成果物 / ブロッカー を追加** | 01 の O-2 が作業指示の必須項目としているため。これによりタスクファイルが作業指示を兼ねる |
| D-7 | サイクルは 仕様確認→実装→テスト→更新→commit→**Draft PR**→報告 | **PR は要求しない。** commit は論理単位、push はタスク完了時（03 確定事項 B）。TDD適用タスクの順序は テスト先行→実装→テスト実行→レビュー（05 確定事項 D） | §16 は status/diff/commit/push のみを要求する。PR 運用はプロジェクト側の裁量 |
| D-8 | 完了報告は 差分/テスト結果/コミットSHA/未検証事項 | **01 の I-3 の形式**（タスクID / 結果 / 成果物 / 実施内容の要約 / 完了条件の充足状況 / 派生して判明したこと）。ロール別の追加項目は 03〜06 に従う | 報告先が人間ではなくオーケストレーターであり、コンテキスト膨張を避けるため要約と参照で渡す（00 §2.1） |
| D-9 | 停止条件は §4 の4項目 | **08 の共通停止条件**へ拡張（task-cycle の4項目を含む） | §12 のエスカレーション原則と統合する必要がある |
| D-10 | 台帳の更新は作業者が行う | **CSV はオーケストレーターのみ**が書く。エージェントは自分のタスクの詳細ファイルのみ | 並列実行での書き込み衝突を構造的に防ぐ |

**採用したまま変えないもの**（明示しておく。変えない判断も判断である）: ID規約（`T-###` 連番・再利用禁止）、CSV索引 + タスク別ファイルの2分割、3つの記録の分離と決定ログの形式、`特記なし` / `（記録なし）` の約束事、空欄禁止（`無し` / `不明` の明示）、§3 の禁止事項（スコープ外の修正、テストを緩めて通すこと、不明点の推測補完、ID再利用）。

最後の一つは、本組織では既に別経路で確定している——03 の「スコープを勝手に広げない」、03 の I-1b「受け入れテストを書き換えてはならない」、§12「分からないことを無理に決めない」。**独立に導いた規約が一致したことは、この方式が本組織と噛み合っている傍証である。**

## 品質基準はどこにあるか

04 が未確定として残した論点（§9「品質基準を満たしているか」の中身）に、置き場所と主体だけを与える。**中身はプロジェクトごとに異なるため、ここでは確定しない。**

| | 置き場所 | 定める主体 | 参照する主体 |
| --- | --- | --- | --- |
| **プロジェクト全体の品質基準** | 開発対象リポジトリの層2（`CLAUDE.md` / `.claude/rules/`） | 設計エージェントが方式設計時に定め（02 確定事項 A）、**オーケストレーターが層2へ書く**（06 確定事項 D） | 全ロール。CLAUDE.md 階層はサブエージェントへ継承される（00 §1.1） |
| **タスク固有の基準** | タスク別ファイルの `## 完了条件` | オーケストレーター（01 確定事項 A） | レビュー・テスト |

**タスクごとに繰り返さない。** 「テストが通ること」「命名規約に従うこと」のようなプロジェクト全体に効く基準を各タスクの完了条件へ複写すると、量が増える上に、基準を変えるときに全タスクを直すことになる。層2 に一度書けば全エージェントが参照する——これが 00 §1.1 の「CLAUDE.md 階層は継承される」を使う意味である。

完了条件に書くのは、**そのタスクでしか成り立たない基準**だけである。

## ブートストラップ

開発対象リポジトリで最初のタスクを登録する前に、オーケストレーターが以下を作る。

1. `docs/task-list-{project-name}.csv` — ヘッダ行のみ
2. `docs/tasks/` ディレクトリ
3. `docs/tasks/README.md` — 台帳の読み方（ID規約、列の意味、状態の一覧、タスクファイルの雛形）

`README.md` は層2（組織自身への指示）であり、オーケストレーターの保守対象である（06 確定事項 D）。
