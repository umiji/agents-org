# 21. 決定ログを引けるようにする — 索引の生成と、決定が失効したことの表し方

**Status:** Confirmed（PO 承認 2026-08-28）
**根拠:** `docs/experiments/02-decision-records.md`（§0 の現物調査と §4 の外部調査。判定基準 K-1〜K-5 は調査前に固定した）、`docs/decisions/07-task-management.md`（決定ログの形式を定めた文書。本記録はその限定改訂を含む）、要件定義書 v0.2 §4.5（単純な繰り返し処理はスクリプトへ切り出す）/ §18（独自設定ファイルを作らない）/ §19
**position:** §23 の12項目には無い。運用の不備（書かれるが引けない）への対処として確定させた。
**実装:** 未着手（末尾「作るもの」の9件）

## この文書が確定したこと

- **決定の正典は動かさない。** 決定は今までどおり、タスク別ファイル `docs/tasks/T-XXX.md` の `## 決定ログ` に、担当エージェントが自分のタスクのファイルへ追記する
- **索引を機械生成する。** 全タスクファイルの決定ログを走査し、1決定＝1行の一覧 `docs/decisions-index.md` を吐くスクリプトを作る。**手では書かない**
- **決定ログに2つの欄を足す** — `対象`（その決定が支配する領域）と `上書き対象`（この決定が失効させる過去の決定）
- **決定が失効したことは、索引の上でだけ表す。** 過去の決定ログは一文字も書き換えない
- **決定ログを書く条件に4つ目を足す** — 「理由を知らない担当が、将来これを元に戻してしまいそうか」
- **配布物が使っている「決定記録」という語を「決定ログ」に統一する。** 開発対象リポジトリに `docs/decisions/` は存在せず、担当エージェントは存在しないものを探しに行かされていた
- **索引を読む経路を3箇所に作る。** 索引は、作っただけでは読まれない

## A. 何が問題だったか

**決定ログの目的は「再燃防止」である。** これは決定記録07（`docs/decisions/07-task-management.md`）に明文がある——担当エージェント同士の自由な通信を禁じている以上、会話の中にしか無い理由はセッションが終われば組織から永久に失われ、同じ論点が別のタスクで、しばしば違う結論で、また争われる。

**再燃防止が目的である以上、引けることが機能の本体である。** 書くこと自体には価値がなく、次に同じ論点へ当たった誰かが見つけられて初めて目的が達成される。

現物を調べた結果（`docs/experiments/02-decision-records.md` §0）、**引く経路が実質的に存在しなかった**。

- **自動で読み込まれるものは無い。** 担当エージェントへ自動で入るのは層2の運営規約（開発対象リポジトリの `CLAUDE.md`）だけである
- **完了タスクの決定ログは、規約上そもそも読まれない。** セッション再開の手順書（`org/skills/org-session-resume/SKILL.md`）がタスク別ファイルについて「進行中のものだけ。完了済みは読まない」と定めている。コンテキストの節約としては正しいが、結果として完了タスクの決定は誰も読み返さない
- **索引が無い。** 決定はタスク別ファイルの中に埋まっており、タスクは**決定の主題ではなく、作業が起きた順番**で並んでいる。「認証ライブラリをなぜこれにしたか」を調べたい側にとって、その決定は「ログイン画面の実装」という名前のタスクの中にある
- **横断検索（`Grep`）は道具としてはあるが、引くキーワードを既に知っていないと引けない。** 理由を調べたい側は、たいてい語をまだ知らない

**つまり、書く費用は毎回かかるのに、効果が0という状態だった。** 規約の不備というより、目的と手段が繋がっていなかった。

**トライアル先ではまだ表面化していない。** タスク数が少なく同じセッションが続いている間は、理由が会話の中に残っているため困らない。困り始めるのは、セッションが切り替わった後、同じ領域を2回目に触るときである。

## B. 外の既成解を調べた結果、何を採り、何を採らなかったか

**ADR（Architecture Decision Records、アーキテクチャ決定記録）** が、まさにこの用途の確立された方式である。原典（Michael Nygard, 2011）、定型化された仕様（MADR）、実装（`adr-tools` のソース、Log4brains）、AIエージェント向けの手順書まで当たった。全文は `docs/experiments/02-decision-records.md` §4 にある。ここには判断に効いた4点だけを置く。

### B-1. 索引は生成物であって、手書きではない（採る）

道具を持つ実装は例外なく、**ファイル群が唯一の正典で、索引はそこから導出される**形を採っていた。`adr-tools` の目次生成コマンドは、決定記録のフォルダを走査して各ファイルの先頭見出しを拾い、箇条書きを吐くだけである。MADR 自身の一覧ページには説明文しか書かれておらず、一覧は自動生成に任せている。

**手で索引を更新させているのは、調べた中では AI エージェント向けの手順書1つだけ**で、そこでは追記が守られるかどうかが規約頼みになっていた。

**本リポジトリには同じ形の先例がある** — 層3ドキュメントの人間用ビューを生成するスクリプト（`org/scripts/org-docs.py`）が「マスタだけが正典、ビューは生成物」を既に採っている。要件定義書 §4.5（単純な繰り返し処理はスクリプトへ切り出し、LLM のトークンは判断に使う）にも沿う。

### B-2. 並列で壊れない仕組みは、既成解の側に無い（採らない）

`adr-tools` の採番は、ソースを読むと**「フォルダを走査して、今ある最大の番号＋1」**である。中央の採番役が居ないため、2つのエージェントが同時に作れば同じ番号になる。実務でも並行ブランチ間の番号衝突を手で解決している報告がある。

**本組織はここで既に強い前提を持っている** — タスク番号はオーケストレーター（司令塔となるメインセッション）だけが採番し、連番・再利用禁止と定めてある。

**だからこそ、決定に新しい採番を導入しない。** 決定を独立ファイルにすると、担当エージェントは決定のたびに司令塔へ番号を貰いに行くことになり、往復が増える。**採番を一切増やさない形にすれば、この問題は発生しない。**

### B-3. ADR の「不変」は、本組織の「書き換えない」と同じではない（形を変えて採る）

原典が不変にしているのは**本文だけ**で、**状態欄は書き換える**（「置き換え済み（置き換え先：ADR-0015）」へ変える）。`adr-tools` の実装は、置き換える新記録を作るときに**新旧2つのファイルを両方書き換え**、古い側に逆リンクを追記して「承認」の行を消す。

本組織の規約は「過去の項目を書き換えず、上書きする新項目を追記する」という完全追記である。**そのままでは採れない。**

**採った形**: 逆リンクを、過去のファイルではなく**索引の上で作る**（C-3）。過去は不変のまま、逆向きのリンクだけ手に入る。

### B-4. 「語を知らない側でも引ける」は、既成解でも解けていない（自前で埋める）

MADR は数百件規模を想定して分類（サブフォルダ）を導入したが、その決定記録自身が欠点として「**分類が分からないときに、どのフォルダを見ればよいか分からない**」「新規参加者を妨げる」と書いている。これは本件の問題とまったく同じ形である。

AI エージェント向けの議論（2026年）は問題意識こそ同じだったが（モデルは毎セッション記憶がゼロから始まる／エージェントは見えない理由をリファクタリングで消してしまう）、示されている手順は「規約ファイルに『設計変更の前に決定記録を読め』と書く」の一行に留まり、**コンテキストへ読み込む量が費用になるという論点には触れていない**。

**したがって、引ける形は自前で設計する。** 採ったのは `対象` の欄（C-1）と、それで束ねた索引（C-2）である。

### B-5. 判定基準（調査前に固定した K-1〜K-5）との対応

| 基準 | この方式でどうなるか |
| --- | --- |
| K-1 **主題から引ける** | 索引が「日付・要約の一行・対象領域・タスクID・状態」を持つ。語を知らなくても対象領域から辿れる |
| K-2 **正典が1つ** | 決定の本体はタスク別ファイルだけ。索引は生成物で、手で書くことを禁じる |
| K-3 **並列で壊れない** | 各担当は今までどおり自分のタスクファイルだけを書く。**新しい採番を一切導入しない。** 索引を書くのはスクリプトだけ |
| K-4 **読む費用が件数に比例しない** | 1決定1行なので、索引だけ読めば開くべき1件が決まる |
| K-5 **書く手間が増えない** | 主題の一行は**現在の雛形が既に書かせている**（`### YYYY-MM-DD 一行でわかる決定の要約`）。増えるのは短い2行だけで、しかも決定ログを書く条件に該当する稀な場面のみ |

### B-6. 採らなかった案

**(a) 独立した決定記録フォルダへ一本化する** — 採らない。理由は3つ。**採番の往復が1決定ごとに増える**（B-2）。**同じ決定がタスクファイルにも書かれる誘惑が残り、正典が2つになる**。**決定記録07 が「変えない」と明示したもの（3つの記録の分離と決定ログの形式）を全面的に覆すことになる**。得られる利点（ファイル名が主題になる）は、索引の生成で代替できる。

**(c) 重い決定だけ独立文書へ昇格させる** — **今は採らない。後から足せる**ため、先に決める必要がない。索引がスクリプトによる走査である以上、走査先を1つ増やすだけで済む。今採らない理由は、決定のたびに「これは重いか」を判断する費用が乗り、決定の家が2つになるためである。

**分類のサブフォルダを持つ** — 今は不要。MADR 自身が欠点を認めており（B-4）、`対象` の欄で足りる。

## C. 決めた仕様

### C-1. 決定ログの書式 — 欄を2つ足す

現在の書式（`org/rules/org-task-ledger.md`）に、`対象` と `上書き対象` を足す。**既存の項目は変えない。**

```markdown
### YYYY-MM-DD 一行でわかる決定の要約
- 対象: 認証 / ログインAPI
- 決定: 実際に決めたこと
- 却下案: 採らなかった案 → なぜ負けたか
- 付帯条件: 承認に付いた条件（無ければ省略）
- 上書き対象: T-003 2026-05-10（この決定が失効させる過去の決定。無ければ省略）
- 出典: コミットSHA / 設計成果物のパス /「セッション内の判断、成果物なし」
```

**`対象`（必須）** — その決定が支配する領域や部品を1〜3語で書く。索引を束ねる単位であり、**語をまだ知らない側が辿り着くための入口**である。用語集（`docs/glossary.md`）に載っている語があればそれを使う。複数にまたがるときは ` / ` で区切る。

**`上書き対象`（該当するときだけ）** — この決定が失効させる過去の決定を、**タスクIDと日付**で指す（例: `T-003 2026-05-10`）。日付まで書くのは、1つのタスクが決定を複数持ちうるためである。

**見出しの行（`### YYYY-MM-DD 一行でわかる決定の要約`）は書式を厳守する。** 索引を作るスクリプトがこの行を主題として読む。要約は**短い名詞句か、決定を言い切る一文**にする（「調査した」「検討した」は決定ではない）。

### C-2. 索引 `docs/decisions-index.md` — 生成物であって、手で書かない

**開発対象リポジトリ**の `docs/decisions-index.md` に置く。**この位置は、既存の6種類（タスク索引・タスク別ファイル・PO確認待ちキュー・セッション引き継ぎ記録・トークン消費の記録）に7種類目として加わる。**

- **全タスク別ファイルの `## 決定ログ` を走査して生成する。** 完了・中止を含む**すべての**タスクが対象である（引けない原因が「完了済みは読まない」規約にあったため）
- **`対象` ごとに束ね、その中は日付の新しい順**に並べる
- 1決定＝1行。持つ列は **日付 / 要約の一行 / タスクID / 状態**
- 冒頭に**対象の一覧**を置く。ここだけ読めば、どの領域に決定があるかが分かる
- **ファイルの先頭に「これは生成物である。手で編集しない」と明記する**（トークン消費の記録と同じ扱い）

生成のタイミングは2つ。**セッション開始時の検査で毎回作り直す**（既に停滞検知のスクリプトを走らせている hook に相乗りする）ことと、**書き込まずに古くなっていないかだけ見る `--check`** を持つこと。後者は層3ドキュメントの生成スクリプト（`org/scripts/org-docs.py`）と同じ形である。

### C-3. 決定が失効したことは、索引の上でだけ表す

**過去の決定ログは書き換えない。** 新しい決定の側にだけ `上書き対象` を書かせ、**スクリプトがそれを読んで、古い側の行に「置き換え済み → T-021」と描く。**

```
## 認証

| 日付 | 決定 | タスク | 状態 |
| --- | --- | --- | --- |
| 2026-08-12 | 認証ライブラリを B へ移す | T-021 | 有効 |
| 2026-05-10 | 認証ライブラリは A を使う | T-003 | 置き換え済み → T-021 |
```

**これで、古い決定に先にあたった側が、それが失効していることを知れる。** 外の既成解は同じ目的を「古いファイルの状態欄を書き換える」ことで達成しているが（B-3）、本組織の完全追記の規約と衝突するため、索引側に寄せた。

`上書き対象` が実在しないタスクや日付を指していたら、整合性検査で警告する。

### C-4. 決定ログを書く条件 — 4つ目を足す

現在の3条件に、4つ目を足す。

1. 人間（PO）の判断を仰いで得た
2. 別の選択肢が実際にあった技術選定
3. 登録後にスコープ・完了条件・禁止事項が変わった
4. **理由を知らない担当が、将来これを元に戻してしまいそうなもの**（新規）

**なぜ足すか。** 上の3条件はどれも「決めた瞬間に、決めたと自覚できるもの」である。4つ目はそうではないものを拾う——**意図的に共通化していない箇所、削れない待ち時間、あえて素朴に書いた実装**のような、後から見ると不自然で、理由を知らなければ「整理」されて消えるものである。

**この組織はその失敗が起きる構造そのものを持っている。** 担当エージェントは会話履歴を継承せず、担当同士は自由に話せない。人間のチームなら口頭の記憶で補われる部分が、構造的に存在しない。外部調査でも同じ観点が挙がっていた（`docs/experiments/02-decision-records.md` §4.6）。

**判定が主観的になることは承知の上で採る。** 迷ったら書く側に倒してよい。書きすぎの害（索引が伸びる）より、書かなかった害（消される）のほうが大きいためである。

### C-5. 「決定記録」という語の不備を直す

配布物の4箇所（`org/rules/org-escalation.md`・`org/rules/org-task-ledger.md`・`org/templates/T-XXX.md`・`org/agents/org-design.md`）が「確定済みの決定記録」を担当エージェントの情報源として挙げているが、**開発対象リポジトリに `docs/decisions/` は存在しない。** 決定記録は層1（組織そのものを設計する本リポジトリ）だけにある概念である。

**担当エージェントは、存在しないものを探しに行かされていた。**

- 配布物の「決定記録」を **「決定ログ（および `docs/decisions-index.md`）」** に直す
- 層2の用語集（`org/glossary.md`）に **`decisions-index.md`（決定ログ索引）** を登録する。決定ログの項との関係（正典と生成物）を明記する

### C-6. 索引を読む経路を3箇所に作る

**索引は、作っただけでは読まれない。** 事実、読まれない状態こそが本件の出発点だった（A）。

| 場所 | 入れる手順 |
| --- | --- |
| 層2の運営規約（`org/CLAUDE.md`） | 索引の場所と役割を一行で書く。全担当エージェントへ自動で入る唯一の経路である |
| オーケストレーターの手順書（`org/skills/org-orchestrate/SKILL.md`） | タスクを割り当てるとき、**その `対象` の決定を索引で引き、効くものがあれば `## 参照すべき成果物` に書く**。完了報告を受けたら索引を作り直す |
| セッション再開の手順書（`org/skills/org-session-resume/SKILL.md`） | **完了タスクの本文は今までどおり読まない。索引だけは読む。** 1決定1行なので費用が小さい |

## D. 決定記録07 との関係 — 限定改訂として扱う

決定記録07 は末尾で「採用したまま変えないもの」を列挙しており、その中に **「3つの記録の分離と決定ログの形式」** が入っている。

- **3つの記録の分離（決定ログ／作業ログ／証拠）は変えない。** そのまま維持する
- **決定ログの形式は変える。** ただし**既存の項目を一切変えない追記だけの改訂**である（C-1 の2欄と、C-4 の条件1つ）
- **索引の追加は、07 に抵触しない。** 決定ログを正典として残したまま、生成物を1つ足すだけであるため

**07 の末尾に、本記録への参照を追記する。**

## F. 未確定のまま残すもの

- **重い決定を独立文書へ昇格させるか**（B-6 の案 c）。後から足せるため、実運用で必要が見えるまで決めない
- **分類のサブフォルダ**（B-4）。`対象` で足りているかを、件数が増えてから見る
- **索引の形式を Markdown の表としたこと。** PO の当初案は CSV だった。生成物であり機械が書き足すことがないため、読み手（担当エージェントと PO）にとって読みやすい Markdown を採った。**異論があれば差し戻せる**
- **`対象` の語彙を統制するか。** 今は自由記述とし、用語集にある語を優先するに留める。表記ゆれで索引が割れるようなら、その時点で考える

## G. 効果を確かめる方法

**机上で「引きやすくなった」と言っても意味がない**（`docs/experiments/02-decision-records.md` §3.5）。

1. **トライアル先（開発対象リポジトリ SNS Agent）の決定ログが現在何件あるかを数える**
2. 「この決定はどこにあるか」という問いを数本立て、**現方式（タスクファイルを横断検索する）と新方式（索引を引く）で引けるかを比べる**
3. **件数が少なければ比較が成立しない。** その場合は索引を先に入れ、件数が増えてから測る

**測る前に索引を入れること自体は妨げない。** 書く手間がほぼ増えず（K-5）、正典を動かさないため、外して元に戻す費用も小さいからである。
