# 01. オーケストレーター 役割定義

**Status:** Confirmed（PO確認済み 2026-08-19）
**根拠:** 要件定義書 v0.1 §6 / §12 / §13 / §23
**方針:** 実装方式（保存形式・実行形態）には踏み込まない。入力・出力は「何を受け取り、何を返すか」の情報項目として定義する。

---

## ミッション

ユーザーから与えられたゴールを達成するために、AI組織全体を管理・調整する。

自身が成果物を作るのではなく、「誰が・何を・どの順番で行うか」を判断し、組織を動かすことに集中する。（§6.1）

## 責務

§6.2 の通り。ゴール管理／タスク分解／タスク登録／タスク割り当て／進捗管理／停滞管理／ゴール健全性評価／エスカレーション管理／リソース管理。

**担当しないこと**（§6.3）: 本格的なコーディング、詳細なテスト実装、通常のドキュメント作成、通常のコードレビュー、単純な作業の代行。

---

## 入力

オーケストレーターが受け取るもの。発生源ごとに定義する。

### I-1. ゴール入力（PO → オーケストレーター）

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| ゴール記述 | 必須 | 自然言語。「何を実現したいか」 |
| 制約 | 任意 | 期限、技術的制約、使ってはいけないもの等 |
| 対象リポジトリ／作業場所 | 任意 | 未指定なら現在のリポジトリ |

PO が詳細なタスク一覧を用意することは前提としない（§3.2）。ゴール記述だけで受理し、不足はオーケストレーターが質問で補う。

### I-2. PO判断回答（PO → オーケストレーター）

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 対象の確認待ち項目ID | 必須 | どの問いへの回答か |
| 選択された結論 | 必須 | 選択肢のいずれか、または新たな指示 |
| 補足・理由 | 任意 | 判断の背景。以後の類似判断の基準になる |

### I-3. エージェント完了報告（各エージェント → オーケストレーター）

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| タスクID | 必須 | |
| 結果 | 必須 | 完了 / 部分完了 / 失敗 |
| 成果物 | 必須 | 作成・変更したもの（ファイル、コミット等） |
| 実施内容の要約 | 必須 | 何をしたか |
| 完了条件の充足状況 | 必須 | タスクの完了条件を満たしたか。満たさない項目があれば明示 |
| 派生して判明したこと | 任意 | 新たに必要と分かった作業、既存タスクの前提が崩れた等 |

**報告は要約であること。** 成果物の内容（コード全文、ログ全文、ファイル内容）を報告本文に貼らず、**参照**（ファイルパス、コミット、行番号）で渡す。オーケストレーターのコンテキストは報告のたびに膨張し、3エージェントが各2,000トークンを返せば1サイクルで6,000トークン増える（00 §2.1）。ここが膨らむと、オーケストレーターは組織全体を見る余力を失う。

### I-4. エスカレーション（各エージェント → オーケストレーター）

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| タスクID | 必須 | |
| 判断できない事項 | 必須 | 何が決められないのか |
| なぜ自分で決められないか | 必須 | 権限外／情報不足／要件不明／トレードオフ |
| 検討した選択肢 | 必須 | 自分で調べた範囲での案。無ければ「無し」と明示 |
| 影響範囲 | 必須 | このタスクだけか、他タスクにも波及するか |

### I-5. 組織状態（セッション開始時）

新しいセッションで作業を再開するときに読み込むもの（§15）。

- タスクリスト全体（各タスクのステータス・担当・更新日時）
- PO確認待ちキューの未回答項目
- 直近の作業文脈（前セッションで何をしていたか）
- ゴールと、現時点で確定しているゴール達成条件

## 出力

### O-0. タスク分解の方針

**並列実行できる単位を意図的に作る。**

マルチエージェント構成が単一エージェントに勝つのは、タスクが独立した並列スレッドへ分解できるときに限られる（00 §2.5）。直列依存が連なる分解では、組織化のコスト（トークン約15倍）だけを払って利得が出ない。

分解時に確認すること:

- 依存関係は本当に必要か。順序を強制している理由を説明できるか
- PO確認待ちが発生したとき、止まらずに進められるタスクが残るか（§13）
- 1タスクは、担当エージェントが1回の作業で完了できる大きさか

#### TDD 適用可否をタスクごとに判定する

TDD は既定である（05 確定事項 D）。事前にテストを書けないタスク（探索的作業、UI の見た目の調整、設定変更など）については、タスク分解時に **「TDD 適用外」と明示する**。

判定をオーケストレーターが持つのは、適用可否が「そのタスクが何を達成するか」に依存し、タスク分解の時点で最も見えているため。

### O-1. タスク定義

§6.2 の項目に、**完了条件**を追加する（追加提案。理由は後述の「PO判断が必要な点 A」）。

タスクID / タスク名 / 目的 / 詳細 / **完了条件** / **TDD適用可否** / 優先度 / 担当エージェント / 前提タスク / ステータス / 作成日時 / 最終更新日時 / 成果物 / ブロッカー / 備考

### O-2. 作業指示（オーケストレーター → 各エージェント）

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| タスクID | 必須 | |
| 目的 | 必須 | このタスクがゴールに対して何を前進させるか |
| 詳細 | 必須 | 具体的にやること |
| 完了条件 | 必須 | 何が満たされたら完了か |
| 参照すべき成果物 | 任意 | 先行タスクの設計書、既存コード等 |
| 判断してよい範囲 | 必須 | どこまで自律的に決めてよいか。境界を明示する |
| 期待する成果物の形 | 必須 | コード／設計書／テスト／レビュー結果 等 |

「判断してよい範囲」を毎回明示するのは、§12「分からないことを無理に決めない」を機能させるため。境界が不明だと、エージェントは決めすぎるか、逆に些末な事を全部上げてくる。

#### 作業指示は自己完結でなければならない

各エージェントは**新規の隔離コンテキスト**で作業を始め、これまでの会話履歴を一切引き継がない（00 §1.1）。「さきほど決めた方針で」「前回と同様に」は通じない。必要な文脈は指示の中に、または参照先として明示的に含める。

これを外すと **Incomplete Context Transfer**（00 §2.2）が起きる。曖昧な指示を受けたエージェントは、エラーを上げずに誤った前提のまま作業を完了させる。失敗が沈黙するため、手戻りは下流で初めて発覚する。

#### 受け取った側は、着手前に指示の充足を確認する

**全エージェント共通の規約**。作業指示を受けたエージェントは、着手前に以下を確認し、欠けていれば**作業を始めずオーケストレーターへ差し戻す**。

1. 完了条件が書かれているか
2. 判断してよい範囲が書かれているか
3. 参照すべき成果物が実在するか
4. 目的と詳細から、何をすべきかが一意に定まるか

推測で埋めて着手しない。差し戻しのコストは、誤った前提で完成させたものを捨てるコストより常に小さい。

### O-3. PO確認待ち項目

§13 の通り。質問・判断事項 / なぜ判断が必要か / 選択肢 / 各選択肢のメリット・デメリット / 推奨案 / 回答がない場合に影響するタスク。

**登録時に必ず併記する**: この項目の回答を待つ間も進行できるタスク（§13「独立したタスクは継続する」を実際に守るため）。

### O-4. ゴール健全性レポート

§6.2 の8指標。完了タスク数 / 未完了タスク数 / 停滞タスク数 / ブロック中タスク数 / PO確認待ち件数 / 手戻り件数 / ボトルネックとなっている工程 / ゴール達成に必要な残作業。

数値の列挙で終わらせず、**「ゴールに近づいているか」の判定と、そう判断した理由**を添える(§6.2「単純なタスク消化数だけではなく」)。

### O-5. リソース不足の提案（オーケストレーター → PO）

不足しているもの（エージェント／スキル／MCP／外部アクセス）/ なぜ必要か / それが無いことで滞る作業 / 追加案。（§6.2 リソース管理）

## エスカレーション条件（オーケストレーター → PO）

オーケストレーターは組織内の最終判断者だが、以下は自分で決めずPOへ上げる。

| # | 条件 | 判定の目安 |
| --- | --- | --- |
| E-1 | ゴール達成条件がゴール記述から確定できない | 「完成した」と言える状態が複数あり、どれか選べない |
| E-2 | 複数案があり、選択がトレードオフを伴う | 性能とコスト、速度と保守性など、技術的な優劣で決まらない |
| E-3 | 要件の変更・追加に相当する | 元のゴール文の範囲を超える。範囲内かどうか自体が曖昧な場合も上げる |
| E-4 | 停滞が組織内で解決しなかった | 再分割・再割り当てを試みた後も進まない（§6.2 停滞管理の4段目） |
| E-5 | 必要なリソースが組織に存在しない | 担当できるエージェント／スキル／MCP／外部アクセスが無い |
| E-6 | セキュリティ・コスト・外部影響が重大 | 本番データ、課金、外部公開、認証情報に関わる判断 |

**上げない**もの: 実装手段の選択、タスクの分割方法、担当エージェントの割り当て、優先順位の調整、レビュー指摘への対応方針。これらはオーケストレーターが決める。

エスカレーションしても組織は止めない。E-1〜E-6 のいずれでも、PO確認待ちへ登録した上で、その回答に依存しないタスクは進行させる（§13）。

### PO への問い合わせはオーケストレーターだけが行える

これは方針ではなく**技術的な制約**である。Claude Code のサブエージェントは `AskUserQuestion` を使用できない（00 §1.1）。したがって PO と直接やりとりできるのはメインセッションだけであり、PO確認待ちキューをオーケストレーターが一元管理する本設計は必然的な帰結である。

各エージェントが「PO に聞きたい」と考えた場合、必ずオーケストレーター経由になる。

## 実行にあたっての規約

### 委譲を徹底する

既知の失敗モードとして **Failure to Delegate** がある（00 §2.2）— オーケストレーターが担当エージェントを呼ばず、自分で作業を続けてしまう。§6.3「やらないこと」はこれを禁じている。

規約だけでは破られるため、**構成でも担保する**: オーケストレーターの定義から編集系ツール（Write / Edit 等）を外せば、実装は構造的に不可能になる（00 §1.1）。実装方式の選択に踏み込まないため本決定では規定しないが、エージェント定義を書く段階で採用を検討すること。

### 開発対象リポジトリの規約（層2）を保守する

開発対象リポジトリの `CLAUDE.md` / `.claude/rules/` / エージェント定義は、オーケストレーターが保守する（06 確定事項 D）。これらは成果物ではなく**組織自身への指示**であり、§6.3 が担当外とする「通常のドキュメント作成」には当たらない。

保守が要るのは、例えば以下を発見したとき。

- 同じ誤りが複数のタスクで繰り返された（規約として明文化すべき）
- ビルド・テストコマンドが確定した、または変わった
- エージェントが毎回同じ確認を上げてくる（判断基準が書かれていない）

**CLAUDE.md は200行を超えると遵守率が落ちる**（00 §1.2）。超えそうな場合はトピック別に `.claude/rules/` へ分割する。手順に育ったものは Skills へ出す。

### 計画を早期に外部化する

オーケストレーターは、タスク分解の結果を**自分のコンテキストが埋まる前に**外部へ書き出す。コンテキストが上限に達すると切り詰めが起き、計画そのものが失われる（00 §2.4）。

「後でまとめて記録する」は取らない。分解した時点で書く。これは §15 のセッション引き継ぎが成立する前提でもある。

## PO確定事項（2026-08-19）

### A. タスク項目へ「完了条件」を追加する — **確定**

§6.2 のタスク項目リストに `完了条件` を追加する。要件定義書 v0.1 §6.2 に対する追加であり、次版へ反映すること。

理由: レビューエージェント（§9）は「要求・設計・品質基準を満たしているか確認する」、テストエージェント（§10）は「期待どおり動作することを検証する」責務を負う。基準がタスクに書かれていないと両ロールが毎回推測することになり、判定がぶれ、手戻り件数（健全性指標）が増える。

### B. 作業指示の「判断してよい範囲」を必須項目とする — **確定**

O-2 の必須項目として維持する。§8「実装上の軽微な判断は自律的に行う。ただし以下は勝手に決定しない」を実際に機能させるには、境界がタスクごとに示されている必要がある。

### C. ゴール健全性評価の実行タイミング — **10 で確定済み**（2026-08-20）

保留していた論点は `10-goal-health.md` で解いた。**節目 + PO要求時**（セッション開始時 / セッション終了時 / 停滞検知時 / 機能のまとまり完成時 / PO要求時）。指標の算出方法も同ファイルで確定した。
