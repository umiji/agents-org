# 23. テスト担当とレビュー担当の間の直接通信を許可する

**Status:** Confirmed（PO 承認 2026-08-28）。**ただし許可範囲・向き・往復上限は、確定済み事項からの導出である**（後述 D）
**根拠:** 要件定義書 v0.2 §14（担当エージェント同士の直接通信は原則禁止。例外は承認済みの経路のみ）、`docs/decisions/12-agent-addition.md`（**直接通信の経路を増やすときは、定義ファイルの追加では済ませず組織規約の変更として扱う**。追加の4条件もここにある）、`docs/decisions/04-review-agent.md` 確定事項 B（レビュー → 実装の往復上限）、`docs/decisions/05-test-agent.md` 確定事項 B（テスト → 実装の直接通信を許可した先例）、`docs/decisions/02-design-agent.md` 確定事項 C（実装 → 設計は軽微な問合せに限る）
**位置づけ:** §23 の12項目には無い。PO が「テスト担当とレビュー担当の間も直接やりとりさせたい」と述べ、判断を下したことによる追加。

## この文書が確定したこと

- **テスト担当とレビュー担当の間に、直接通信の経路を1つ増やす。** 承認済みの経路は3つから**4つ**になる
- **向きは双方向。** ただし**中身は「観点の受け渡し」だけ**に限る——相手の判定を変えさせるやりとりは経路の対象外
- **往復上限は1往復。** 既存3経路のうち、これは「差し戻しの往復」ではなく「軽微な問合せ」に当たるため、実装 → 設計と同じ1往復に揃える
- **判定が食い違ったら、その場で調停せずオーケストレーターへ返す。** テスト担当とレビュー担当は**どちらも合否を判定する側**であり、互いに差し戻す関係にない
- **やりとりが起きたら、双方が自分の報告に必ず書く。** 直接通信は司令塔の目を通らないため、書かなければ判定の根拠が組織から消える

---

## A. 何を決める必要があったか

要件定義書 v0.2 §14 は、担当エージェント同士が自由に連絡し合うことを禁じ、オーケストレーター（司令塔となるメインセッション）を必ず経由させている。例外として名指しで許可されている経路が3つある。

| 既存の経路 | 許可範囲 | 往復上限 |
| --- | --- | --- |
| レビュー → 実装 | 修正要求と修正結果の往復 | 2往復 |
| 実装 → 設計 | **軽微な問合せに限る**（設計成果物に書いてあることの読み方の確認） | 1往復 |
| テスト → 実装 | 不具合レポートと修正の往復 | 2往復 |

**この3つには共通の性質がある** —— いずれも**実装への差し戻しであり、設計や要件を変えない**（`docs/decisions/05-test-agent.md` 確定事項 B）。だからこそ司令塔を経由させる利得が無く、往復のコストだけが増える、という理由で例外にできた。

**テスト担当とレビュー担当の間は、この性質を持たない。** 両者はどちらも「実装を判定する側」であって、互いに差し戻す関係にない。したがって既存3経路と同じ理屈では正当化できず、経路を増やすなら別の理由が要る。

## B. 前セッションの推奨と、PO の判断

**前のセッションでは、この経路の追加に反対の意見を返している**（`docs/handover.md` の「PO 確認待ち」の節）。理由は A に書いたとおり——両者は判定する側どうしで、**指摘が食い違ったときこそオーケストレーターの調停が要る**、というものだった。

**PO はこれを聞いた上で、許可すると判断した。** 本記録はその判断を受けて書いている。

**反対意見が消えたわけではない。** 消していないので、下の C は「経路を開けるが、前セッションが心配した部分は開けない」という形になっている。具体的には、**合否の判定を相手に変えさせるやりとりを経路から外し、食い違いはオーケストレーターへ戻す**。

## C. 確定した内容

### C-1. 経路と許可範囲

| 経路 | 許可範囲 | 往復上限 |
| --- | --- | --- |
| **テスト → レビュー** | **観点の照会。** テストで見つけた不具合について、レビューがその観点を見ていたかを確かめる | **1往復** |
| **レビュー → テスト** | **観点の引き渡し。** レビューで気づいた懸念のうち、コードを読むだけでは確かめられないものを、テストの確認項目として渡す | **1往復** |

**「観点」とは、何を確かめるべきかという着眼点のことである。** 例えば「入力が空文字のときの扱いが仕様に書かれていない」「この処理は同時に2つ走ると壊れうる」といった、確かめるべき対象の指定である。**確かめた結果としての合否ではない。**

### C-2. 経路に載せてはいけないもの

次のやりとりは、この経路の対象外である。**オーケストレーターへ上げる。**

| 載せないもの | なぜ |
| --- | --- |
| **相手の合否判定を変えるよう求めること** | 判定を下すのは各担当の責務であり、相手に譲らせてよいものではない。判定の対立は組織として裁く事項である |
| **実装への修正要求** | それは既存の「レビュー → 実装」「テスト → 実装」の経路で行う。判定する側どうしで実装の直し方を決めてはならない |
| **完了条件・設計・要件の解釈を変えること** | 既存3経路すべてに共通する禁止事項（`docs/decisions/02-design-agent.md` 確定事項 C）。書かれていないことをする必要が出たらオーケストレーター経由 |
| **どちらの指摘が正しいかの決着** | 次の C-3 |

### C-3. 判定が食い違ったら、その場で決めない

**テスト担当が「通った」と言い、レビュー担当が「通していない」と言う**——このように**判定が正面から食い違ったとき、両者の間で決着させてはならない。** それぞれが自分の判定を保ったまま、**双方がオーケストレーターへ報告して終わる。**

理由は2つある。

1. **裁定は司令塔の責務である。** レビューと実装が対立した場合の扱いを定めた `docs/decisions/04-review-agent.md` 確定事項 C が、既に「決着しなければオーケストレーターが裁定する」と定めている。判定する側どうしの対立に、それより弱い扱いを与える理由が無い
2. **判定する側どうしが直接合意できると、基準が緩む向きに動きやすい。** どちらも「自分の指摘を取り下げれば往復が終わる」立場にある。実装への差し戻しと違い、**緩めた結果が誰の目にも触れずに済んでしまう**

### C-4. やりとりの結果は、双方が自分の報告に書く

**直接通信はオーケストレーターの目を通らない。** 既存3経路では、往復の結果が最終的に実装の成果物として現れるため、通らなくても跡が残る。**この経路にはそれが無い**——観点の受け渡しは、受けた側の判定の中に溶けて見えなくなる。

そこで**送った側・受けた側の双方が、自分の報告に次の3点を書く。**

- 誰と何をやりとりしたか
- 受け取った観点を、自分の判定にどう反映したか（反映しなかったならその理由）
- 食い違ったまま終わったものがあるか

**書かない場合、この経路は使わなかったものとして扱う。** 跡が残らない直接通信は、組織にとって存在しないのと同じである。

### C-5. 宛先の渡し方は既存と同じ

**担当エージェントは、誰が動いているかを自分で一覧する手段を持たない。** 宛先を教えられていない相手には送れない（`docs/decisions/19-agent-teams.md`）。したがってこの経路も、既存3経路とまったく同じ手順で開通させる。

1. オーケストレーターがエージェントを起こすとき、**タスク番号を含む一意な名前**を付ける（`org-test-T-007` のように）。役割名だけを使い回すと、**同じ名前が1セッション内で2回使われた時点で、その名前宛ての送信が拒否される**
2. **相手の宛先を、タスク別ファイル `docs/tasks/T-XXX.md` の `## 連絡してよい相手` の欄に書く**
3. 書かなければ、その経路は使えない（`org/rules/org-escalation.md`）

**この経路は、テストとレビューが同じタスクに対して同時に動いているときにしか意味を持たない。** 片方しか動いていないタスクでは、宛先を書かない。

## D. `12-agent-addition.md` が定めた4条件の確認

決定記録12（`docs/decisions/12-agent-addition.md`）は、直接通信の経路を増やすときに満たすべき条件を4つ挙げている。**開けたい側が理由を負う**という建て付けなので、1つずつ確認する。

| 条件 | 満たしているか |
| --- | --- |
| **定型的である**（その場限りの相談ではない） | **満たす。** テストとレビューが同じ実装を判定する場面は、標準フローで毎タスク発生する。観点の受け渡しはその都度同じ形をとる |
| **設計・要件を変えない** | **満たす。** C-2 で、完了条件・設計・要件の解釈を変えるやりとりを明示的に経路から外した |
| **反復上限がある** | **満たす。** 1往復。既存3経路の中では、差し戻しの往復（2往復）ではなく軽微な問合せ（実装 → 設計の1往復）と同型である |
| **オーケストレーターを通す利得が無いことを説明できる** | **部分的にしか満たさない。** 下記 |

### 4つ目の条件について、正直に書いておく

**「通す利得が無い」とは言い切れない。** 判定する側どうしのやりとりには、司令塔が見ている価値が確かにある（B に書いた前セッションの反対意見はこれである）。

利得として言えるのは次の1点に限られる。

- **観点の受け渡しは、司令塔を経由すると要約で細部が落ちる。** 「この処理は同時に2つ走ると壊れうる」という懸念は、どの処理のどの経路の話かまで含めて初めて確認項目になる。司令塔が中継すると、報告は要約であるべき（要件定義書の設計制約——司令塔のコンテキストは報告のたびに膨張するため）という規約と正面から衝突する

**通す利得が残っている部分——判定の対立の裁定——は、C-3 で経路から外して司令塔に戻した。** つまりこの経路は、4つ目の条件を「利得が無い部分だけを切り出して開ける」形で満たしている。

**この切り分けは PO へ問うたものではなく、確定済み事項からの導出である。** 導出の根拠は C-3 に挙げた2件（04 確定事項 C、および判定する側どうしという構造）。**異論があれば差し戻せる**——本リポジトリの規約どおり、導出であることを明記する。

## E. 反映が必要な箇所

**決定記録を書くだけでは、この経路は開かない。** 経路の一覧は複数の場所にあり、そのすべてが「3経路」と書いている。

| 対象 | 何をするか | 層 |
| --- | --- | --- |
| `org/CLAUDE.md`（開発対象リポジトリのルートへ追記される運営規約） | 「例外は以下の3経路だけ」の表へ4行目を足し、C-2〜C-4 の制限を書く | 層2・**配布物** |
| `org/rules/org-escalation.md`（エスカレーションの規約） | 「直接通信の3経路」という表現を直す | 層2・**配布物** |
| `org/agents/org-test.md` / `org/agents/org-review.md`（担当エージェントの定義） | 直接通信の節へ、相手と許可範囲・上限・報告義務を書く | 層2・**配布物** |
| `docs/decisions/08-escalation-criteria.md`（エスカレーション段2で使える経路の一覧） | 表へ1行足し、「この3つ以外に直接通信は無い」を4つに直す | 層1 |
| `docs/decisions/12-agent-addition.md` | 「現在の例外は3つ」を4つに直す。**共通性の記述（実装への差し戻し）はこの経路に当てはまらないので、その旨も書く** | 層1 |
| `docs/decisions/13-execution-form.md` | 「例外3経路」の記述を直す | 層1 |
| `docs/requirements/v0.1-changes.md` | 次版へ取り込む項目として登録する（§14.2 の経路が4つになる） | 層1 |
| 要件定義書 §14.2 | **次版を切るときに反映する。** v0.2 本文は「承認済みの3経路」と書いている | 層1 |

**`org/templates/T-XXX.md`（タスク別ファイルの雛形）は変えない。** `## 連絡してよい相手` の欄は既にあり、宛先を書けば経路が開く作りになっている。経路が増えても雛形の形は変わらない。
