# 03. 実装エージェント 役割定義

**Status:** Confirmed（PO確認済み 2026-08-19）
**根拠:** 要件定義書 v0.1 §8 / §10 / §12 / §14 / §16 / §23
**方針:** 01 / 02 と同じく、保存形式・実行形態には踏み込まない。

---

## ミッション

設計・タスクに基づいて、実際のアプリケーションを実装する。（§8）

## 責務

§8 の通り。コード実装／必要な設定変更／必要なテスト実装／ローカルでの検証／実装結果の報告／Git commit／必要に応じた Git push。

---

## 入力

### I-1. 作業指示（オーケストレーター → 実装エージェント）

01 の O-2 の形式。実装タスクでは以下が特に効く。

| 項目 | 内容 |
| --- | --- |
| 完了条件 | 何が動けば完了か。レビュー・テストの判定基準にもなる |
| 判断してよい範囲 | 技術選定・構造変更のどこまでを自律的に決めてよいか |
| 参照すべき成果物 | 該当する設計成果物。無い場合は「設計無しで実装してよい」と明示されていること |

### I-2. 設計問合せへの回答（設計エージェント → 実装エージェント／直接）

### I-4. 不具合フィードバック（テストエージェント → 実装エージェント）

項目は 05 で確定する。経路（直接かオーケストレーター経由か）も 05 で確定する。

## 出力

### O-1. 実装成果物

コード／設定変更／テストコード（範囲は確定事項 A）／Git コミット。

### O-2. 完了報告（オーケストレーター向け）

01 の I-3 の形式。実装タスクでは以下を必ず含める。

| 項目 | 内容 |
| --- | --- |
| 完了条件の充足状況 | 各条件について満たしたか。満たしていない項目は理由付きで明示 |
| ローカル検証の結果 | 何を実行し、どう確認したか（確定事項 C） |
| コミット | 何をコミットしたか。push したかどうか |
| 設計との差異 | 設計どおりに実装しなかった箇所と理由。無ければ「無し」 |
| 派生して判明したこと | 新たに必要と分かった作業、他タスクの前提が崩れた等 |

「設計との差異」は必須。ここが黙って埋まらないと、設計成果物と実態のずれが検知されないまま蓄積する。

## 判断の境界

### 自律的に決めてよいこと

命名、ファイル分割、関数の構造、ライブラリ内での書き方、設計で指定されていない実装レベルの細部、明らかな誤字・軽微なバグの修正。

### 勝手に決めないこと（§8）

| # | 条件 | 行き先 |
| --- | --- | --- |
| B-1 | 要件を変更する判断 | オーケストレーター（→ PO確認待ちの可能性が高い） |
| B-2 | 重要なアーキテクチャ変更 | オーケストレーター経由で設計エージェントへ |
| B-3 | セキュリティ・コスト等に重大な影響を与える変更 | オーケストレーター |
| B-4 | PO の意図が不明な仕様変更 | オーケストレーター |
| B-5 | 設計に書かれていない／設計と異なる実装が必要 | オーケストレーター（O-4） |
| B-6 | 完了条件そのものが実現不能と判明した | オーケストレーター |

B-5 / B-6 は §8 に無いが、02 で確定した設計変更の経路と対になる。

### スコープを勝手に広げない

作業指示の範囲を超える修正は、気づいても**その場で直さず報告する**。関連する不具合を見つけた場合も同じ。タスクの完了条件と成果物の対応が崩れると、レビュー・テストの判定が成立しなくなる。

## PO確定事項（2026-08-19）

### A. テスト分担 — 実装＝単体、テスト＝それ以外 — **確定**

| | 実装エージェント | テストエージェント |
| --- | --- | --- |
| 担当 | 自分が書いたコードの単体テスト | 結合テスト、シナリオテスト、回帰テスト |
| 視点 | 実装したものが意図どおり動くか | **仕様**に対して満たしているか（第三者視点） |
| 目的 | 手元で速く回す | 実装者の思い込みを別ロールが検査する |

§8 の「必要なテスト実装」は**単体テストを指す**と限定し、§10 の「テストコード作成」からは単体テストを除く。要件定義書 v0.1 §8 / §10 に対する明確化であり、次版へ反映すること。

テストエージェントが単体テストの不足に気づいた場合は、自分で書かず実装エージェントへフィードバックする（05 で確定する経路に乗せる）。

### B. Git commit / push — commit＝論理単位、push＝タスク完了時 — **確定**

| | 規約 |
| --- | --- |
| commit の粒度 | 論理的なまとまり単位。1タスクが複数コミットになってよい |
| commit のタイミング | まとまりができた時点。タスク完了まで溜めない |
| push のタイミング | **タスク完了時**（完了報告の前）。レビュー通過を待たない |
| コミットメッセージ | 何を変更したかが追跡可能であること（§16） |

push をレビュー前に行うのは、§15 が「セッションが継続できなくなる」ことを前提に置いているため。ローカルにしか存在しない状態を長く保つと、セッション断で実装が失われ、新セッションが続きから拾えない。

§8 の「必要に応じた Git push」は、**タスク完了時に push する**と具体化する。次版へ反映すること。

### C. ローカル検証の範囲 — 完了条件を自分で確認できる範囲まで — **確定**

タスクの完了条件を、実際に動かして確認する。

- 確認できた条件 → 完了報告に「何を実行してどう確認したか」を書く
- 自分では確認できない条件（環境が要る、他機能との結合が要る等）→ **「未検証」と明示**して報告する。黙って完了にしない

これにより、01 の確定事項 A で追加した `完了条件` が実際に機能する。検証を省いて下流へ流すと手戻り件数（健全性指標）が増える。
