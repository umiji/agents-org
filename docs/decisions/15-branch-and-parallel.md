# 15. ブランチ運用と並列実行

**Status:** Confirmed（PO の指示により確定 2026-08-25）
**位置づけ:** 要件定義書 §23 の12項目には無い。配布物（`org/`）に Git のブランチ規約が一切無く、並列実行の指示と正面から衝突していたため確定させた
**関連:** `07`（タスク管理仕様）/ `13`（実行形態と配置）/ `14` 論点2（担当エージェントを独立セッションで動かすか）

## この文書が確定したこと

- **作業ブランチは「まとまり（機能・マイルストーン）」ごとに1本。** タスクごとには切らない
- **既定ブランチ（`main` 等）の上で組織を動かさない。** マージはレビュー通過後にオーケストレーターが行う
- **ブランチを作る・切り替えるのはオーケストレーターだけ**
- **並列に走らせてよいのは、触るファイルが重ならないタスクだけ。** 保証するのはタスク分解の側
- 担当エージェントの書いたものが失われそうなとき、オーケストレーターは**内容を書き換えずに退避コミットしてよい**

---

## なぜ決める必要があったか

配布物には commit の粒度・タイミング・push の規約はあったが、**ブランチに関する記述が1行も無かった**。一方でオーケストレーターの手順は「依存関係の無いタスクは同時に走らせる」と指示し、層2の規約は「push はタスク完了時、レビュー通過を待たない」と定めている。

この3つを素直に実行すると、**複数の実装エージェントが、未レビューのコードを、既定ブランチへ同時に push する**。開発対象リポジトリが既定ブランチを保護していれば全タスクが止まり、保護していなければ未レビューのコードが積み上がる。

---

## 決定を規定する事実 — 作業ツリーは1つしかない

担当エージェントは Claude Code のサブエージェント（子プロセス）として起動され、**メインセッションと同じ作業ツリー（同じチェックアウト）で動く**。

Git のチェックアウトに出せるブランチは1本である。したがって:

**同時に走る2つの担当エージェントは、必ず同じブランチの上にいる。**

これは運用の選択ではなく構造である。「1タスク1ブランチ」と「並列実行」は、この構成では**両立しない**。

---

## 選択肢

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A. 1タスク1ブランチ | タスクごとにブランチを切る | 変更の単位が明快。1タスクだけを取り消せる | **並列実行ができなくなる。** 同時に走らせる相手ごとにブランチを分けられないため |
| **B. まとまり単位で1ブランチ**（採用） | 機能・マイルストーンごとに1本。並列タスクは同じブランチの上で走る | 並列実行を保てる。既定ブランチは常にレビュー通過後の状態 | 1タスクだけを取り消しにくい。同じファイルを触るタスクを同時に走らせられない |
| C. タスクごとに worktree | タスクごとに別チェックアウトを作る | 完全に分離できる | **タスク台帳が分裂する。** 各チェックアウトが自分の台帳へ書くため（`14` 論点2で確認済み）。MVP の範囲を超える |

## なぜ B か

**並列に走れる単位を作ることが、組織化の利得の源である**（要件定義書 §4 / 調査メモ `00`）。直列依存が連なる分解では、組織化のコストだけを払って利得が出ない。A はその利得を構造的に捨てる。

C は分離としては最も強いが、台帳の分裂という未解決の問題（`14` 論点2）を先に解く必要がある。**解決済みの問題を、未解決の問題に交換することになる。**

B の欠点である「同じファイルを触るタスクを同時に走らせられない」は、**タスク分解の側で保証できる**。分解時に触る範囲を見ているのはオーケストレーターであり、そこで重なりを避ける判断ができる。重なるなら並列にせず順番に走らせればよい。

---

## 並列実行の可否と、その根拠

| 問い | 答え |
| --- | --- |
| 担当エージェントを同時に起動できるか | **できる。** Agent ツールで複数を一度に起動する |
| タスクごとにブランチを分けられるか | **できない。** 作業ツリーが1つのため |
| 何を確認すれば安全に並列化できるか | **触るファイルが重ならないこと。** 分解時にオーケストレーターが確認する |
| 独立セッションで動かせば分離できるか | できるが、Git の worktree 分離が台帳の共有と衝突する（`14` 論点2。**未決**） |

## 副次的に直したもの — 共通の停止条件 S-3

「作業開始時点で、作業ツリーに未確認の差分があれば止まる」という停止条件は、**単独実行を前提にしていた**。並列実行では、他のタスクが書いている途中の差分が見えるのが正常である。

そのままにすると、並列化した瞬間に全エージェントが停止条件に引っかかるか、もっと悪い場合は**他人の作業中の差分を巻き戻す**。

但し書きを足した——止まるのは**自分のタスクの `変更範囲` の中に身に覚えのない差分があるときだけ**。範囲外の差分は触らず、報告だけする。

## 例外 — オーケストレーターがコミットしてよい場合

実運用（開発対象リポジトリ SNS Agent）で、担当エージェントの未完成の作業を、実行環境が揮発する前にオーケストレーターがコミットした事例が出た。判断が分かれうるとして報告されている。

**認める。** ただし条件を付ける。内容を一切書き換えないこと、コミットメッセージに未完成・未検証であることを明記すること。

これは「オーケストレーターは実装しない」（要件定義書 §6.3）の例外ではない。**書かれたものを保全する操作であって、書く操作ではない。**

## 未確定のまま残すもの

- ブランチ名の規約は `org/<まとまりの名前>` としたが、開発対象リポジトリに既存の命名規約があればそちらへ合わせる。組織側が譲る（`13` の既存拡張との共存と同じ原則）
- プルリクエストを使うかどうか。開発対象リポジトリの運用に依存するため、組織側では決めない
