## この文書が確定したこと

- **組織自身を改善するループを、4工程として定義した** — 観測 → 診断 → 反映 → 追随。既に散在していた部品を、この4工程のどこかへ割り当て直した
- **改善エージェント（`org-improvement`）を担当エージェントの6体目として足す。** 観測対象が「開発の成果物」ではなく「組織自身」である点で、既存5ロールのどれとも責務が重ならない
- **改善エージェントは自分では直さない。** 提案までを担当し、層2（組織自身への指示）への反映はオーケストレーターが行う。レビューエージェントと同じ形である
- **人間（PO）の承認でループを閉じる。** ただし全件を上げるとエスカレーション過多になるため、**反映の重さで3段に分けた**
- **担当エージェントが「組織の仕組みへの指摘」を、作業を止めずに残せる場所を作る** — タスク別ファイルの `## 組織への指摘` 節。エスカレーション（作業を止めて判断を仰ぐこと）とは別物として扱う
- **改善提案には「期待する効果」を必須欄にする。** どの指標がどう動けば成功かを書けない提案は受け付けない。**これが検証の最小形である**
- **定期実行の外部機構は作らない。** セッション開始時に走る検査へ「前回の組織点検から何件完了したか」を1行足し、点検の呼び出し時期が目に入るようにする
- **層2で閉じる改善と、配布物（層1）を直さないと全導入先で再発する改善を、提案の時点で区別する**

## A. なぜこれが要るのか

### A-1. 意図が言語化されないまま、部品だけが増えた

PO はこの組織の重要な性質として「課題を発見したら改善するサイクルを回せること」を挙げていた。**しかしそれは、要件定義書にも決定記録21件にも配布物にも、一度も書かれていない**（調査の詳細は `docs/experiments/04-self-improving-org.md` §1 事実1）。

一方で、部品にあたるものは既にある——組織の異常を検知しうるものが7つ、見つけたものを反映する規約が3つ（同 事実2）。**つまり、目的が無いまま手段だけが個別の必要に応じて作られてきた状態である。** これは決定ログの索引を作ったとき（`docs/decisions/21-decision-log-index.md`）と同じ形の問題で、そのときの言葉を借りれば「書く費用は毎回かかるのに、効果が0」に近づく。

### A-2. 散在した部品では、拾えないものが4つある

| # | 拾えないもの | いま何が起きているか |
| --- | --- | --- |
| 1 | **2回目以降の点検** | 組織そのものの点検（`org/skills/org-first-run-check/SKILL.md`）は**最初のタスクが1件完了した時点で1回だけ**である。2回目をいつやるかが決まっていない。結果、「数タスク後に、ツールの実行許可の確認が何回出たかを見る」といった予定が、本リポジトリの `CLAUDE.md` に手書きのメモとして置かれているだけになっている |
| 2 | **層2 → 層1 の還流** | 開発対象リポジトリで見つかった不備を配布物へ戻す経路が、規約としては存在しない。**実害が出ている** — トライアル先が同じ不具合を独自に直し、**同じ問題を2箇所で別々に直した状態**になっている（`docs/handover.md` 現在地、`docs/decisions/14-open-questions.md` 論点1） |
| 3 | **組織の仕組みそのものへの異議** | エスカレーション（判断を上へ上げること）の4段階は、どれも**目の前のタスクをどう進めるか**を上げる経路である。「この規約には無理がある」「この道具が足りない」を、作業と独立に上げる先が無い |
| 4 | **改善の判断の記録先** | 決定記録（`docs/decisions/`）は層1だけの概念で、開発対象リポジトリには存在しない。改善をなぜそう決めたかを書く場所が無い（`docs/decisions/21-decision-log-index.md` が指摘済み） |

### A-3. 現状の引き金は「2回目」しか拾わない

層2の保守の引き金として明文化されているのは3つで、**いずれも「同じことが2回起きたら規約へ書け」の形である**（`org/skills/org-orchestrate/SKILL.md` 第8節）。1回目を拾う経路が書かれていない。1回目で拾えるものまで2回待つのは、単純に高くつく。

## C. ループの定義 — 4工程

**「観測 → 診断 → 反映 → 追随」の4工程とする。** 前3つは Anthropic の「集める → 行動する → 検証する」に対応し、4つ目は**この組織に固有の工程**である——組織の定義が層1（本リポジトリ）と層2（各開発対象リポジトリ）に分かれているため、片方だけ直しても他の導入先では再発するためである。

| 工程 | 何をするか | 担当 | 起動条件 | 出力 |
| --- | --- | --- | --- | --- |
| **1. 観測** | 組織の異常を示す信号を集める。数え上げはスクリプト、読み取りは改善エージェント | 改善エージェント | §C-5 の3条件 | 信号の一覧 |
| **2. 診断** | 信号から原因を推定し、**最小の編集**として改善案を書く | 改善エージェント | 工程1の直後 | 改善提案（§F-2 の書式） |
| **3. 反映** | 提案を層2へ適用する。重さに応じて PO の承認を挟む | オーケストレーター（承認は PO） | 提案を受けた時点 | 層2の変更、または PO確認待ちキューの項目 |
| **4. 追随** | 層2で閉じない改善を、配布物（層1）へ戻す | オーケストレーター → PO → 本リポジトリ | 提案の適用範囲が「配布物」のとき | 本リポジトリへの差し戻し報告 |

### C-1. 観測・診断を、反映から切り離す

**これが要点である。** 反映する権限を持つ者が観測もすると、自分の失敗を見落とす。これは本リポジトリの既存の明文であり、2箇所で述べられている（`docs/experiments/04-self-improving-org.md` §1 事実6）。

> オーケストレーター自身が点検すると、自分の失敗を見落とすためである。（初回点検の手順）

> 書き換えられる側が自分を書き換えると、何が変わったのかを確かめる立場が消える。（導入時の初期シーケンス）

### C-2. 反映はオーケストレーターに残す

要件定義書 §6.2 が「層2の保守はオーケストレーターの責務」と定めている。**これを動かさない。** 改善エージェントに書き換えまで持たせると、§C-1 の分離が逆向きに壊れる（観測する者が反映もする）。

**レビューエージェントと同じ形である** — 指摘はするが、自分では直さない。

### C-3. 工程4（追随）が要る理由

層2は各開発対象リポジトリに置かれるコピーである。**そこだけを直すと、同じ組織を導入した他のリポジトリでは同じ問題が再発する。** これは既に起きている（§A-2 の2）。

**ただし配布方式そのものは、この文書では決めない。** 未決の論点として PO の判断待ちである（`docs/decisions/14-open-questions.md` 論点1）。ここで決めるのは、**「どの改善が配布物由来か」を提案の時点で機械的に拾える形にしておく**ことだけである。配布方式が決まったとき、その情報がそのまま使える。

### C-4. ループは「回す」のであって「回り続ける」のではない

**無人で回し続けることは狙わない。** 要件定義書 §3.3 が24時間無人運転を MVP 対象外としている。工程1が起動するのは §C-5 の3条件のときだけで、それ以外の時間、この仕組みは何もしない。

### C-5. 起動条件 — 定期実行の機構を作らずに定期性を得る

| # | 条件 | 意図 |
| --- | --- | --- |
| 1 | **最初のタスクが1件完了したとき**（現行の初回点検） | 導入直後の設定ミスを早く拾う。既存の手順をそのまま使う |
| 2 | **前回の組織点検から、タスクが N 件完了したとき** | 蓄積に対して動かす。N の既定値は §I の判断2 で PO に問う |
| 3 | **ゴール健全性評価の節目、または PO の指示** | 既に「節目ごと」と決まっている評価（`docs/decisions/10-goal-health.md`）に相乗りする |

**条件2を人が覚えていなくても分かるようにする。** セッション開始時に必ず走る検査（停滞検知・整合性検査 `org/scripts/org-check.py`）の出力へ、**「前回の組織点検から N 件完了している」の1行を足す**。これで、スケジューラを導入せずに呼び出し時期が目に入る。

**これは §4.1（Claude Code 標準機能を最大限使う）と §18（独自設定ファイルを作らない）に沿った選択である。** 外部のスケジューラも新しい設定ファイルも要らない。

## D. 改善エージェント（`org-improvement`）

### D-1. なぜロールを増やすのか

要件定義書 §17.3 と `docs/decisions/12-agent-addition.md` は「**ロールを増やす前に確認する。専門知識が要るだけならスキルを足す。ロールは責務の単位であって、知識の単位ではない**」と定めている。この確認に答える。

| 問い | 答え |
| --- | --- |
| 既存5ロールのどれかに入らないか | **入らない。** 5ロールはいずれも**開発の成果物**（設計・実装・レビュー・テスト・利用者向け文書）を対象にしている。改善エージェントの対象は**組織自身**であり、成果物ではない |
| オーケストレーターに持たせられないか | **持たせられない。** ①自分で自分を点検すると失敗を見落とす（§C-1 の既存明文）。②オーケストレーターの文脈は報告を受けるたびに膨張することが調査で分かっている（`docs/decisions/00-research-notes.md`）。観測は台帳・作業ログ・集計結果を横断して読むため、最も文脈を食う作業である |
| 知識が足りないだけではないのか | **違う。** 足りないのは知識ではなく**立場**である。既存の誰も「組織自身を対象にする」責務を負っていない |
| 既存ロールとの境界を一文で言えるか | **言える。**「レビューエージェントは成果物を見る。改善エージェントは組織を見る」 |

**加えて、サブエージェントは独立した文脈領域を持つ**という性質が、この用途に合う（`docs/experiments/04-self-improving-org.md` §2.2）。大量に読み、結論だけを親へ返す作業に向いている。

### D-2. 定義の5要素

`docs/decisions/12-agent-addition.md` が定めた必須構成（ミッション／責務／入力／出力／エスカレーション条件）に従う。

**ミッション**

組織が最大の成果を出すことを妨げているものを見つけ、**それをどう直すかの提案**を作る。開発の成果物には触れない。

**責務 — 担当すること**

- 観測（工程1）— 信号を集め、異常を特定する
- 診断（工程2）— 原因を推定し、**最小の編集**として改善案を書く
- 効果の照合 — 前回の提案が適用されていた場合、**期待した効果が出たかを指標で照合する**（§G）
- アセットの不足の検知 — この実行環境から呼べるスキルと、このリポジトリの技術構成を突き合わせ、足りないものを挙げる（導入時の初期シーケンス `org/skills/org-init/SKILL.md` の段1・段2 の再実行にあたる）

**責務 — 担当しないこと**（要件定義書 §6.3 が「やらないこと」を明示したのと同じ形）

- **層2（`CLAUDE.md`・`.claude/rules/`・エージェント定義・用語集）を自分で書き換えない。** 提案までである
- **開発の成果物に触れない。** コード・テスト・設計成果物・利用者向け文書のいずれも対象外
- **個々の担当エージェントの出来を評定しない。** 対象は仕組みであって、担当者ではない
- **タスクを登録・割り当てしない。** 登録はオーケストレーターの責務（要件定義書 §6.2）

**入力**

| # | 何を | どこから |
| --- | --- | --- |
| I-1 | 起動理由（§C-5 のどれか）と、前回の組織点検の時点 | オーケストレーター |
| I-2 | タスク台帳（索引 `docs/task-list-{project-name}.csv` と、タスク別ファイル `docs/tasks/T-XXX.md`） | 開発対象リポジトリ |
| I-3 | 停滞検知・整合性検査とゴール健全性の集計結果 | `org/scripts/org-check.py` の出力 |
| I-4 | トークン消費の集計結果 | `org/scripts/org-tokens.py` の出力 |
| I-5 | この実行環境から呼べるスキルの一覧 | `org/scripts/org-skills.py` の出力 |
| I-6 | PO確認待ちキュー（`docs/po-queue.md`） | 開発対象リポジトリ |
| I-7 | 前回までの改善提案とその状態 | 改善提案の台帳（§F-1） |

**出力**

| # | 何を | 誰へ |
| --- | --- | --- |
| O-1 | 改善提案（0件のこともある。§F-2 の書式） | オーケストレーター |
| O-2 | 前回提案の効果の照合結果（効いた／効かなかった／まだ判定できない） | オーケストレーター |
| O-3 | 観測したが提案に至らなかった信号と、その理由 | オーケストレーター |

**O-3 を必須にする理由。** 何も出さないと「見ていないのか、見たうえで問題無しなのか」が区別できない。**判定できなかったこと自体が信号である。**

**エスカレーション条件 — 上げるもの**

- 観測に必要なファイルが存在しない、または壊れていて読めない
- 提案が**ゴール自体の見直し**を要する（ゴール健全性評価の「ゴールが揺らいでいる」に相当。`docs/decisions/10-goal-health.md`）
- 同じ問題を**2回続けて提案し、2回とも反映されなかった**

**エスカレーション条件 — 上げないもの**

- 提案が採用されなかったこと（採否はオーケストレーターと PO の判断であり、差し戻しではない）
- 信号が0件だったこと（O-3 で報告すれば足りる）

### D-3. 直接通信は許さない

`docs/decisions/12-agent-addition.md` は「**直接通信の経路を増やすときだけは摩擦を残す。ファイル追加では済ませず、組織規約の変更として扱う**」と定めている。

**改善エージェントに直接通信の例外は与えない。** 返す先はオーケストレーターだけである。承認済みの3経路（レビュー→実装、実装→設計、テスト→実装）はいずれも「実装への差し戻しであり、設計や要件を変えない」という共通の性質を持つが、**改善の提案は組織の規約を変えるものであり、この性質を満たさない**。

## E. 観測する信号

### E-1. 何を集めるか

**大半は既存の仕組みから機械的に取れる。** 新しく作るのは信号7と8だけである。

| # | 信号 | 出所 | 何を疑うか |
| --- | --- | --- | --- |
| 1 | 実時間基準の停滞（更新が2日以上止まっている） | `org-check.py` | 指示の不足、依存の見落とし |
| 2 | サイクル基準の停滞（手戻り回数3以上） | 同（タスク別ファイルの `手戻り回数`） | 完了条件が曖昧、設計の欠陥 |
| 3 | ボトルネックとなっている工程（状態別の滞留日数の中央値） | `org-check.py --summary` の指標7 | その工程の担当への指示不足、道具の不足 |
| 4 | エスカレーションの偏り（同じ論点が複数タスクから／特定のロールからばかり） | `docs/po-queue.md` の横断 | 層2に判断基準が無い。回答の還元を怠っている（要件定義書 §12.5 の「症状 → 疑うべき原因」の対応表がそのまま使える） |
| 5 | PO確認待ちの滞留（未回答が2日以上） | `org-check.py` | ゴール達成条件が確定していない |
| 6 | トークン消費の偏り（特定の担当・モデル・タスクへの集中） | `org-tokens.py --by agent / --by model / --by task` | 手順の冗長、委譲の設計ミス |
| 7 | **担当エージェントからの、組織の仕組みへの指摘** | **新設**（§E-2） | 規約の無理、道具・アセットの不足 |
| 8 | **PO の差し戻し・却下・言い直し** | **新設**（§E-3） | 最も価値の高い信号。§B-1 のとおり、量より質である |
| 9 | 呼べるスキルと技術構成の食い違い | `org-skills.py` ＋ 依存関係の宣言ファイル | アセットの不足（`docs/decisions/20-skill-assignment.md`） |

### E-2. 信号7 — 担当エージェントが、作業を止めずに指摘を残す場所

**タスク別ファイル `docs/tasks/T-XXX.md` へ `## 組織への指摘` 節を足す。** 担当エージェントは、完了報告を書くついでにここへ1行書く。

**これはエスカレーションではない。** エスカレーションは「判断できないので作業を止めて仰ぐ」ことであり、4段階の経路がある（`docs/decisions/08-escalation-criteria.md`）。ここに書くのは**作業を止めずに残す一方向の記録**であり、返事を期待しない。

書くものは3種に限る（何でも書ける欄にすると読めなくなる）。

| 種別 | 書く条件 |
| --- | --- |
| `規約` | 層2の規約に従うと作業が進まない、または矛盾する箇所に当たった |
| `道具` | 必要な道具・スキル・外部アクセスが無く、遠回りをした |
| `反復` | 同じ種類の手戻りを、このタスクで2回以上経験した |

**書式は1行1件で `- [種別] 内容` とする。** 機械が拾うためである。**書式を文章でだけ規定して雛形を配らないのは、本リポジトリが既に踏んだ失敗である**（`docs/handover.md` 末尾の教訓）。タスク別ファイルの雛形 `org/templates/T-XXX.md` へ、この節を実物として入れる。

**Warp の「フィードバックは作業が起きている場所で受け取る。提出のための別作業を作らない」を、この形で実現している**（§B-1）。専用の報告先を作ると、報告そのものが仕事になり、書かれなくなる。

### E-3. 信号8 — PO の反応を残す

**PO の差し戻し・却下・言い直しが、最も価値の高い信号である**（§B-1）。しかし現状、PO の反応は会話の中にしか無く、セッションが終われば消える。

**PO確認待ちキュー（`docs/po-queue.md`）の各項目へ `反応` 欄を1行足す。** 回答そのものとは別に、**「なぜその回答になったか」「問いのどこが悪かったか」**を、オーケストレーターが PO の言葉に近い形で残す。

要件定義書 §13.3「回答の還元」が既に「一度の回答を、以後の判断基準にする」と定めている。**この欄はその入力を残すためのものであり、新しい規約ではなく既存規約の実行部分である。**

## F. 提案と反映

### F-1. 台帳 `docs/org-improvements.md` を新設する（**PO 承認 2026-09-01**）

改善は、セッションをまたいで残らなければならない（起票 → 診断 → 承認 → 適用 → 効果の照合、が複数セッションにまたがるため）。**専用の台帳を1つ新設する。** 開発対象リポジトリに置くファイルの7種類目になる。

**1課題1ブロックとし、課題の一生をそのブロックの中で進める。** 課題の台帳と提案の台帳を分けない——分けると、どの提案がどの課題に対するものかを人が突き合わせることになる。

| 状態 | 意味 | 次に動かすのは誰か |
| --- | --- | --- |
| `未処理` | 起票されたが、まだ誰も診ていない | 改善エージェント（次の点検で） |
| `診断済み` | 原因の推定と対応策が書かれた。優先度がついた | オーケストレーター |
| `承認待ち` | PO確認待ちキューへ載せた（重さが `中` か `重` のもの） | PO |
| `承認済み` | PO が承認した。まだ適用していない | オーケストレーター |
| `適用済み` | 層2へ反映した。効果はまだ見ていない | 改善エージェント（次の点検で照合） |
| `効果確認済み` | §G の照合で「効いた」と判定した。**ここで閉じる** | — |
| `却下` | 採らないと決めた。**理由を必ず書く** | — |
| `見送り` | 今は対処しないが、消さない。再燃したら `未処理` へ戻す | — |

### F-1-a. 台帳へ書いてよいのは誰か — **担当エージェントは直接書かない**

**PO が示した流れ**（各エージェントが台帳へ都度書き出し、改善エージェントが定期的に読む）**のうち、「台帳へ直接書く」部分だけを変える。** 理由は、既に確定している並列実行の規約と正面から衝突するためである。

> **並列に走らせてよいのは、触るファイルが重ならないタスクだけ。**（`docs/decisions/15-branch-and-parallel.md`）

担当エージェント全員が1つの台帳へ書くと、**その台帳は全タスクが触るファイルになり、並列実行が構造的に成立しなくなる。** 加えて、同時に走る2体が同じファイルへ書けば、片方の追記が消える。

**既存の共有ファイルは、すべて同じ方法でこれを避けている** — タスク索引の CSV も、PO確認待ちキューも、**書くのはオーケストレーターだけ**という不変条件で守られている（`docs/decisions/07-task-management.md`）。台帳もこれに合わせる。

| 誰が | 台帳へ書くか | 何を書くか |
| --- | --- | --- |
| **担当エージェント**（設計・実装・レビュー・テスト・ドキュメント） | **書かない** | 自分のタスクファイルの `## 組織への指摘` へ1行書き、**完了報告にも含める**（§E-2）。**自分しか触らないファイルなので衝突しない** |
| **オーケストレーター** | **書く（唯一の書き手）** | 担当エージェントから吸い上げた指摘を**1課題1レコードにまとめて起票**する。以後の状態の更新、診断結果の転記、PO の回答、適用の記録も行う |
| **改善エージェント** | **書かない** | 診断結果はオーケストレーターへ返す。編集系ツールを持たない（§D-2） |
| **スクリプト**（`org-check.py`） | **書かない** | **タスクファイルに書かれているのに台帳へ起票されていない指摘**を検出して警告する。起票そのものはしない |

**「まとめる」は判断であり、機械にはできない。** 3つの別々のタスクから同じ趣旨の指摘が出たとき、それを**1レコードに束ねるか、別々の課題として立てるか**の判断が要る。機械に集約させると3レコードになり、優先度づけの基準（「同じ課題が3件以上の別タスクから出ている」）が働かなくなる。**両者の報告を受け取るオーケストレーターだけが、この判断ができる位置にいる。**

**スクリプトに書かせないもう1つの理由。** 停滞検知・整合性検査のスクリプト（`org-check.py`）は、**読んで警告を出すだけで何も書かない道具**である。ここへ書き込みを足すと、その性格が壊れる。**検出だけを足す**——タスクファイルに書かれているのに台帳に無い指摘があれば警告する。これは既存の整合性検査と同じ性質の機能である。

**PO の流れの意図は変わっていない。** 「各エージェントが課題と感じたことを都度書き出す」はそのままで、書き出す先が自分のタスクファイルと完了報告になり、**台帳への集約をオーケストレーターが行う**。

**タスクファイルの節と台帳の関係。** タスクファイルの `## 組織への指摘` が**担当エージェントが書いた原文（正典）**、台帳が**まとめた作業台**である。これは既存の「タスク別ファイルが正典で、CSV が索引」という関係と同じ形である。

**取りこぼしへの備え。** オーケストレーターが起票を怠っても、原文はタスクファイルに残る。**改善エージェントは点検のたびに、台帳に無い指摘が残っていないかを確かめる**（スクリプトの警告と、自分での横断検索の両方で）。

**タスクの外で気づいた課題**（オーケストレーター自身が気づいたもの、PO の反応から拾ったもの）も、オーケストレーターが直接起票する。

### F-1-b. 優先度は改善エージェントがつける

PO の流れどおり、**改善エージェントは全件を上げず、優先度の高いものを対応策とともにエスカレートする。** 3値とする。

| 優先度 | 基準 |
| --- | --- |
| **高** | 組織が止まっている、または止まりかけている（停滞・ブロックの原因になっている）／同じ課題が**3件以上の別タスク**から出ている／**PO の反応（信号8）に由来する** |
| **中** | 手戻りやトークンの無駄が、測れる形で出ている |
| **低** | 不便ではあるが、作業は進んでいる |

**優先度を件数だけで決めない。** Warp の「フィードバックは量より質」（§B-1）に従い、**PO 由来の指摘1件は、担当エージェント由来の3件より重く扱う。**

**1回の点検でエスカレートするのは最大3件とする。** 全件を上げると、この仕組み自体が「エスカレーションが多すぎる」という症状の原因になる（要件定義書 §12.5）。残りは台帳に `未処理` のまま残り、次の点検で再び優先度づけの対象になる。

### F-2. 提案の書式

**1提案1ブロック。** 欄は7つで、**すべて必須**とする。

| 欄 | 内容 | なぜ必須か |
| --- | --- | --- |
| `信号` | どの信号（§E-1 の1〜9）から、何件観測したか | 推測で提案させないため |
| `原因の推定` | なぜそれが起きていると考えるか | 症状への対症療法を防ぐ |
| `変更` | **どのファイルを、どう直すか。最小の編集で書く** | Warp の「最小の編集」（§B-1）。大きい変更は検証できない |
| `適用範囲` | `このリポジトリのみ` / `配布物` のいずれか | 工程4（追随）が機械的に拾えるようにするため（§C-3） |
| `重さ` | `軽` / `中` / `重` のいずれか（§F-3） | 承認経路が決まる |
| `期待する効果` | **どの指標がどう動けば成功か** | §G。書けない提案は検証できない |
| `悪化しうるもの` | この変更で悪くなる可能性があるもの | 「片側だけの評価は片側だけの最適化を生む」（§B-1） |

### F-3. 反映の3段 — 承認をどこまで PO へ上げるか

**全件を PO へ上げると、この仕組み自体がエスカレーション過多の原因になる**（要件定義書 §12.5 が挙げる症状そのものである）。重さで分ける。

| 重さ | 該当するもの | 承認 | 記録 |
| --- | --- | --- | --- |
| **軽** | 層2の規約への追記、用語集への語の登録、判断してよい範囲の明文化、ビルド・テストのコマンドの修正 | **不要。** オーケストレーターが反映し、**事後に PO へ1行で報告する** | 改善提案の台帳に「適用済み」として残す |
| **中** | エージェント定義の変更、スキル割り当ての変更、停滞判定などの閾値の変更、タスク別ファイルの書式変更 | **PO確認待ちキューへ載せる** | 同上 ＋ PO確認待ちキューの `Q-XXX` |
| **重** | ロールの追加・削除、直接通信の経路の追加、配布物（層1）の変更、ゴール自体の見直し | **PO確認待ちキューへ載せる。** さらに層1では**決定記録が要る** | 同上 ＋ 本リポジトリの `docs/decisions/` |

**軽を事後報告で通す根拠。** 要件定義書 §6.2 が層2の保守をオーケストレーターの責務として既に与えており、そこに PO の事前承認は要求されていない。**この文書はその範囲を広げない。**

**重に「配布物の変更」が入る理由。** 層1の変更は全導入先へ波及する。`docs/decisions/12-agent-addition.md` が直接通信経路の追加について「ファイル追加では済ませず、組織規約の変更として扱う」と定めたのと同じ趣旨である。

## G. 検証 — 改善が効いたかをどう見るか

**「期待する効果」欄が、この組織における eval（試験用課題の集合。エージェントの出来を測るための課題）の代わりである。**

提案を出す時点で「どの指標がどう動けば成功か」を書かせ、**次の組織点検で照合する。** 照合に使うのは、すべて既に集計できる数値である。

| 使う指標 | 出所 |
| --- | --- |
| ゴール健全性の8指標（完了・未完了・停滞・ブロック中・PO確認待ち・手戻り件数・ボトルネック工程・残作業） | `org-check.py --summary`（`docs/decisions/10-goal-health.md`） |
| 手戻り回数（タスク別） | タスク別ファイルのメタデータ |
| トークン消費（担当別・モデル別・タスク別） | `org-tokens.py` |
| 組織への指摘の件数（種別ごと） | §E-2 の新設節 |

照合の結果は3値とする。

| 判定 | 意味 | 次にすること |
| --- | --- | --- |
| **効いた** | 期待した指標が期待した向きに動いた | 提案を「確定」にする |
| **効かなかった** | 動かなかった、または逆に動いた | **変更を戻すか、原因の推定をやり直す。上乗せで別の変更を積まない** |
| **まだ判定できない** | 母数が足りない（対象の工程をまだ通っていない等） | 次回へ持ち越す。**持ち越し2回で、判定できない理由を報告する** |

**「効かなかった」で上乗せを禁じる理由。** 効かない変更の上に別の変更を積むと、層2が誰も意図していない規約の堆積物になる。これは停滞管理が「同じ手を繰り返すのは停滞の解消ではなく停滞の継続である」と述べたのと同じ構造である（`docs/decisions/09-stagnation.md`）。

**モデルによる判定（LLM-as-Judge）は使わない。** 理由は §B-2 のとおり。

## I. PO の判断が要る点

**推測で埋めない**（本リポジトリの確定作業の規約）。3件ある。

### 判断1. 改善提案をどこに置くか → **決着（PO 承認 2026-09-01）**

**専用の台帳 `docs/org-improvements.md` を新設する。** 開発対象リポジトリに置くファイルの7種類目になる。既存のタスク台帳への相乗りは採らない——ゴール健全性評価（`docs/decisions/10-goal-health.md`）は「タスクは消化されているのにゴールへ近づいていない」を検知するために作られており、そこへ組織改善のタスクが混ざると、まさにその検知が効かなくなるためである。

**台帳の設計は §F-1 にある。** PO が示した流れのうち「担当エージェントが台帳へ直接書く」部分だけは、並列実行の規約と衝突するため、**タスクファイルへ書いてスクリプトが集約する形**へ置き換えた（§F-1-a）。意図は変えていない。

### 判断2. 組織点検の起動間隔（§C-5 の条件2の N）→ **暫定で 5 を採用。PO の明示的な回答は未取得**

| 案 | N | 利害 |
| --- | --- | --- |
| **A（推奨）** | **5件** | 信号が溜まる程度に大きく、問題が固着する前に拾える程度に小さい。トライアル先の現在の規模（完了数件）では**まだ1度も起動しない**——それでよい。母数の無い観測は当てにならない |
| B | 3件 | 早く回るが、母数が足りず、提案が推測になりやすい |
| C | 10件 | 提案の質は上がるが、1回目の起動までが遠い |

**A を推す。** ただし**これは暫定値であり、実測で見直す。** 停滞判定の閾値（手戻り回数3以上）も同じ扱いで置かれている（`docs/decisions/09-stagnation.md` の末尾）。

### 判断3. 配布物にバージョンの刻印を入れるか

工程4（追随）は、導入先が「自分がどの版の配布物を使っているか」を言えないと成立しない。**ただしこれは配布方式の論点**（`docs/decisions/14-open-questions.md` 論点1）**の一部であり、本来はそちらで決めるべきものである。**

- **先に刻印だけ入れる**（`org/VERSION` に日付を書き、`org-check.py` が起動時に表示する）——配布方式が未決でも、追随の前提だけは満たせる
- **配布方式の決定まで待つ**——二度手間を避けられるが、その間の追随は今までどおり人の記憶に頼る

**PO が配布方式をいつ決めるかによる。** 判断を仰ぐ。

## J. やらないこと

**過剰に作らない**（PO の作業スタイル）。この文書の範囲外とするものを明示する。

- **提案の自動適用。** 人間の承認でループを閉じる（§B-2）
- **試験用課題の集合（eval）の基盤。** 失敗事例が20〜50件溜まるまで作らない（§B-2）
- **定期実行の外部機構。** §C-5 の代替で足りる
- **改善エージェントに編集系ツールを与えること。** §H の1 で構造的に防ぐ
- **ロールをさらに増やすこと。** 6体目で止める。次に「足りない」と感じたら、まずスキルを疑う（要件定義書 §17.3）
- **改善エージェントが個々の担当エージェントを評定すること。** 対象は仕組みであって担当者ではない（§D-2）
- **層3（開発対象アプリの利用者向け文書）への関与。** ドキュメントエージェントの担当である
