### 事実3. 層2の保守は、引き金が3つだけ明文化されている

`org/skills/org-orchestrate/SKILL.md` 第8節の原文が挙げる引き金。

- 同じ誤りが複数のタスクで繰り返された（規約として明文化すべき）
- ビルド・テストコマンドが確定した、または変わった
- エージェントが毎回同じ確認を上げてくる（判断基準が書かれていない）

**いずれも「同じことが2回起きたら規約へ書け」の形である。** 1回目を拾う経路は書かれていない。

### 事実4. 層2 → 層1 の還流経路は、規約として存在しない

事実として動いてはいる。トライアル運用先（PO が別リポジトリで動かしている SNS Agent の開発）のオーケストレーターからの差し戻し報告を受け、配布物へ6件の修正を入れた（2026-08-25。`docs/handover.md`「現在地」）。**ただしこれは人が手で運んでおり、手順としてはどこにも書かれていない。**

**実害が既に出ている。** 配布物を更新しても導入済みの先へ追随させる仕組みが無く（`docs/decisions/14-open-questions.md` 論点1）、トライアル先が同じ不具合を独自に直した結果、**同じ問題を2箇所で別々に直した状態**になっている。

### 事実5. 「組織の仕組みそのものへの異議」を上げる経路が無い

エスカレーションの4段階（自分の担当範囲 → 許可された他エージェントへ相談 → オーケストレーター → PO確認待ちキュー。`docs/decisions/08-escalation-criteria.md`）は、**どれも目の前のタスクをどう進めるかを上げるための経路**である。「この規約には無理がある」「この道具が足りない」を、作業の完了報告と独立に上げる先が定義されていない。

### 事実6. 「自分で自分を点検すると失敗を見落とす」は、既に本リポジトリの明文である

初回点検の手順（`org/skills/org-first-run-check/SKILL.md`）の原文。

> **自己申告を証拠にしない。**「委譲しました」という報告ではなく、**ファイルに残った痕跡**で判定する。オーケストレーター自身が点検すると、自分の失敗を見落とすためである。

同じ趣旨が、導入時の初期シーケンス（`org/skills/org-init/SKILL.md`）にもある——エージェント定義の書き換えを担当エージェント自身にやらせない理由として「書き換えられる側が自分を書き換えると、何が変わったのかを確かめる立場が消える」。

## §2 外部資料の調査（2026-09-01 実施）

PO から指示のあった資料と、そこから辿った Anthropic（Claude の開発元）の技術記事3本。**以下は資料が述べている内容であり、本リポジトリへの適用可否の判断は含まない。**

### §2.1 Warp の自己改善エージェント

出典: [How Warp builds self-improving agents on Claude](https://claude.com/blog/how-warp-builds-self-improving-agents-on-claude)（Anthropic 公式ブログ）。Warp は端末アプリケーションを作っている会社で、自社の公開リポジトリでコードレビュー・仕様作成・課題の仕分けをエージェントに行わせている。

**構成は「スキル2層 + 人間のフィードバック」である。** スキルとは、呼ばれたときだけ読み込まれる手順書のファイルを指す。

| 層 | 名前 | 何をするか | 起動 |
| --- | --- | --- | --- |
| 内側 | 基礎スキル（base skill） | 領域固有の手順。例: プルリクエストが開かれたらコードレビューを行う | 作業のたび |
| — | 人間のフィードバック | 良し悪しの評価。単純な良い／悪いの2値から、詳細な理由まで | 作業の結果に対して随時 |
| 外側 | 改善スキル（improver skill） | 溜まったフィードバックを引き出し、エージェントの出力と人間の反応を突き合わせ、**基礎スキルへの限定的な編集を提案する** | **スケジュール実行。作業のたびではない** |

創業者 Zach Lloyd の言葉として引かれている原文: 「A human could affirm, 'this was a good, useful comment,' but the human could also give detailed reasons why a code review wasn't good.」

**ループの4工程**（記事の記述順）。

1. **信号の収集** — フィードバックは**作業が起きている場所で**受け取る（プルリクエストのコメント、課題票）。提出のための別作業を作らない
2. **分析** — 改善スキルがスケジュール実行され、同梱の Python スクリプトで最近のフィードバックを引き出し、機械可読な形（JSON）へ要約する
3. **提案** — 具体的なフィードバックを特定し、**「それらを捉える最小の編集」**（the smallest edit that captured them）を提案する
4. **検証と適用** — 提案は**通常のコードレビューの流れに乗る**。人間が読み、承認し、統合する。次回の実行から改善が効く

記事が挙げている実装上の要点。

- **スキルがただのテキストファイルであること**が効いている。エージェントは「extremely good at updating them」であり、更新が「reviewable, approvable, and mergeable」（レビュー可能・承認可能・統合可能）になる
- **スクリプトを同梱する。** 毎回コードを生成させず、スキルから既存のファイルを参照させる
- **人間の最終承認がループを閉じ、人が制御を保つ**（closes the loop and keeps a person in control）
- **フィードバックは量より質。**「a small amount of detailed, domain-specific feedback from a senior engineer can be worth more than lots of cursory feedback」
- 規模: 「thousands of code reviews」「hundreds of people contributing」

### §2.2 エージェントのループ構造と「検証」

出典: [Building agents with the Claude Agent SDK](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)（Anthropic 技術記事）。

**ループの定義（原文）:** 「gather context -> take action -> verify work -> repeat」（文脈を集める → 行動する → 仕事を検証する → 繰り返す）。

**検証（verify）が信頼性の本体であるとしている。** 原文: 「Agents that can check and improve their own output are fundamentally more reliable」。

検証の3方式と、記事が挙げるその利害。

| 方式 | 内容 | 利害 |
| --- | --- | --- |
| **規則ベース** | 出力に対する明確な規則を与え、**どの規則がなぜ失敗したかを説明して返す**。原文「The best form of feedback is providing clearly defined rules for an output, then explaining which rules failed and why」 | **最良の形式であるとされている。** 規則を作り込むほど結果が良くなるが、設計に手間がかかる |
| **視覚ベース** | 画面の見た目を扱う作業で、スクリーンショットを撮って確認させる | 1枚では見える範囲が限られる |
| **モデルによる判定**（LLM-as-Judge） | 別の言語モデルに、曖昧な基準で出力を判定させる | 原文「This is generally not a very robust method, and can have heavy latency tradeoffs」——**堅牢でなく、待ち時間の代償が重い** |

記事が述べる文脈の扱い方。

- **ファイルシステムを文脈の置き場として使う。** フォルダ構成そのものが文脈設計になる
- **サブエージェント**（親から呼ばれる子のセッション）の利点は2つ——並列化と、**独立した文脈領域を持つこと**。関係するものだけを上へ返すため、親の文脈が膨らまない

### §2.3 評価（eval）の作り方

出典: [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)（Anthropic 技術記事）。「eval」とは、エージェントの出来を測るための試験用課題の集合を指す。

- **始めるのに要る規模:** 「20-50 simple tasks drawn from real failures is a great start」——**実際に起きた失敗から取った20〜50件で十分な出発点**。開発初期は効果が大きいため少数で足りる。「Evals get harder to build the longer you wait」（待つほど作りにくくなる）
- **課題の出どころ:** ①開発中に手で確認している項目、②実際に起きた不具合と苦情
- **測るもの:** **経路ではなく結果を測る。** 原文「it's often better to grade what the agent produced, not the path it took」。道具の呼び出し順序のような手順の固定は硬すぎるとしている
- **採点者の種類:** コードによる採点（速く・安く・再現するが、正しいが形の違う答えに弱い）／モデルによる採点（柔軟だが非決定的で、人間の採点との較正が要る）
- **偏りの回避:** 「Test both the cases where a behavior should occur and where it shouldn't」——**起こるべき場合と起こるべきでない場合の両方**を入れる。「One-sided evals create one-sided optimization」
- **課題の品質条件:** 指示に正しく従うエージェントなら通せること。**2人の詳しい人間が独立に同じ合否へ至ること**
- **飽和の監視:** 解ける課題を全部通してしまったら、伸びしろが無くなった信号なので、難しい課題を足す
- **人間が実際の記録を読むこと:** 「You won't know if your graders are working well unless you read the transcripts and grades from many trials」
