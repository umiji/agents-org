## 0. この調査で答えようとした問い

1回目の調査（`04`）は「組織が自分を改善するループをどう作るか」を調べ、設計の骨格を得た。**今回の問いはその次段にあたる** —— 骨格ができたうえで、**改善する側のエージェント自身を、外の実践に照らしてどう作り込むか**である。

具体的には次の4つを確かめた。

| # | 確かめたこと |
| --- | --- |
| Q-1 | 「改善するエージェント」に相当する既成の型が世の中にあるか。あるならその構造はどうなっているか |
| Q-2 | その型が名指ししている**失敗の仕方**は何か。現行設計はそれを踏んでいないか |
| Q-3 | それらはソフトウェアの成果物を良くする仕組みである。**組織そのものを良くする**側に、同じ形が存在するか |
| Q-4 | Q-1〜Q-3 で得たものと、現行設計（`25`）が食い違う点はどこか |

## 1. 現物調査 — 現行設計が、いま何に依存しているか

**外部の出典を読む前に、比較の基準を固定した**（後から都合よく読まないため。`docs/experiments/02-decision-records.md` が採った手順と同じ）。

### 事実1. 改善エージェントが読む材料は、6種がエージェント自身の書いたものである

`org/skills/org-improve/SKILL.md` 段2 が定める信号9種の出所を数えた。

| 出所の種別 | 信号の番号 | 件数 |
| --- | --- | --- |
| **スクリプトが台帳から機械的に数えた数字** | 1, 2, 3, 5, 6, 9 | 6 |
| **エージェントまたはオーケストレーターが文章で書いたもの** | 4, 7, 8 | 3 |
| **Claude Code の会話記録そのもの（生の実行記録）** | — | **0** |

**会話記録を直接読む信号は1つも無い。** ただし、それを読む道具は既に2本ある——トークン消費の集計（`org/scripts/org-tokens.py`）と稼働状況のモニタ（`org/scripts/org-monitor.py`）は、いずれも `~/.claude/projects/` の下の会話記録を読んでいる。**トークン集計の出力（信号6）は会話記録に由来するが、改善エージェントが受け取る時点では集計後の数字であり、実行の中身は残っていない。**

### 事実2. 台帳の状態8種に、「適用した改善を撤回する」経路が無い

`org/templates/org-improvements.md` の状態は8種（`未処理` `診断済み` `承認待ち` `承認済み` `適用済み` `効果確認済み` `却下` `見送り`）。

- **`効果確認済み` は終端である。** そこから戻る遷移が定義されていない
- 手順スキルの段1は、効果の照合で「効かなかった」と判定したとき「変更を戻すか、原因の推定をやり直す」と書いている。**しかし戻したことを台帳に表す状態が無い**
- **`効果確認済み` にした後で、その改善が害だったと分かった場合の経路は、どこにも書かれていない**

### 事実3. 担当エージェントが書ける指摘は3種別で、ロールの過不足を書く枠が無い

`org/templates/T-XXX.md` の `## 組織への指摘` 節が定める種別は `規約` `道具` `反復` の3つ。書式は `- [種別] 内容` の1行1件。

**「この役が足りない」「この役に仕事が集まりすぎている」を書く枠は無い。** 3種別のうち最も近いのは `道具` だが、その定義は「必要な道具・スキル・外部アクセスが無く、遠回りをした」であり、ロールの過不足を指していない。

**一方で、要求の側（`docs/decisions/22-org-self-improvement.md`）はこれを明示的に対象に含めている。**

> **「新しいロールが要る」という提案も、その対象に含む。** 例: 問い合わせが逼迫して司令塔が回らないので、質問をさばく役を置きたい

### 事実4. 改善の反映先として想定されている場所は、行数の上限を持っている

- 層2の規約（開発対象リポジトリのルート `CLAUDE.md`）は**毎セッション全文が読み込まれ、200行を超えると遵守率が落ちる**（`docs/decisions/00-research-notes.md`。Claude Code の制約として確認済みの事実）
- 手順スキル段3の最後の行は、症状「成果物はできるのに手順が守られない」に対する裏の取り方として **「`CLAUDE.md` の行数。200行を超えると遵守率が落ちる」** を挙げている
- 同節は「規約を足す方向にだけ倒さない」「減らす・別ファイルへ出す・スキルへ移すも対応策である」と書いている

**つまり現行設計は、改善が積み上がると規約が長くなり、長くなると守られなくなる、という循環を既に認識しており、対策として「移す・減らす」を挙げている。**

### 事実5. 現行設計に、変更の受け入れ可否を測定で判定する仕組みは無い

`org/skills/org-improve/SKILL.md` 段1 の判定は3値（`効いた` / `効かなかった` / `まだ判定できない`）で、**判定の材料は事後に測る指標の変化だけ**である。適用前に対照群を取る、変更を一部にだけ当てて比べる、といった手続きは無い。

理由は決定記録に書かれている——`25` の §B-2 が、試験用課題の集合（eval）の基盤を作らないと決めており、その根拠は**「トライアル先の完了タスクは数件規模で母数が無い」**である。

### 事実6. 「組織がそのプロジェクトに馴染んできたか」を表す指標は定義されていない

`org/skills/org-improve/SKILL.md` 段5 が「期待する効果」に使ってよいと列挙している数値は4群（ゴール健全性の8指標／手戻り回数／トークン消費／組織への指摘の件数）。**いずれも個々の改善が効いたかを見るためのものであり、組織全体が導入先に適合してきたかを表す量は定義されていない。**

要求の側（`22`）は、これを到達点として挙げている。

> 導入先ごとに改善を繰り返し、**そのプロジェクトに最適化された組織になっていく**サイクルが要る

### 事実7. 台帳の雛形に、確定済みの決定と食い違う記述が1行残っている

`org/templates/org-improvements.md` は、上部で **「オーケストレーターが唯一の書き手であり、機械に集約させない」** と明記している（PO 決定 2026-09-01。「まとめる」は判断であり機械にはできない、というのがその理由）。

**しかし同じファイルの書式の見本の最終行が、それと食い違う。**

```
- 経過:
  - 2026-09-01 起票（スクリプトが3件のタスクファイルから集約）
```

**見本は、却下されたほうの案（スクリプトが集約する）を書いている。** 見本はそのまま模倣されるため、この1行は残せない。

### 事実8. 層2の規約は、すでに行数の上限を超えている

配布物の層2の規約（`org/CLAUDE.md`。開発対象リポジトリのルート `CLAUDE.md` へ追記される内容）の行数を数えた。

```
$ wc -l org/CLAUDE.md org/rules/*.md
  222 org/CLAUDE.md
  120 org/rules/org-escalation.md
  220 org/rules/org-task-ledger.md
```

**`org/CLAUDE.md` は 222 行で、遵守率が落ちるとされる 200 行を既に超えている。** しかもこれは配布物の側の行数であり、**導入先の既存の `CLAUDE.md` へ追記される**建て付けなので、実際に読み込まれる全文はこれより長い。

一方 `org/rules/` の下のファイルは、トピック別・パス限定で読み込まれる建て付けであり、常時全文が読まれるわけではない。

## 2. 外部調査

**読んだのは5件である。** それぞれ「何と書いてあったか」だけを写す。

### 2-1. ACE（Agentic Context Engineering）

**何か:** エージェントが繰り返し実行するなかで学んだことを、playbook（手引き）という1つの文書へ蓄積していく方式。原典は SambaNova・スタンフォード大学・カリフォルニア大学バークレー校の共同研究。
**出典:** [Agentic Context Engineering — Encyclopedia of Agentic Coding Patterns](https://aipatternbook.com/agentic-context-engineering)

**役割を3つに分ける。**

| 役割 | 原文の記述 |
| --- | --- |
| **Generator（実行役）** | 実際の作業を行い、推論の過程と、**手引きのどの項目を参照したか**を残す |
| **Reflector（振り返り役）** | 実行の記録を事後に分析して教訓を取り出す。**自己批評ではなく「他人の実行記録の第三者としての分析」**（原文: "third-person analysis of someone else's run" rather than self-critique） |
| **Curator（取り込み役）** | 教訓を手引きへどう入れるかを決める。**"small, targeted edit[s], never a rewrite of the whole document"**（小さく狙いを定めた編集。文書全体の書き直しは決してしない） |

**手引きの1行の形式。** 番地（安定した識別子）と、役に立った回数・害になった回数のカウンタを持つ。

```
[strategies-00042] helpful=7 harmful=0 :: When the schema migration touches
both `users` and `profiles`, run them in one transaction.
```

- **番地が付いているのは、あとから「この行を直す」と指せるようにするため**（原文: stable tags for addressability across edits）
- 節に分けて整理する（STRATEGIES & INSIGHTS / FORMULAS & CALCULATIONS / COMMON MISTAKES）
- **出自を追える**ようにする（provenance tracking linking entries back to originating cases）
- **退役の規則:** 参照実装は **`harmful >= 3` かつ `helpful = 0` の項目を退役させる**

**名指しされている失敗が2つある。**

| 名前 | 原文の記述 |
| --- | --- |
| **brevity bias**（短くしたがる偏り） | 書き直すたびに、その領域固有の細部が落ちて短い要約に置き換わり、エージェントが少しずつ曖昧になる |
| **context collapse**（積み上げた知識の崩壊） | **"After enough rewrites, the accumulated knowledge degrades into a small generic blob. It's the cassette-tape problem."**（十分な回数書き直すと、蓄積された知識は小さな一般論の塊へ劣化する。カセットテープ問題である） |

**数値。** AppWorld というエージェント評価用の課題集で 10.6ポイント改善、金融分野の課題集で 8.6ポイント、正解ラベルを使わず実行の成否だけを使った条件でも 17.1ポイント。**ただし原文は「これらはその評価課題とその参照実装に紐づいたものであり、この構成が効くという証拠として扱うべきで、保証ではない」と明記している。**

### 2-2. 自己改善ループの実装スキル（公開されているもの）

**何か:** エージェントが自分の実行環境（プロンプト・手順・コード）を書き換えて改善していくループの、実装レベルの規則をまとめた公開資料。
**出典:** [Agent-Skills-for-Context-Engineering / skills/self-improvement-loops/SKILL.md](https://github.com/muratcankoylan/Agent-Skills-for-Context-Engineering/blob/main/skills/self-improvement-loops/SKILL.md)

**ループの構造は3段。** ①失敗の掘り起こし（失敗した実行記録を、エラー文字列ではなく**検証可能な原因・責任を負う役・再利用できる行動の型**で束ねる）→ ②範囲を限った提案（提案役には4つの入力を渡す: 手を入れてよい面／掘り起こした失敗／**壊してはいけない、いま通っている振る舞い**／過去の編集記録）→ ③検証と併合。

**「はしご」の概念。** 手を入れられる場所を段に並べる（第1段のプロンプトから第6段のオプティマイザのコードまで）。規則は **"fix a recurring failure at the lowest rung that can express the fix"**（再発する失敗は、その修正を表現できる最も低い段で直す）。

**名指しされているアンチパターンが5つある。**

| # | 名前 | 原文の記述 |
| --- | --- | --- |
| 1 | **採点関数を見せると細工される** | "hacking became more frequent when the checking code was visible"（採点コードが見えているときのほうが、細工が頻発した） |
| 2 | **全面書き直しによる崩壊** | 蓄積した手引きの全面的な書き直しをモデルに任せると、**一度の操作で桁違いに縮み、一度も改善していない出発点より品質が下がりうる** |
| 3 | **最新のものだけで登る** | "Discarding the archive and iterating only on the current best gets stuck after one bad modification"（過去の候補を捨てて現在の最良だけで反復すると、一度の悪い変更で行き詰まる） |
| 4 | **自己申告の成功** | エージェント自身が書いた報告ファイルから評価するループは **"inherit its over-optimism: noise declared as signal, bugs interpreted as breakthroughs"**（その楽観をそのまま受け継ぐ——雑音が信号と宣言され、バグが突破口と解釈される） |
| 5 | **プロンプトに書いた制約は消える** | 種となるプロンプトに書いた制約は、自己書き換えの過程で落ちる。**"Budgets, permissions, and sandboxing are enforced by the runtime, outside every editable surface."**（予算・権限・隔離は、書き換え可能なあらゆる面の外側で、実行基盤が強制する） |

**その他の規則。**

- **生の記録から評価する。** "Evaluate from raw logs and original outputs, never from model-written reports of them."（生のログと元の出力から評価せよ。モデルが書いたそれらの報告からは決して評価するな）。同資料は、**生の実行記録に全面的にアクセスできる提案役が、スコアだけを渡された提案役と、モデルが書いた要約を渡された提案役の両方を、明確に上回った**という証拠を挙げている
- **受け入れ判定は2分割で行う。** 狙った弱点が解消されたかを見る分（held-in）と、**提案役が一度も見ていない分**（held-out）に分ける。**両方が悪化せず、少なくとも片方が確かに改善したときだけ採る。** 片方を犠牲にして合計が上がる候補は、合計が正でも却下する
- **スコアだけでなく編集の差分を追う。** "Track edit diffs, not only scores" —— 入力をそのまま返す壊れた改善役は、集計指標の上では「安定」に見える
- **手を入れてよい面を明示的に宣言し、固定した領域は毎回機械的に再検査する**

### 2-3. 振り返り役を実行役と分けるかどうか

**出典:** [Self-Improving AI Agents: The Reflection Loop (2026)](https://www.taskade.com/blog/self-improving-ai-agents-reflection)

- **同一のモデルに下書きと批評を兼ねさせる形**は安く速く単純だが、**両方の役で盲点を共有する**
- **別の批評役を立てる**と、それ自身のコンテキストと評価基準（できれば別のモデル）で走るため、その盲点が割れる。代償は呼び出し1回分と段取りの手間
- **"run tests when possible, and save intrinsic critique for soft, subjective polish that no test can capture"**（可能なときはテストを走らせ、内的な批評は、どのテストでも捉えられない主観的な仕上げのために取っておく）
- 2026年時点の到達点として、最終的な答えだけでなく**推論の各段階を採点する**モデル（process reward model）が挙げられている
- 実務上の要点として **「批評役を実地に接地させる／ループに上限をかける／痕跡を表に出す」** が挙げられている

### 2-4. Team Topologies 第8章「組織的センシングでチーム構造を進化させる」

**何か:** ソフトウェア組織のチーム構成の設計論。第8章が、チーム構造を**いつ**変えるかを扱っている。
**出典:** [Team Topologies — Book notes](https://danlebrero.com/2021/01/20/team-topologies-summary/) / [Team Topologies 公式](https://teamtopologies.com/)

**構造を変える引き金として6つが挙げられている。**

1. ソフトウェアが1チームには大きくなりすぎた
2. **あるチームの前で仕事が滞留している**（原文: "Work queued in a team"）
3. チームの内部で専門が分岐しはじめた
4. 文書が無いという苦情が出る
5. 提供のテンポが遅くなってきた
6. 複数の事業サービスが、同じ下回りのサービス群に依存している

**チームの型は4つ**（流れに沿ったチーム／能力を育てるチーム／複雑な部分系を担うチーム／基盤チーム）、**関わり方は3つ**（協働／サービスとして提供／伴走）。

**認知負荷**（1つのチームが抱え込める理解の量）を信号として使う。**"collaboration is expensive, so it must be planned and justified"**（協働は高くつくので、計画され正当化されなければならない）。

### 2-5. Toyota Kata（トヨタの改善の型）

**何か:** 継続的な改善と学習を、個人の資質ではなく**日々繰り返す型**として定着させる方法論。
**出典:** [Toyota Kata — Habits for Continuous Improvements](https://www.methodsandtools.com/archive/toyotakata.php) / [Toyota Kata (Wikipedia)](https://en.wikipedia.org/wiki/Toyota_Kata)

**改善の型は4段階。** ①向かう方向を理解する → ②現状を掴む → ③**次の「目標状態」を定める** → ④その目標状態へ向けて小さな実験（計画・実行・確認・処置）を回す。

- **目標状態**とは、**あるべき状態を、その工程がどう機能しているかとして記述したもの**である。到達したい先を先に言葉にする
- **道筋を予測して実行することに重点を置く手法とは対照的に**、この型は**進む途中で得られる発見の上に組み立てる**。目標状態へ向かう過程で学び、学んだことに応じて適応する
- **指導の型**（Coaching Kata）は別に定義されている。**指導する側は出来合いの答えを与えない。** 問いを立て、相手が問題を理解し、状況を評価し、自分で結論に達するのを助ける

## 3. 突き合わせ — 現行設計と外部の出典が、どこで一致し、どこで食い違うか

**採否は書かない。** 一致・食い違いという事実だけを並べる。

### 3-1. 一致している点

| # | 外部の出典 | 現行設計の対応箇所 |
| --- | --- | --- |
| 一致1 | 振り返り役を実行役から分ける（2-1 / 2-3） | 改善エージェントを担当エージェントの6体目として独立させた（`25` §D） |
| 一致2 | 制約は書き換え可能な面の外側で、実行基盤が強制する（2-2 の5） | 改善エージェントの定義に編集系ツールを与えていない（`org/agents/org-improvement.md`）。**規約の文言ではなく、ツールの割り当てで担保している** |
| 一致3 | 小さく狙いを定めた編集。全体の書き直しはしない（2-1 / 2-2 の2） | 提案の書式の `変更` 欄が「最小の編集で」と規定し、「規約を全面的に見直す」は対応策ではないと明記（`org-improve/SKILL.md` 段5） |
| 一致4 | 目標状態を先に定める（2-5） | 提案の必須欄 `期待する効果`（どの指標がどう動けば成功か）。**書けない提案は出さない**と規定 |
| 一致5 | 指導する側は答えを与えず問う（2-5） | 人（PO）の承認でループを閉じる。改善エージェントは提案までで、反映はしない |
| 一致6 | 過去の候補を捨てない（2-2 の3） | 上げなかった課題は台帳に `未処理` のまま残り、次の点検で再び優先度づけの対象になる（`org-improve/SKILL.md` 段4）。**「消えるわけではない」と明記** |
| 一致7 | ループに上限をかける（2-3） | 1回の点検でエスカレートするのは最大3件 |
| 一致8 | 量より質（2-3 の「詳しい人からの少数の具体的な指摘」） | PO 由来の指摘1件を、担当エージェント由来の3件より重く扱う（`org-improve/SKILL.md` 段2） |

### 3-2. 食い違っている点

| # | 外部の出典 | 現行設計 | 食い違いの中身 |
| --- | --- | --- | --- |
| **差1** | **生の記録から評価する。エージェントが書いた報告からは決して評価しない**（2-2 の4） | 信号9種のうち3種がエージェント／オーケストレーターの書いた文章、6種が台帳から数えた数字。**会話記録を直接読む信号は0**（事実1） | **現行設計は、名指しされたアンチパターン「自己申告の成功」に該当する構造を持っている。** ただし会話記録を読む道具は既に2本ある |
| **差2** | 蓄積した知識は、書き直すたびに具体が落ち、一般論の塊へ劣化する（2-1 の brevity bias / context collapse） | 改善の反映先である層2の規約は**200行を超えると遵守率が落ちる**（事実4）。手順スキルは対策として「移す・減らす」を挙げている | **「短く保て」という制約と「要約するな」という警告が、同じ対象に対して逆向きに働く。** 現行設計はこの循環を認識しているが、どちらを優先するかは決めていない |

| **差4** | 構造を変える引き金が6つ定義され、うち1つは**あるチームの前での仕事の滞留**（2-4） | 担当エージェントが書ける指摘は3種別で、ロールの過不足を書く枠が無い（事実3）。一方で要求（`22`）はロールの提案を明示的に対象に含めている | **要求が対象に含めているものを、書く枠が受けていない** |

### 3-3. 外部の出典に有り、現行設計に対応物が無いもの

| # | 外部の出典の記述 | 現行設計の状況 |

## 4. この調査で確かめられなかったこと

**確かめていないものを、確かめたことのように書かない。**
