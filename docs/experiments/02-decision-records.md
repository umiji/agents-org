## §0 いま分かっていること（2026-08-27 時点の事実）

**すべて本リポジトリの現物を読んで確認した。推測は含まない。**

### 事実1. 開発対象リポジトリに「決定記録」は作られない

組織を導入した開発対象リポジトリに作られるのは6種類だけで、`docs/decisions/` は含まれない。決定記録（`docs/decisions/`）は**層1、つまり組織そのものを設計する本リポジトリの中だけ**にある概念である（要件定義書 v0.2 の文書3層の表）。

決定記録に相当する役割は、**タスク別ファイル `docs/tasks/T-XXX.md` の中の `## 決定ログ` という節**が担っている。

### 事実2. 決定ログの意図は「再燃防止」であって、知識の蓄積ではない

明文がある（`docs/decisions/07-task-management.md`）。

> 決定ログは事務ではない。担当エージェント同士の自由な通信を原則として禁じている以上、**会話の中にしか存在しない理由は、そのセッションが終われば組織から永久に失われる**。同じ論点が別のタスクで、しばしば違う結論で、また争われることになる。

**この組織で特に問題になるのは、条件が3つ重なっているためである** — 担当エージェントは会話履歴を継承しない／担当エージェント同士の自由な通信を禁じている／セッションは終わる。人間のチームなら口頭の記憶や履歴で補われる部分が、構造的に存在しない。

### 事実3. 配布物は「決定記録」を参照しろと命じているが、それが何かを定義していない

`org/` の4箇所が「確定済みの決定記録」を担当エージェントの情報源として挙げている。

| 場所 | どう書いてあるか |
| --- | --- |
| `org/rules/org-escalation.md` 段1 | 自分で解決する際に確認する4つの情報源の1つ |
| `org/rules/org-task-ledger.md` | `## 参照すべき成果物` 欄の説明 |
| `org/templates/T-XXX.md` | 同じ欄の記入例 |
| `org/agents/org-design.md` | 参照先として、および「確定済みの事項は再検討しない」 |

**ところが、開発対象リポジトリにおいて「決定記録」が何を指すのかは、配布物のどこにも定義されていない。** 用語集（`org/glossary.md`）に載っているのは「決定ログ」であり、「決定記録」の項目は無い。両者の関係も書かれていない。

### 事実4. 決定ログは書かれるが、読まれる経路が無い

- **自動で読み込まれるものは無い。** 担当エージェントへ自動で入るのは `CLAUDE.md`（層2の運営規約）だけである
- **過去タスクの決定ログを読む経路が実質無い。** セッション再開の手順書は、タスク別ファイルについて「**進行中のものだけ。完了済みは読まない**」と明記している（`org/skills/org-session-resume/SKILL.md`）。コンテキスト節約としては正しいが、結果として完了タスクの決定は誰も読み返さない
- **読まれる経路は1つだけ** — オーケストレーターが `## 参照すべき成果物` にパスを明示的に書いたとき

### 事実5. 検索の道具はあるが、手順が無く、引くための索引も無い

- **道具はある** — 5つの担当エージェント全員が `Grep`（中身の横断検索）と `Glob`（ファイル名の検索）を持っている
- **手順は無い** — `org/` 全体を検索しても、探し方に触れた記述は初回点検の「テストファイルが実在するか。リポジトリ内を探す」の一行だけだった
- **索引が無い** — 決定ログは `docs/tasks/T-XXX.md` の中に埋まっており、タスクは**決定の主題ではなく、作業が起きた順番**で並んでいる

| 引きたいこと | 実際に起きること |
| --- | --- |
| 「認証ライブラリをなぜこれにしたか」 | その決定は「ログイン画面の実装」という名前のタスクの中にある。**タスク名からは辿れない** |
| CSV索引を見る | 索引が持つのは ID・日付・タスク名・状態・優先度・担当・依存・ドキュメント。**どのタスクが何を決めたかは載っていない** |
| `docs/tasks/*.md` を全部 grep する | **引くキーワードを既に知っていないと引けない。** 理由を調べたい側は、たいてい語をまだ知らない |
| 片端から読む | タスクが増えるほど費用が増える。しかもセッション再開の手順が「完了済みは読まない」と定めている |

唯一まともに機能しそうな入口は**用語集**（`docs/glossary.md`）である。設計エージェントが新しく定義した語を申告し、オーケストレーターが登録する仕組みがあるため、**語だけは索引されている。** ただし用語集が持つのは語の定義であって、決定の理由や却下案ではない。

### 事実6. 対照 — 層1（本リポジトリ）の決定記録は引ける

同じ「決定の記録」でも、本リポジトリの `docs/decisions/`（19本）は引ける。理由は3つある。**次の方式を考えるときの参考になる。**

- **ファイル名が主題になっている**（`07-task-management.md`、`11-session-handoff.md`）
- **各文書の冒頭に「この文書が確定したこと」という要約がある** — 全文を読まずに、開くべきか判断できる
- **`CLAUDE.md` に主題と文書番号の対応表がある** — 入口が固定されている

つまり**決定の主題で並べてあるので、主題から引ける。**

## §1 何が問題なのか

**決定ログの目的が「再燃防止」（事実2）である以上、引けることが機能の本体である。**

書くこと自体に価値があるのではなく、次に同じ論点へ当たった誰かがそれを見つけられて初めて目的が達成される。見つけられなければ、どれだけ厳密に書かせても目的は達成されず、**書く費用だけが毎回かかって効果が0**という状態になる。

**これは規約の不備というより、目的と手段が繋がっていないということである。**

**トライアル先ではまだ表面化していないはずである。** タスク数が少なく、同じセッションが続いている間は理由が会話の中に残っているため、引けなくても困らない。**困り始めるのは、セッションが切り替わった後、同じ領域を2回目に触るときである。**

## §3 確かめるべきこと

### §3.1 外の既成解を調べる（**実施済み → 結果は §4**）

**ADR（Architecture Decision Records、アーキテクチャ決定記録）** が、まさにこの用途の確立された方式である。1つの決定を1ファイルに、連番と状態（提案中／承認／廃止／置き換え済み）を持たせる。

調べる対象:

| # | 対象 | 見るところ |
| --- | --- | --- |
| 1 | Michael Nygard の原型 | 最小の項目立て。なぜその項目なのか |
| 2 | MADR（Markdown Any Decision Records） | 定型化された項目。却下案の書かせ方 |
| 3 | `adr-tools` / Log4brains 等の索引生成 | **索引をどう作っているか。手で書かせているのか生成しているのか** |
| 4 | 「決定が古くなったとき」の扱い | 状態遷移（廃止・置き換え）をどう表現しているか。**この組織では決定ログが「過去の項目を書き換えず、上書きする新項目を足す」規約になっており、そこと突き合わせる** |

**調べ方の順序**（開発ワークフローの規約に従う）: GitHub のコード検索で実物を見る → 一次資料（原典・仕様）で確認する → 足りなければ広く web を当たる。

**注意**: ADR は**人間のチーム向けに設計されており、この組織固有の条件が考慮されていない** — 会話履歴を継承しない／担当エージェント同士が直接話せない／複数が並列で走る／コンテキストへ読み込む量そのものが費用になる。**そのまま採れるかは別に検証する。**

### §3.2 判定基準（**調べる前にここで固定する**）

前回の Agent Teams の検証と同じく、**走らせる前に基準を決めておく。** 後から基準を動かすと、結論が調査結果に引きずられる。

採るべき方式は、次の5つを満たさなければならない。

| # | 基準 | 満たさないとどうなるか |
| --- | --- | --- |
| K-1 | **主題から引ける。** 決定を探す側が、語をまだ知らない状態でも辿り着ける入口がある | §1 の問題が解決しない。作る意味が無い |
| K-2 | **正典が1つに定まる。** 同じ決定が2箇所に書ける状態を作らない | 必ず乖離する（層3ドキュメントで確認済みの失敗） |
| K-3 | **並列で書いても壊れない。** 複数の担当エージェントが同時に決定を書く場面で、衝突・採番競合が起きない | 並列実行が組織化の利得の源なので、ここが壊れると本体が壊れる |
| K-4 | **読む費用が件数に比例しない。** 索引だけ読めば、開くべき1件が決まる | タスクが増えるほど重くなり、結局読まれなくなる |
| K-5 | **書く手間が今より大きく増えない。** | 規約が守られなくなる。守られない規約は無いのと同じ |

### §3.3 決めないと動かない論点（**選択肢だけ挙げる。推奨は書かない**）

**論点1 — 決定ログと決定記録の二重化をどうするか（K-2）**

| 案 | 内容 |
| --- | --- |
| a | 決定ログを廃し、独立した決定記録へ一本化する |
| b | 決定ログを正典のまま残し、**索引だけを機械生成する**（層3ドキュメントと同じ「マスタ＋生成ビュー」の形） |
| c | 決定ログは残し、**重い決定だけ**独立文書へ昇格させる |

**論点2 — 誰が書くか。並列で衝突しないか（K-3）**

現在のタスク台帳が並列で壊れないのは、書き手を厳密に分けているためである——**各担当エージェントは自分のタスクのファイル1つしか書かない／CSV索引はオーケストレーターだけが書く。** 決定を独立ファイルにすると、複数の担当が同時に決定を書く場面が出る。**タスクIDは連番・再利用禁止で、オーケストレーターが一元的に採番している**が、決定の番号も同じ形にできるか。

**論点3 — 何を昇格させるか（K-4 / K-5）**

全決定を独立文書にすると数が爆発し、索引が効かなくなって元の木阿弥になる。現在の決定ログを書く条件は3つ（(1) PO の判断を仰いで得た (2) 別の選択肢が実際にあった技術選定 (3) 登録後にスコープ・完了条件・禁止事項が変わった）。**これがそのまま昇格の基準として使えるのか、もっと絞るべきか。**

### §3.4 事前に知っておくべき制約

**決定記録07（`docs/decisions/07-task-management.md`）は Confirmed 済みであり、末尾に「採用したまま変えないもの」を明示的に列挙している。その中に「3つの記録の分離と決定ログの形式」が入っている。**

> **採用したまま変えないもの**（明示しておく。変えない判断も判断である）: ID規約、CSV索引 + タスク別ファイルの2分割、**3つの記録の分離と決定ログの形式**、…

- 決定ログを残したまま索引を足すだけなら**抵触しない**
- **一本化する案（論点1の a）を採る場合は、明示的に「変えない」と宣言したものを覆すことになる。** 止める理由ではないが、決定記録07の改訂として扱う必要がある

**机上で「引きやすくなった」と言っても意味がない。** 何をもって K-1 と K-4 を満たしたと言うのかを、走らせる前に決めること。

### §4.1 原型（Nygard, 2011）— 項目立てとその理由

項目は5つだけで、それぞれに理由がある。

| 項目 | 内容 | 添えられている理由 |
| --- | --- | --- |
| Title（表題） | 短い名詞句 | **何を決めた記録なのかが表題だけで分かること** |
| Context（背景） | 働いている力（技術・政治・社会・プロジェクト固有）を中立の言葉で | 事実を書く場所であって、主張する場所ではない |
| Decision（決定） | 「我々は〜する」と能動態・完全な文で | 曖昧さを残さない |
| Status（状態） | 提案中 / 承認 / 非推奨 / 置き換え済み（置き換え先への参照つき） | 現在有効かどうかを、本文を読まずに判定できる |
| Consequences（結果） | 良い・悪い・どちらでもない結果を**すべて** | 都合のよい結果だけを書かせない |

設計の芯は2つ。**1決定1ファイル**（構造・非機能特性・依存・インターフェース・作り方に影響するものだけを1件として扱う）と、**不変性**（過去の記録を消したり書き直したりせず、状態を「置き換え済み」に変えて置き換え先を指す）。「当時の決定は何だったか」と「今の決定は何か」を両方残すため、と説明されている。

### §4.2 MADR — 定型化された項目と、却下案の書かせ方

MADR は Nygard の5項目を、**書き手が埋めるだけで却下案が残る形**に定型化している。

- メタデータ（状態・日付・決定者・意見を求めた相手・共有先）は **YAML front matter**（ファイル冒頭を `---` で挟んだ機械可読の欄）に置く
- 本文は「背景と課題」→「決定を左右した要因」→「**検討した選択肢**」→「決定の結果（選んだ選択肢と、その理由）」→「結果（良い/悪い）」→「**選択肢ごとの良し悪し**」→「確認方法（決定が守られていることをどう確かめるか）」
- 却下案は箇条書きの語頭を固定して書かせる — `Good, because 〜` / `Bad, because 〜` / `Neutral, because 〜`。**理由なしの一行を書けなくする形になっている**
- 雛形は**完全版と最小版の2つ**が配られている。最小版は「背景と課題／検討した選択肢／決定の結果」だけ

MADR 自身が、自分の形式を決めた過程を決定記録として残している。本件に直接効くのは4本ある。

| MADR の決定 | 決めたこと | 添えられた理由（本件に効く部分） |
| --- | --- | --- |
| 0013 メタデータは YAML front matter へ | 状態・日付等を本文から追い出す | **本文（決定の本体）を短く保てる／道具が扱いやすい**。反面「取りうる状態の値が厳密に決まっているかのように見えてしまう」ことを欠点として自認 |
| 0008 状態欄を持たせる | 状態も front matter へ | バッジ画像・表・独立見出しなど6案を比較した上で |
| 0010 分類はサブフォルダ＋フォルダ内連番 | `docs/decisions/<分類>/0000-....md` の形 | **「数百件の中から まとまりを見つけやすいこと」を第一の要因に挙げている。** ただし欠点も明記 — **一意な番号が無くなる／索引を2つ保守することになる／分類が分からないときにどのフォルダを見ればよいか分からない** |
| 0004 一覧を作る道具を自作 | `adr-log`（一覧生成コマンド）を作った | 既存の道具の一覧形式が要求に合わなかったため |

**0010 の「分類が分からないときは、どのフォルダを見ればよいか分からない」は、本件 §1 の問題（語をまだ知らない側が引けない）と同じ形の指摘である。既成解の側でも解けていない。**

### §4.3 索引の作り方 — **調べた実装では、索引は例外なく生成物であって手書きではない**

§3.1 の調査項目3（索引をどう作っているか。手で書かせているのか生成しているのか）への答え。

| 実装 | 索引の作り方 | 索引が持つ情報 |
| --- | --- | --- |
| adr-tools | `adr generate toc`（目次を出すコマンド）が決定記録のフォルダを走査し、各ファイルの**先頭見出しをタイトルとして拾って**箇条書きを標準出力へ吐く。ファイルには書き込まない | タイトルとリンクだけ |
| adr-tools（関係図） | `adr generate graph` が、記録どうしの「置き換えた／補正した」というリンクを Graphviz（関係図を描く道具）の形式で吐く | 記録間の関係 |
| MADR | `adr-log`（自作の一覧生成コマンド）＋サイト生成側の目次機能。**MADR 自身の `index.md` には説明文しか書かれておらず、一覧は自動生成に任せている** | 番号とタイトル |
| Log4brains | front matter と **git の履歴**から日付等を推測し、**検索できる静的サイト**を生成する | 状態・日付・関係・全文検索 |
| ECC の決定記録スキル（AI向け） | **LLM が手で `README.md` の表へ追記する**（手順8「インデックスを更新する」） | 番号・タイトル・状態・日付の4列の表 |

**道具を持つ実装はいずれも「ファイル群が唯一の正典で、索引はそこから導出される」という形である**（本リポジトリが層3ドキュメントで既に採っている「マスタ＋生成ビュー」と同じ形）。手で索引を更新させる形になっているのは、調べた中では**AIエージェント向けの ECC スキル1つだけ**で、そこでは追記が守られるかどうかが規約頼みになっている。

### §4.4 採番と並列 — **既成解の弱点はここに集中している（K-3）**

adr-tools の `adr new`（新しい決定記録を作るコマンド）の採番は、ソースを読むと次の3行に尽きる。

```sh
maxid=$(ls $dstdir | grep -Eo '^[0-9]+' | sed -e 's/^0*//' | sort -rn | head -1)
newnum=$(($maxid + 1))
newid=$(printf "%04d" $newnum)
```

**作成時にフォルダを走査して「今ある最大の番号＋1」を採る。中央の採番役が居ない。** したがって2人（2エージェント）が同時に作れば同じ番号になる。ECC の AI 向けスキルの手順6（「既存の決定記録を走査して増分する」）も、同じ方式である。

- 実務でも、並行して進むブランチが同じ番号の決定記録を作り、手で解決している、という報告がある（二次情報）。回避策として挙がっているのは**日付を含む ID**（`ADR-2026-03-27-kafka` の形）や、ファイルを使わず git の付箋機構（git notes）へ書く方式など
- MADR 0010 の「サブフォルダ＋フォルダ内連番」は衝突する面を分類ごとに分割するだけで、**同じ分類の中では解消しない**。0010 自身が「一意な番号が無くなる」を欠点として挙げている

**対して本組織は、タスク台帳で既に「オーケストレーター（司令塔となるメインセッション）だけが採番し、番号は連番・再利用禁止」という中央採番を採っている。** 既成解より強い前提を既に持っている、という対比になる。ただし決定を独立ファイルにした場合、**採番を頼む往復が1決定ごとに発生する**（現在の決定ログは、担当エージェントが自分のタスクのファイルへ追記するだけで済んでいる）。これは K-5（書く手間が増えない）に跳ね返る。

### §4.5 古くなった決定の扱い — 「本文は不変・状態欄は可変」であり、完全追記ではない

§3.1 の調査項目4への答え。**ADR の不変性は、本組織の決定ログ規約の「過去の項目を書き換えない」とは同じではない。**

- Nygard の原型: 過去の記録の**本文**は書き換えない。ただし **状態欄は書き換える** — 「置き換え済み（置き換え先：ADR-0015）」へ変える
- adr-tools の実装: `adr new -s 12`（12番を置き換える新記録を作る）は、**新旧2つのファイルを両方書き換える**。新側に「Supercedes（置き換える）」リンクを、**旧側に「Superceded by（〜に置き換えられた）」リンクを追記し、旧側の「Accepted（承認）」の行を消す**
- MADR: front matter の状態欄を `superseded by ADR-0123` にする。同じく旧側を書き換える

**本組織の規約は「過去の項目を書き換えず、上書きする新項目を足す」**（`org/glossary.md` の決定ログの行、および `org/rules/org-task-ledger.md`）。**差は、古い決定から新しい決定への逆向きのリンクが張られないことにある。** 完全追記のままだと、古い決定に先にあたった側が、それが失効していることを知る経路が無い（新しい方を読むまで分からない）。既成解はこれを、旧側の1行を書き換えることで解いている。

### §4.6 AIエージェント向けの議論（2026年の二次情報）— 問題意識は同じだが、解は示されていない

- 主張されている問題は本件 §1 とほぼ同じ — **モデルは状態を持たず、セッションごとに記憶が0から始まる**／**エージェントは、見えない理由をリファクタリングで消してしまう**／エージェントは1セッションの中で小さな設計判断を何十も下す
- 提案されている扱いは「決定記録は文書ではなく、**その領域に触れるタスクごとに必ず読み込ませる入力**である」「取得できなければ存在しないのと同じ」
- **ただし、具体的な索引・検索の機構は示されていない。** 実際に書かれている手順は「`CLAUDE.md`（セッション開始時に必ず読まれる規約ファイル）に、設計変更の前に `docs/decisions/` を読めと書いておく」という一行に留まる
- 記録する条件を絞れという主張がある — **実際に争われた決定／自明な選択が非自明な理由で誤りだった場合／将来のエージェントが元に戻しそうなもの**。「全部書くと書き手が燃え尽き、記録が腐る。腐った記録は無い方がまし」
- **コンテキストへ読み込む量そのものが費用になる**という論点（本件の K-4）には、調べた範囲では触れられていない。**外の議論にまだ無い論点である**

### §4.7 判定基準（§3.2 の K-1〜K-5）との突き合わせ

**採否は書かない。既成解が何を持っていて、何を持っていないかだけを対応させる。**

| 基準 | 既成解が持っている仕掛け | 埋まっていないところ |
| --- | --- | --- |
| K-1 主題から引ける | 表題を短い名詞句にする規約／ファイル名に主題を入れる／分類をサブフォルダにする（MADR 0010）／全文検索つきサイト生成（Log4brains） | **語をまだ知らない側が引ける保証は無い。** MADR 0010 自身が「分類が分からないとどのフォルダか分からない」を欠点に挙げている |
| K-2 正典が1つ | 1決定1ファイルで、索引は生成物（adr-tools・MADR・Log4brains） | **手で索引を更新させる形（ECC スキル）だけは二重化する。** 規約が守られるかに依存 |
| K-3 並列で壊れない | **無い。** 採番は「今ある最大＋1」をその場で走査する方式で、中央の採番役が居ない | **既成解の最大の穴。** 本組織のタスクID方式（司令塔が一元採番）の方が強い。ただし1決定ごとに採番の往復が要る |
| K-4 読む費用が件数に比例しない | 索引がタイトル（＋状態・日付）だけを持つので、開くべき1件を索引だけで決められる／MADR は本体を短く保つためにメタデータを front matter へ追い出した | 索引そのものが件数に比例して伸びる点は、どの実装も解いていない（分類で割るのが唯一の緩和） |
| K-5 書く手間が増えない | **最小版の雛形を別に配る**（MADR）／「争われた決定だけ書く」という絞り込み／雛形からファイルを作るコマンド | 本組織では **AI が書き手である**ため、手間の実体はトークン消費と往復回数になる。**外の議論はこの費用を扱っていない** |

### §4.8 調査で新しく出た論点（**選択肢だけ。推奨は書かない**）

§3.3 の論点1〜3 に加えて、調べた結果として次が出た。

**論点4 — 状態欄を可変にするか（§4.5 の差）**

| 案 | 内容 |
| --- | --- |
| a | 完全追記のまま（現規約どおり）。古い決定から新しい決定への逆リンクは持たない |
| b | 本文は不変のまま、**状態欄だけ書き換えを許す**（既成解と同じ形）。「過去の項目を書き換えない」規約の例外を1箇所だけ開ける |
| c | 状態は索引側だけで管理する（記録本体は触らない）。索引を生成物にする案と組み合わせになる |

**論点5 — 索引を機械生成にするか、書き手（LLM）の追記に任せるか**

調べた実装のうち、道具を持つものは全て生成側で、手で追記させているのは AI 向けスキル1つだけだった（§4.3）。本リポジトリには**同じ形の先例がある** — 層3ドキュメントの人間用ビューを生成するスクリプト（`org/scripts/org-docs.py`）は「マスタだけが正典で、ビューは生成物」という方式を既に採っている。生成にする場合は**配布物のスクリプトが5本目になる**（＋回帰テスト1本）。

**論点6 — 分類（サブフォルダ）を持つか**

MADR は数百件を想定して分類を導入したが、欠点も明記している（§4.2 の表）。本組織のタスク件数の規模でこれが要るかは、実測が要る。

**論点7 — 昇格の条件を、外の基準に寄せるか**

現行の決定ログを書く3条件（PO の判断を仰いだ／別の選択肢が実際にあった技術選定／登録後にスコープ・完了条件・禁止事項が変わった）に対し、AI エージェント向けの議論が挙げている条件は「実際に争われた／自明な選択が非自明な理由で誤りだった／**将来のエージェントが元に戻しそうなもの**」。**3つ目は現行の3条件に無い観点である**（§3.3 の論点3 に対する材料）。

### §4.9 まだ確かめていないこと

- **§3.5（実際に効くかの実測）は未着手。** トライアル先（別の開発対象リポジトリ）の決定ログが現在何件あるかを確認していない。**件数が少なければ比較そのものが成立しない**
- 既成解を「そのまま採れるか」は未検証。§3.1 の注記のとおり、ADR は**人間のチーム向けに設計されており**、会話履歴を継承しない・担当エージェントどうしが直接話せない・複数が並列で走る・読み込む量が費用になる、という本組織の条件は考慮されていない。§4.7 の突き合わせは机上の対応づけであって、実測ではない
