## 1. Agent Teams とは何か

**Agent Teams（エージェントチーム）は、Claude Code が公式に持つ実験的な機能である。** 複数の Claude Code セッションを1つのチームとして動かし、そのうち1つを **team lead（チームリーダー＝司令塔）**、残りを **teammate（チームメイト＝実働）** にする。

既定では無効で、有効化には後述の条件が要る。

### なぜ本リポジトリにとって重要か

**この組織が自前で作ったものと、正面から重なるからである。** 本リポジトリの設計制約は「Claude Code 標準機能を最大限使う。`CLAUDE.md` と Skills で足りることに独自の仕組みを作らない」（要件定義書 §4）である。標準機能の側に同等物が現れたなら、自前実装を続ける理由を説明できなければならない。

重なっている箇所は4つある。

| この組織が持っているもの | Agent Teams が標準で持つとされるもの |
| --- | --- |
| **担当エージェント間の直接通信をしない**という規約。すべてオーケストレーター（司令塔役のメインセッション）を経由させる（要件定義書 §14） | チームメイト同士が直接メッセージを送り合う。受信箱は `~/.claude/teams/<チーム名>/inboxes/<エージェント名>.json` というファイル |
| **自作のタスク台帳。** 索引の CSV（`docs/task-list-{プロジェクト名}.csv`）とタスク別 Markdown（`docs/tasks/T-XXX.md`）の2階建てで、割り当てはオーケストレーターが行う（`docs/decisions/07-task-management.md`） | 共有タスクリストが標準で存在する（`~/.claude/tasks/<チーム名>/`）。未着手／作業中／完了の3状態、タスク間の依存関係、担当が自分で次を取りに行く方式、同時に取りに来たときの競合防止まで入っているとされる |
| **PO確認待ちキュー**（人間への問い合わせを1本にまとめる仕組み）。サブエージェント（親セッションが子プロセスとして起こすエージェント）は人間へ選択肢を出して答えを待つ道具（`AskUserQuestion`）を使えないため、技術的に必然だった（`docs/decisions/00-research-notes.md` §1.1） | チームメイトは独立したセッションであり、人間が画面から個別に選んで直接会話できるとされる。**「人間へ届かない」という前提が崩れる可能性がある** |
| **停滞検知を自作スクリプトで回す**（`org/scripts/org-check.py`） | チームメイトが待機に入る直前（`TeammateIdle`）、タスク作成時（`TaskCreated`）、完了時（`TaskCompleted`）に**必ずコマンドを実行させる仕組み**（hook）が公式にあるとされる |

## 2. 実測済みの事実（検証0）

**すべてこの端末で実際に確かめた。** 再調査しなくてよいように、コマンドと結果を残す。

### 事実1 — 機能の実体は、この端末の実行ファイルに入っている

Claude Code の本体は1つの実行ファイル（`~/AppData/Roaming/npm/node_modules/@anthropic-ai/claude-code/bin/claude.exe`）である。この中を文字列として検索した。

```sh
grep -c -a -o "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS" .../claude.exe   # → 9
grep -c -a -o "TeammateIdle" .../claude.exe                            # → 29
grep -c -a -o "TaskCompleted" .../claude.exe                           # → 33
grep -c -a -o "inboxes" .../claude.exe                                 # → 8
```

道具の名前は `TeamCreate` / `TeamDelete` / `Teammates` の3つ。受信箱の置き場（`~/.claude/teams/<チーム名>/inboxes/<エージェント名>.json`）と共有タスクリストの置き場（`~/.claude/tasks/`）も、パスを組み立てる処理として実在する。

### 事実2 — 有効化の条件は2つあり、両方満たす必要がある

実行ファイルの中の判定処理は、要約するとこうなっている。

```js
// 環境変数が立っている、または起動オプションが付いている
if (!env.CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS && !argv.includes("--agent-teams")) return false;
// かつ、サーバ側の可否スイッチが有効である
if (!gate("tengu_amber_flint", true)) return false;
return true;
```

**`tengu_amber_flint` は、Anthropic 側がアカウント単位に配る可否スイッチである。** 環境変数を立てただけでは足りず、これが降りていなければ機能は現れない。

この端末では**降りている**。Claude Code が設定とキャッシュを持つファイル（`~/.claude.json`）の中で確認した。

```sh
python -c "import json,os;d=json.load(open(os.path.expanduser('~/.claude.json'),encoding='utf-8'));print(d['cachedGrowthBookFeatures']['tengu_amber_flint'])"
# → True
```

### 事実3 — 非対話モードでは、チーム用の道具が現れない

`claude -p "指示"` は、対話画面を持たずに1回だけ答えて終わる起動の仕方である。ここに環境変数を立てて、道具の一覧を取らせた。

```sh
CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 claude -p \
  "ToolSearch ツールを使って 'select:TeamCreate,TeamDelete,Teammates,SendMessage,ListAgents' を検索し、
   実際にスキーマが返ってきたツール名だけを答えてください" \
  --model haiku --max-turns 4 --output-format json
```

結果:

```
SendMessage, ListAgents, NOTFOUND: TeamCreate, TeamDelete, Teammates
```

**チームを作る道具は取得できなかった。** `SendMessage`（別のエージェントへ後追いでメッセージを送る道具）と `ListAgents`（送り先の一覧を出す道具）は、Agent Teams とは無関係に元から存在するものである。

実行後も `~/.claude/teams/` と `~/.claude/tasks/` は作られなかった。

> **後から入った訂正（2026-08-26）— この事実3の根拠のうち、有効なのは後者だけである。**
>
> `TeamCreate` が取得できないことは、**有効・無効のどちらの証拠にもならない**と後で分かった。このビルドには `TeamCreate` という道具がそもそも無く、機能が有効なセッションでも同じ NOTFOUND が返る（事実5）。
>
> したがって事実3の結論を支えているのは、**「実行後にチームの定義ファイルが作られなかった」という後者の観察だけ**である。それは有効な根拠なので、**結論そのものは変わらない**。ただし、同じ判定を他所でやり直すときは前者を使ってはいけない。

### 事実4 — 起動オプション `--agent-teams` は、このビルドでは受け付けられない

```sh
claude --agent-teams -p "..."
# → error: unknown option '--agent-teams'
```

実行ファイルの中に判定処理としては存在するが、**オプション解析の側に登録されていない**ため即座に落ちる。有効化の入口は環境変数だけである。

### 事実5 — 対話セッションでは有効化に成功する。ただし `TeamCreate` は存在せず、チームは自動で作られる

（2026-08-26 実測）

確認方法: サンドボックスのディレクトリで、シェルから直接環境変数を立てて対話セッションを起こした（方法A）。

```sh
cd ".../scratchpad/agent-teams-trial"
CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 claude
```

そのセッションで `ToolSearch`（遅延読み込みの道具の定義を後から取りに行く仕組み）に `select:TeamCreate` を渡した結果は **NOTFOUND（該当なし）**。`TeamCreate` / `TeamDelete` / `Teammates` はいずれも道具として提供されていない。

**しかし、機能そのものは有効になっていた。** 明示的にチームを作る操作を一切していないのに、セッションの起動時点で、端末ごとの共有場所にチームの定義ファイルが作られていた。

```
~/.claude/teams/session-a6669ada/config.json
```
```json
{
  "name": "session-a6669ada",
  "leadAgentId": "team-lead@session-a6669ada",
  "leadSessionId": "a6669ada-4867-4262-86a0-ebbc62f30428",
  "members": [{ "name": "team-lead", "agentType": "team-lead",
                "cwd": "...\scratchpad\agent-teams-trial",
                "backendType": "in-process" }]
}
```

対照として、**環境変数を立てずに起動した別の対話セッション（会話記録の識別子 `36ff5d4c`）では、`~/.claude/teams/` にも `~/.claude/tasks/` にも何も作られていない。** つまりこの定義ファイルは、Agent Teams が有効なセッションでだけ作られる。

**結論:** このビルドでは、チームは**セッションの起動時に自動で1つ作られ、そのセッション自身がリーダー（`team-lead`）になる**。操作の入口は次の3つで、チームを作る／消す道具は経由しない。

| 道具 | 何をするか | 読み込み方 |
| --- | --- | --- |
| `ListAgents` | いま誰が居るかを一覧する（自分のチームのメンバー、同じ端末で動いている他の Claude Code セッションを含む） | 常時ロード済み |
| `SendMessage` | 既に動いているエージェントやセッションへ、後追いで指示を送る | 遅延読み込み（`ToolSearch` で取得） |
| `Agent` | エージェントを起こす | 常時ロード済み |

事実1で実行ファイルの文字列検索から見つかった `TeamCreate` / `TeamDelete` / `Teammates` は、このビルドの道具一覧には登録されていないコード経路のものである。**「`TeamCreate` が取れない」を「機能が無い」と読んではいけない。**

**この読み方は、あとで道具の定義文そのものによって裏づけられた（2026-08-26）。** `Agent` ツール（エージェントを起こす道具）が受け取るパラメータは8件（`description` / `isolation` / `mode` / `model` / `name` / `prompt` / `subagent_type` / `team_name`）で、そのうち `team_name` の定義文にこう書いてある。

> Deprecated; ignored. **The session has a single implicit team.**
> （非推奨。無視される。**セッションは暗黙のチームを1つだけ持つ。**）

つまり「セッションごとにチームが1つ自動で存在する」ことは、こちらの推測ではなく**道具の仕様として明記されている**。チーム名を指定する余地は既に取り除かれている。

**未確認のまま残った点 — 設定ファイル経由での有効化（方法B）。** 今回は方法A（シェルで環境変数を直接立てる）を使ったため、`.claude/settings.local.json`（そのリポジトリでだけ効き、Git の追跡対象外になる設定ファイル）の `env` 欄に `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` を書く方法が、単独で機能判定に間に合うかは分かっていない。**方法Bが効くなら、配布物へ有効化の設定を混ぜないまま、リポジトリ単位で実験を切り分けられる**ので、確かめる価値がある。

---

### 検証0の結論

> **Agent Teams は対話セッション専用である。** 非対話モード（`claude -p`）では、環境変数を立てても機能が現れない。

したがって以降の検証1〜4は、**環境変数を立てた状態で起動した対話セッション**でしか行えない。

> **その対話セッションでの有効化は成功している（事実5）。** ただしチームは自動で作られ、`TeamCreate` という道具は存在しない。

## 3. 検証の準備

### 3.1 サンドボックスを作る

**トライアル先の開発対象リポジトリ（SNS Agent）でいきなり試さない。** チームの状態は端末ごとの共有場所（`~/.claude/teams/` と `~/.claude/tasks/`）に作られるため、実運用中の台帳と混ざる可能性がある。使い捨ての Git リポジトリを1つ作って、そこで確かめる。

```sh
SB=<一時ディレクトリ>/agent-teams-trial
SRC=<agents-org のパス>/org

rm -rf "$SB"; mkdir -p "$SB"; cd "$SB"
git init -q
mkdir -p .claude/agents .claude/rules .claude/skills .claude/scripts .claude/templates docs/tasks

cp    "$SRC"/glossary.md docs/
cp    "$SRC"/agents/*    .claude/agents/
cp    "$SRC"/rules/*     .claude/rules/
cp -r "$SRC"/skills/*    .claude/skills/
cp    "$SRC"/scripts/org-check.py       .claude/scripts/
cp    "$SRC"/scripts/org-tokens.py      .claude/scripts/
cp    "$SRC"/scripts/org-monitor.py     .claude/scripts/
cp    "$SRC"/scripts/org-monitor-page.html .claude/scripts/
cp    "$SRC"/templates/* .claude/templates/
cp    "$SRC"/CLAUDE.md   CLAUDE.md
cp    .claude/templates/po-queue.md     docs/po-queue.md
cp    .claude/templates/tasks-README.md docs/tasks/README.md
```

さらに、検証用の最小タスクを1件だけ登録する。索引は `docs/task-list-agent-teams-trial.csv`（ファイル名の `agent-teams-trial` の部分は、リポジトリのディレクトリ名と一致させる規約）、詳細は `docs/tasks/T-001.md`。中身は「`hello.txt` を作り、`cat hello.txt` が `hello from the team` と出力すること」だけでよい。**検証したいのはチームの動き方であって、タスクの中身ではない。**

登録できたら、台帳の整合性検査を1回通しておく。

```sh
PYTHONIOENCODING=utf-8 python .claude/scripts/org-check.py --root .
# → 「タスク台帳: 停滞なし・警告なし（停滞の基準 2日）」が出れば準備完了
```

> `PYTHONIOENCODING=utf-8` を付けているのは、Windows の既定の文字コードのままだと日本語の出力が化けるためである。検査そのものには影響しない。

### 3.2 稼働状況のモニタを立ち上げる

配布物には、動いている担当エージェント・タスク・トークン消費をブラウザに出す簡易モニタが入っている（`org/scripts/org-monitor.py`。読むだけで組織の動作には干渉しない）。**検証中これを開いておく。** 検証4（チームメイトがモニタに映るか）に必要である。

```sh
PYTHONIOENCODING=utf-8 python .claude/scripts/org-monitor.py --root .
# → 「モニタ: http://127.0.0.1:7391 （画面を閉じて10分で自動終了）」
```

### 3.3 環境変数を立てて、対話セッションを起こし直す

**ここが唯一の有効化の入口である。** 方法は2つある。

**方法A — その場かぎり（推奨）。** サンドボックスのディレクトリで、環境変数を付けて起動する。

```sh
CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 claude
```

**方法B — 設定ファイルに書く。** サンドボックスの `.claude/settings.local.json`（そのリポジトリでだけ効き、Git の追跡から外れる設定ファイル）に次を書き、Claude Code を起こし直す。

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

**この設定を配布物（`org/settings.snippet.json`）へは入れていない。** 配布物は開発対象リポジトリへ丸ごとコピーされるものであり、そこに実験的機能の有効化を混ぜると、**組織の実行モデルが黙って変わる。** 検証が終わって採否が決まるまで、有効化は手で行う。

### 3.4 有効になったかの確認

起こし直したセッションで、まずこれを確かめる。**ここが通らなければ以降の検証はすべて実施できない。**

**判定に使うのは、チームの定義ファイルが作られたかどうかである。** 起こし直したセッションで、次を実行する。

```sh
ls ~/.claude/teams/
# → session-<会話記録の識別子> というディレクトリがあれば有効
cat ~/.claude/teams/session-<識別子>/config.json
# → members に自分が team-lead として入っていれば有効
```

**`ToolSearch` で `select:TeamCreate` を検索する方法は使わない。** 当初はこれを判定に使う予定だったが、このビルドには `TeamCreate` という道具がそもそも存在せず、**有効なセッションでも NOTFOUND が返る**ことが実測で分かった（事実5）。この方法では「機能が無い」と誤判定する。

## 4. 検証項目

**それぞれ「何を見るか」と「どちらの結果なら何が言えるか」を先に決めてある。** 走らせてから解釈を決めない。

### 検証1 — `org/agents/` の5つの定義が、そのままチームメイトとして機能するか

**なぜ確かめるか:** 機能するなら、この組織の資産（5ロールの定義ファイル）は書き直さずに Agent Teams へ載る。機能しないなら、載せ替えのコストが判断材料に入る。

**手順:** チームを1つ作り、レビューエージェントの定義（`.claude/agents/org-review.md`）を指定してチームメイトを1体立てる。

**見るもの:**

| # | 見るもの | どう確かめるか |
| --- | --- | --- |
| 1-a | チームメイトが立つか | `~/.claude/teams/<チーム名>/` の中身をファイルとして読む |
| 1-b | **道具の許可リストが引き継がれるか** | レビューエージェントは定義上、編集系の道具（`Write` / `Edit`）を持たない。立ったチームメイトに「ファイルを1つ作れ」と指示し、**断るかどうか**を見る |
| 1-c | モデルの指定が引き継がれるか | 定義ファイルの `model` 欄と、実際に使われたモデルを突き合わせる |
| 1-d | スキルとMCPサーバの指定が無視されるか | 事前情報では「無視され、プロジェクト設定側から読まれる」とされている。実際にそうか |

**判定:** 1-b が通れば「そのまま使える」と言ってよい。**1-b が通らない場合が最も重い。** レビューエージェントが編集系の道具を持たないことは、この組織で**設定ではなく道具の取り上げによって強制している唯一の規約**である（`org/README.md` の実行許可の節）。これが引き継がれないなら、Agent Teams 上ではレビューの独立性が担保できない。

**記録欄:**

（2026-08-26 実測。サンドボックスのチームリーダーのセッションから `Agent` ツールで1体起こし、その記録ファイルを直接読んで確認した）

```
1-a  結果: 立つ（ただし手順が想定と違う）
1-b  結果: 引き継がれる — 合格
1-c  結果: 判定不能（定義に model 欄が無いため）
1-d  結果: 未実施（この定義では確かめられない）
```

**1-a — 立つ。ただし「チームを作ってからメイトを立てる」という手順は存在しない。**

`Agent` ツール（エージェントを起こす道具）で起こしただけで、チームの定義ファイルの `members` に自動で追加された。

```json
{ "agentId": "review-probe@session-a6669ada", "name": "review-probe",
  "agentType": "org-review", "model": "opus",
  "tmuxPaneId": "in-process", "backendType": "in-process",
  "prompt": "このディレクトリに hello.txt というファイルを作り、中身を hello の1行にしてください。" }
```

同時に受信箱（`~/.claude/teams/session-a6669ada/inboxes/review-probe.json` と `team-lead.json`）も作られた。

**1-b — 引き継がれる。この検証で最も重い項目が合格した。**

レビューエージェントの定義ファイルの先頭には `tools: Read, Grep, Glob, Bash, SendMessage` と書いてある。編集系の道具（`Write` / `Edit`）は無い。起こしたチームメイトへ「`hello.txt` を作れ」と指示した結果、**ファイルは作られず、チームリーダーへ差し戻された。**

差し戻しの文言（原文）:

> 私は `org-review` です。成果物の作成・修正は行いません（CLAUDE.md の組織構成、およびレビューエージェント定義「自分では修正しない」）。**私の構成に編集系ツールが与えられていないのも同じ理由で、Bash で迂回して作るのは構成の意図に反するため行いません。**

**太字部分は想定を超えた結果である。** この定義には `Bash` が含まれているので、`echo hello > hello.txt` と打てば編集系の道具なしでもファイルは作れた。**それを自分で禁じている。** 道具の取り上げが効いただけでなく、取り上げの意図まで引き継がれていた。

**1-b に付随して分かったこと — 層2の規約がチームメイトへ継承されている。**

差し戻しの根拠として、チームメイトは次を挙げた。いずれも組織の規約類であって、こちらから渡した指示には含まれていない。

- 開発対象リポジトリの `CLAUDE.md`（層2の組織規約）
- `.claude/rules/org-escalation.md` の段1（分からないことを推測で埋めることの禁止）
- 共通停止条件 S-1（指示と登録済みタスクの内容が矛盾）と S-6（指示として成立していない）
- タスク台帳の `docs/tasks/T-001.md` の「判断してよい範囲」欄

さらに、**こちらが気づいていなかった矛盾を自力で検出した。** 与えた指示は「中身を `hello` の1行にせよ」だったが、台帳の T-001 の完了条件は「`cat hello.txt` が `hello from the team` と出力すること」だった。チームメイトはこの食い違いを指摘し、「どちらが正かは私では決められない」としてリーダーへ確定を求めた。

**1-c — 判定不能。** レビューエージェントの定義ファイルに `model` 欄が無い。チームの定義ファイルには `"model": "opus"` と記録されたが、これは親セッションのモデルが使われた結果とみられる。**定義ファイルに `model` を明示した場合に引き継がれるかは、この実験では確かめていない。**

**1-d — 未実施。** レビューエージェントの定義にスキルとMCPサーバの指定が無いため、この定義では確かめられない。ただし、プロジェクト設定の側のファイル（`CLAUDE.md`・`.claude/rules/`・`docs/tasks/`）が読まれていたことは 1-b の通り確認できている。

### 検証2 — 共有タスクリストが、自作の CSV 台帳を置き換えられるか

**なぜ確かめるか:** 置き換えられるなら、台帳の書式・整合性検査・停滞検知の一部を捨てられる。置き換えられないなら、**両方を持つことになり、二重管理が発生する**——これは採否を分ける。

**手順:** チームメイトへタスクを1件割り当て、実際にできた共有タスクリスト（`~/.claude/tasks/<チーム名>/` 以下のファイル）を読む。

**見るもの:** 自作のタスク別ファイル（`docs/tasks/T-XXX.md`）が持つ項目が、共有タスクリスト側に入るかを1件ずつ突き合わせる。左の列は既に埋めてある。**右の列を埋めるのが検証2である。**

| 自作台帳の項目 | それが無いと何が壊れるか | 共有タスクリストに入るか |
| --- | --- | --- |
| 完了条件 | 二値で判定できる完了の定義。レビューとテストの判定基準でもある | **該当なし（機能が存在しない）** |
| 判断してよい範囲 | 空だと担当は決めすぎるか、些末なことを全部エスカレーションしてくる | **該当なし（機能が存在しない）** |
| 変更範囲 | ここに無いものは触らない、という境界 | **該当なし（機能が存在しない）** |
| 禁止事項 | 触ってはいけないもの | **該当なし（機能が存在しない）** |
| 成果物（証拠） | 完了の裏付け。整合性検査が「完了なのに証拠が空」を検出する対象 | **該当なし（機能が存在しない）** |
| 申し送り | 上流タスクの結果を下流の担当へ渡す唯一の場所。**トライアル先の実運用で不足が発見されて追加した項目である** | **該当なし（機能が存在しない）** |
| 依存タスク | 依存待ちを停滞と誤判定しないために必要 | **該当なし（機能が存在しない）** |
| 手戻り回数 | サイクル基準の停滞（同じ工程を往復し続けている状態）の検知に使う | **該当なし（機能が存在しない）** |
| 決定ログ | なぜそう決めたかの記録 | **該当なし（機能が存在しない）** |
| ブロッカー | いま止めているもの。PO確認待ちとの紐付け | **該当なし（機能が存在しない）** |

**判定の目安:**

- **入る項目が「完了条件」だけなら、置き換えは不成立。** 自作台帳を残し、共有タスクリストは使わない
- **半分以上入るなら、両方を突き合わせる価値がある。** ただし「入れられる（自由記述欄に書ける）」と「機能として持っている（検査や判定に使われる）」は別である。**自由記述欄へ押し込めるだけなら、置き換えたことにはならない**
- **停滞検知と整合性検査（`org/scripts/org-check.py`）が読めるか**も同時に見る。読めないなら、スクリプトを書き換えるコストが乗る

**記録欄:**

（2026-08-26 実測）

```
共有タスクリストの実際の形式: 存在しない
突き合わせ結果: 全10項目「該当なし」
org-check.py が読めるか: 判定の必要なし（読む対象が無い）
```

**置き換えは成立しない。理由は「入る項目が少ない」ではなく、共有タスクリストという機能がこのビルドに無いからである。**

確認できた事実は3つ。

1. **チームのセッションは `TodoWrite`（作業項目リストを書く道具）を持っていない。** 常時ロードされる道具の一覧にも、遅延読み込みの道具の一覧にも無い。`ToolSearch` に `select:TodoWrite` を渡しても `No matching deferred tools found`（該当なし）が返る。
2. **共有タスクリストの置き場は作られるが、中身は空のままである。** `~/.claude/tasks/session-a6669ada/` というディレクトリはセッション起動時に作られるが、検証1〜3を通してファイルは1件も生成されなかった。
3. 事実1で実行ファイルから見つかった「共有タスクリストの置き場（`~/.claude/tasks/`）のパスを組み立てる処理」は、**ディレクトリを作るところまでは動いているが、そこへ書く道具が提供されていない。**

**したがって、この組織の自作タスク台帳（CSV索引＋タスク別Markdown）を Agent Teams 側へ寄せる選択肢は、現時点では存在しない。** 上の突き合わせ表は全項目「該当なし」で埋まる。二重管理の心配も生じない代わりに、**台帳まわりで得られるものも何も無い。**

**注記（この確認の限界）:** 検証3のあとに共有タスクリストの置き場を再確認する予定だったが、サンドボックスのセッション側で PO がそのコマンドの実行を承認しなかったため、実施していない。ただし上の1（書く道具が存在しない）が確定しているため、**結論は変わらない。**

### 検証3 — チームメイトから PO へ直接問いを出せるか

**なぜ確かめるか:** **この組織で最も重い設計前提がここに懸かっている。** PO確認待ちキュー（人間への問い合わせを1本にまとめ、オーケストレーターが一元管理する仕組み）は、「サブエージェントは人間へ選択肢を出して答えを待つ道具を使えない」という技術的制約への対処として設計された（`docs/decisions/00-research-notes.md` の制約1）。**制約が消えるなら、設計の根拠が変わる。**

**手順:** チームメイトへ、**わざと判断できない指示**を与える。たとえば「`hello.txt` に書く文言を決めて作れ。ただし文言は指定しない」のように、選択肢が複数あって勝手に決めてはいけない形にする。

**見るもの:**

| # | 見るもの | 判定 |
| --- | --- | --- |
| 3-a | チームメイトが人間へ問いを出せるか | 出せる／出せない |
| 3-b | 出せる場合、PO はどこで気づくか | チームリーダーの画面に出るのか、チームメイトを選ばないと見えないのか |
| 3-c | 問いが出ている間、他のチームメイトは止まるか | 止まる／止まらない |
| 3-d | 出せない場合、どう振る舞うか | 勝手に決める／チームリーダーへ聞く／止まる |

**判定の目安:**

- **3-a が「出せる」でも、PO確認待ちキューを捨ててよいことにはならない。** キューは技術的制約への対処であると同時に、**人間への問い合わせの流量を絞る役割**も持っていた（`docs/decisions/14-open-questions.md` の論点2）。人間は同時に1つしか答えられない。3-b と 3-c まで見て初めて判断できる
- **3-a が「出せない」なら、キューの設計根拠は変わらない。** その場合 Agent Teams を採っても、人間への問い合わせは今の設計のままでよい

**記録欄:**

（2026-08-26 実測。**2種類のエージェントで2回試し、同じ結果になった**）

```
3-a  結果: 出せない — 道具が与えられていない（切り分け済み）
3-b  結果: 該当なし（問いが出なかったため）
3-c  結果: 止まらない — リーダーは他の作業を続けられた
3-d  結果: リーダーへ聞き返した（2種類とも一致）
```

**試した2種類と、その結果。**

| 起こしたエージェント | 道具の制限 | 与えた指示 | 振る舞い |
| --- | --- | --- | --- |
| `org-review`（組織の定義） | あり（`Read` `Grep` `Glob` `Bash` `SendMessage` のみ） | 「`greeting.txt` を作れ。文言は指定しない。勝手に決めるのは禁止」 | 作らず、リーダーへ差し戻し |
| `general-purpose`（Claude Code 標準の汎用エージェント） | **なし**（道具の指定は `*` ＝全部） | 同上（「文言は人間に選ばせてください」を追加） | 作らず、リーダーへ差し戻し |

**道具の制限を外しても結果が変わらなかった。** 差が出たのは差し戻しの理由づけだけで、`org-review` は「ロール外＋指示として成立していない」、`general-purpose` は「PO への問い合わせ経路の制約」を挙げた。

汎用エージェントが返した文言（原文）:

> PO（人間）へ問い合わせできるのはメインセッションだけです（CLAUDE.md「組織の構成」）。したがって、PO の選択が返るまで作業を止めます。

なお汎用エージェントは、判断できない事項・理由・選択肢A〜Eのたたき台・影響範囲・待つ間に進められること（「無し」）を構造化してリーダーへ送っている。**推奨案は「推奨を出すことは実質的に自分が決めることになる」として意図的に出していない。**

**3-c — 止まらない。** チームメイトが判断待ちで止まっている間、チームリーダーは他の道具（`Agent` でのエージェント起動、`SendMessage`、`Bash`）を並行して実行できた。**画面の占有は起きていない。**

**切り分けの結果 — 「呼ばなかった」のではなく「呼べなかった」。**

汎用エージェントの返答は層2の規約（`CLAUDE.md`）を理由に挙げていたため、**道具を持っていなかったのか、持っていたが規約に従っただけなのかが区別できなかった。** これを潰すため、規約の話を一切持ち込ませず、道具の有無だけを聞くエージェント（`general-purpose`、道具の指定は `*` ＝全部）をもう1体起こした。

その回答（原文）:

> 1. **ない。** 私の道具一覧に `AskUserQuestion` はありません。トップレベルのツール定義（Agent / Artifact / Bash / Edit / Glob / Grep / PowerShell / Read / Skill / ToolSearch / Write）にも、遅延ロード可能なツール一覧にも含まれていません。
>
> 2. `ToolSearch` に `select:AskUserQuestion` を渡した結果: `No matching deferred tools found`
>
> 補足: 私が使える対話系の道具は `SendMessage`（チームメイト宛て）だけで、**人間へ選択肢を提示して回答を待つ経路は持っていません。**

一方、**チームリーダー（メインセッション）は `AskUserQuestion` をトップレベルの道具として持っている。** 検証中も呼び出し可能な状態だった。

> **結論: チームメイトから PO へ直接問いを出すことはできない。技術的制約が先に存在する。**
>
> したがって **PO確認待ちキューの設計根拠（`docs/decisions/00-research-notes.md` の制約1「サブエージェントは人間へ選択肢を出して答えを待つ道具を使えない」）は、Agent Teams の下でもそのまま有効である。** 人間への問い合わせをオーケストレーターが一元管理する設計は、Agent Teams を採っても変える必要がない。

**判定の目安に照らすと:** 事前に決めておいた判定は「3-a が『出せない』なら、キューの設計根拠は変わらない。その場合 Agent Teams を採っても、人間への問い合わせは今の設計のままでよい」であった。**この通りの結果になった。**

**付随して分かったこと2件。**

1. **遅延読み込みの道具の配布内容が、メインセッションと子エージェントで違う。** メインセッション側にあって子エージェント側に無いものが10件あった（`DesignSync` / `EndConversation` / `EnterPlanMode` / `ExitPlanMode` / `ListMcpResourcesTool` / `PushNotification` / `ReadMcpResourceDirTool` / `ReadMcpResourceTool` / `RemoteTrigger` / `TaskOutput`）。**道具の差は `AskUserQuestion` だけではない。**
2. **道具の制限が無い汎用エージェントには `Edit` / `Write` が入っていた。** レビューエージェント（`org-review`）にそれが無かったのは定義の `tools` 欄が効いた結果であり（検証1-b）、**両者の対比によって、定義ファイルによる道具の絞り込みが確かに効いていることが二重に裏づけられた。**

### 検証4 — チームメイトが、稼働状況のモニタに映るか

**なぜ確かめるか:** 配布物のモニタ（`org/scripts/org-monitor.py`）は、**サブエージェント**——親セッションが子プロセスとして起こすエージェント——を検出する作りである。1体につき Claude Code が書く小さなファイル（`agent-XXXX.meta.json`）を読み、その識別番号が親の会話記録に「実行結果」として現れていなければ稼働中と判定する（`docs/decisions/18-agent-monitor.md`）。

**チームメイトは独立したセッションであって、サブエージェントではない。** したがって**映らない可能性が高い。** 映らないなら、Agent Teams を採る場合はモニタの作り替えが要る。

**手順:** 検証1〜3を行っている最中に、モニタの画面（`http://127.0.0.1:7391`）と、状態を1回だけ出す確認用の実行を見る。

```sh
PYTHONIOENCODING=utf-8 python .claude/scripts/org-monitor.py --root . --once
```

**見るもの:** 出力の `agents` の配列にチームメイトが入るか、`running` の数が増えるか。

**判定:** 映らない場合、作り替えの規模を1行で見積もっておく。**モニタは状態を組み立てる部分と画面が分かれている**ので、読む先を `~/.claude/teams/` へ足すだけで済む可能性がある。

**記録欄:**

（2026-08-26 実測）

```
モニタに映ったか: 映った（想定と逆の結果）
映らない場合の作り替えの見積もり: 不要。ただし条件つき（下記）
```

**映った。** チームメイトが動いた直後にモニタの状態を1回だけ出させたところ、`agents` の配列に1体入っていた。

```json
"agents": [{ "id": "agent-areview-probe-8c91e02898f32b5e",
             "role": "review-probe", "description": "Create hello.txt",
             "running": false, "elapsed": 51.9, "tokens": 164187 }]
```

**理由:** `Agent` ツールで起こしたチームメイトは、チームの定義ファイル上で `backendType: "in-process"`（親セッションと同じプロセスの中で動く）と記録される。**従来のサブエージェントとまったく同じ場所に、同じ `agent-XXXX.meta.json` というファイルを書く。** モニタが元から読んでいるファイルなので、何も足さずに映った。

**ただし限定つきである。** これは in-process のチームメイトの場合の結果でしかない。**別プロセスの独立したセッションがチームに加わる形（`backendType` が `in-process` 以外になる形）は、この実験では試していない。** その形が使えるなら、そのチームメイトは `agent-XXXX.meta.json` を書かないので映らない見込みで、その場合はモニタが読む先に `~/.claude/teams/<チーム名>/config.json` の `members` を足す改修が要る。

## 4.5 対照実験 — Agent Teams を切った状態で、エージェント間通信は使えるか

**2026-08-26 実測。検証1〜4のあとに追加した項目である。**

**なぜ必要だったか:** 検証1〜4は Agent Teams を有効にした状態でしか行っていない。そのため「Agent Teams でしか出来ないこと」を特定できていなかった。**上乗せ分が何も無いなら、採る理由も無い。** そこを確かめる。

**手順:** Agent Teams を**無効**にした対話セッション（本リポジトリの作業ツリー、環境変数なし）で、`Agent` ツールにより子エージェントを2体起こし、`SendMessage`（他のエージェントやセッションへメッセージを送る道具）が実際に届くかを見た。

| 調べたこと | 結果 |
| --- | --- |
| 子エージェントは `SendMessage` を持つか | **持つ**（遅延読み込みの道具の一覧にある） |
| `ToolSearch` で定義を取得できるか | **できた** |
| 子エージェント → 親（メインセッション）へ送れるか | **送れた。** 本文が親に届いた |
| **子エージェント → 別の子エージェントへ送れるか** | **送れた。** 受け手が「受信しました: 兄弟エージェントからの疎通確認です」と返した。**ただし条件つき（下記）** |
| 子エージェントは `ListAgents`（誰が居るかを一覧する道具）を持つか | **持たない** |
| 子エージェントは `AskUserQuestion` を持つか | **持たない。** 常時の一覧にも遅延読み込みの一覧にも無く、名指しの検索でも該当なし |

**宛先の書き方に1点注意がある。** 子エージェントから親へ送るとき、セッション名（`agents-org-9a`）を指定するとエラーになり、「自分のプロセスのメインセッションなので `main` を使え」と返る。**親宛ては `main` と書く。**

**兄弟エージェント宛ての送信には条件がある。これは設計上重要である。**

- **識別子（agentId）を指定すると届く。** `a53f633a4f326bd90` のような、エージェントを起こしたときに返ってくる識別子で成功した
- **子エージェントは `ListAgents`（誰が居るかを一覧する道具）を持たない。** つまり**自分で相手を探せない**
- **名前でも届く（2026-08-26 の追試で確定）。** `Agent` ツールの `name`（エージェントに名前を付けるパラメータ）を渡して起こせば、兄弟エージェントは**素の名前だけ**を宛先にして送れる。ただし**名前は使い回せない**。詳細と根拠は下の「追試」を見ること。なお最初の試行で `No agent named 'probe-b' is reachable.`（その名前のエージェントには到達できない）というエラーになったのは、`name` を渡さず指示文の中で「あなたの名前は probe-b です」と伝えただけだったためで、**名前が登録されていない以上、届かないのが当然だった。試行の不備であって、機能の制限ではない**

**現時点で言えること: 子エージェントは、オーケストレーターが作業指示の中で宛先（少なくとも識別子）を教えた相手にしか送れない。自分で相手を探す手段が無いためである。**

**追試で確定した。オーケストレーターは名前で経路を指定できる。** ただし**名前は1セッション内で使い回せない**という条件がつき、これが組織の運用に直接効く。この節の末尾の追試を見ること。

**これは §14 の設計にとって好都合である。** 要件定義書は「担当エージェント同士の自由な通信はしない」と定め、`docs/decisions/12-agent-addition.md` は「直接通信の経路を増やすときだけは意図的に摩擦を残す」としている。**この環境では、経路の制限が規約だけでなく仕組みとしても成立している** —— 相手の識別子を知らなければ送れないため、オーケストレーターが渡した経路以外は自然に閉じる。

**なお Agent Teams を有効にすると、この制約は緩む。** チームのメンバーは名簿（`config.json`）に登録され、名前で呼び合える形になる。**経路を絞りたいこの組織にとっては、緩むこと自体が不利に働く。**

> **結論: 要件定義書 §14.2 の承認済み3経路（レビュー → 実装 / 実装 → 設計 / テスト → 実装）は、Agent Teams を使わずに実装できる。**
>
> §14.3 は「直接通信は環境によって使えないことを前提に置く」として、使えない場合はオーケストレーターが往復を中継する代替を定めていた。**この環境は「使える」側である。**

**あわせて確認できたこと:** `AskUserQuestion` が子エージェントに与えられないのは、Agent Teams の有無と無関係である。調査メモの制約1（`docs/decisions/00-research-notes.md`）は、どちらの状態でも成立している。

**この対照実験によって、Agent Teams の上乗せ分は次の3つだけに絞られた。**

| 上乗せ分 | 中身 |
| --- | --- |
| 名簿 | `~/.claude/teams/<チーム名>/config.json` に、誰が居るかが記録される |
| 受信箱 | メンバーごとの `inboxes/<名前>.json` ができる |
| 伝言の体裁 | 指示が `<teammate-message teammate_id="...">` という形で届き、送り主が明示される |

**通信そのものは上乗せ分ではない。**

### 追試 — 名前を宛先にできるか（2026-08-26）

**Agent Teams を無効にした本リポジトリのセッションで実施。** 上の対照実験で「未確定」として残した唯一の点を潰すために行った。

**手順:** `Agent` ツールで子エージェントを起こすとき、`name`（エージェントに名前を付けるパラメータ）を明示的に渡す。そのうえで別の子エージェントに、`SendMessage`（他のエージェントへメッセージを送る道具）の宛先へ**その名前だけ**を書かせて送らせ、受け手が本文を引用して返すかを見た。

| 調べたこと | 結果 |
| --- | --- |
| `Agent` ツールは `name` を受け付けるか | **受け付ける。** Agent Teams が無効でも効く。`ListAgents`（誰が居るかを一覧する道具）の出力に、指定した名前で並ぶ |
| 素の名前だけを宛先にして、兄弟エージェントへ届くか | **届く。** 受け手が本文を一字一句そのまま引用して返した |
| 受け手は送信の時点で生きている必要があるか | **不要。** 終了済みのエージェントが再開される形で配送される |
| 同じ名前を使い回すとどうなるか | **送信が拒否される。** 誤配ではない（後述） |

**送信が成功したときの返り値:**

```json
{"success":true,"message":"Resuming agent probe-zulu","resumedAgentId":"...","pin":{"id":"...","name":"probe-zulu","ref":"1b29b8"}}
```

`Resuming agent`（エージェントを再開する）とある通り、**メッセージの配送は、終了しているエージェントを起こし直す操作である。** 受け手を待機させ続ける必要はない。

#### 名前は使い回せない。これが設計に効く

**同じ名前を1セッション内で2回使うと、その名前宛ての送信は拒否される。** 実測した文言:

```
'probe-r' now resolves to a different agent than it did earlier in this conversation:
earlier sends went to [3d2c1b], which this name no longer reaches. Nothing was sent.
It now resolves to:
  probe-r [932e85] — subagent, in this session, started 25s ago
To message the new agent, re-send with its ref:
e.g. {"to": "probe-r [932e85]", ...}
```

日本語にすると「`probe-r` は、この会話の中で以前は別のエージェントを指していた。以前の送信は `[3d2c1b]` へ届いており、その名前ではもう到達できない。**何も送っていない。** 今は `[932e85]` を指している。新しい方へ送るなら `probe-r [932e85]` のように参照符号を添えて送り直せ」。

**重要なのは、黙って新しい方へ配送されるのではなく、送信そのものが止まる点である。** 誤配より安全な倒れ方だが、**気づかなければ通信が成立しない。**

**この組織の使い方に直撃する。** オーケストレーターは `org-implementation`（実装担当）のような**役割名を1セッション内で何度も使い回す**——タスクごとに同じ役割のエージェントを起こし直すためである。素の役割名をそのまま宛先に据えると、**2回目の割り当て以降、直接通信が黙って機能しなくなる。**

**したがって、宛先はタスクごとに一意でなければならない。** 取れる形は2つ:

| 形 | 宛先の書き方 | 利点と難点 |
| --- | --- | --- |
| 名前にタスク番号を混ぜる | `Agent` の `name` に `org-implementation-T-007` と付ける | 宛先が作業指示を書く時点で決まる。**オーケストレーターが起動前に確定させられる** |
| 名前に参照符号を添える | `org-implementation [932e85]` | 参照符号は起動してみないと分からない。**起動後に作業指示へ書き足す手間が要る** |

**前者を推す。** タスク番号は台帳で既に一意であり、オーケストレーターが割り当ての時点で知っている。**起動の順番や結果に依存せずに宛先を書ける**ため、作業指示を自己完結させるという原則（各エージェントは会話履歴を引き継がない）と噛み合う。

#### この追試で変わらなかったこと

**「子エージェントは自分で相手を探せない」は変わらない。** 子エージェントは `ListAgents` を持たないままで、名前が使えるようになっても、**オーケストレーターが作業指示の中で教えた宛先にしか送れない。** 経路が仕組みとして絞られるという §14 にとって好都合な性質は、そのまま残る。

### トークン消費の実測（2026-08-26）

サンドボックスで検証1〜4を回した時点の集計（`python .claude/scripts/org-tokens.py --root . --update`）。

| モデル | 合計 | 出力 | キャッシュ書込 | キャッシュ読出 | 返答回数 |
| --- | --- | --- | --- | --- | --- |
