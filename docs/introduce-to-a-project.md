# この AI開発組織を、別のプロジェクトへ導入する手順

**読む人:** PO（プロジェクトオーナー＝人間の依頼主）と、導入を手伝うセッション
**位置づけ:** 上から順に実行する手順書。**なぜそうするのかの説明は `org/README.md` にある**（このファイルは順番と確認方法に徹する）

**現在の配布方式は手動コピーである。** 2026-08-28 に「Claude Code のプラグイン機構（スキル・担当エージェントの定義・フックをまとめて配る仕組み）へ移す」と決めたが（`docs/decisions/24-distribution-plugin.md`）、**移行はまだ済んでいない。** 移行が済むまではこの手順で入れる。移行後はこのファイルを書き換える。

---

## 0. その前に — 何を入れようとしているのか

入れるのは**アプリケーションではなく、開発を進める組織の定義**である。具体的には次の3種類のファイルが、導入先のリポジトリへ置かれる。

| 種類 | 中身 |
| --- | --- |
| **担当エージェントの定義**（5つ） | 設計・実装・レビュー・テスト・ドキュメントの各担当が、何を責務とし、何を入力に取り、何を出力し、どういうときに判断を上へ返すか |
| **運営規約とスキル** | 組織の標準フロー、エスカレーションの段取り、タスク台帳の書き方、そしてオーケストレーター（司令塔となるメインセッション）が従う手順書 |
| **スクリプト5本とその自動実行の設定** | 台帳の停滞検知・整合性検査、トークン消費の集計、稼働状況のモニタ、利用者向け文書の生成、呼べるスキルの収集 |

**オーケストレーターの定義ファイルは無い。** オーケストレーターは**あなたが話しかけるメインセッションそのもの**である。担当エージェントは人間へ質問する手段を持たないため、司令塔が担当エージェントであることはあり得ない。

### 導入する前に満たしておくこと

| 前提 | なぜ |
| --- | --- |
| 導入先が **Git のリポジトリ**であること | 組織の規約が、ブランチ・コミット・push を前提に書かれている |
| **Python 3.8 以降**が入っていること | スクリプト5本が動かない。追加のインストールは要らない（標準ライブラリだけで書いてある） |
| **PO がゴールを言葉で持っていること** | 組織はゴールを受けて動く。「何を作るか」が無い状態で入れても、何も始まらない |

**技術スタックが未定の新規リポジトリでも導入してよい。** ただし手順6（スキルの割り当て）だけは、方式設計が終わってからもう一度やり直すことになる。

## 1. 配布物をコピーする

**`{agents-org}` は、このリポジトリ（`agents-org`）をチェックアウトした場所に読み替える。** 以下は導入先のリポジトリのルートで実行する。

```sh
mkdir -p .claude/agents .claude/rules .claude/skills .claude/scripts .claude/templates docs

cp    {agents-org}/org/glossary.md              docs/
cp -r {agents-org}/org/agents/*                 .claude/agents/
cp -r {agents-org}/org/rules/*                  .claude/rules/
cp -r {agents-org}/org/skills/*                 .claude/skills/
cp -r {agents-org}/org/templates/*              .claude/templates/
cp    {agents-org}/org/scripts/org-check.py     .claude/scripts/
cp    {agents-org}/org/scripts/org-tokens.py    .claude/scripts/
cp    {agents-org}/org/scripts/org-monitor.py   .claude/scripts/
cp    {agents-org}/org/scripts/org-monitor-page.html .claude/scripts/
cp    {agents-org}/org/scripts/org-docs.py      .claude/scripts/
cp    {agents-org}/org/scripts/org-skills.py    .claude/scripts/
```

**`org-monitor.py` と `org-monitor-page.html` は2つで1組である。** 稼働状況を見せる画面の中身が後者にあり、同じ場所に無いとモニタが動かない。

**`org/README.md` はコピーしない。** 配布物の説明であって、組織の実行時ファイルではない。

### 確認

```sh
ls .claude/agents .claude/rules .claude/skills .claude/scripts .claude/templates
```

担当エージェントの定義が5本（`org-design` / `org-implementation` / `org-review` / `org-test` / `org-documentation`）、スキルが4本（`org-orchestrate` / `org-session-resume` / `org-init` / `org-first-run-check`）、スクリプトが5本と画面のファイル1つ、あることを見る。

### 台帳そのものは、まだ作らない

タスクの索引（`docs/task-list-{プロジェクト名}.csv`）、タスク別ファイルの置き場（`docs/tasks/`）、PO確認待ちキュー（`docs/po-queue.md`）は、**この時点では作らない。**

作るのは、ゴールを受けたオーケストレーターが最初のタスクを登録する直前である（手順8）。**空の台帳を先に置くと、組織がまだ動いていないのか、動いて0件なのかが区別できなくなる。**

## 2. 層2の運営規約を `CLAUDE.md` へ追記する

`{agents-org}/org/CLAUDE.md` の中身を、**導入先のリポジトリのルートにある `CLAUDE.md` へ追記する。**

**既に `CLAUDE.md` があるなら、置き換えてはならない。** 組織の節として下へ足す。開発対象そのものの規約（技術スタック、ビルド手順、コーディング規約）は、さらにその下へ書く。

`CLAUDE.md` は、Claude Code が**毎セッション全文を読み込むファイル**である。ここに置いたものは担当エージェントにも自動的に渡る。

### 200行を超えたら気をつける

**`CLAUDE.md` は長くなるほど守られなくなる。** 200行を超えたあたりから遵守率が落ちる。導入先に既存の規約が大量にあるなら、**トピック別の規約は `.claude/rules/` へ、多段階の手順はスキル（`.claude/skills/`）へ逃がす。** どちらも必要なときにだけ読み込まれる。

## 3. 設定ファイルへ追記する

`{agents-org}/org/settings.snippet.json` の中身を、導入先の `.claude/settings.json` へ**追記する。**

**ファイルごと上書きしてはならない。** 他の拡張が入れた設定を消してしまう。`permissions`（ツールの実行許可）や `hooks`（決まった場面で必ずコマンドを実行させる仕組み）の項目が既にあるなら、**その中の配列へ足す。配列を丸ごと差し替えない。**

入っているのは2つの塊である。

| 塊 | 何を決めるもの |
| --- | --- |
| `permissions` | **ツールの実行許可。** どのコマンドを PO への確認なしで実行してよいか、どれを禁じるか |
| `hooks` | **必ず実行させる処理。** 台帳の検査・トークン集計・モニタの起動を、決まった場面で自動的に走らせる |

### 3-a. 開発対象のビルドとテストのコマンドを、自分で足す

**これを飛ばすと、テストを1回走らせるたびに人間へ確認が出る。**

配布物はどのリポジトリへも入るため、そこで何を実行するかは書きようがない。**導入した側が `permissions` の `allow` へ足す。**

```jsonc
// 例: Node.js のリポジトリ。実際のコマンドはそのリポジトリのものに置き換える
"Bash(npm test:*)",
"Bash(npm run build:*)",
"Bash(npx tsc --noEmit:*)"
```

```jsonc
// 例: Python のリポジトリ
"Bash(pytest:*)",
"Bash(ruff check:*)"
```

**足す前に、そのコマンドが何を書き換えるかを確かめること。** テストの実行に見えて、実際にはデータベースを作り直す・外部へ通信する、といったものがある。

### 3-b. Python の呼び出し名を確かめる

**`python3` というコマンド名は、どの環境にもあるわけではない。** Windows で python.org の配布物を入れた場合、存在するのは `python` だけである。

配布する設定は「`python3` を試し、失敗したら `python` を試す」形に書いてあるので、**設定そのものは直さなくてよい。** 手で実行するときだけ読み替える。

```sh
python3 --version || python --version
```

## 4. セッションを開き直す

**ここで一度止まる。** Claude Code は、担当エージェントの定義・規約・設定を**セッションが始まった時点の内容で読み込む。** 置いただけでは、いま動いているセッションには効かない。

## 5. 入ったことを確認する

開き直した新しいセッションで、次を確かめる。

| 確かめること | やり方 | 期待する結果 |
| --- | --- | --- |
| 台帳の検査スクリプトが動くか | `python3 .claude/scripts/org-check.py` | **エラーで落ちないこと。** 台帳がまだ無いので「台帳が見つからない」という趣旨の結果になるのが正しい |
| セッション開始時の検査が自動で走ったか | セッション開始直後の表示を見る | 検査の出力が出ている。**出ていなければ手順3の追記が効いていない** |
| 呼べるスキルを集めるスクリプトが動くか | `python3 .claude/scripts/org-skills.py --names` | 名前の一覧が出る。**1本も出なくてもよい**（その環境にスキルが入っていないだけ。手順6で扱う） |
| 組織の規約が読まれているか | メインセッションへ「この組織のエスカレーションは何段あるか」と聞く | **4段**と答える（自分で解決 → 許可された相手へ相談 → オーケストレーターへ → PO確認待ちキューへ） |

## 6. 導入時の初期シーケンスを1回だけ走らせる

**メインセッションへ「組織を導入したので初期設定をして」と伝える。** `org-init` というスキル（`.claude/skills/org-init/`）が走る。

### これが何をするか

**担当エージェント5つの定義には、使うスキルが最初から数本だけ書いてある。** スキルとは、Claude Code が呼ばれたときにだけ読み込む手順書のことである。

初期状態で書いてあるのは、**言語やフレームワークに依存しないものだけ**である。書いた側は、この組織がどのリポジトリへ導入されるかを知らないためである。放っておくと2つのことが起こる。

- **書いてあるスキルが、この実行環境に入っていない。** 呼んでも失敗する
- **このリポジトリの技術構成に必要なスキルが、書かれていない**

**どちらも黙って起きる。** エラーは出ず、成果物も一応できあがる。だから導入時に1回、環境と突き合わせる。

### 走らせたあと、もう一度セッションを開き直す

**エージェント定義を書き換えたので、また効かない。** 開き直したうえで、初期シーケンスの最後の段（効いているかの確認）まで済ませる。**ここを飛ばすと、担当エージェントがスキルを1本も持たない状態で動き続け、それに気づく手段が無い。**

### 技術スタックがまだ決まっていない新規リポジトリの場合

**この手順は飛ばしてよい。** 技術構成は設計担当がこれから決めるものであり、決まっていないものと突き合わせることはできない。

**ただし、やり直す時機を引き継ぎ記録（`docs/handover.md`）へ書いておくこと。** 方式設計が終わった直後である。

## 7. モニタを確認する（任意）

稼働状況のモニタは、セッション開始時に自動で立ち上がる設定になっている。**読むだけで何も書き換えない。**

```sh
python3 .claude/scripts/org-monitor.py --once   # 状態を1回だけ文字で出す（確認用）
```

**台帳がまだ無い間は、担当エージェント・タスク・トークンがすべて空の状態が返る。** これは正しい動作である（実測: 終了コード0、`agents` と `tasks` が空の一覧）。

## 8. 最初のゴールを渡す

**ここから組織が動き始める。** PO がメインセッションへゴールを伝える。

**細かな作業指示は出さない。** この組織は「PO はゴールと判断を提供し、作業の段取りは組織が決める」という前提で設計されている。

オーケストレーターがやること（`org-orchestrate` スキルの手順）:

1. 雛形（`.claude/templates/`）から台帳を作る——索引 `docs/task-list-{プロジェクト名}.csv`、タスク別ファイルの置き場 `docs/tasks/`、PO確認待ちキュー `docs/po-queue.md`
2. ゴールをタスクへ分解し、索引へ登録する
3. タスクごとに詳細ファイル `docs/tasks/T-XXX.md` を作り、**完了条件・判断してよい範囲・変更範囲・禁止事項**を書く
4. 担当エージェントを起こして割り当てる

**`{プロジェクト名}` は、そのリポジトリのルートディレクトリの名前である**（`Hawkeye-Re` としてチェックアウトされていれば `docs/task-list-hawkeye-re.csv`）。

### 判断を求められたら答える

**組織は、分からないことを推測で埋めない設計になっている。** PO確認待ちキューへ質問が積まれるので、それに答える。**答えている間も、依存関係のないタスクは止まらない。**

---

## 9. 最初のタスクが1件完了したら、初回点検をする

**メインセッションへ「初回点検をして」と伝える。** `org-first-run-check` というスキル（`.claude/skills/org-first-run-check/`）が走る。

**これは省略しない。** 組織が設計どおりに動いているかを、**自己申告ではなくファイルに残った痕跡で**判定する。「委譲しました」という報告は証拠にならない。

見るのは、担当エージェントへ実際に委譲されたか／タスク別ファイルが作業指示として機能したか／完了条件がテストへ変換できたか／セッション開始時の台帳検査が走ったか／ツールの実行許可が足りていたか（**確認が何回出たか**）である。

**ここで実行許可の不足が分かる。** 手順3-a で足し忘れたコマンドが、この点検で件数として出る。

## 10. 更新に追随する（暫定手順）

**現在の配布方式では、配布元を直しても導入先には届かない。** 手でコピーし直す必要がある。

```sh
# 導入先のリポジトリのルートで、手順1 のコピーをもう一度実行する
```

**ただし、そのままコピーすると導入先の変更を潰すことがある。** 次の2つは導入先で書き換えているため、上書きする前に差分を見ること。

| 上書きに注意するもの | なぜ |
| --- | --- |
| `.claude/agents/org-*.md`（担当エージェントの定義5本） | **手順6 で、その環境に合わせてスキルの割り当てを書き込んである。** 上書きすると消える |
| `.claude/settings.json` | **手順3-a で、開発対象のビルドとテストのコマンドを足してある。** そもそもこのファイルは配布物では上書きしない（追記するもの） |

```sh
# 上書き前に、何が違うかを見る
diff -r {agents-org}/org/agents .claude/agents
```

**導入先が独自に不具合を直していることがある。** その場合は、どちらが新しいかを突き合わせたうえで、**直した内容を配布元へ戻す**（戻さないと次の更新でまた消える）。

**この面倒さが、配布方式をプラグイン機構へ移すと決めた理由そのものである**（`docs/decisions/24-distribution-plugin.md`）。移行後、この節は書き換わる。

## つまずきやすいところ

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| **`git status` ひとつ動かすのに確認が出続ける** | 手順3 の設定の追記が効いていない | `.claude/settings.json` を見る。`permissions` を既存の配列へ足したか、ファイルごと置き換えていないかを確かめる |
| **テストを走らせるたびに確認が出る** | 手順3-a を飛ばした | 開発対象のテストコマンドを `allow` へ足す |
| **セッション開始時に台帳の検査が走らない** | `hooks` の追記漏れ、または Python の呼び出し名 | 手順5 の確認表を上から順に |
| **担当エージェントがスキルを1本も呼ばない** | 手順6 のあとにセッションを開き直していない | 開き直し、初期シーケンスの最後の段（効いているかの確認）をやる |
| **モニタが真っ白** | `org-monitor-page.html` が同じ場所に無い | `.claude/scripts/` に2つ揃っているか見る |
| **担当エージェント同士の往復が成立しない** | 作業指示に相手の宛先が書かれていない | 担当エージェントは誰が居るかを一覧できない。オーケストレーターがタスク別ファイルの `## 連絡してよい相手` へ宛先を書く。**役割名だけを書いてはならない**（同じ名前が1セッション内で2回使われた時点で、その名前宛ての送信が拒否される） |
| **既存の拡張が壊れた** | 配布物で既存のファイルを上書きした | 組織のファイルはすべて `org-` で始まる。**既存の commands / skills / hooks は触らない。** 名前が衝突したら組織側の名前を変える |

## 導入しないほうがよい場合

**組織を入れること自体が費用である。** 次のときは入れないほうがよい。

- **1回きりの小さな変更をするだけのリポジトリ。** 台帳・委譲・レビュー・テストの一巡は、変更1件あたりの費用が大きい
- **PO がゴールではなく手順を指示したい場合。** この組織は作業指示を受け取る形になっていない
- **リリース・デプロイまで自動で回したい場合。** **この組織にはリリース／デプロイの工程が存在しない。** 「完了」の実質は push までである（PO の判断待ちの論点）
