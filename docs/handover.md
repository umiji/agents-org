### Agent Teams の検証を終え、採らないと決めた（2026-08-26）

**Claude Code 本体が「Agent Teams（エージェントチーム）」という機能を公式に持っている。** 複数の Claude Code セッションを1つのチームとして動かし、1つを司令塔、残りを実働にするもので、既定では無効の実験的機能である。**これがこの組織の自前実装と4箇所で正面から重なっていた**——担当エージェント間の直接通信を禁じる規約、自作のタスク台帳、PO確認待ちキュー、停滞検知。

**検証0〜4と対照実験・追試をすべて実施し、採否を確定させた。**

- **結果の記録（判断は書かない）**: `docs/experiments/01-agent-teams.md`
- **採否の判断**: `docs/decisions/19-agent-teams.md` ——**MVP では採らない。既定（無効）のまま運用する**

| 重なっていたもの | 実測の結果 |
| --- | --- |
| 直接通信の禁止（§14） | **Agent Teams 無しでも直接通信は使える。** 3経路はこの機能を採らずに実装できる（実装済み） |
| 自作タスク台帳 | **置き換えられない。** 「入る項目が少ない」のではなく、**共有タスクリストへ書き込む道具が存在しない** |
| PO確認待ちキュー | **設計根拠はそのまま有効。** 担当エージェントに人間へ問う道具が与えられないのは、この機能の有無と無関係 |
| 停滞検知・稼働状況のモニタ | **作り替え不要。** チームメイトは従来のサブエージェントと同じファイルを書き、モニタにそのまま映った |

**採らない理由の要点:** 上乗せ分は「名簿・受信箱・伝言の体裁」の3つだけに絞られた。そのうち筆頭の名簿は、**この組織にとっては利点ではない**——無効な状態では担当エージェントが相手を探せず、オーケストレーターが教えた宛先にしか送れないため、§14 の経路制限が規約だけでなく仕組みとしても成立している。名簿はその壁を下げる。加えて対話セッション専用であること、実験的で仕様が固まっていないことが重なる。

**有効化の設定は配布物（`org/settings.snippet.json`）へ入れていない。** 採らない以上、混ぜない。

### 検証の副産物 — 直接通信の欠落を埋めた（2026-08-26）

**検証の過程で、要件定義書 §14.2 が認めた3経路（レビュー → 実装 / 実装 → 設計 / テスト → 実装）が、規約としては在るのに実際には成立していないことが判明した。** 担当エージェントは誰が居るかを一覧する手段を持たず、**宛先を教えられなければ送れない**のに、作業指示の雛形に宛先の欄が無く、渡す手順もどこにも書かれていなかった。往復はすべてオーケストレーターを経由する形に落ちていたはずである。

**宛先はタスクごとに一意でなければならない。** 実測で、同じ名前を1セッション内で2回使うとその名前宛ての送信が**拒否される**ことを確認した（黙って新しいほうへ届くのではなく、送信が止まる）。オーケストレーターは同じ役割のエージェントをタスクごとに起こし直すため、役割名だけの宛先は2回目の割り当てで必ず壊れる。**役割名にタスク番号を混ぜる形**（`org-implementation-T-007`）を採った。

配布物5ファイルに入れた（コミット `252e29d`）——タスク別ファイルの雛形と台帳の書式仕様に `## 連絡してよい相手`、オーケストレーターの手順書に割り当て前の確認項目（5→6項目）と起動時の手順、層2の規約に宛先の作り方、エスカレーションの規約に段2で使う宛先の取得元。**この欄は機械的な検査の対象にしていない**（直接通信の要らないタスクのほうが多く、必須にすると意味の無い記入を強いるため）。

**トライアル先には届いていない。** 反映は PO が行う。

### 利用者向けドキュメントの人間用ビューの生成スクリプトを作った（2026-08-27）

**配布物のドキュメントエージェントの定義が、存在しないスクリプトを使えと命じていた。** 禁止事項に「人間用ビュー（README、handbook）を手で書かない。生成スクリプトを使う」と書いてあるのに、そのスクリプトが無かった。**トライアル先で最初のドキュメントタスクが起きた瞬間、担当エージェントは実行できない指示に当たり、PO への確認往復が1回発生する**状態だった。

作ったのは `org/scripts/org-docs.py`（回帰テスト `tests/test_org_docs.py` 22件）。**Python 3.8 以降・標準ライブラリのみ**という、他の配布スクリプト3本と同じ条件で書いてある。

- **入力**は層3のエージェント用マスタ（`docs/features/` `docs/guides/` `docs/api/` の Markdown）
- **出力**は2つだけ。`docs/handbook.md` は丸ごと作り直す。`README.md` は**目印（`<!-- org:docs:begin -->` と `<!-- org:docs:end -->`）で挟んだ区間だけ**を索引に差し替える
- **README を丸ごと生成しない**のは、そこに題名・導入・ライセンスなど、マスタから導けない手書きの内容が入っているためである。**目印が無ければ README には触らず、その旨を出力する**
- マスタが1本も無いリポジトリでは何も作らない。組織を動かしていない普通の作業でファイルが増えない

### 稼働状況のモニタの作り替えを設計した（2026-09-02。**実装済み。上の節を見ること**）

**pergram で組織を動かしたところ、モニタが3つの壊れ方をした。** PO からの報告と、コードを読んだ結果の原因、そして PO と合意した直し方を残す。**実装は次のセッションで行う。**

#### 症状

1. 稼働中の担当エージェントが**数秒しか表示されない**
2. 表示される役割が**2種類しか出ない**
3. **終了した欄に入っているのに、起動時間とトークン数が伸び続ける**
4. **たまに、終了した欄が丸ごと消える**

#### 原因

**親玉は1つで、症状1・3・4はすべてここから出ている。**

**モニタは「このリポジトリで記録ファイルが一番新しく更新された会話」を一定間隔で選び直し、前回と違うものが選ばれると `reset()` で記憶を全部捨てる**（`org/scripts/org-monitor.py` の `pick_session` と `reset`）。捨てるのは、表示中のエージェント一覧・終了済みの識別子の集合・記録をどこまで読んだかの位置・トークンの累計の4つ。

**複数のウィンドウで同じリポジトリを開いていると、「一番新しい」が行ったり来たりする。** そのたびに全消去が走る（症状4）。しかも**消去のあと再構築されると、終了済みの集合が空なので、終わっていたエージェントが「稼働中」へ根拠なく戻る**。稼働中の間は経過時間を `いま − 起動時刻` で計算するため、実時間で伸び続ける（症状3）。次の巡回でまた終了へ戻る。**この往復が症状1である。**

**副次の原因が2つ。** 終了後の経過時間の終点を、**記録ファイルの更新時刻**で毎回取り直している（ファイルを触っただけでも動く）。役割名の対応表 `ROLE_NAMES` が**5体のままで、6体目の改善エージェント `org-improvement` が入っていない**（症状2の一部。ただし対応表に無くても生の名前で出るので、症状2の主因は上の消去だと見ている）。**あわせて、モニタが持つ台帳の並び順表 `STATE_ORDER` に `テスト作成中` という、台帳の状態10種に存在しない状態が入っている。**

#### 直し方（PO と合意済み）

**当初「一度終了したものを稼働中へ戻さない」を提案したが、これは誤りだった。** 担当エージェントは**文脈を保ったまま再開できる**ため、終了から稼働中への遷移は正当である。**封じると本物の再開を隠す。** PO の指摘で撤回した。

**正しい形は、エージェントごとに状態を持たせること。** いまは状態を持たず、巡回のたびに「終了済みの集合に入っていないか」だけで計算し直しているので、集合が消えると根拠なく戻る。

**用語をここで固定する。以降の「セッション」は必ずこの意味である。**

| 語 | 範囲 |
| --- | --- |
| **ターン** | PO がプロンプトを投げ、回答が出て、次のプロンプト待ちになるまでの1往復 |
| **セッション** | **ウィンドウを開いてから閉じるまで。中にターンが何十回も入る。** 記録ファイル（`~/.claude/projects/<リポジトリ>/<識別子>.jsonl`）1本がこれ1つに対応する |

**担当エージェントの文脈は、ターンをまたいでも生き続け、セッションが閉じたときに消える。** 文脈は動いているプロセスの中にあり、記録ファイルではない——**ファイルを残しても、閉じた後は再開できない。**

#### 状態は2つ。過去のセッションは追わない（案A。PO 判断 2026-09-02）

**エージェントの状態は「稼働中」と「待機」の2つだけ。**

| 状態 | 意味 | 判定の根拠 |
| --- | --- | --- |
| **稼働中** | いま動いている | 起動の結果が、メインセッションの記録にまだ返っていない |
| **待機** | そのターンは返したが、**呼べば文脈を保ったまま続きができる** | 結果が返った |

**「終了」という状態は持たない。** 検討の過程で3つ（稼働中・待機・終了）を考えたが、**終了はエージェント1体ごとには起きない**——エージェントを名指しで閉じる手段が存在せず、同じセッションのエージェントは必ず全部同時に終了する。**つまり終了はエージェントの状態ではなくセッションの属性である。**

**そして案Aでは、閉じたセッションを画面に出さない。** 出さないものに属性は要らないので、終了という概念そのものがモニタから消える。

**過去のセッションを追う案（案B）は採らなかった。** 案Bは、セッション終了時に必ず走る処理で「閉じた」印をファイルへ残し、過去のセッションのエージェントを「終了」「終了（中断＝結果を返さないまま閉じられた）」として並べ、プルダウンで切り替えるもの。**自動化は可能である**（印を置く仕組みは Claude Code の標準機能で、独自の仕組みは要らない）。**採らなかったのは、いま出ている症状が案Aで全部止まるからである。** 症状の原因は「乗り換えのたびに記憶を捨てる」ことであり、乗り換えをやめれば消える。

**案Bの価値は症状の解消ではなく、「結果を返さないままセッションが閉じられた担当エージェント」が見えること**にある。作業が失われてタスクが中途半端に残る事故は、組織を長く動かすほど起きる。**まだ一度も委譲していない現時点では価値が出ない。実際に事故が起きてから判断する。**

#### 未確認の論点 — 閉じたセッションを再開したとき、担当エージェントは戻るか

**上の設計は「戻らない」を前提にしている。確かめていない。**

そう考えた根拠は、担当エージェントが**起動元のプロセスの中で動く**仕組みだからである。一方で**担当エージェントごとの記録ファイルはディスクに残っている**（モニタが読んでいるのがそれ）。**記録が残ることと文脈を復元できることは別なので、残っているからといって戻るとは限らない。** PO は IDE 拡張機能版を使っており、タブを閉じるとまっさらになるという認識である。

**確かめ方**: 担当エージェントを1体起動して結果を受け、セッションを閉じ、再開してから同じ宛先へ指示を送る。文脈を持って返ってくるかを見る。

**結果で設計が変わる。** 戻らないなら上のまま。**戻るなら、閉じたという属性の意味が変わり、終了は記録ファイルを削除したときくらいしか起きなくなる。**

**経過時間は状態に紐づけて区間で持つ。** 待機へ移った時点で区間を閉じ、再開したら新しい区間を開く。**「記録が伸びたか」は、ファイルの更新時刻ではなく読み進めた位置（行）で見る。**

#### セッションが複数あるときどうするか（案A。PO 判断 2026-09-02）

**乗り換えをやめる。** いまは一定間隔で「記録ファイルが一番新しく更新されたセッション」を選び直しており、**複数のウィンドウを開いていると選択が行ったり来たりして、そのたびに全消去が走る。これが症状の親玉である。**

**直し方は、最初に選んだセッションに固定すること。** 見張る相手を途中で変えない。**プルダウンも、閉じた印のファイルも、過去の記録の読み直しも要らない。**

**引き換えに、別のウィンドウで動いている担当エージェントは見えない。** タブを閉じたら、その中身は次から見えない。**PO はこれを了解のうえで案Aを選んでいる。**

#### モニタの起動条件も直す

**いまは、既にモニタが動いていても毎回ブラウザを開いている**（立て直してはいない）。**PO から「毎回同じタブが立ち上がって煩わしい」と報告があった。** 既に動いていたら**何もしない**に変え、URL はセッション開始時の出力へ1行出す（フックの出力は会話の文脈へ入るので見失わない）。**初回だけ開く挙動になる。**
