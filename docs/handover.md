### 稼働状況のモニタを足した（2026-08-25）

PO の要求により、**セッション開始時にブラウザで稼働状況を見せる簡易モニタ**を配布物へ足した（`org/scripts/org-monitor.py` と `org/scripts/org-monitor-page.html` の2つで1組、`docs/decisions/18-agent-monitor.md`）。出すのは「動いている担当エージェント」「タスクの状態」「トークン消費」の3つだけ。**読むだけで組織の動作には干渉しない。**

- 立ち上げるのは**セッション開始時のフック**であって、オーケストレーターではない（手順書には強制力が無いため。PO が選択）
- **タスク台帳が無いセッションでは何もしない**ので、組織を動かしていない普通の作業でブラウザは開かない
- **PO は「将来ダッシュボード化する可能性がある」と明言している。** そのときは要件定義書 §3.3（MVP対象外に「複雑なWebダッシュボード」がある）に触れるので、範囲の切り直しの判断が要る

### Agent Teams の検証を終え、採らないと決めた（2026-08-26）

**Claude Code 本体が「Agent Teams（エージェントチーム）」という機能を公式に持っている。** 複数の Claude Code セッションを1つのチームとして動かし、1つを司令塔、残りを実働にするもので、既定では無効の実験的機能である。**これがこの組織の自前実装と4箇所で正面から重なっていた**——担当エージェント間の直接通信を禁じる規約、自作のタスク台帳、PO確認待ちキュー、停滞検知。

**検証0〜4と対照実験・追試をすべて実施し、採否を確定させた。**

- **結果の記録（判断は書かない）**: `docs/experiments/01-agent-teams.md`
- **採否の判断**: `docs/decisions/19-agent-teams.md` ——**MVP では採らない。既定（無効）のまま運用する**

| 重なっていたもの | 実測の結果 |
| --- | --- |
| 直接通信の禁止（§14） | **Agent Teams 無しでも直接通信は使える。** 3経路はこの機能を採らずに実装できる（実装済み） |
| 自作タスク台帳 | **置き換えられない。** 「入る項目が少ない」のではなく、**共有タスクリストへ書き込む道具が存在しない** |
| PO確認待ちキュー | **設計根拠はそのまま有効。** 担当エージェントに人間へ問う道具が与えられないのは、この機能の有無と無関係 |
| 停滞検知・稼働状況のモニタ | **作り替え不要。** チームメイトは従来のサブエージェントと同じファイルを書き、モニタにそのまま映った |

**採らない理由の要点:** 上乗せ分は「名簿・受信箱・伝言の体裁」の3つだけに絞られた。そのうち筆頭の名簿は、**この組織にとっては利点ではない**——無効な状態では担当エージェントが相手を探せず、オーケストレーターが教えた宛先にしか送れないため、§14 の経路制限が規約だけでなく仕組みとしても成立している。名簿はその壁を下げる。加えて対話セッション専用であること、実験的で仕様が固まっていないことが重なる。

**有効化の設定は配布物（`org/settings.snippet.json`）へ入れていない。** 採らない以上、混ぜない。

### 検証の副産物 — 直接通信の欠落を埋めた（2026-08-26）

**検証の過程で、要件定義書 §14.2 が認めた3経路（レビュー → 実装 / 実装 → 設計 / テスト → 実装）が、規約としては在るのに実際には成立していないことが判明した。** 担当エージェントは誰が居るかを一覧する手段を持たず、**宛先を教えられなければ送れない**のに、作業指示の雛形に宛先の欄が無く、渡す手順もどこにも書かれていなかった。往復はすべてオーケストレーターを経由する形に落ちていたはずである。

**宛先はタスクごとに一意でなければならない。** 実測で、同じ名前を1セッション内で2回使うとその名前宛ての送信が**拒否される**ことを確認した（黙って新しいほうへ届くのではなく、送信が止まる）。オーケストレーターは同じ役割のエージェントをタスクごとに起こし直すため、役割名だけの宛先は2回目の割り当てで必ず壊れる。**役割名にタスク番号を混ぜる形**（`org-implementation-T-007`）を採った。

配布物5ファイルに入れた（コミット `252e29d`）——タスク別ファイルの雛形と台帳の書式仕様に `## 連絡してよい相手`、オーケストレーターの手順書に割り当て前の確認項目（5→6項目）と起動時の手順、層2の規約に宛先の作り方、エスカレーションの規約に段2で使う宛先の取得元。**この欄は機械的な検査の対象にしていない**（直接通信の要らないタスクのほうが多く、必須にすると意味の無い記入を強いるため）。

**トライアル先には届いていない。** 反映は PO が行う。

### 利用者向けドキュメントの人間用ビューの生成スクリプトを作った（2026-08-27）

**配布物のドキュメントエージェントの定義が、存在しないスクリプトを使えと命じていた。** 禁止事項に「人間用ビュー（README、handbook）を手で書かない。生成スクリプトを使う」と書いてあるのに、そのスクリプトが無かった。**トライアル先で最初のドキュメントタスクが起きた瞬間、担当エージェントは実行できない指示に当たり、PO への確認往復が1回発生する**状態だった。

作ったのは `org/scripts/org-docs.py`（回帰テスト `tests/test_org_docs.py` 22件）。**Python 3.8 以降・標準ライブラリのみ**という、他の配布スクリプト3本と同じ条件で書いてある。

- **入力**は層3のエージェント用マスタ（`docs/features/` `docs/guides/` `docs/api/` の Markdown）
- **出力**は2つだけ。`docs/handbook.md` は丸ごと作り直す。`README.md` は**目印（`<!-- org:docs:begin -->` と `<!-- org:docs:end -->`）で挟んだ区間だけ**を索引に差し替える
- **README を丸ごと生成しない**のは、そこに題名・導入・ライセンスなど、マスタから導けない手書きの内容が入っているためである。**目印が無ければ README には触らず、その旨を出力する**
- マスタが1本も無いリポジトリでは何も作らない。組織を動かしていない普通の作業でファイルが増えない
- `--check` を付けると書き込まず、マスタと食い違っていないかだけを見る（食い違えば終了コード 1）

`docs/decisions/06-documentation-agent.md` の確定事項Aが「生成物なので後から変えられる」として固定していなかった3点（生成先・結合順・目次）と、A が触れていなかった2点（**見出しの段下げをコードブロックの中には及ぼさない**、**マスタ同士のリンクを文書内の行き先へ書き換える**）を決め、同じ文書の末尾へ追記した。

**A は「最初のドキュメントタスクが発生した時点で作る」として先送りしていた**が、トライアルが始まっている以上、先に作るほうを採った。**この判断に異論があれば差し戻せる**（作ったものを消すコストは低い）。

**まだ決めていないこと**: セッション開始・終了のフックから自動実行するかどうか。**いまは自動実行しない**——ドキュメントエージェントが自分で実行する。トライアルで実際にドキュメントタスクが回ってから判断する。

**トライアル先には届いていない。**

## PO の作業スタイル（重要）

**この節を読まずに書き始めると、ほぼ確実に差し戻される。**

### ハイコンテキストに書かない

コマンド名・設定項目名・ドキュメントの章番号・略語を「名前だけ」で置かない。それが何であり何をするのかを、必ずその場で説明する。

- ✗ 「`subagentStatusLine` で行を書き換えられる」
- ○ 「設定ファイルに `subagentStatusLine` という項目がある。各エージェントの表示行を、自分で書いたスクリプトの出力に差し替えられる」

- ✗ 「`08` の段4で対処する」
- ○ 「判断できないものは PO確認待ちキューへ登録する、というエスカレーション規約の4段目で対処する（`docs/decisions/08-escalation-criteria.md`）」

**適用先はチャットの返答だけでなく、コミットメッセージ・決定記録・プルリクエストの本文を含む。** 詳細は `.claude/skills/low-context-communication/SKILL.md`。

### 語に厳しい

**「サブエージェント」を組織上の役割の意味で使わない。** それは Claude Code の実行機構を指す語である。役割は「担当エージェント」。

このプロジェクトで実際に起きた最大の齟齬がこれだった。**両方の意味で文が成立してしまうため、何往復しても誰も気づかなかった。**

### 選択肢を出して問う

判断が要る場面では、**選択肢・各案の利害・推奨案**を添えて問う。推測で埋めない。

## この作業で踏んだ失敗（繰り返さないため）

| 失敗 | 教訓 |
| --- | --- |
| 「サブエージェント」を2つの意味で使い続けた | **片方しか読んでいない資料から来た語**が事故を起こす。新しい語を持ち出すときは出所を明示する |
| タスク別ファイルのメタデータ書式が機械に読めなかった | **仕様を書くとき、機械が読む部分は行の形まで決める。** 項目名の羅列では足りない |
| 停滞検知スクリプトの終了コードでフックの出力が届かなくなるところだった | **仕様だけでは見えない問題がある。** 実装して初めて分かった |
| 提案を広げすぎた（2回） | **PO は範囲を絞る指摘をする。** 先に「何を載せないか」を決めると早い |
| 機械が読む書式を文章でだけ規定し、雛形を配らなかった | **書式を決めたら、その形の実ファイルを配る。** 文章だけでは毎回組み立て直しになり、揺らぐ |
| 単独実行を前提にした規約（着手前に作業ツリーの差分を確認する）を、並列実行の指示と並べて置いた | **「同時に走らせる」と書いたら、共有されるもの（作業ツリー・ブランチ・台帳）を全部洗う** |
