# 用語集

**Status:** Confirmed（2026-08-20）
**位置づけ:** 正典。このリポジトリと、この組織が動く先のリポジトリで使う語を固定する。

---

## この用語集に載せる語・載せない語

判断の基準は1つ。

> **その語を一般的な意味のまま使ったら、この組織では間違った行動になるか。**
>
> **なる → 載せる。ならない → 載せない。**

「べき等」「トランザクション」「リファクタリング」のような一般的な技術用語は載せない。**読み手（人間もAIも）が既に正しく理解しており、載せても何も買えないうえに、毎回読む量だけが増える。**

載せるのは次の3種類。

| 分類 | 何か | 例 |
| --- | --- | --- |
| **1. 一般的な意味と違う語** | 誰でも知っている語だが、この組織が意味を狭めた／変えたもの | 「テスト」「レビュー」「完了」 |
| **2. 範囲を明示しないと曖昧になる語** | 指す対象が2つ以上あり、文脈だけでは決まらないもの | 「ユーザー」「リポジトリ」 |
| **3. この組織が作った語** | この組織の外では通じないもの | 「担当エージェント」「タスク台帳」 |

**1が最も危険で、最も見落とされる。** 見慣れない語が出てくれば人は調べるが、「テスト」では調べない。知っているつもりでいるからである。**一般語であることが、狭められている事実を隠す。**

### 語の定義を変えるとき

このファイルを直したうえで、**その語を使っている決定記録も直す。** 定義だけ変えて放置すると、古い文書が別の意味で読まれる。

# 1. 一般的な意味と違う語

**この節の語は、一般的な意味のまま使うと規約違反になる。**

## テスト

一般的には「動作を検証する作業」全般を指すが、**この組織では書く主体が分担で決まっている。**

| | 実装エージェント | テストエージェント |
| --- | --- | --- |
| 書くもの | **自分が書いたコードの単体テストだけ** | 結合テスト、シナリオテスト、回帰テスト |
| 視点 | 実装したものが意図どおり動くか | **仕様**に対して満たしているか（第三者の視点） |

「必要なテストを書く」という指示を一般的な意味で受け取ると、実装エージェントが結合テストまで書いてしまう。**一般常識としては正しいが、この組織の規約に反する。**

テストエージェントが単体テストの不足に気づいた場合は、自分で書かず実装エージェントへ差し戻す。

## 単体テスト

**実装エージェントが書く。テストエージェントは書かない。** 上記の分担の片側。

## 受け入れテスト

**完了条件を、実行できる形にしたもの。** テストエージェントが実装より先に書く。

**書いた時点では落ちているのが正しい。** 一般的な「テストは通るもの」という感覚と逆になる。実装前に通ってしまうなら、テストが完了条件を検証できていないか、既に実装済みかのどちらかであり、オーケストレーターへ報告する対象になる。

## レビュー

一般的な「レビュー」に合格基準は無い。**この組織では明確に決まっている。**

| 重大度 | 意味 | 扱い |
| --- | --- | --- |
| **Blocker** | 完了条件を満たさない／明らかなバグ／セキュリティ上の問題 | 修正必須。残っている限り通過させない |
| **Major** | 設計との食い違い／保守性の重大な問題 | 修正必須。ただし別タスクに切り出す相談ができる |
| **Minor** | 改善提案。動作にも保守性にも実害がないもの | 任意。残っていても通過する |

**通過の条件は Blocker と Major が0件。** 「だいたい良さそう」で通してはいけない。

レビューエージェントは**自分では直さない。** 一般的なコードレビューでは指摘者が直すこともあるが、この組織では修正は実装エージェントの担当である。

## 完了

**完了条件を全て満たし、かつ証拠（実行したコマンドとその実際の出力）が記録されている状態。**

一般的な「終わった」よりも厳しい。証拠が無いものは完了ではない。

## 完了条件

**コマンドを実行して出力を見れば、満たしたかどうかが二値で判定できる形で書かれたもの。**

「使いやすくなっていること」のような主観的な記述は完了条件として成立しない。レビューとテストの両方がこれを判定の基準にするため、書かれていないタスクは着手前に差し戻す。

## エスカレーション

**自分で決められないことを上へ渡すこと。この組織では4段階と、各段の打ち切り条件が決まっている。**

1. 自分で解決する（作業指示・参照すべき成果物・既存コード・確定済みの決定記録を確認する）
2. 直接やりとりが許可された相手へ相談する（許可されている経路は3つだけ）
3. オーケストレーターへ渡す
4. オーケストレーターでも決まらなければ PO確認待ちキューへ登録する

**段1の打ち切りは、時間ではなく「情報源を尽くしたか」で決める。** 上の4つを見ても答えが一つに定まらないなら、それ以上は推測になる。

## 停滞

**2種類ある。単独で「停滞」と書かない。**

| | 実時間基準 | サイクル基準 |
| --- | --- | --- |
| 捉えるもの | セッションをまたいで**放置された**タスク | 1セッション内で**空回りしている**タスク |
| 判定 | 索引の更新日が **2日以上前**、かつ完了でも中止でもない | 往復が**上限（2往復）に達した**、または手戻り回数が3以上 |
| 検知する主体 | スクリプト | オーケストレーター |

**PO確認待ちのタスクは停滞に数えない。** 組織側の停滞ではないため。ただし別枠でリマインド候補として数える。

## 手戻り

**一度先の工程へ進んだタスクが、前の工程へ差し戻されること。数える対象が決まっている。**

| 数える | 数えない |
| --- | --- |
| レビューからの修正要求 | 実装エージェントが自分で気づいて直したもの |
| テストからの不具合レポート | Minor（軽微な改善提案）への対応 |
| オーケストレーターによる担当の差し戻し | |

タスク別ファイルに回数を記録し、組織の健全性を測る指標に使う。

## 設計

**この組織では2種類に分かれ、別のタスクになる。**

| | 方式設計 | 詳細設計 |
| --- | --- | --- |
| 実施時期 | ゴール受領直後 | 各機能の実装直前 |
| 決めること | 全体構成、技術選定、主要なデータ構造、機能間の境界 | API仕様、処理フロー、画面遷移、個別のデータ項目 |
| 完了条件 | 実装タスクへ分割できる状態 | 実装エージェントが判断に迷わず着手できる状態 |

分けるのは、初期の大きな設計タスクが単一の詰まりどころになるのを避けるためと、詳細設計に先行実装で得た知見を反映できるようにするため。

## commit（コミット）

**論理的なまとまり単位で作る。1つのタスクが複数のコミットになってよい。** まとまりができた時点で作り、タスク完了まで溜めない。

## push（プッシュ）

**タスク完了時に行う。レビュー通過を待たない。**

一般的には「レビューを通してから共有する」運用も多いが、この組織では逆である。セッションが途中で切れることを前提に置いているため、ローカルにしか存在しない状態を長く保つと、実装が失われて新しいセッションが続きから拾えなくなる。

## 優先度

**`高` / `中` / `低` の3つだけ。** タスク索引の列に入る値であり、自由記述ではない。

## 依存

**2つの形式があり、書き分ける。**

| 書き方 | 意味 |
| --- | --- |
| `T-001（ブロッカー）` | T-001 が完了するまで、このタスクを開始できない |
| `T-001（推奨: 理由）` | 必須ではないが、この順で進める方が合理的 |
| `無し` | 依存がないことを**確認済み**である |

**ブロッカー指定には理由を必ず書く。理由が書かれていない依存は、依存として認めない。** 説明できない依存は、並行して走れるはずのタスクを不要に直列化する。

## ドキュメント

**単独で使わない。3つの層のどれかを明示する。**（詳細は分類2を参照）

# 2. 範囲を明示しないと曖昧になる語

## ユーザー

**2つを指しうる。**

| 指すもの | 書き方 |
| --- | --- |
| 人間のプロジェクトオーナー | **PO** と書く |
| 開発対象アプリを使う人 | 「アプリの利用者」「エンドユーザー」と書く |

## リポジトリ

**2つを指しうる。混同すると、作るべき場所を間違える。**

| 指すもの | 書き方 | 何が置かれるか |
| --- | --- | --- |
| `agents-org`。組織の**定義**を持つ場所 | **本リポジトリ** | 要件定義書、決定記録、配布物 |
| 組織が実際に働く先 | **開発対象リポジトリ** | タスク台帳、PO確認待ちキュー、引き継ぎ記録、アプリのコード |

## エージェント

**総称。オーケストレーターを含む6つ全部を指す。** 5つだけを指したいときは「担当エージェント」と書く。

## ドキュメント（3つの層）

| 層 | 中身 | 読み手 | 保守する主体 |
| --- | --- | --- | --- |
| **層1** | 本リポジトリの要件定義と決定記録 | 組織を設計する人間（PO） | PO と、その作業を支援するセッション |
| **層2** | 開発対象リポジトリの `CLAUDE.md`、`.claude/rules/`、エージェント定義、用語集 | **AI組織自身**（全エージェント） | **オーケストレーター** |
| **層3** | 開発対象アプリの成果物ドキュメント（README、API文書、利用者向け仕様） | AI組織 と 人間 の両方 | **ドキュメントエージェント** |

**層2をドキュメントエージェントが持たない理由**: 層2は成果物の説明ではなく、**組織自身への指示**である。「このリポジトリでは pnpm を使う」は層2、「この API はこう呼ぶ」は層3。

## 品質基準

**2種類あり、置き場所が違う。**

| | プロジェクト全体の品質基準 | タスク固有の基準 |
| --- | --- | --- |
| 置き場所 | 層2（`CLAUDE.md` / `.claude/rules/`） | タスク別ファイルの `## 完了条件` |
| 定める主体 | 設計エージェントが方式設計時に定め、オーケストレーターが層2へ書く | オーケストレーター |

**タスクごとに全体の基準を複写しない。** 「テストが通ること」のようなプロジェクト全体に効く基準を各タスクへ写すと、量が増えるうえに、基準を変えるとき全タスクを直すことになる。

## スキル

**Claude Code の機構としてのスキル**（呼ばれたときだけ読み込まれる手順書）と、**一般的な意味での「能力」**が紛らわしい。機構を指すときはそう明示する。

# 3. この組織が作った語

## PO（プロジェクトオーナー）

**人間のユーザー。このリポジトリの所有者。** ゴールと判断を提供する立場であり、細かな作業指示は出さない前提で組織が設計されている。**AI組織の中で、PO だけが人間である。**

## オーケストレーター

**組織全体を管理・調整する司令塔。** 誰が・何を・どの順番で行うかを判断する。

自分では成果物を作らない。コーディング、テスト実装、通常のドキュメント作成、通常のコードレビューは担当しない。

**PO と直接やりとりできる唯一のエージェント**でもある。これは方針ではなく技術的な制約による（分類4の「サブエージェント」を参照）。

## 担当エージェント

**オーケストレーターからタスクを割り当てられて、実際にそれを実行する側。** 現在は5つ。

| 名前 | 何をするか |
| --- | --- |
| 設計エージェント | 要件を、実装できる形の設計へ変換する |
| 実装エージェント | コードを書く。設定を変える。単体テストを書く。Git へコミットする |
| レビューエージェント | 実装が要求・設計・品質基準を満たしているか確認する。自分では直さない |
| テストエージェント | 仕様の側から動作を検証する |
| ドキュメントエージェント | 利用者や将来の開発者に向けた文書を最新に保つ |

「担当」はタスク索引の列名でもあり、そこに入る値がこの5つのいずれか、または `未割当` である。

> **この語を選んだ理由**: 要件定義書 v0.1 が既に2箇所（タスク項目の一覧、完了条件のチェック項目）でこの語を使っている。新語を作るより、既にある語を格上げする方が、直す文書が少なくて済む。
>
> **却下した候補**: 「専門エージェント」は要件定義書が「後から追加する特化ロール」の意味で既に使っており衝突する。「ワーカー」「メンバー」は要件定義書に一度も出てこず、採用すると差分が増えるだけ。「実行エージェント」は「実装エージェント」と字面が近く紛らわしい。

## 専門エージェント

**後から組織へ追加される、特定分野に特化した担当エージェント。** SNS、マーケティング、データ分析、UI/UX、セキュリティなどが想定されている。MVP（最小限の動く組織）では作らない。

## ロール

**責務の単位。** 「何を担当するか」だけを指し、どう起動するかは含まない。同じロールを、サブエージェントとしても独立セッションとしても動かせる。

**ロールは責務の単位であって、知識の単位ではない。** 「セキュリティに詳しいエージェントが欲しい」の多くは、レビューロールにセキュリティ用のスキルを足せば済む。

## タスク台帳

**進捗についての唯一の真実。2つのファイルに分かれている。**

| ファイル | 役割 | 誰が書くか |
| --- | --- | --- |
| `docs/task-list-{プロジェクト名}.csv` | **索引。** ID・日付・タスク名・状態・優先度・担当・依存・詳細ファイルへのパス、それだけ | **オーケストレーターだけ** |
| `docs/tasks/T-XXX.md` | **タスク別の詳細。** 目的、完了条件、決定ログ、作業ログ、証拠など | 担当エージェント（自分のタスクの分だけ） |

**分けてある理由**: 1つのタスクを触るときに、完了済み全タスクの記録まで読み込まずに済むようにするため。加えて、ファイルが分かれていれば、並行して走る作業が同時に書いても衝突しない。

**索引を書ける者を1人に絞ってある理由**: 索引は1ファイルなので、複数が同時に書けば必ず壊れる。

**タスク別ファイルは、そのまま作業指示である。** 作業指示を別途書き下ろさない。項目が空であることが、指示の抜けを目に見える形にする。

## PO確認待ちキュー

`docs/po-queue.md`。**PO の判断を仰いでいる質問の一覧。** 1件を `Q-001` のような番号で識別する。

質問ごとに、何を決めてほしいか・なぜ組織で決められないか・選択肢と各案の利害・推奨案・回答がないと止まるタスク、を書く。

**必ず併記するもの**: この回答を待つ間も進められるタスク。書けないなら組織全体が止まっているということであり、それ自体が報告に値する。

## 引き継ぎ記録

`docs/handover.md`。**「今どこにいるか」を1枚に書いたもの。** 常に上書きし、過去分は Git の履歴に残す。

**節目ごとに更新する。** セッション終了時にまとめて書く運用は成立しない。上限は予告なく訪れ、書く余裕が残っていない状態で切れるため。

## 決定ログ / 作業ログ / 証拠

タスク別ファイルの中にある、**性質の違う3つの記録**。混ぜない。

| 名前 | 答えるもの | 寿命 |
| --- | --- | --- |
| **決定ログ** | **なぜそうしたか** | 恒久。過去の項目を書き換えず、上書きする新項目を足す |
| **作業ログ** | 何が、どの順で起きたか | 一時的。完了時に数行へ畳む |
| **証拠** | 完了条件を満たしたと何故言えるか。コマンドとその実際の出力だけ | 恒久 |

決定ログには**却下した案とその理由**を必ず書く。「X を選んだ」は数週間で「なぜ X なのか」に劣化するが、「Y が使えないので X」は劣化しない。

2つの決まり文句がある。

- **`特記なし`** — このタスクに決定が本当に無かった。項目自体は常に置くので、無いことが「まだ書いていない」を意味する状態を保つ
- **`（記録なし）`** — 決定はあったが理由が当時記録されず、もう復元できない。**推測で理由を作って埋めない。** 作られた理由は後から事実として読まれるため、認めた空白より悪い

## 設計成果物

**設計エージェントが書く、組織の内側に向けた文書。** 何をどう作るか、そして**なぜその方式にしたか、どの案を却下したか**を記録する。層3の文書とは読み手が違う。

## エージェント用マスタ / 人間用ビュー

層3の文書は2階建てになっている。

| | エージェント用マスタ | 人間用ビュー |
| --- | --- | --- |
| 位置づけ | **正典。ここだけが真実** | マスタからの**生成物** |
| 粒度 | 機能・目的・シーン単位に細かく分割 | 結合された通し読み用 |
| 更新 | ドキュメントエージェントが直接書く | **スクリプトで生成する。手で書かない** |

**生成の一方向に固定する理由**: 二重に手で書くと必ず食い違う。人間用ビューは常に捨てて作り直せる状態を保つ。

## TDD適用可否

**そのタスクで、テストを実装より先に書くかどうか。** TDD（テスト駆動開発 — 先に失敗するテストを書き、それを通すように実装する進め方）は既定である。

事前にテストを書けないタスク（探索的な調査、見た目の調整、設定変更など）は「適用外」と明示する。**判定するのはオーケストレーター**で、タスクを分解する時点で決める。

## ゴール健全性評価

**組織が最終ゴールへ近づいているかの判定。** タスクの消化数だけを見ない。判定は3つ。

| 判定 | 目安 |
| --- | --- |
| **前進している** | 完了数が増え、かつ**残作業が減っている** |
| **停滞している** | 完了数が増えていない。停滞やブロックが積み上がっている |
| **ゴールが揺らいでいる** | 完了数は増えているのに、**残作業が減っていない、または増えている** |

**3つ目がこの評価の存在理由である。**「タスクは消化されているのにゴールに近づいていない」という状態に名前を付けて、検知できるようにしてある。

## 反復上限（2往復）

**レビューや不具合修正の往復は2回で打ち切る。**「レビュー → 修正 → 再レビュー」で1往復と数える。

2往復して解決しないなら、指摘の伝わり方か、設計・要件の側に構造的な問題がある。**往復が収束しないこと自体が、判定基準（完了条件や設計）の不備を示す信号**なので、修正を続けず再計画へ回す。

# 4. Claude Code という道具の語

**この節は本リポジトリ（層1）でのみ必要である。** 開発対象リポジトリへ配る用語集には入れない——担当エージェントはこの機構の中で動いている当事者であり、自分がそうであることを説明されても行動は変わらないため。

ここは**PO が Claude Code の資料を読まずに議論できるようにするため**の節である。

## セッション

**Claude Code の会話1本分。** 起動してから終了するまでの、記憶を共有するひとまとまり。

## メインセッション

**人間が直接やりとりしている最上位のセッション。** 端末に表示され、人間が入力する先。**この組織の設計では、オーケストレーターがこれにあたる。**

## サブエージェント

**メインセッションから起動される子プロセス。** Claude Code が持つ特定の実行機構を指す。**組織上の役割の意味では使わない**（それは「担当エージェント」）。

重要な性質が3つ。

1. **人間に直接質問できない。** 選択肢を提示して人間に選ばせる機能が、この方式では強制的に取り除かれる
2. **記憶が独立している。** 親の会話履歴も、他のサブエージェントの会話も一切見えない
3. **途中で止まって問い合わせることができない。** いったん結果を返して終わり、親からメッセージを受けて再開する

**1が、オーケストレーターをサブエージェントにできない理由である。** PO と話せない司令塔は成立しない。

### 記憶に何が入るか

| 入る | 入らない |
| --- | --- |
| そのロールの定義文 | **親（オーケストレーター）と PO の会話** |
| **親がそのとき書いた依頼文1通だけ** | **他の担当エージェントの会話** |
| `CLAUDE.md` と `.claude/rules/` の全階層 | 親が既に読んだファイル、既に呼んだスキル |
| Git の状態（親セッション開始時点） | 自動メモリ、出力スタイル |
| 事前読み込みを指定したスキルの全文 | |

**外の世界からの入口は、親が依頼文に書いた文字列と、共有しているファイルだけである。** だから作業指示は自己完結でなければならない。「さきほど決めた方針で」が通じないのは、規約の問題ではなく**情報がそもそも届いていない**ためである。

再開したときも同じで、**止まっていた間に親側で起きたことは入らない。**

## 独立セッション

**それ自体が最上位であるセッション。** 担当エージェントを、親を持たない形で起動したもの。

サブエージェントとの違いは、**人間に直接質問できること**と、**Git の作業ツリー（同じリポジトリの別チェックアウト）が自動的に分離されること**。MVP では使わない。

## フォーク

**親の会話をまるごと引き継いで分岐したサブエージェント。** 通常のサブエージェントが記憶ゼロから始まるのに対し、これだけは親の履歴を全部持つ。**この組織では使わない。**

## スキル（機構としての）

**呼ばれたときだけ読み込まれる手順書。** 常に読み込まれる `CLAUDE.md` と対になる。**「常に必要な事実」は `CLAUDE.md`、「呼ばれたときに必要な手順」はスキル。**

## ルール

**話題ごとに分割した規約。** `.claude/rules/` 以下に置く。`CLAUDE.md` と同じく毎回読み込まれるが、話題別にファイルが分かれている点が違う。

`CLAUDE.md` は200行を超えると守られる率が落ちるため、超えそうなときはここへ分割する。

## フック

**決められたタイミングで必ずコマンドを実行させる仕組み。** 例えばセッション開始時。

**`CLAUDE.md` は強制力を持たない**（読まれる文脈であって、実行される設定ではない）。「必ずやらせたいこと」はフックにする。停滞検知の実行がこれにあたる。
