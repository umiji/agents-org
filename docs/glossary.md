# 用語集

**Status:** Confirmed（2026-08-20）
**位置づけ:** 正典。このリポジトリと、この組織が動く先のリポジトリで使う語を固定する。

同じ語が別のものを指していると、設計の議論が噛み合わなくなる。特に危険なのは、**組織上の役割を指す語**と、**Claude Code という道具の機構を指す語**が同じ綴りになる場合である。以下はその区別を明示する。

語の定義を変えるときは、このファイルを直したうえで、その語を使っている決定記録も直すこと。**定義だけ変えて放置すると、古い文書が別の意味で読まれる。**

---

## 1. 人と役割

### PO（プロジェクトオーナー）

**人間のユーザー。このリポジトリの所有者。**

ゴールと判断を提供する立場であり、細かな作業指示は出さない前提で組織が設計されている。AI組織の中で、**PO だけが人間**である。

「ユーザー」「あなた」と書かれている場合も、原則としてこの PO を指す。

### エージェント（総称）

**組織を構成する AI 全般。** オーケストレーターも含む。

「各エージェント」「全エージェント」と書いた場合、オーケストレーターを含む6つ全部を指す。

### オーケストレーター

**組織全体を管理・調整する司令塔。** 誰が・何を・どの順番で行うかを判断する。

自分では成果物を作らない。コーディング、テスト実装、通常のドキュメント作成、通常のコードレビューは担当しない。

**PO と直接やりとりできる唯一のエージェント**でもある。これは方針ではなく技術的な制約による（後述の「サブエージェント」を参照）。

### 担当エージェント

**オーケストレーターからタスクを割り当てられて、実際にそれを実行する側のエージェント。** 現在は5つある。

| 名前 | 何をするか |
| --- | --- |
| 設計エージェント | 要件を、実装できる形の設計へ変換する |
| 実装エージェント | コードを書く。設定を変える。自分が書いたコードの単体テストを書く。Git へコミットする |
| レビューエージェント | 実装が要求・設計・品質基準を満たしているか確認する。自分では直さない |
| テストエージェント | 仕様の側から動作を検証する。受け入れテスト・結合テスト・回帰テストを書く |
| ドキュメントエージェント | 利用者や将来の開発者に向けた文書を最新に保つ |

**「担当」はタスク索引（後述）の列名でもある。** その列に入る値がこの5つのいずれか、または `未割当` である。

> **この語を選んだ理由**: 要件定義書 v0.1 が既に2箇所（§6.2 のタスク項目一覧、§21 の完了条件）でこの語を使っている。新語を作るより、既にある語を正式なものとして固定する方が、直す文書が少なくて済む。
>
> **却下した候補**: 「専門エージェント」は、要件定義書が「後から追加する専門ロール（SNS、セキュリティ、データ分析など）」の意味で既に使っており、流用すると衝突する。「ワーカー」「メンバー」は要件定義書に一度も出てこないため、採用すると既存文書との差分が増えるだけで得がない。「実行エージェント」は「実装エージェント」と字面が近く紛らわしい。

### 専門エージェント

**後から組織へ追加される、特定分野に特化した担当エージェント。** SNS、マーケティング、データ分析、UI/UX、セキュリティなどが想定されている。

MVP（最小限の動く組織）では作らない。ただし、定義ファイルを1つ足すだけで追加できる構造を目指している。

### ロール

**責務の単位。** 「何を担当するか」を指す抽象的な区分であり、それがどう起動されるかは含まない。

「実装ロール」と言えば、実装という責務そのものを指す。**同じロールを、後述の「サブエージェント」としても「独立セッション」としても動かせる。**

**ロールは責務の単位であって、知識の単位ではない。** 「セキュリティに詳しいエージェントが欲しい」の多くは、レビューロールにセキュリティ用のスキルを足せば済む。ロールを増やす前に、スキルで足りないか確認する。

## 2. Claude Code の実行機構

ここから先は、組織の話ではなく**道具の話**である。同じ担当エージェントを、どちらの方式でも動かせる。

### セッション

**Claude Code の会話1本分。** 起動してから終了するまでの、記憶を共有するひとまとまり。

### メインセッション

**人間が直接やりとりしている最上位のセッション。** 端末に表示され、人間が入力する先。

**このリポジトリの設計では、オーケストレーターがこれにあたる。**

### サブエージェント

**メインセッションから起動される子プロセス。** Claude Code が持つ特定の実行機構を指す。

重要な性質が3つある。

1. **人間に直接質問できない。** 選択肢を提示して人間に選ばせる機能（`AskUserQuestion` というツール）が、この方式では強制的に取り除かれる
2. **記憶が独立している。** 親の会話履歴も、他のサブエージェントの会話も、一切見えない（詳細は次項）
3. **途中で止まって問い合わせることができない。** いったん結果を返して終わり、親からメッセージを受けて再開する

**1 が、オーケストレーターをサブエージェントにできない理由である。** PO と話せない司令塔は成立しない。

#### サブエージェントの記憶に何が入るか

| 入る | 中身 |
| --- | --- |
| そのロールの定義文 | エージェント定義ファイルに書いた指示 |
| 依頼文 | **親がそのとき書いた1通だけ** |
| 組織の規約 | リポジトリの `CLAUDE.md` と `.claude/rules/` 以下の規約。全階層が入る |
| Git の状態 | 親セッションが始まった時点のスナップショット |
| 事前読み込みスキル | エージェント定義で名前を指定したスキルの全文 |

| 入らない |
| --- |
| **親（オーケストレーター）と PO の会話** |
| **他の担当エージェントの会話** |
| 親が既に読んだファイル、既に呼んだスキル |

**外の世界からの入口は、親が依頼文に書いた文字列と、共有しているファイルだけである。** だから作業指示は自己完結でなければならない。「さきほど決めた方針で」が通じないのは、規約の問題ではなく**情報がそもそも届いていない**ためである。

再開したときも同じで、**止まっていた間に親側で起きたことは入らない。**

### 独立セッション

**それ自体が最上位であるセッション。** 担当エージェントを、親を持たない形で起動したもの。

サブエージェントとの違いは、**人間に直接質問できること**と、**Git の作業ツリー（同じリポジトリの別チェックアウト）が自動的に分離されること**。

MVP では使わない。オーケストレーターのコンテキストが手狭になったときの移行先として検討対象に残してある。

### フォーク

**親の会話をまるごと引き継いで分岐したサブエージェント。** 通常のサブエージェントが記憶ゼロから始まるのに対し、これだけは親の履歴を全部持つ。

**この組織では使わない。** 設計ロールに実装の会話まで渡す必要がなく、記憶を無駄に圧迫するため。

### スキル

**呼ばれたときだけ読み込まれる手順書。** 多段階の作業やチェックリストを置く場所。

常に読み込まれる `CLAUDE.md` と対になる。**「常に必要な事実」は `CLAUDE.md`、「呼ばれたときに必要な手順」はスキル**、という使い分けをする。

### ルール

**話題ごとに分割した規約。** `.claude/rules/` 以下に置く。`CLAUDE.md` と同じく毎回読み込まれるが、話題別にファイルが分かれている点が違う。

`CLAUDE.md` は200行を超えると守られる率が落ちるため、超えそうなときはここへ分割する。

### フック

**決められたタイミングで必ずコマンドを実行させる仕組み。** 例えばセッション開始時。

**`CLAUDE.md` は強制力を持たない**（読まれる文脈であって、実行される設定ではない）。「必ずやらせたいこと」はフックにする。停滞検知の実行がこれにあたる。

## 3. 組織が持つ記録

これらは**開発対象リポジトリ**（組織が実際に働く先）に作られる。このリポジトリ（`agents-org`）に作るものではない。

### タスク台帳

**進捗についての唯一の真実。** 2つに分かれている。

| ファイル | 役割 | 誰が書くか |
| --- | --- | --- |
| `docs/task-list-{プロジェクト名}.csv` | **索引。** ID・日付・タスク名・状態・優先度・担当・依存・詳細ファイルへのパス、それだけ | **オーケストレーターだけ** |
| `docs/tasks/T-XXX.md` | **タスク別の詳細。** 目的、完了条件、決定ログ、作業ログ、証拠など | 担当エージェント（自分のタスクの分だけ） |

**分けてある理由**: 1つのタスクを触るときに、完了済み全タスクの記録まで読み込まずに済むようにするため。加えて、タスクごとにファイルが分かれていれば、並行して走る作業が同時に書いても衝突しない。

**索引を書ける者を1人に絞ってある理由**: 索引は1ファイルなので、複数が同時に書けば必ず壊れる。書き手を1人にすることで構造的に防いでいる。

### タスク別ファイルは、そのまま作業指示である

作業指示を別途書き下ろさない。タスク別ファイルに必要な項目（目的・完了条件・判断してよい範囲・参照すべき成果物）が揃っているため、それを読ませればよい。

**項目が空であることが、指示の抜けを目に見える形にする。**

### PO確認待ちキュー

`docs/po-queue.md`。**PO の判断を仰いでいる質問の一覧。** 1件を `Q-001` のような番号で識別する。

質問1件ごとに、何を決めてほしいか・なぜ組織で決められないか・選択肢と各案の利害・推奨案・回答がないと止まるタスク、を書く。

**必ず併記するもの**: この回答を待つ間も進められるタスク。書けないなら組織全体が止まっているということであり、それ自体が報告に値する。

### 引き継ぎ記録

`docs/handover.md`。**「今どこにいるか」を1枚に書いたもの。** セッションが途中で切れても、次のセッションが続きから拾えるようにする。

常に上書きする。過去の分は Git の履歴に残るので、追記して膨らませない。

**節目ごとに更新する。** セッション終了時にまとめて書く運用は成立しない。上限は予告なく訪れ、書く余裕が残っていない状態で切れるため。

### 決定ログ / 作業ログ / 証拠

タスク別ファイルの中にある、**性質の違う3つの記録**。混ぜない。

| 名前 | 答えるもの | 寿命 |
| --- | --- | --- |
| **決定ログ** | **なぜそうしたか** | 恒久。過去の項目を書き換えず、上書きする新項目を足す |
| **作業ログ** | 何が、どの順で起きたか | 一時的。完了時に数行へ畳む |
| **証拠** | 完了条件を満たしたと何故言えるか。コマンドとその実際の出力だけ | 恒久 |

決定ログには**却下した案とその理由**を必ず書く。「X を選んだ」は数週間で「なぜ X なのか」に劣化するが、「Y が使えないので X」は劣化しない。

2つの決まり文句がある。

- **`特記なし`** — このタスクに決定が本当に無かった。項目自体は常に置くので、無いことが「まだ書いていない」を意味する状態を保つ
- **`（記録なし）`** — 決定はあったが理由が当時記録されず、もう復元できない。**推測で理由を作って埋めない。** 作られた理由は後から事実として読まれるため、認めた空白より悪い

### 設計成果物

**設計エージェントが書く、組織の内側に向けた文書。** 何をどう作るか、そしてなぜその方式にしたか、どの案を却下したかを記録する。

後述の「層3」の文書とは読み手が違う（下記）。

## 4. 文書の3つの層

「ドキュメント」という語が指すものは、層によって全く違う。**混同すると、誰が保守するのかが分からなくなる。**

| 層 | 中身 | 読み手 | 保守する主体 |
| --- | --- | --- | --- |
| **層1** | このリポジトリ（`agents-org`）の要件定義と決定記録 | 組織を設計する人間（PO） | PO と、その作業を支援するセッション |
| **層2** | 開発対象リポジトリの `CLAUDE.md`、`.claude/rules/`、エージェント定義 | **AI組織自身**（全エージェント） | **オーケストレーター** |
| **層3** | 開発対象アプリの成果物ドキュメント（README、API文書、利用者向け仕様） | AI組織 と 人間 の両方 | **ドキュメントエージェント** |

**層2 をドキュメントエージェントが持たない理由**: 層2 は成果物の説明文書ではなく、**組織自身への指示**である。「このリポジトリでは pnpm を使う」は層2、「この API はこう呼ぶ」は層3。

### エージェント用マスタ / 人間用ビュー

層3 はさらに2階建てになっている。

| | エージェント用マスタ | 人間用ビュー |
| --- | --- | --- |
| 位置づけ | **正典。ここだけが真実** | マスタからの**生成物** |
| 粒度 | 機能・目的・シーン単位に細かく分割 | 結合された通し読み用 |
| 更新 | ドキュメントエージェントが直接書く | **スクリプトで生成する。手で書かない** |

**生成の一方向に固定する理由**: 二重に手で書くと必ず食い違う。人間用ビューは常に捨てて作り直せる状態を保つ。

## 5. 進め方の語

### 完了条件

**そのタスクが終わったと言える基準。** コマンドを実行して出力を見れば、満たしたかどうかが二値で判定できる形で書く。

レビューとテストの両方が、これを判定の基準にする。書かれていないタスクは着手前に差し戻す。

### TDD適用可否

**そのタスクで、テストを実装より先に書くかどうか。** TDD（テスト駆動開発 — 先に失敗するテストを書き、それを通すように実装する進め方）は既定である。

事前にテストを書けないタスク（探索的な調査、見た目の調整、設定変更など）は「適用外」と明示する。**判定するのはオーケストレーター**で、タスクを分解する時点で決める。

### 受け入れテスト

**完了条件を、実行できる形にしたもの。** テストエージェントが実装より先に書く。

**書いた時点では落ちているのが正しい。** 実装前に通ってしまうなら、テストが完了条件を検証できていないか、既に実装済みかのどちらかである。

### エスカレーション

**自分で決められないことを、上へ渡すこと。** 4段階ある。

1. 自分で解決する（作業指示・参照すべき成果物・既存コード・確定済みの決定記録を確認する）
2. 直接やりとりが許可された相手へ相談する
3. オーケストレーターへ渡す
4. オーケストレーターでも決まらなければ PO確認待ちキューへ登録する

**段1 の打ち切りは時間ではなく「情報源を尽くしたか」で決める。** 上の4つを見ても答えが一つに定まらないなら、それ以上は推測になる。

### 停滞

**タスクが進んでいない状態。2種類ある。**

| | 実時間基準 | サイクル基準 |
| --- | --- | --- |
| 捉えるもの | セッションをまたいで**放置された**タスク | 1セッション内で**空回りしている**タスク |
| 判定 | 索引の更新日が **2日以上前**、かつ完了でも中止でもない | レビューやテストの往復が**上限（2往復）に達した**、または手戻り回数が3以上 |
| 検知する主体 | スクリプト（機械的に判定できる） | オーケストレーター |

**両方が要る。** 実時間だけでは数十分で10回空回りしているループを捉えられず、サイクルだけではセッション終了後に放置されたタスクを捉えられない。

**PO確認待ちのタスクは停滞に数えない。** 組織側の停滞ではないため。ただし放置はせず、PO へのリマインド候補として別に数える。

### 手戻り

**一度先の工程へ進んだタスクが、前の工程へ差し戻されること。** タスク別ファイルに回数を記録し、組織の健全性を測る指標に使う。

数えるもの: レビューからの修正要求、テストからの不具合レポート、オーケストレーターによる担当の差し戻し。

数えないもの: 実装エージェントが自分で気づいて直したもの、軽微な改善提案（下記 Minor）への対応。

### 重大度（Blocker / Major / Minor）

レビューの指摘と、テストが見つけた不具合に付ける3段階。**両方で同じ体系を使う**（尺度が2つあると優先順位の判断が複雑になるため）。

| 段階 | 意味 | 扱い |
| --- | --- | --- |
| **Blocker** | 完了条件を満たさない／明らかなバグ／セキュリティ上の問題 | 修正必須。残っている限り通過させない |
| **Major** | 設計との食い違い／保守性の重大な問題 | 修正必須。ただし別タスクに切り出す相談ができる |
| **Minor** | 改善提案。動作にも保守性にも実害がないもの | 任意。残っていても通過する |

**通過の条件は Blocker と Major が0件。**

### 反復上限（2往復）

**レビューや不具合修正の往復は、2回で打ち切る。**「レビュー → 修正 → 再レビュー」で1往復と数える。

2往復して解決しないなら、指摘の伝わり方か、設計・要件の側に構造的な問題がある。**往復が収束しないこと自体が、判定基準（完了条件や設計）の不備を示す信号**なので、修正を続けるのではなく再計画へ回す。

### 依存の2形式（ブロッカー / 推奨）

| 書き方 | 意味 |
| --- | --- |
| `T-001（ブロッカー）` | T-001 が完了するまで、このタスクを開始できない |
| `T-001（推奨: 理由）` | 必須ではないが、この順で進める方が合理的 |
| `無し` | 依存がないことを**確認済み**である |

**ブロッカー指定には理由を必ず書く。理由が書かれていない依存は、依存として認めない。** 説明できない依存は、並行して走れるはずのタスクを不要に直列化する。

### ゴール健全性評価

**組織が最終ゴールへ近づいているかの判定。** タスクの消化数だけを見ない。

判定は3つ。

| 判定 | 目安 |
| --- | --- |
| **前進している** | 完了数が増え、かつ**残作業が減っている** |
| **停滞している** | 完了数が増えていない。停滞やブロックが積み上がっている |
| **ゴールが揺らいでいる** | 完了数は増えているのに、**残作業が減っていない、または増えている** |

**3つ目がこの評価の存在理由である。**「タスクは消化されているのにゴールに近づいていない」という状態に名前を付けて、検知できるようにしてある。

## 6. 使い方に注意する語

| 語 | 注意 |
| --- | --- |
| **サブエージェント** | 組織上の役割の意味で使わない。**Claude Code の実行機構**を指す語として固定する。役割を指すときは「担当エージェント」を使う |
| **ドキュメント** | 単独で使わない。層1・層2・層3 のどれかを明示するか、「設計成果物」「利用者向け文書」のように具体名で書く |
| **タスクリスト** | 「タスク台帳」に統一する。索引と詳細の2ファイルからなることを含意させるため |
| **エージェント** | オーケストレーターを含む総称。5つだけを指したいなら「担当エージェント」と書く |
| **停滞** | 2種類あるので、どちらの基準の話かを明示する |
| **ユーザー** | 開発対象アプリの利用者と、PO の両方を指しうる。PO を指すなら「PO」と書く |
